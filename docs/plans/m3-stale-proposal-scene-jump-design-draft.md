## 一枚目

**作らないもの**：ヘッダーのトレイの項目ごとの行（Work Layer の最初の版で選ばれていない）、提案の中身や引用の表示、直す操作、通知。

## 1. 現状（確かめた事実）

### 1.1 件数と一覧の読み取り
- 件数の定義は、`narrative_consumer_freshness` の `proposal-revision` の行のうち Freshness が `stale`・`source-missing`・`anchor-mismatch`・`read-set-drift`・`unknown` のものから、期限内の snooze で隠れる分を引いた数。**提案の状態や現在の版とは結合しない**【確認済み】。
- 読み取りの経路は 2 つ。「健全性」の画面は `narrative_maintenance_inbox_list` を読んで renderer の `summarizeInbox` が数える。ヘッダーの Work Layer は `count_stale_proposals`（`inbox_read_model.rs`）を呼ぶ。2 つの数が一致することは差分の試験で固定している（DR-M3-31）【確認済み】。
- `narrative_maintenance_inbox_list` の行は 9 欄で、`proposal-revision` の行の `consumer_key` は版の ID。renderer の wrapper は 3 欄に絞る【確認済み】。

### 1.2 版から場面を引く方法
- 版の `reconciliation_envelope_json` の `effectiveMaterialBasis.evidenceSet[].sourceKey`（`project:scene:<id>`）が、根拠として引用した場面。1 つの版が複数の場面を持ちうる【確認済み：`scene_proposals.rs`】。
- 依存の辺（`narrative_dependency_edges`）は、読んだ source の全部に張られる。読んだだけの場面も含むので、辺だけでは引用した場面を決められない【確認済み】。
- 辺ごとの最後の判定は `narrative_dependency_edge_states`。診断の値で、Freshness の正本は Consumer の表【確認済み：`publish_runtime.rs` の module の説明】。
- 版の ID から場面を返す専用の読み取りは、今は無い【確認済み（typed IPC を読んだ範囲）】。
- 逆向きの `narrative_extraction_list_scene_proposals`（場面→提案）は、年表の提案の現在の版だけを返す。画面からの呼び手はまだ無い。23 の lane の回答（2026-11-25）：使う予定はエディタの場面の節で承認する画面（未設計）で、逆向きの読み取りを足す予定は無い。飛び先が要ると分かったら、この草稿の契約に合わせたい。

### 1.3 場面を開く操作と、消えた場面
- 構造抽出の review 画面は、根拠の `sceneId` を `openEditorDocument`（`kind: "scene"`）に渡して開き、画面を閉じる【確認済み：read-only の調査の報告。実装の PR で読み直す】。
- 場面が消えても、版の `sourceKey` に場面の ID は残る。題は残らない【同上】。

### 1.4 件数には、済んだ提案の版も含まれる
- 【確認済み：使い捨ての試験（repo には入れていない）】承認済みの現在の版（状態 `approved`）でも、依存する Codex の項目の説明を名前変更の伝播で直すと、`count_stale_proposals` が 0 から 1 になり、Inbox に行が出る。提案の状態は変わらない。
- 【確認済み：同上】却下した版（状態 `rejected`）も、依存する Codex の項目を直すと数えられる（件数 1。古いと判定された辺は直した項目だけ）。
- 【読み。試験は未実施】差し替えられた古い版も同じ。`proposal-revision` の辺と Freshness の行を消す製品の経路は見つからない。
- 承認済みが数えられるのは「承認の前提が古くなった」と読めば意味がある。承認し直し（SRD/1）の対象になりうる（23 の lane に知らせた）。

### 1.5 提案の型ごとの根拠の欄と依存
- 構造抽出の提案：根拠の欄（`evidenceSet`）は引用ごとの場面（`codexStructureExtractionApi.ts` の `nativeEvidenceSet`）。依存の辺は解析で読んだ全場面と Codex の一覧（`sourceBasis`）。引用していない場面の変更や Codex の一覧の変化でも古くなる【確認済み：コードの読み。試験は未実施】。
- Entity／Relation の版（試験の土台）：根拠の欄は Codex の項目で、**場面が無い**。辺は Codex の項目・関係・場面の適用範囲【確認済み：使い捨ての試験】。
- 年表の提案：根拠の欄が場面を含む【確認済み：`scene_proposals.rs` の読み】。

## 2. 読み取りの形

### 場面ごとの件数（採る形）
- `narrative_maintenance_stale_proposal_scenes`。引数 `{ projectId, cursor?, limit? }`。
- 応答 `{ scenes: [{ sceneId, proposalCount }], withoutSceneCount, nextCursor? }`。
- 返すのは場面の ID と数だけ。題・本文・引用・提案の ID は返さない。場面の題は、renderer が持つ場面の木から引く。木に無い ID を消えた場面として扱うのは、**同じ project の木の読み込みが終わった後だけ**（`treeStore` の `projectId` と `isLoading`）。読み込み中は判定しない。
- `proposalCount` は引用の行の数ではなく、**版と場面の組を重複なく数える**（根拠の欄は引用ごとの配列で、同じ場面が何度も現れうる）。
- 1 つの版が複数の場面を引くので、**場面ごとの数の合計は、件数と一致しないことがある**。画面でそう分かるようにする（文言は J4 と一緒に伺う）。
- `withoutSceneCount` は、根拠に場面が 1 つも無い版の数。

### 採らない形
- 提案ごとの行（版の ID・提案の ID・題・場面）：題が要り、返す欄が増える。
- Inbox の行に場面の ID を足す：Inbox は作品の全行を組み立てる。DR-M3-31 の測定では Consumer 50,000 件で約 2.6 秒かかり、その間は共有の DB 接続を握る。

### 上限（bounded lookup）
- 場面の ID の昇順で cursor と limit を置く。limit の上限を決め、超えた指定は切り詰める。
- **除外（snooze）と集計を済ませてからページに切る**。先に切った一覧を絞って「無い」と推測しない（`policies/quality/iron-laws.md` の immutable-identity の節）。
- 集計の対象は、件数と同じ集合（古いと判定された版）の全部。

## 3. 件数との一致
- 対象の版の集合は `count_stale_proposals` と同じ述語にする。snooze の判定は同じ関数（`snooze_hides_consumer`）を使い、述語を共有の形に切り出す。
- 差分の試験：固定の seed の DB で、この読み取りが対象にした版の数が `count_stale_proposals` と一致する。

## 4. gate と信頼境界【起案者の意見】
- 分類は `own-data-read`。`projectId` の扱いは `narrative_maintenance_inbox_list` と同じ（呼び手が指定した project に限って読む）。未知の key は拒否する。
- 保存・外部への送信・AI への入力は無い。返すのは作者自身の場面の ID と数。
- 実装の PR は `add-electron-command` の手順に沿う。

## 5. 画面
- 「健全性」の画面を開いたときに 1 回読む（今の件数と同じ契機）。
- 行は場面の題と件数。押すと場面を開き、画面を閉じる。消えた場面と「場面なし」は、押せない行にする。
- `ForeshadowPanel.tsx` は変えない。

## 6. 試験と測定
- Rust：複数の場面を引く版、1 つの版が同一の場面を複数回引用する例（1 と数える）、消えた場面、場面の無い版、snooze、他の project、ページの境界（N 件と N+1 件）、件数との差分、壊れた根拠の欄（Inbox に合わせて失敗にするか、数に入れて飛ばすかを実装で決める）。
- renderer：行の表示、場面を開く操作、木の読み込み中に「消えた場面」と出さないこと。
- 所要は DR-M3-31 と同じ合成の DB で測って記録する（閾値は置かない）。

2. 年表の提案と構造抽出の提案で、根拠の欄の場面の書き方が同じことを試験で確かめる。
3. 場面を開く操作が、モーダルの画面からも同じに働くか。
