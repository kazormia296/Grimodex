## 0. 一枚目

**何を決める案か。** 年表の「AI 抽出」が出す出来事の提案を、エディタの中で、場面ごとに 1 件ずつ確かめられるようにする。承認した 1 件は、そのまま年表に入り、関連する過去シーンにも使われる。そのために、今は閉じている「年表への取り込み」を、既定で有効にする。

**形**
1. エディタのサイドペイン「シーン詳細」に、節「この場面の解釈」を足す。今の場面を根拠に持つ提案を、根拠の引用つきで出す。
2. 未確認の提案に、承認・拒否・保留のボタンを置く。
3. 承認を押すと、その 1 件について、秘密の印を外した版を作り、承認を記録し、年表に入れる。3 つを続けて行う。
4. 取り込みは、提案 1 件の単位でできるようにする。「抽出 1 回ぶんの組を全部決めるまで取り込めない」という今の規則をやめる。
5. 取り込むたびに、同じ出来事が年表に既にあるかを、その時点の年表で調べ直す。「抽出の後に年表が少しでも変わっていたら取り込めない」という今の検査をやめる。
6. 間違えて承認したときは、年表でその出来事を消す。消すと、その提案の承認も外れ、関連からも外れる。
7. 年表への取り込みを、既定で有効にする。
8. 承認して年表に入れた出来事には、「AI に秘匿」の印を付けない。ふつうの年表の出来事として入れる。

**作者にとって変わること**
- 今は、抽出のダイアログで「取り込む」を押しても必ず失敗する（取り込みが閉じているため）。この案の後は、承認した提案が年表に入る。
- 今は、承認しただけでは関連する過去シーンに出ない（「まとめて承認」だけが出す）。この案の後は、1 件ずつの承認でも出る。
- 今は、提案を見る場所が抽出のダイアログだけである。この案の後は、原稿を書いている画面の横で、その場面の提案を見られる。
- 「関連には使うが、年表には入れない」という承認は無くなる。
- 承認した出来事は、根拠の場面より前を書いているときにも、AI に渡るようになる。経路は、チャットの道具（出来事の一覧・詳細・人物の年表・検索）と MCP である。今の規則では、根拠の場面以降を書いているときだけ渡る。位置で絞る仕組みは足さない。代わりに、チャットの道具の返り値に、位置の印（これまで／今の場面／同時進行／これから／不明）を付ける（CPL/1）。MCP の一覧には付かない。AI に渡したくない出来事には、作者が年表の画面で印を付ける。

**変えないこと**
- 作者が付ける印（Codex の hidden、年表の出来事の秘密の印）は守る。取り込んだ後に、作者が年表で印を付けると、その出来事は、根拠の場面より前を書いているときには、AI に渡らなくなる。根拠の場面と、それより後を書いているときは、印があっても渡る（開示の場面が、根拠の場面になるため）。MCP には、印のある出来事は渡らない。
- この案は、手書きの出来事の扱いを変えない。印の無い手書きの出来事は、今も、チャットの道具と MCP に、位置に関係なく出ている。手書きの出来事の前後の比べ方と、道具の返り値は、CED/1 と CPL/1 が変える。
- 抽出が最初に作る提案の版は、今までどおり秘密の印つきである。評価の準備が、この形を前提にしている。

## 1. 確かめた事実

### 1.1 ユーザーの決定（2026-11-21〜22）

1. 場面の情報（サイドペイン、Scene Context、解釈）は、エディタに統合する。
2. 「この場面の解釈」には、承認・拒否・保留のボタンを置く。
3. 承認したら、その 1 件をそのまま年表に入れる。「関連には使うが年表には入れない」承認は無くす。
4. 承認した解釈は、関連する過去シーンにも使う。
5. 根拠が複数の場面にまたがる提案は、根拠のある場面すべてに出す。
6. 間違えて承認したときは、年表で出来事を消し、承認も外す。
7. 上を、最初の公開（PUB-G）の前に入れる。年表への取り込みは、公開の前に、既定で有効にする（回答の原文「公開前、既定で取り込み有効でいいです」）。
8. Work Layer との分担は、場面の分をこの節が持ち、作品全体の件数・入口・まとめて処理・変更レビューを Work Layer が持つ。承認の操作と件数の数え方は共通にする。
9. この lane は、起案から実装・PR・merge まで、起案者のセッションが通しで持つ。
10. 「まとめて承認」は、1 つのボタンで、対象を承認し、そのまま年表に入れる。承認済みで年表に入っていない提案を、まとめて年表に入れるボタンも置く（2026-11-22）。
11. 承認して年表に入れた出来事に、「AI に秘匿」の印を付けない（2026-11-22）。
12. 印を付けない出来事について、位置の絞りは足さない。今の経路のまま AI に渡す（2026-11-22。§1.8 の調べた結果を見たうえでの回答「絞らずに渡す」）。
13. MCP には、手書きの出来事と同じに出す。外部の AI が、その出来事を更新・削除できるようにもなる（2026-11-22）。
14. 承認を外した提案は、却下として扱う（2026-11-22）。
15. 「『これまで』と『これから』を区別し、また今の日時、時制、等を渡す必要が有るかもしれません」（2026-11-22、発言の原文）。位置の区別は、チャットの道具の一覧にも、公開の前に入れる。作中の日時をはっきり書き、場面の視点の人物を渡す。複数選択では「場面ごとの時制を渡す」も選ばれ、「場面ごとの時制はシーンの作中日時がはっきりすれば渡さなくてもなんとかなるかも？分からないですが」と添えられた。規則と、時制の進め方は、CPL/1 に置く。
16. ADR 013 の「送る量を増やす変更は測定の後」は、この変更に当てない。測定を待たない（2026-11-22）。
17. 抽出のダイアログの提案カードから、秘密の印の切替と、「開示の場面」の欄を外す（2026-11-22）。AI に渡したくない出来事には、取り込んだ後に、年表の画面で印を付ける。
18. 年表の出来事は、必ず日時を持つ。承認して入れる出来事の日時は、根拠の場面から取り、取れなければ、抽出のときに AI が推定する（2026-11-22）。規則は CED/1 に置く。

### 1.2 年表への取り込みは、今の製品では閉じている

- 取り込みの許可は、workspace の DB の表 `narrative_runtime_policy` の 1 行が持つ。project ごとではない。【読んだ（`narrative_runtime_policy.rs` の表の定義）】
- 行が無いときは、`('review-only', 0, 0, 0, version 1)` で作られる。表の既定も `review-only` である。【読んだ】
- 取り込みの準備と実行は、`require_narrative_apply_allowed` を通る。`manual-apply` か `automatic` でなければ、`NARRATIVE_REVIEW_ONLY` で拒まれる。【読んだ（`commit.rs:204`、`:995`）】
- この設定を書く口 `narrative_runtime_policy_set` を呼ぶ製品のコードは無い。呼ぶのは、試験、実機の検査の手順、評価の準備だけである。【読んだ（`src`・`electron`・`src-tauri/crates` の grep）】
- 抽出のダイアログは、この設定を見ない。「取り込む」は押せるが、押すと一般の失敗の文言が出るだけで、理由は出ない。【報告】
- 同じ許可を通る操作が、ほかにもある。取り消しのやり直し（redo）と、generic import の取り込みである。後者は、別の旗 `generic_import_enabled`（既定 0）も要る。【読んだ】
- 保守の書き込みは、別の旗 `maintenance_enabled`（既定 0）と、取り込みのできる設定の両方を要る。【読んだ（関数名と文言まで。中の式は【未確認】）】
- この既定を、いつ・どの条件で開けるかの記録は、見つかっていない。8 月の Gate B の計画には「設定が欠けていたら `review-only` に倒す」とある。【読んだ（計画の該当行）。ほかの文書は【未確認】】

### 1.3 取り込みの単位と、年表全体との照合

- 承認・拒否・保留は、提案 1 件ずつ記録できる。【報告】
- 取り込みは、抽出 1 回ぶんの組が単位である。組の提案が全部、承認か拒否に決まるまで実行できない。保留が 1 件でもあると実行できない。【報告（`commit.rs` の `validate_current_chronicle_apply_coverage`）】
- この規則は、2026-08-27 の PR #559（`65179165`）で入った。その差分で、画面の条件が「承認済みが 1 件以上」から「全件が決まっている」に置き換わっている。【読んだ（差分）】理由の記録は、コードのコメントのほかに見つかっていない。【報告】
- 取り込みの準備と実行は、抽出の時点で封印した「既存の出来事の一覧」と、今の年表の全部の出来事を照合する。1 件でも違うと `NEX_CHRONICLE_RESUME_LIVE_CATALOG_DRIFT` で拒む。重複の判定を、抽出の時点の一覧に対して封印しているためである。【報告（`commit.rs:245-257`、`:1007-1015`）】
- この照合があるので、1 件取り込むと、同じ組の 2 件目も、ほかの抽出の取り込みも通らなくなる。抽出の後に作者が年表の出来事を 1 件直した場合も同じである。【報告】
- 取り込みの記録、根拠の本文が古くなっていないかの検査、年表の並びの割当、承認の権限の検査は、もともと提案 1 件の単位で動く。【報告】
- NIR-0 の認証の記録は、「年表の一覧が変わっていたら、取り込みの記録を書く前に失敗する」を、認証済みの防御として持つ。【報告（`docs/certification/nir0/NIR0-CERT.md:109`）】

### 1.4 承認した解釈が、関連する過去シーンに使われる条件

- 関連の資格は、年表の出来事も取り込みの記録も見ない。見るのは、提案が承認済みであること、最新の決定が人の承認で、今の版に付いていること、版の秘密の印が外れていること、根拠の場面の Scope が解けること、鮮度、読む順である。【報告（`retrieval_admission`）】
- 抽出が作る最初の版は、秘密の印つきである（`proposalPlanner.ts:182`。2026-08-13 の PR #509）。【読んだ】この版を承認しても、資格は通らない。【報告】
- 「まとめて承認」が作る子の版は、秘密の印だけを外し、場面の Scope への依存の印を Native が付ける。この子の版は資格を通り、取り込みの後も資格が残る。【報告（実際の取り込みを通した試験がある）】
- 同じことを 1 件で行う経路は、既にある。版を作る操作と、承認を記録する操作を、続けて呼ぶ。【報告】
- 次の 2 つは、承認しても関連に使われない。根拠が複数の場面にまたがる提案（`EvidenceMismatch`）と、Scope が未設定の場面を根拠にする提案である。【報告】
- IR の admission の規則は、PUB-G の後まで変えない。凍結済みの評価の期待値が動くためである。【読んだ（ADR 013 の記述は調査の報告による。起案者が読んだのは 11-19 の確認の記録）】

### 1.5 取り消し

- 年表の画面で、取り込み済みの出来事を消すと、出来事の行だけが消える。提案・版・承認・取り込みの記録には、何も起きない。提案は「取り込み済み」のまま残る。【報告】
- 取り込み済みの提案には、決定を足せない（`NEX_PROPOSAL_ALREADY_APPLIED`）。却下も足せない。【報告（`repository.rs:385-399`）】
- 今ある取り消し（`undo_commit`）は、出来事を戻すが、提案を未決に戻さず、関連の資格も外さない。製品の画面から呼ぶ経路は無い。【報告】
- 関連の資格を外すには、同じ版に、人の却下か保留の決定を 1 件足せば足りる。取り込みの記録・版・過去の決定は、書き換えずに済む。【報告】

### 1.6 場面から提案を引く

- 提案の表に、場面の列は無い。【報告】
- 提案の版ごとに、「読んだ場面」の記録（`narrative_revision_source_basis`）と、場面から版を引ける依存の索引がある。ただし「読んだ場面」と「根拠のある場面」は同じではない。根拠の場面だけを言えるのは、版の envelope の `evidenceSet` である。【報告】
- 「場面 → 提案」を引く読み取りは、無い。今ある近い読みは、新しい順に最大 50 回ぶんの抽出を 1 つずつ読む形で、bounded lookup の規則に合わない。【報告】

### 1.7 評価の準備との関係

- CP-4 の測定は、製品の `EditorPane` を mount する。サイドペインは既定で開いているので、測定の間も mount されている。サイドペインの中の読み取りは、測定の窓に入る。【報告】
- 評価の準備は、製品の関数 `reviseChronicleProposal`、`decideChronicleProposal`、`recordChronicleProposalDecision` を使い、承認を「取り込みなし」で行う。取り込みは呼ばない。【報告】
- 凍結に束ねる file（`cp4-harness.ts`、`frozen-setup-driver.mjs`）は、画面を操作せず、API だけを使う。提案の秘密の印も、API の改版（`reviseChronicleProposal` の secret の指定）で外している。【報告（点検）】
- 画面のボタンを押す手順は、別にある。提案カードの秘密の印の切替を押すのは、評価の準備 2 本（`setup-nir1-retrieval.mjs`、`setup-nir1-recovery.mjs`）と、実機の検査 4 本である。ダイアログの「承認」を押す手順と、「取り込む」を押す手順もある。これらは、承認の後に年表に入らない前提で書かれている。凍結に束ねる file には入っていない。【報告（点検）】
- 評価の準備は、「最初の提案が秘密の印つきである」ことを前提にしている。【報告（`frozen-setup-driver.mjs`）】
- 評価の準備は、`narrative_runtime_policy` を書く（`maintenance-enabled` の段など）。既定が変わると、読み戻しの値や受領書の記録が変わりうる。【報告（統合者の連絡）】
- Native の `ensure_current_chronicle_proposal_set_unconsumed` は、評価の準備の版の作成と決定も通る。【報告】

### 1.8 年表の出来事が AI に渡る経路と、位置の扱い

決定 11〜13 の前に、ユーザーに見せた調べの結果である。基点のコードの読みで、実行はしていない。

- 印の判定は 1 つである。印の無い出来事は、常に AI に見せる。印のある出来事は、今の場面が、読む順で開示の場面より前の間だけ隠す。【読んだ（`src/features/chronicle/chronicleSecrecy.ts:72-90`）】
- チャットの自動のまとめは、見える出来事から、今の場面の「作中の現在地」を決め、年表の並びがそれ以前の出来事を入れる。【読んだ（`chronicleSnapshot.ts:101-104`、`:397-413`）】件数は最大 8 件と、場面に結び付かない出来事が最大 3 件である。【報告】
- 「作中の現在地」（コードでは anchor）の決め方は、次の順である。場面に作中日付があれば、その日付。無ければ、その場面に結び付いた出来事のうち、年表の並びが最も後ろのもの。それも無ければ、読む順で手前の、最も近い場面の現在地を借りる。【読んだ（`resolveSceneAnchor.ts:73-191`）】
- チャットの道具のうち、出来事の一覧・詳細・人物の年表は、印の判定だけで絞る。印の無い出来事は、今の場面の位置に関係なく返す。【読んだ（`src/features/chat/agent/chronicleReadTools.ts:79-97`。3 本がこの関数を通ることは【報告】）】検索の道具には位置の絞りの部品があるが、定数で止まっている。【報告】
- MCP は、場面の位置を持たない。印のある出来事を一律に除き、印の無い出来事を全部返す。【読んだ（`src-tauri/crates/grimodex-mcp/src/db.rs:1979-1991`）】書き込みの道具（更新・削除）も、印の無い出来事には届く。【報告】
- 取り込みで作る出来事は、今は必ず印つきで、年表の末尾に追記される。【読んだ（`commit.rs:2287-2292`、`:3129-3139`、`src/features/chronicle/extraction/compiler.ts:118-127`）】作中の日時は入らず、根拠の場面に結び付く。【報告】
- 年表の抽出そのもの、あらすじ、続きを書く、校閲、伏線、地図は、年表の出来事を AI に送らない。関連する過去シーンは、画面に出るだけである。【報告】
- 凍結に束ねる評価の道具は、年表への取り込みを呼ばず、年表の出来事の印を期待値に使わない。実機の検査のうち、取り込んだ出来事の印を検査しているのは 1 本である（`chronicle-edited-apply-product-journey.mjs`）。「取り込む」を押す手順は 3 本、提案カードの印の切替を押す手順は 4 本ある。【報告（点検）】

ここから言えること：

1. 印を付けないと、承認した出来事は、チャットの道具と MCP で、その出来事が起きる場面より前を書いているときにも AI に渡る。
2. 今の作りのまま取り込みを開けると、取り込んだ出来事は、日時を持たず、年表の並びの末尾に入る。その出来事が結び付いた場面と、読む順でその後ろの作中日付の無い場面では、「作中の現在地」が年表の末尾に寄り、チャットの自動のまとめに、先の出来事が「これまで」として入る。【報告】直し方は、CED/1 に置く（2026-11-22 のユーザーの決定）。出来事は必ず日時を持ち、前後は日時で比べる。確度が「不明」の出来事は、「作中の現在地」を決める材料にしない（出来事が全部「不明」で、作中日付のある場面も無い作品を除く。CED/1 の C3a）。

## 2. 規則

### 2.1 節（S1〜S6）

- **S1**　節「この場面の解釈」は、エディタのサイドペイン「シーン詳細」の中に置く。既定で閉じていて、開くまで読み込まない。
- **S2**　節は、今の場面を根拠に持つ提案を出す。根拠が複数の場面にまたがる提案は、根拠のある場面すべての節に出る。作品全体の件数では、1 件と数える。
- **S3**　カードは、題、根拠の引用と場面名、確認の状態、参照元の状態、年表の状態を出す。3 つの状態は別々の印にする。色だけに頼らない。
- **S4**　関連に使われない提案（§1.4 の 2 つの場合）には、その旨を出す。判定は Native が返したものをそのまま出し、画面で計算しない。
- **S5**　提案が届いても、節を自動で開かない。通知を出さない。フォーカスを動かさない。変わるのは件数だけである。
- **S6**　画面に「NIR」「IR」「Revision」という語を出さない。

### 2.2 読み取り（R1〜R3）

- **R1**　Native に、場面から提案を引く読み取りを 1 本足す。入力は project と場面の id、出力はその場面を根拠に持つ提案の、現行の版である。ページ付きで、上限を持つ。
- **R2**　返すのは、提案と版の id、題、根拠の引用と場面、3 つの状態、関連に使われるかの見込みとその理由、重複の疑いである。本文の全体は返さない。
- **R3**　この読み取りは、自分のデータを読む命令の一覧（今 39 本）に 1 本足す形で登録する。保存する場所は増やさない。索引を足す必要があるかは、実装の前に確かめる（足すなら schema の版が上がるので、あらためて伝える）。

### 2.3 承認（A1〜A6）

- **A1**　承認を押すと、その 1 件について、次を続けて行う。(1) 秘密の印を外した子の版を作る。既に外れていれば作らない。(2) その版に、作者の承認を記録する。(3) その版を年表に入れる。
- **A2**　A1 は、新しい入口として足す。評価の準備が使う既存の関数の意味は、変えない。
- **A3**　「見せる理由」（回想・伝聞・登場人物の発言の中の出来事など）のある提案も、1 件ずつの承認では、同じ扱いである。承認すれば、年表に入り、関連にも使う。
- **A4**　拒否と保留は、今までどおり、決定を記録するだけである。
- **A5**　同じ出来事が年表に既にある疑いは、2 種類ある。(1) 抽出の時点で付いた疑いと、題を直した版の疑い。これは、今の Native の規則どおり、承認の前に選択を求める。A1 の (2) は、選択つきの承認を記録する。(2) 取り込む時点の調べ直し（§2.4 の D3）で、新しく見つかった疑い。カードがその場で選択を出し、選択つきの決定を 1 件足して続ける。選択は 3 つである。別の出来事として入れる（承認）、同じものとして入れない（却下）、保留する。
- **A6**　途中で失敗したときの扱いは、§5 の表のとおりである。承認の記録は残し、年表に入っていないことをカードに出して、やり直せるようにする。

### 2.4 取り込み（D1〜D9）

- **D1**　取り込みは、提案 1 件の単位でできる。組のほかの提案が未決でも、保留でも、取り込める。
- **D2**　「抽出の時点の年表の一覧と、今の年表が一致すること」を、取り込みの条件から外す。外すのは、取り込みの準備と実行の 2 か所だけである。抽出の途中の検査、再開の候補の判定、やり直し（redo）の同じ検査は、変えない。【同じ検査が 5 か所から呼ばれることは報告（点検）】
- **D3**　代わりに、取り込む時点で、Native が今の年表に対して重複の疑いを調べ直す。疑いがあるのに、作者の選択（A5）が付いていなければ、取り込みを拒む。画面が出した判定は信頼しない。選択の有無は、現行の版の最新の決定で判定する。Native は今、題の照合を持たない（画面の側と 1 文字単位で一致する保証が無いので、わざと持っていない【報告（点検）】）。この案は、取り込む時点の調べ直しに限って、Native に題の照合を足す。画面の側と同じ判定になることを、共有の例で試験する。判定がずれうるときは、疑いを出す側に倒す。
- **D4**　取り込みで作る年表の出来事の印は、承認した版の印に合わせる。A1 の承認は印を外した版を作るので、出来事に印は付かない。
- **D4a**　今の形式の取り込みでは、「常に印つきで作る」という Native の検査を外し、Native が版から操作を組み立て直すときに、印を版から読むように変える。操作と、組み立て直した値との照合（`NEX_PROPOSAL_PAYLOAD_MISMATCH`）が、印の一致を保つ。画面の側の組み立ては、同じ PR で変える。開示の場面は、印の有無に関わらず、今までどおり付ける。古い形式の取り込み（Native が組み立て直さない枝）は、「印つきでなければ拒む」検査を残す。【報告（点検。`commit.rs` の該当の行を、点検が読んだ）】
- **D4b**　この案の実装より前に、印の付いた版のまま承認された提案を E2 で入れるときは、出来事にも印が付く。その提案は、関連する過去シーンには使われない。画面の承認（A1）では、新しくは生じない。承認の API を直接呼ぶ経路（評価の準備など）では、印つきの版を承認したまま残せる。
- **D4c**　取り込みで作る出来事には、必ず日時を入れる。決め方は、CED/1 の G1〜G9 である。根拠の場面の作中日付を使う。無ければ、提案が持つ推定の日時を使う。それも無ければ、Native が機械的に決め、確度を「不明」にする。日時を決めるのは Native だけで、画面の側の組み立ては、日時については変えない。秘密の印（D4a）は、画面の側の組み立てと Native の両方を、同じ PR で変える。
- **D5**　1 件取り込んでも、同じ組のほかの提案の承認・編集・取り込みを止めない。止めるのは、取り込み済みのその提案だけである。
- **D6**　印を付けない出来事に、位置の絞りは足さない。チャットの自動のまとめ・道具・検索と MCP は、手書きの印の無い出来事と同じ規則で扱う。MCP の読み取りと書き込みの道具にも、手書きと同じに出す。前後の区別は、CPL/1 が付ける。
- **D7**　既に取り込み済みの出来事の印は、自動では変えない。
- **D8**　まとめて年表に入れるとき（E2・E3）は、読む順で手前の場面の提案から、1 件ずつ入れる。同じ場面の中は、提案の並びの順である。各件の日時は、CED/1 の G2〜G5 で決まる。これは起案者の技術判断で、ユーザーの決定ではない。
- **D9**　取り込みを呼ぶたびに、画面の側が、年表の末尾の並びの値を読んで渡す。年表が空なら、「空」と渡す。末尾が変わっていて拒まれたときは、1 回だけ読み直して試す。今の製品の呼び出しは、この値を渡していない。出来事が 1 件でもある作品では、取り込みが拒まれる見込みである。【報告】

### 2.5 取り消し（U1〜U3）

- **U1**　年表の画面で、抽出から入れた出来事を消すと、その提案の承認も外す。1 回の操作で行う。
- **U1a**　アプリ内の AI や MCP の道具が、抽出から入れた出来事を消したときも、その提案の承認を外す。外さないと、年表に無い出来事の解釈が、関連する過去シーンに出続ける。出来事を消す Native の処理の中で行う。【AI と MCP が消せることは報告。実装の前に、消す経路を読む】
- **U2**　そのために、取り込み済みの提案にも、作者の却下を 1 件足せるようにする。取り込みの記録・版・過去の決定は、書き換えない。
- **U3**　承認を外した提案は、却下として扱う。同じ場面を抽出し直すと、同じ内容の提案がまた出ることがある。

### 2.6 既定（P1〜P4）

- **P1**　取り込みの設定の既定を、「作者が承認したものを年表に入れられる」（`manual-apply`）にする。自動の取り込み（`automatic`）にはしない。ユーザーの回答は「公開前、既定で取り込み有効でいいです」で、「人の承認が要る形」と読むのは、起案者の読みである。P2・P3 も、起案者の技術判断である。
- **P2**　保守の旗、generic import の旗、背景の AI の旗は、変えない。既定は閉じたままである。
- **P3**　一度も設定していない workspace（版が 1 で、`review-only` の行）は、新しい既定として読む。設定を書いたことのある workspace は、書かれた値のままにする。
- **P4**　設定が欠けている、壊れている、表が無い場合は、今までどおり `review-only` に倒す。

### 2.7 ほかの入口（E1〜E3）

- **E1**　抽出のダイアログの 1 件ずつの承認は、節と同じ動きにする。承認した 1 件が、年表に入る。
- **E2**　承認済みで、まだ年表に入っていない提案を、まとめて年表に入れるボタンを置く。置き場所は、抽出のダイアログと、節である。節のボタンは、その場面の分だけを入れる。中の処理は 1 件ずつで、1 件が失敗しても、残りは年表に入る。
- **E3**　「まとめて承認」は、1 つのボタンで、対象を承認し、そのまま年表に入れる。対象の判定（見せる理由の無い提案だけ）は、今までどおり Native が行う。途中で失敗した分は、承認済みで年表に入っていない提案として残り、E2 のボタンで入れられる。

## 3. 残る制限

- 根拠が複数の場面にまたがる提案と、Scope が未設定の場面を根拠にする提案は、承認して年表に入れても、関連する過去シーンには使われない。規則を変えるのは PUB-G の後である。
- 承認を取り消す場所は、年表の画面だけである。節のカードからは取り消せない。
- 承認して年表に入れた出来事は、根拠の場面より前を書いているときにも、チャットの道具と MCP で AI に渡る。チャットの道具の返り値には、位置の区別と確度が付く（CPL/1）。MCP の一覧には、位置の区別は付かない。MCP の向こうの AI には、前後の区別が無い。
- AI に渡したくない出来事には、作者が年表の画面で印を付ける。印は 1 件ずつ付ける。承認のときに印を選ぶ操作は、置かない。取り込んでから、作者が印を付けるまでの間は、AI に渡りうる。
- 年表で印を付けても、関連する過去シーンの表示は変わらない。関連する過去シーンは、承認した版を見ていて、年表の出来事を見ないためである。画面に出るだけで、AI には送らない。
- 取り込んだ出来事の日時は、抽出のときの推定が入るまで、根拠の場面の日付か、仮の日時である（CED/1 の G2〜G5）。確度は「不明」で入る。作者が、年表の画面で動かして、確度を直す。
- 抽出のダイアログの提案カードから、秘密の印の切替と、「開示の場面」の欄を外す（決定 17）。API の改版の入口（印と開示の場面の指定）は残す。凍結に束ねる評価の道具が、これを呼ぶためである。
- 1 件取り込むと、年表の一覧が変わる。そのとき進行中の別の抽出は、次の段で「年表が変わった」として失敗しうる（D2 が外すのは、取り込みの 2 か所だけである）。手書きで年表を直したときに、今も起きる失敗と同じ種類である。抽出の途中の検査も調べ直しに寄せるかは、実装のときに H1 の範囲で決め、変えるなら、あらためて伝える。
- 重複の調べ直しは、題の一致によるものである。題が違う同じ出来事は、見つけられない。
- 既に承認済みで、まだ年表に入っていない提案は、自動では年表に入れない。E2 のボタンで、作者が入れる。
- サイドペインの幅は、エディタの 20% が既定である。既定の配置では、計算上 82〜130px で、カードを読むには狭い見込みである。幅は測っていない。作者はペインを広げられる（50% まで）。
- レイアウトの作り替え（Scene Context パネルの廃止、左右の領域の幅、チップ行を常に出すこと）と、Work Layer の実データへの接続は、この案に含めない。
- phone の幅では、サイドペインは全画面のシートになる。節はその中に出る。

## 4. 脅威モデル（draft）

変える防御は 5 つある。どれも、ユーザーの確認まで draft である。

| 変える防御 | 信頼する相手 | 信頼しない相手 | 範囲内の攻撃・事故 | 必須の防御 | 受入れへの影響 |
| ---------- | ------------ | -------------- | ------------------ | ---------- | -------------- |
| H1 年表全体との照合をやめ、取り込む時点の調べ直しにする（D2・D3） | Native、作者の操作 | 画面（renderer）が出す判定と操作、古い画面が準備した取り込みの計画 | 重複の疑いを黙って通す。抽出の後に足された出来事と同じ出来事を、二重に作る。古い判定を保存に残す | Native が、取り込みの transaction の中で、今の年表に対して判定し直す。疑いがあるのに選択が無ければ拒む。準備と実行の両方で行う | NIR-0 の認証の該当の行（一覧の変化で失敗する）を、年表の抽出の取り込みについて D3 に置き換える。試験を書き換える |
| H2 取り込み済みの提案に、作者の却下を 1 件足せるようにする（U2） | Native、作者の操作 | 画面が指定する提案と版の id、AI の経路、MCP | 作者でない経路が、承認を外す。取り込みの記録や過去の決定を書き換える。別の版に決定を付ける | 足せるのは、人の review の経路の却下 1 件だけ。現行の版にだけ付く。記録の更新・削除は、今までどおり trigger が拒む | 「取り消した取り込みの提案は取り込み済みのまま」を固定している試験を書き換える。取り込み済みで却下の状態を、ほかの検査が許すかは【未確認】 |
| H3 取り込みの既定を有効にする（P1〜P4） | 作者（承認を押す人） | 設定の欠損・破損、AI の経路、背景の処理 | 作者の承認なしに年表が変わる。壊れた設定で開く。ほかの閉じた機能まで開く | 取り込みには、今までどおり、人の承認の決定が要る。自動の取り込みにはしない。欠損・破損は `review-only` に倒す。保守・generic import・背景の AI の旗は変えない | 既定を固定している試験（13 file の見込み【報告】）と、評価の準備の読み戻しを確かめる。同じ許可を通る redo も通るようになる |
| H4 場面から提案を引く読み取りを足す（R1〜R3） | Native、作者の画面 | 画面が渡す project と場面の id、制限モードの外の経路 | ほかの project の提案を読む。上限なしに読む。本文の全体を持ち出す | project の束縛を Native が確かめる。ページと上限を持つ。返すのは引用までで、本文の全体は返さない。自分のデータを読む命令として登録する | 命令の一覧が 39 本から 40 本になる。返す引用は、今も抽出のダイアログに出ている平文と同じ種類である |
| H5 取り込みで作る年表の出来事に、秘密の印を付けない（D4・D6） | 作者（承認を押す人）、Native | 画面が渡す操作の印の値、作者の承認を経ない経路（AI、背景の処理、MCP） | 作者が承認していない提案が、印なしで年表に入り AI に渡る。画面が、版と違う印の値を渡す。作者が年表で付けた印が外れる。既に取り込み済みの出来事の印が、黙って外れる | 取り込みには、今までどおり、人の承認の決定が要る。出来事の印は、Native が版から組み立て直した値と照合する。取り込みで入れる日時・粒度・確度の欄は、承認した人の値ではなく、「機械が入れた値」として記録する（CED/1 の G9）。作者が年表で付けた印の判定（チャットの文脈・道具・MCP）は変えない。既存の出来事の印は変えない | CAS/1 の検査 1 つを外し、その試験の組を書き換える。取り込んだ出来事の印を検査している実機の検査 1 本を書き換える。**外部の AI の提供者と、MCP の向こうの AI に渡る内容が増える。送信先は増えない。** 受け入れる残り：位置の絞りが無いので、前の場面を書いているときに、後の場面の出来事が AI に渡りうる（決定 12） |

H5 の変更の種類：新しい送信先は無い。保存の範囲は変わらない（列も表も足さない）。変わるのは、既にある送信先（外部の AI の提供者、MCP の向こうの AI）に渡る内容の範囲である。ADR 013 が「別に確認する」と置く種類の変更に当たり、ユーザーが 2026-11-22 に決めた（決定 11〜13・16）。

H5 で受け入れる残り：(1) 根拠の場面より前を書いているときに、後の場面の出来事が AI に渡りうる。位置の区別は付くが、AI が区別を無視することは防げない。(2) 取り込んでから、作者が年表で印を付けるまでの間は、AI に渡りうる。(3) この案の実装より前に準備された取り込みの計画は、版と印が食い違うので、Native が拒む。準備し直せば通る。

範囲外：DB のファイルを直接書き換える相手（今ある脅威モデルでも範囲外）。関連する過去シーン（画面に出るだけで、AI に送らない）。AI が返す文章の中のネタバレの抑制（ADR 013 の J5 の範囲）。

## 5. 承認の途中で失敗したとき

| 失敗する段 | 残るもの | カードの見え方 | やり直し |
| ---------- | -------- | -------------- | -------- |
| 子の版を作る | 何も残らない | 未確認のまま。失敗の理由を出す | もう一度承認を押す |
| 承認を記録する | 未承認の子の版 | 未確認のまま（子の版が現行の版になる） | もう一度承認を押す。子の版は作り直さない |
| 重複の疑いが、取り込む時点で新しく見つかる（抽出の時点で付いた疑いは、承認の前に選ぶ） | 承認済みの版 | 「同じ出来事が年表にあるかもしれません」と 3 つの選択 | 選ぶと続きを行う |
| 年表に入れる（原稿が保存の途中・変わっていた） | 承認済みの版。年表には入っていない | 承認済み・年表に未取り込み。理由を出す | 「年表に入れる」を押す |
| 年表に入れる（年表の末尾の並びが競合した） | 同上 | 同上 | 画面が 1 回だけ読み直して試す。だめなら上と同じ |
| 年表に入れる（根拠の場面の 1 つが変わっていた。複数の場面の提案） | 同上 | 同上。どの場面が変わったかを出す | 抽出し直すか、拒否する |
| 「まとめて承認」の途中（一部の提案で失敗した） | 成功した分は年表に入る。失敗した分は、承認済みの版。年表には入っていない | 入った件数と、入らなかった件数を出す | 「承認済みをまとめて年表に入れる」を押す |
| 年表に入れる（操作の印が、版の印と違う。この案の実装より前に準備された計画など） | 承認済みの版。年表には入っていない | 承認済み・年表に未取り込み。理由を出す | 「年表に入れる」を押すと、準備し直して入れる |

印の無い版で承認済みの間は、年表に入っていなくても、その解釈は関連に使われる。資格が承認を見て、取り込みを見ないためである。

## 6. 変える場所の見込みと、順番

1. **Native：取り込みの単位と調べ直し**（D1〜D5、H1）。`commit.rs` の被覆の検査、`repository.rs` の組の消費済みの検査、年表全体との照合。評価の準備が通る関数は、未取り込みの組での挙動を変えない。試験で示す。
2. **Native：取り消しのための決定**（U1a・U2・U3、H2）。
3. **Native と IPC：場面から提案を引く読み取り**（R1〜R3、H4）。
4. **年表の出来事の印**（D4〜D7、H5）。`commit.rs` の「常に印つき」の検査と、出来事を組み立てる 2 か所（`commit.rs` と画面の `compiler.ts`。同時に変える）。CAS/1 の試験の組、取り込んだ出来事の印を検査している実機の検査 1 本、画面の文言 4 つ【報告】、年表の設計書と `docs/CONTEXT_INJECTION.md` への追記、ADR 013 の追補。MCP とチャットの道具のコードは、この段では変えない。

## 8. 未確認と限界

- この文書の【報告】は、read-only の調査の結果で、起案者は該当の行を読んでいない。実装の前に、基点のコードで読み直す。
- どの挙動も、実行して確かめていない。別のセッションが評価の測定を回していたため、起動や試験は行っていない。
- D3 の調べ直しを Native に置くとき、題の正規化（今は画面の側にある）を Native に持つ必要がある。同じ判定になることを、試験で示す必要がある。
- 取り込み済みで却下の状態を、取り込みのやり直し・被覆の検査・review の一覧が許すかは、確かめていない。
- P3 の読み替え（版が 1 の行を新しい既定として読む）が、schema の版を上げずにできるかは、確かめていない。上げる場合は、release の移行の試験（schema 2 からの upgrade）を通す。
- 1 件の取り込みにかかる時間は、測っていない。「まとめて承認」で数百件を入れる場合の時間は、merge の前に測る。
- 公開済みの版（v2.0.10）に、提案の表と `narrative_runtime_policy` の表が無いことは、tag での確認による。更新した利用者の workspace で、行が新しい既定で作られることは、確かめていない。
- 11-11 と 11-12 のユーザーの確認の記録のファイルは、見つけられていない。CAS/1 と BAO/1 が確認済みであることは、それぞれの決定の文書の記述による。
- §1.8 の【報告】は、2026-11-22 の read-only の調査の結果である。チャットの道具 3 本が同じ印の判定を通ること、検索の位置の絞りが定数で止まっていること、MCP の書き込みの道具の届く範囲、取り込みで作中の日時が入らないことは、起案者が読んでいない。
- 承認した出来事が増えたとき、チャットの 1 回の送信に入る年表の量がどう変わるかは、測っていない。自動のまとめは件数の上限を持つ。道具の一覧には、上限があるかを確かめていない。
- 「取り込んだ出来事は印つきで、AI に送られない」に当たる文言が、画面・ヘルプ・設計書のどこにあるかは、調査の報告による。実装のときに、当たりを読み直して書き換える。
- チャットの道具は、別の lane（Mastra への移行）が作り直している。この案は道具のコードを変えないが、移行後の道具が、印の無い出来事を同じ規則で返すことは、その lane の設計と照らす必要がある。
- チャットの IR（承認した解釈を、チャットの道具で渡す仕組み。今は定数で止めてある）の除外の近似は、「取り込みで作る出来事は常に秘密の印つき」を前提にしている（`chronicleReadingPosition.ts:50-53` の説明。起案者が読んだ）。この案の後は、前提が崩れる。チャットの IR を開ける前に、見直す。
- 承認済みの版に、選択つきの決定をもう 1 件足すこと（A5 の (2)）を、今の Native の規則が許すかは、確かめていない。
- 2026-11-22 の点検の結果は、repo の外の `design-notes/editor-scene-interpretation-2026-11-21/wf13.json` にある。
