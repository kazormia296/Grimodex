## 0. 一枚目

**何を決める案か。** 年表の「AI 抽出」が出す出来事の提案を、エディタの中で、場面ごとに 1 件ずつ確かめられるようにする。承認した 1 件は、そのまま年表に入り、関連する過去シーンにも使われる。そのために、今は閉じている「年表への取り込み」を、既定で有効にする。

**形**
1. エディタのサイドペイン「シーン詳細」に、節「この場面の解釈」を足す。今の場面を根拠に持つ提案を、根拠の引用つきで出す。
2. 未確認の提案に、承認・拒否・保留のボタンを置く。
3. 承認を押すと、その 1 件について、秘密の印を外した版を作り、承認を記録し、年表に入れる。3 つを続けて行う。
4. 取り込みは、提案 1 件の単位でできるようにする。「抽出 1 回ぶんの組を全部決めるまで取り込めない」という今の規則をやめる。
5. 取り込むたびに、同じ出来事が年表に既にあるかを、その時点の年表で調べ直す。「抽出の後に年表が少しでも変わっていたら取り込めない」という今の検査をやめる。
6. 間違えて承認したときは、年表でその出来事を消す。消すと、その提案の承認も外れ、関連からも外れる。
7. 年表への取り込みを、既定で有効にする。
8. 承認して年表に入れた出来事には、「AI に秘匿」の印を付けない。ふつうの年表の出来事として入れる。

**作者にとって変わること**
- 今は、抽出のダイアログで「取り込む」を押しても必ず失敗する（取り込みが閉じているため）。この案の後は、承認した提案が年表に入る。
- 今は、承認しただけでは関連する過去シーンに出ない（「まとめて承認」だけが出す）。この案の後は、1 件ずつの承認でも出る。
- 今は、提案を見る場所が抽出のダイアログだけである。この案の後は、原稿を書いている画面の横で、その場面の提案を見られる。
- 「関連には使うが、年表には入れない」という承認は無くなる。
- 承認した出来事は、AI にも渡るようになる。チャットの道具（出来事の一覧・詳細・人物の年表・検索）と MCP では、その出来事が起きる場面より前を書いているときにも渡る。位置で絞る仕組みは足さない（2026-11-22 のユーザーの決定）。AI に渡したくない出来事には、作者が年表の画面で印を付ける。

**変えないこと**
- 作者が付ける印（Codex の hidden、年表の出来事の秘密の印）は守る。取り込んだ後に作者が年表で印を付ければ、その出来事は AI に渡らなくなる。
- 手書きの出来事の扱いは変えない。印の無い手書きの出来事は、今も、チャットの道具と MCP に、位置に関係なく出ている。
- 抽出が最初に作る提案の版は、今までどおり秘密の印つきである。評価の準備が、この形を前提にしている。

## 1. 確かめた事実

### 1.1 ユーザーの決定（2026-11-21）

1. 場面の情報（サイドペイン、Scene Context、解釈）は、エディタに統合する。
2. 「この場面の解釈」には、承認・拒否・保留のボタンを置く。
3. 承認したら、その 1 件をそのまま年表に入れる。「関連には使うが年表には入れない」承認は無くす。
4. 承認した解釈は、関連する過去シーンにも使う。
5. 根拠が複数の場面にまたがる提案は、根拠のある場面すべてに出す。
6. 間違えて承認したときは、年表で出来事を消し、承認も外す。
7. 上を、最初の公開（PUB-G）の前に入れる。年表への取り込みは、公開の前に、既定で有効にする（回答の原文「公開前、既定で取り込み有効でいいです」）。
8. Work Layer との分担は、場面の分をこの節が持ち、作品全体の件数・入口・まとめて処理・変更レビューを Work Layer が持つ。承認の操作と件数の数え方は共通にする。
9. この lane は、起案から実装・PR・merge まで、起案者のセッションが通しで持つ。
10. 「まとめて承認」は、1 つのボタンで、対象を承認し、そのまま年表に入れる。承認済みで年表に入っていない提案を、まとめて年表に入れるボタンも置く（2026-11-22）。
11. 承認して年表に入れた出来事に、「AI に秘匿」の印を付けない（2026-11-22）。
12. 印を付けない出来事について、位置の絞りは足さない。今の経路のまま AI に渡す（2026-11-22。§1.8 の調べた結果を見たうえでの回答「絞らずに渡す」）。
13. MCP には、手書きの出来事と同じに出す。外部の AI が、その出来事を更新・削除できるようにもなる（2026-11-22）。
14. 承認を外した提案は、却下として扱う（2026-11-22）。

### 1.2 年表への取り込みは、今の製品では閉じている

- 取り込みの許可は、workspace の DB の表 `narrative_runtime_policy` の 1 行が持つ。project ごとではない。【確認済み（`narrative_runtime_policy.rs` の表の定義）】
- 行が無いときは、`('review-only', 0, 0, 0, version 1)` で作られる。表の既定も `review-only` である。【確認済み】
- 取り込みの準備と実行は、`require_narrative_apply_allowed` を通る。`manual-apply` か `automatic` でなければ、`NARRATIVE_REVIEW_ONLY` で拒まれる。【確認済み（`commit.rs:204`、`:995`）】
- この設定を書く口 `narrative_runtime_policy_set` を呼ぶ製品のコードは無い。呼ぶのは、試験、実機の検査の手順、評価の準備だけである。【確認済み（`src`・`electron`・`src-tauri/crates` の grep）】
- 抽出のダイアログは、この設定を見ない。「取り込む」は押せるが、押すと一般の失敗の文言が出るだけで、理由は出ない。【報告】
- 同じ許可を通る操作が、ほかにもある。取り消しのやり直し（redo）と、generic import の取り込みである。後者は、別の旗 `generic_import_enabled`（既定 0）も要る。【確認済み】
- 保守の書き込みは、別の旗 `maintenance_enabled`（既定 0）と、取り込みのできる設定の両方を要る。【確認済み（関数名と文言まで。中の式は【未確認】）】
- この既定を、いつ・どの条件で開けるかの記録は、見つかっていない。8 月の Gate B の計画には「設定が欠けていたら `review-only` に倒す」とある。【確認済み（計画の該当行）。ほかの文書は【未確認】】

### 1.3 取り込みの単位と、年表全体との照合

- 承認・拒否・保留は、提案 1 件ずつ記録できる。【報告】
- 取り込みは、抽出 1 回ぶんの組が単位である。組の提案が全部、承認か拒否に決まるまで実行できない。保留が 1 件でもあると実行できない。【報告（`commit.rs` の `validate_current_chronicle_apply_coverage`）】
- この規則は、2026-08-27 の PR #559（`65179165`）で入った。その差分で、画面の条件が「承認済みが 1 件以上」から「全件が決まっている」に置き換わっている。【確認済み（差分）】理由の記録は、コードのコメントのほかに見つかっていない。【報告】
- 取り込みの準備と実行は、抽出の時点で封印した「既存の出来事の一覧」と、今の年表の全部の出来事を照合する。1 件でも違うと `NEX_CHRONICLE_RESUME_LIVE_CATALOG_DRIFT` で拒む。重複の判定を、抽出の時点の一覧に対して封印しているためである。【報告（`commit.rs:245-257`、`:1007-1015`）】
- この照合があるので、1 件取り込むと、同じ組の 2 件目も、ほかの抽出の取り込みも通らなくなる。抽出の後に作者が年表の出来事を 1 件直した場合も同じである。【報告】
- 取り込みの記録、根拠の本文が古くなっていないかの検査、年表の並びの割当、承認の権限の検査は、もともと提案 1 件の単位で動く。【報告】
- NIR-0 の認証の記録は、「年表の一覧が変わっていたら、取り込みの記録を書く前に失敗する」を、認証済みの防御として持つ。【報告（`docs/certification/nir0/NIR0-CERT.md:109`）】

### 1.4 承認した解釈が、関連する過去シーンに使われる条件

- 関連の資格は、年表の出来事も取り込みの記録も見ない。見るのは、提案が承認済みであること、最新の決定が人の承認で、今の版に付いていること、版の秘密の印が外れていること、根拠の場面の Scope が解けること、鮮度、読む順である。【報告（`retrieval_admission`）】
- 抽出が作る最初の版は、秘密の印つきである（`proposalPlanner.ts:182`。2026-08-13 の PR #509）。【確認済み】この版を承認しても、資格は通らない。【報告】
- 「まとめて承認」が作る子の版は、秘密の印だけを外し、場面の Scope への依存の印を Native が付ける。この子の版は資格を通り、取り込みの後も資格が残る。【報告（実際の取り込みを通した試験がある）】
- 同じことを 1 件で行う経路は、既にある。版を作る操作と、承認を記録する操作を、続けて呼ぶ。【報告】
- 次の 2 つは、承認しても関連に使われない。根拠が複数の場面にまたがる提案（`EvidenceMismatch`）と、Scope が未設定の場面を根拠にする提案である。【報告】
- IR の admission の規則は、PUB-G の後まで変えない。凍結済みの評価の期待値が動くためである。【確認済み（ADR 013 の記述は調査の報告による。起案者が読んだのは 11-19 の確認の記録）】

### 1.5 取り消し

- 年表の画面で、取り込み済みの出来事を消すと、出来事の行だけが消える。提案・版・承認・取り込みの記録には、何も起きない。提案は「取り込み済み」のまま残る。【報告】
- 取り込み済みの提案には、決定を足せない（`NEX_PROPOSAL_ALREADY_APPLIED`）。却下も足せない。【報告（`repository.rs:385-399`）】
- 今ある取り消し（`undo_commit`）は、出来事を戻すが、提案を未決に戻さず、関連の資格も外さない。製品の画面から呼ぶ経路は無い。【報告】
- 関連の資格を外すには、同じ版に、人の却下か保留の決定を 1 件足せば足りる。取り込みの記録・版・過去の決定は、書き換えずに済む。【報告】

### 1.6 場面から提案を引く

- 提案の表に、場面の列は無い。【報告】
- 提案の版ごとに、「読んだ場面」の記録（`narrative_revision_source_basis`）と、場面から版を引ける依存の索引がある。ただし「読んだ場面」と「根拠のある場面」は同じではない。根拠の場面だけを言えるのは、版の envelope の `evidenceSet` である。【報告】
- 「場面 → 提案」を引く読み取りは、無い。今ある近い読みは、新しい順に最大 50 回ぶんの抽出を 1 つずつ読む形で、bounded lookup の規則に合わない。【報告】

### 1.7 評価の準備との関係

- CP-4 の測定は、製品の `EditorPane` を mount する。サイドペインは既定で開いているので、測定の間も mount されている。サイドペインの中の読み取りは、測定の窓に入る。【報告】

### 1.8 年表の出来事が AI に渡る経路と、位置の扱い

決定 11〜13 の前に、ユーザーに見せた調べの結果である。基点のコードの読みで、実行はしていない。

- 印の判定は 1 つである。印の無い出来事は、常に AI に見せる。印のある出来事は、今の場面が、読む順で開示の場面より前の間だけ隠す。【確認済み（`src/features/chronicle/chronicleSecrecy.ts:72-90`）】
- チャットの自動の文脈は、見える出来事から、今の場面の「作中の時点」を決め、年表の並びがそれ以前の出来事を入れる。【確認済み（`chronicleSnapshot.ts:101-104`、`:397-413`）】件数は最大 8 件と、場面に結び付かない出来事が最大 3 件である。【報告】
- 「作中の時点」の決め方は、次の順である。場面に作中日付があれば、その日付。無ければ、その場面に結び付いた出来事のうち、年表の並びが最も後ろのもの。それも無ければ、読む順で手前の、最も近い場面の時点を借りる。【確認済み（`resolveSceneAnchor.ts:123-176`）】
- チャットの道具のうち、出来事の一覧・詳細・人物の年表は、印の判定だけで絞る。印の無い出来事は、今の場面の位置に関係なく返す。【確認済み（`src/features/chat/agent/chronicleReadTools.ts:79-97`。3 本がこの関数を通ることは【報告】）】検索の道具には位置の絞りの部品があるが、定数で止まっている。【報告】
- MCP は、場面の位置を持たない。印のある出来事を一律に除き、印の無い出来事を全部返す。【確認済み（`src-tauri/crates/grimodex-mcp/src/db.rs:1979-1991`）】書き込みの道具（更新・削除）も、印の無い出来事には届く。【報告】
- 取り込みで作る出来事は、今は必ず印つきで、年表の末尾に追記される。【確認済み（`commit.rs:2287-2292`、`:3129-3139`、`src/features/chronicle/extraction/compiler.ts:118-127`）】作中の日時は入らず、根拠の場面に結び付く。【報告】
- 年表の抽出そのもの、あらすじ、続きを書く、校閲、伏線、地図は、年表の出来事を AI に送らない。関連する過去シーンは、画面に出るだけである。【報告】
- 評価の道具は、年表への取り込みを呼ばず、年表の出来事の印を期待値に使わない。実機の検査の手順 3 本は、「取り込んだ出来事は印つき」を検査している。【報告】

ここから言えること：

1. 印を付けないと、承認した出来事は、チャットの道具と MCP で、その出来事が起きる場面より前を書いているときにも AI に渡る。
2. 取り込んだ出来事は、年表の末尾に、取り込んだ順で並ぶ。作中の順ではない。その出来事が結び付いた場面では、「作中の時点」が年表の末尾に寄る。読む順でその後ろにある、作中日付の無い場面も、同じ時点を借りる。すると、チャットの自動の文脈で、年表の末尾側の出来事が「これまで」として入る。手書きの出来事も含む。これは印の有無と関係がなく、取り込みを有効にすると起きる（今は取り込みが閉じているので、起きていない）。扱いは ★6 で伺う。

## 2. 規則

### 2.1 節（S1〜S6）

- **S1**　節「この場面の解釈」は、エディタのサイドペイン「シーン詳細」の中に置く。既定で閉じていて、開くまで読み込まない。
- **S2**　節は、今の場面を根拠に持つ提案を出す。根拠が複数の場面にまたがる提案は、根拠のある場面すべての節に出る。作品全体の件数では、1 件と数える。
- **S3**　カードは、題、根拠の引用と場面名、確認の状態、参照元の状態、年表の状態を出す。3 つの状態は別々の印にする。色だけに頼らない。
- **S4**　関連に使われない提案（§1.4 の 2 つの場合）には、その旨を出す。判定は Native が返したものをそのまま出し、画面で計算しない。
- **S5**　提案が届いても、節を自動で開かない。通知を出さない。フォーカスを動かさない。変わるのは件数だけである。
- **S6**　画面に「NIR」「IR」「Revision」という語を出さない。

### 2.2 読み取り（R1〜R3）

- **R1**　Native に、場面から提案を引く読み取りを 1 本足す。入力は project と場面の id、出力はその場面を根拠に持つ提案の、現行の版である。ページ付きで、上限を持つ。
- **R2**　返すのは、提案と版の id、題、根拠の引用と場面、3 つの状態、関連に使われるかの見込みとその理由、重複の疑いである。本文の全体は返さない。
- **R3**　この読み取りは、自分のデータを読む命令の一覧（今 39 本）に 1 本足す形で登録する。保存する場所は増やさない。索引を足す必要があるかは、実装の前に確かめる（足すなら schema の版が上がるので、あらためて伝える）。

### 2.3 承認（A1〜A6）

- **A1**　承認を押すと、その 1 件について、次を続けて行う。(1) 秘密の印を外した子の版を作る。既に外れていれば作らない。(2) その版に、作者の承認を記録する。(3) その版を年表に入れる。
- **A2**　A1 は、新しい入口として足す。評価の準備が使う既存の関数の意味は、変えない。
- **A3**　「見せる理由」（回想・伝聞・登場人物の発言の中の出来事など）のある提案も、1 件ずつの承認では、同じ扱いである。承認すれば、年表に入り、関連にも使う。
- **A4**　拒否と保留は、今までどおり、決定を記録するだけである。
- **A5**　取り込む前に、同じ出来事が年表に既にあるかを、その時点の年表で調べ直す（§2.4 の D3）。疑いがあれば、カードがその場で 3 つの選択を出す。同じものとして入れない、別の出来事として入れる、保留する、である。
- **A6**　途中で失敗したときの扱いは、§5 の表のとおりである。承認の記録は残し、年表に入っていないことをカードに出して、やり直せるようにする。

### 2.4 取り込み（D1〜D5）

- **D1**　取り込みは、提案 1 件の単位でできる。組のほかの提案が未決でも、保留でも、取り込める。
- **D2**　「抽出の時点の年表の一覧と、今の年表が一致すること」を、取り込みの条件から外す。
- **D3**　代わりに、取り込む時点で、Native が今の年表に対して重複の疑いを調べ直す。疑いがあるのに、作者の選択（A5）が付いていなければ、取り込みを拒む。画面が出した判定は信頼しない。
- **D4**　取り込みで作る年表の出来事の印は、承認した版の印に合わせる。A1 の承認は印を外した版を作るので、出来事に印は付かない。この案より前に、印の付いた版のまま承認された提案を E2 で入れるときは、出来事にも印が付く。「常に印つきで作る」という Native の検査は外す。出来事の印が版と一致することは、Native が版から組み立て直した操作との照合で保つ。【照合が既にあることは報告】
- **D5**　1 件取り込んでも、同じ組のほかの提案の承認・編集・取り込みを止めない。止めるのは、取り込み済みのその提案だけである。
- **D6**　印を付けない出来事に、位置の絞りは足さない。チャットの自動の文脈・道具・検索と MCP は、手書きの印の無い出来事と同じ規則で扱う。MCP の読み取りと書き込みの道具にも、手書きと同じに出す。
- **D7**　既に取り込み済みの出来事の印は、自動では変えない。
- **D8**　まとめて年表に入れるとき（E2・E3）は、読む順で手前の場面の提案から入れる。同じ場面の中は、提案の並びの順である。

### 2.5 取り消し（U1〜U3）

- **U1**　年表の画面で、抽出から入れた出来事を消すと、その提案の承認も外す。1 回の操作で行う。
- **U2**　そのために、取り込み済みの提案にも、作者の却下を 1 件足せるようにする。取り込みの記録・版・過去の決定は、書き換えない。
- **U3**　承認を外した提案は、却下として扱う。同じ場面を抽出し直すと、同じ内容の提案がまた出ることがある。

### 2.6 既定（P1〜P4）

- **P1**　取り込みの設定の既定を、「作者が承認したものを年表に入れられる」（`manual-apply`）にする。自動の取り込み（`automatic`）にはしない。
- **P2**　保守の旗、generic import の旗、背景の AI の旗は、変えない。既定は閉じたままである。
- **P3**　一度も設定していない workspace（版が 1 で、`review-only` の行）は、新しい既定として読む。設定を書いたことのある workspace は、書かれた値のままにする。
- **P4**　設定が欠けている、壊れている、表が無い場合は、今までどおり `review-only` に倒す。

### 2.7 ほかの入口（E1〜E3）

- **E1**　抽出のダイアログの 1 件ずつの承認は、節と同じ動きにする。承認した 1 件が、年表に入る。
- **E2**　承認済みで、まだ年表に入っていない提案を、まとめて年表に入れるボタンを置く。置き場所は、抽出のダイアログと、節である。節のボタンは、その場面の分だけを入れる。中の処理は 1 件ずつで、1 件が失敗しても、残りは年表に入る。
- **E3**　「まとめて承認」は、1 つのボタンで、対象を承認し、そのまま年表に入れる。対象の判定（見せる理由の無い提案だけ）は、今までどおり Native が行う。途中で失敗した分は、承認済みで年表に入っていない提案として残り、E2 のボタンで入れられる。

## 3. 残る制限

- 根拠が複数の場面にまたがる提案と、Scope が未設定の場面を根拠にする提案は、承認して年表に入れても、関連する過去シーンには使われない。規則を変えるのは PUB-G の後である。
- 承認を取り消す場所は、年表の画面だけである。節のカードからは取り消せない。
- 承認して年表に入れた出来事は、チャットの道具と MCP で、その出来事が起きる場面より前を書いているときにも AI に渡る。防ぐ手段は、作者が年表の画面で付ける印だけである。印は 1 件ずつ付ける。承認のときに印を選ぶ操作は、置かない。
- 取り込んだ出来事は、年表の末尾に、取り込んだ順で並ぶ。作中の順に並べ替えるのは、作者が年表の画面で行う。並べ替えるまでの、チャットの自動の文脈への影響は、§1.8 の 2 と ★6 のとおりである。
- 抽出のダイアログにある、提案の秘密の印の切替は、残す（評価の準備と実機の検査が使う）。承認を押すと A1 が印を外すので、切替の見え方と文言は、実装のときに合わせる。
- 重複の調べ直しは、題の一致によるものである。題が違う同じ出来事は、見つけられない。
- 既に承認済みで、まだ年表に入っていない提案は、自動では年表に入れない。E2 のボタンで、作者が入れる。
- サイドペインの幅は、エディタの 20% が既定である。既定の配置では、計算上 82〜130px で、カードを読むには狭い見込みである。幅は測っていない。作者はペインを広げられる（50% まで）。
- レイアウトの作り替え（Scene Context パネルの廃止、左右の領域の幅、チップ行を常に出すこと）と、Work Layer の実データへの接続は、この案に含めない。
- phone の幅では、サイドペインは全画面のシートになる。節はその中に出る。

## 5. 承認の途中で失敗したとき

| 失敗する段 | 残るもの | カードの見え方 | やり直し |
| ---------- | -------- | -------------- | -------- |
| 子の版を作る | 何も残らない | 未確認のまま。失敗の理由を出す | もう一度承認を押す |
| 承認を記録する | 未承認の子の版 | 未確認のまま（子の版が現行の版になる） | もう一度承認を押す。子の版は作り直さない |
| 重複の疑いが見つかる | 承認済みの版 | 「同じ出来事が年表にあるかもしれません」と 3 つの選択 | 選ぶと続きを行う |
| 年表に入れる（原稿が保存の途中・変わっていた） | 承認済みの版。年表には入っていない | 承認済み・年表に未取り込み。理由を出す | 「年表に入れる」を押す |
| 年表に入れる（年表の末尾の並びが競合した） | 同上 | 同上 | 画面が 1 回だけ読み直して試す。だめなら上と同じ |
| 年表に入れる（根拠の場面の 1 つが変わっていた。複数の場面の提案） | 同上 | 同上。どの場面が変わったかを出す | 抽出し直すか、拒否する |
| 「まとめて承認」の途中（一部の提案で失敗した） | 成功した分は年表に入る。失敗した分は、承認済みの版。年表には入っていない | 入った件数と、入らなかった件数を出す | 「承認済みをまとめて年表に入れる」を押す |

承認済みで年表に入っていない間も、その解釈は関連に使われる。資格が承認を見て、取り込みを見ないためである。

## 6. 変える場所の見込みと、順番

1. **Native：取り込みの単位と調べ直し**（D1〜D5、T1）。`commit.rs` の被覆の検査、`repository.rs` の組の消費済みの検査、年表全体との照合。評価の準備が通る関数は、未取り込みの組での挙動を変えない。試験で示す。
2. **Native：取り消しのための決定**（U2、T2）。
3. **Native と IPC：場面から提案を引く読み取り**（R1〜R3、T4）。
4. **既定**（P1〜P4、T3）。
5. **年表の出来事の印**（D4・D6・D7、T5）。`commit.rs` の「常に印つき」の検査と、出来事を組み立てる 2 か所（`commit.rs` と画面の `compiler.ts`。同時に変える）。CAS/1 の試験の組、実機の検査の手順 3 本、画面の文言、年表の設計書、`docs/CONTEXT_INJECTION.md`、ADR 013 の追補。MCP とチャットの道具のコードは変えない（印の無い出来事を返す規則は、今のままである）。4 の既定より先に入れる。先に既定だけを開けると、印つきの出来事が作られる期間ができる。
6. **画面：節と、承認の連鎖、ダイアログの整理**（S1〜S6、A1〜A6、E1〜E3、U1）。実機の検査の手順 7 本と、journey の一覧の digest を直す。
7. **評価の道具の手直し**。S4 が pin する file は、製品の PR に入れない。統合者が、最後の凍結の準備（S4 の枝）に束ねる。一覧は下のとおりである。

評価の道具で確かめる・直す見込みの箇所【報告】：
- `frozen-setup-driver.mjs`、`setup-driver.mjs`：`narrative_runtime_policy` を書く段と、読み戻しの値。既定が変わる。
- `cp4-harness.ts`：`reviseChronicleProposal`・`decideChronicleProposal`・`recordChronicleProposalDecision` の呼び出し。意味を変えないので、直さない見込み。
- 「承認の撤回」（G-08）：取り込み前の提案への保留。U2 は取り込み済みだけを緩めるので、変わらない見込み。
- CP-4 の測定の窓：節は既定で閉じ、開くまで読み込まないので、入らない見込み。

PR は 1 本ずつ出す。全部が master に入ってから、統合者が S4 の枝の改版を始める。この案が入るまで、最後の凍結は始められない。

## 8. 未確認と限界

- この文書の【報告】は、read-only の調査の結果で、起案者は該当の行を読んでいない。実装の前に、基点のコードで読み直す。
- どの挙動も、実行して確かめていない。別のセッションが評価の測定を回していたため、起動や試験は行っていない。
- D3 の調べ直しを Native に置くとき、題の正規化（今は画面の側にある）を Native に持つ必要がある。同じ判定になることを、試験で示す必要がある。
- 取り込み済みで却下の状態を、取り込みのやり直し・被覆の検査・review の一覧が許すかは、確かめていない。
- P3 の読み替え（版が 1 の行を新しい既定として読む）が、schema の版を上げずにできるかは、確かめていない。上げる場合は、release の移行の試験（schema 2 からの upgrade）を通す。
- 1 件の取り込みにかかる時間は、測っていない。「まとめて承認」で数百件を入れる場合の時間は、merge の前に測る。
- 公開済みの版（v2.0.10）に、提案の表と `narrative_runtime_policy` の表が無いことは、tag での確認による。更新した利用者の workspace で、行が新しい既定で作られることは、確かめていない。
- 11-11 と 11-12 のユーザーの確認の記録のファイルは、見つけられていない。CAS/1 と BAO/1 が確認済みであることは、それぞれの決定の文書の記述による。
- §1.8 の【報告】は、2026-11-22 の read-only の調査の結果である。チャットの道具 3 本が同じ印の判定を通ること、検索の位置の絞りが定数で止まっていること、MCP の書き込みの道具の届く範囲、取り込みで作中の日時が入らないことは、起案者が読んでいない。
- 承認した出来事が増えたとき、チャットの 1 回の送信に入る年表の量がどう変わるかは、測っていない。自動の文脈は件数の上限を持つ。道具の一覧には、上限があるかを確かめていない。
