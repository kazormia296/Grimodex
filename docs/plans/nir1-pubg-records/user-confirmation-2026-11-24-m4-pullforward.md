- 問い 2 の表の原文（持ち主の報告による）：
  - a「作者が起こす（推奨）」
    - 動き：古い印が付いた項目に「再解釈」ボタンを出す。押した時だけ、その範囲だけを AI に送る。
    - 送信の性質：作者の操作ごとの送信で、今の抽出と同じ扱い。
  - b「自動で送る」
    - 動き：本文を保存・編集するたびに、影響範囲を裏で AI に送り、結果を変更レビューに積む。
    - 送信の性質：新しい送信。作者が気づかないうちに本文の断片が外へ出る。
  - c「一定の条件で自動」
    - 動き：設定でオンにした作者だけ、または件数・間隔に上限を付けて自動で送る。
    - 送信の性質：b を絞った形。上限・同意の設計が別に要る。
  - 起案者の推奨は「a で始め、運用が固まってから c を別の判断として伺う」だった。
- 6 点の方向：既定はオフ、プロジェクト単位でオンにする、編集が落ち着いた後にまとめて送る、件数と費用に上限を付ける、いつでも止められる、結果は変更レビューに積むだけ。
- 統合者の読み（ユーザーの決定ではない）：
  - 問い 2 は、AI への新しい送信の**方向**の決定である。上限の具体的な数・送る中身・送信先は、設計の時に持ち主が案を出し、改めて伺う。その確認が済むまで、送信の経路は開けない（旗を閉じたままの実装は可）。
  - 問い 1 は、新しい契約（identityDeclaration）を足すことの了承である。契約の文面は docs の起案として整え、PR 本文と decisions に残す。

## 追記 4：前提の誤りの後の進め方（11-25、elastic-lichterman-ef3b03 のセッションで構造化質問。統合者は直接見ておらず、持ち主の報告をそのまま記録する）

- 選択肢（原文）：

  - 「自動送信を先に設計し直す」：既存の内容が無い前提で、自動送信の送る中身と送信先をゼロから起案して伺う。
- 回答（原文）：**「自動送信を先に設計し直す」**（推奨の選択肢ではない）

- 統合者の読み（ユーザーの決定ではない）：
  - 自動送信の送る中身・送信先・hidden の除外・上限・同意・記録は、ゼロから起案する。それを新しい送信として、改めて伺う。
