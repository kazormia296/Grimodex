# ユーザーの回答（2026-11-19 夜、AskUserQuestion）：#41 本文の宣言の確認ダイアログの形

## 経緯
- 11-19 の先の回答で、ユーザーは #41（en の UI でも確認ダイアログが日本語）に「ローカライズのせられないんですか？」と答えた。統合者はローカライズの設計（`fusion-eval-data/design-notes/pubg-parallel-2026-11-19/q41-localize-design.md`）を作り、実装を始めた。
- 統合者が仕組み（Native が固定の文面を組み、digest を grant に束縛し、Main が OS のダイアログを出す）を説明すると、ユーザーは「流石に意味わからん。Fableに相談してください」と答えた。
- Fable（read-only の設計相談）の結論：簡素化を勧める。
  - 宣言が開くものは、関連シーンの追加 1 枠に、Graph が見つけた場面の title・本文の先頭の非空行・位置への移動を出すことだけ（AI 送信・Packing・履歴・export には使わない）。
  - 乗っ取られた renderer は、もともと本文を読め、何でも描ける。OS ダイアログが守っているのは「DB の宣言の記録が人の操作を表す」という完全性だけ。
  - 副作用：二重の確認（renderer の 5 チェック＋ボタンの後に OS ダイアログ）、ダイアログの間に他の保存が最大 60 秒待つ、i18n が使えない。
  - 案 B：製品の OS ダイアログだけをやめ、renderer の既存の 5 チェック＋ボタンを唯一の確認にする。Native の書込み時の照合・失効・veto・確認なしの取消は残す。失う防御は「乗っ取られた renderer が自分で宣言する」の 1 つ。最後の凍結で製品の挙動の変更として開示する。
  - 案 C（機構ごと消す）は、pin 済みの harness の seam の receipt に当たるので、公開の後の掃除に回すのが妥当。
  - profile activation の OS ダイアログは対象外で、そのまま残す（profile 全体に及び、再起動後も続き、アプリから解除できないため）。

## 回答
1. 確認の形：**OS ダイアログをやめる（推奨、案 B）**。
2. 将来、宣言を AI 送信などの根拠に使う予定：**予定はない**。宣言は関連シーンの表示だけに使う。上の判断はこれを前提にする。

## 扱い
- 確認済みの actor・防御の改訂（K2/4 の Trusted actor「Main のダイアログを確定した操作者」、Mandatory defense 1・7、In-scope「確認の偽造」、DR-CB3-8 の U-9、DR-CB2-5／-8）を、ユーザーの決定として改める。実装の PR の最初の commit に DR と信頼境界の変化を書く。
- ローカライズの作業（枝 `claude/pubg41-declaration-dialog-locale`、DR-CB2-17 の commit と未 commit の変更）は採らない。worktree は記録として残し、片付けは後で伺う。
- 案 C は公開の後の掃除の候補として残す。
- 宣言を AI 送信などに広げることになったら、確認の強さを設計し直す（そのときに改めて伺う）。
