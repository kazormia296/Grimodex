# ユーザーの確認（2026-11-20、AskUserQuestion）：PUB-G の方針転換の 4 点

- 草案：`fusion-eval-data/design-notes/pubg-pivot-2026-11-19/` の `declaration-abolition-draftref-v2.md`、`graph-restricted-draftref-v2.md`、`ai-disclosure-adr-v2.md`。
- 点検：同じ dir の `consistency-check-v2.md`。
- 確認文は、点検の指摘（技術語を減らす、二重の確認をやめる、重要な変更に絞る）に合わせて、統合者が平易にまとめた。下に問いの要旨と回答を記す。

## 確認 1：本文の宣言の廃止（K2/4 の改訂 → K2/5。contractId `graph-target-scene-body-disclosure` と `scope-storage-authority`）
- 問いの要旨：
  1. 本文の宣言と veto（秘密の印・視点の記録による拒否）をやめる。Graph が足す 1 件の場面は、作者の操作なしで出す。
  2. その場面に求めるのは、読む順で前であることと、A1（今の場面と同じ世界線・層・知る人／読み手）だけ。
  3. 出すのは title・本文の先頭の 1 行・その位置への移動だけで、AI には載せない。
  4. 保存の列は残して使わない。コードの撤去は PUB-G の後。
  5. 評価の結果は変わらない見込み（fixture の数え上げ。実行での確認は最後の凍結で）。
- 回答：**この内容で確認する（推奨）**。

## 確認 2：Graph の制限の解除（K3/2 `caller-profile-egress` の Graph の行の改訂）
- 問いの要旨：
  - restricted を有効にしていない作者にも Graph を出す。
  - 許すこと：制限なしでも関連シーンに Graph の結果が出る。
  - 許さないこと：Graph の応答を AI への送信・Packing・履歴・書き出しに載せること。新しい送信先はできない。
  - 実装の前に未確認の点（返却時の検査など）を確かめ、問題があれば改めて伺う。
  - PUB-G の公開の条件から「D2a（restricted）が前提」を外すか。
- 回答：**確認し、D2a の前提も外す（推奨）**。

## 確認 3：AI への開示の範囲と印の強さ（ADR 013 の J1・J2）
- 問いの要旨：
  - (a) 全部開示の対象は原稿などの元のデータ。AI が抽出した IR や Graph の応答（新しい種類のデータ）は、今までどおり対象外（記録に無かった点の確認）。
  - (b) Codex の hidden と年表の secret は「どの経路でも AI に渡さない」。伏線の secret と Codex の suppress は「自動では渡さない（作者が尋ねたり tool で開いたりすれば渡る）」。今の挙動の追認。
- 回答：**この内容でよい（推奨）**。
- 画面の判定の撤去は確認 1 で扱い、ADR には二重に書かない。

## 確認 4：読みの一括推定（IME 連携）
- 問いの要旨：hidden の項目の名前と別名も AI に送っている。これは「hidden はどの経路でも渡さない」の例外になる。
- 回答：**直す（hidden は送らない）（推奨）**。hidden の項目は一括推定の対象から外し、読みは作者が手で入れるか個別に推定する。

## 統合者が決めて記録するもの（確認の対象にしない）
- ADR の J3〜J7 の細部は、推奨を既定として起案し、送信範囲が広がるものだけ別に伺う。
  - J3(1)：伏線の新規の既定を false にすると、外部 provider への送信が増える → 別に伺う。
  - J4(b)：まだ明かされていない情報を自動で注入する → 別に伺う。
- 位置の正本の寄せ方、移行の順序、測定の手順は、技術判断として ADR と DR に記録する。
