## 2. 判断

### DR-CED-1　§5 の 2 を、2 本の PR に分ける

- 起案の §5 の 2（比べ方・現在地・仮の日時の決め方。新しい file だけ）を、画面の側（TypeScript）の PR と、Native（Rust）の PR に分ける。
- 理由：Native の側に、暦の計算（改暦を含む）を新しく置く必要が分かり、作業が増えた。1 本ずつ、点検できる大きさにする。
- 1 本目（画面の側）が、試験用の例（fixture）を足す。2 本目（Native）が、同じ fixture を読む。K3 の「同じ fixture で同じ結果」は、2 本目が入ったときに成り立つ。それまで、既にある処理は切り替えない（§5 の 5 は、2 本とも入った後）。

### DR-CED-2　新しい file の置き場と名前

- 画面の側：`electron/shared/readDomain/features/chronicle/` に、`chronicleSpan.ts`（粒度の幅）、`chronicleOrder.ts`（K1 の並びと、K2・K2a の判定）、`chronicleAnchorByDate.ts`（C3・C3a・C4 の現在地）、`chronicleProvisionalDate.ts`（I2 の仮の日時）を足す。道具の作り直しの lane（Mastra への移行）の決まりに従う。相対の import に `.js` を付ける。`@/` を使わない。関連する過去シーンの仕組み（IR）の symbol を含めない。`src/features/chronicle/` の側に、re-export の file は作らない。
- 試験：`src/features/chronicle/` に置く（既にある年表の試験と同じ流儀）。
- Native：`grimodex-core` に、新しい module を足す（2 本目）。取り込み（`grimodex-db`）と MCP（`grimodex-mcp`）の両方から呼べる crate は、`grimodex-core` だけである。`lib.rs` に `pub mod` の 1 行が要る。これは、既にある処理を切り替えない。
- fixture：`src-tauri/crates/grimodex-core/src/chronicle_order/` の下に、JSON で置く（`nir1_local_send_policy/decision_vectors.json` と同じ流儀）。画面の側の試験は、相対の path で読む。Native は `include_str!` で読む。CI の設定は変えない。

### DR-CED-3　「日時がある」の判定

- 開始の日があり、粒度が「なし」でないこと（起案の用語のとおり）。
- 粒度が、知らない文字列のときは、日時が無いものとして扱う（安全な側）。
- 終わりだけがあって、開始が無い出来事は、日時が無い。
- 分は、粒度が「時刻」のときだけ数える。粒度が「時刻」で、分が無ければ、0 分とする（K1）。
- 年表の画面の今の並び（`chronicleAxis.ts`）は、粒度を見ずに、開始の日があるかどうかで決め、分を常に足す。新しい関数は、画面の並びとは別に書く。画面の並びは、この PR では変えない。

### DR-CED-4　幅の出し方

- 幅は、始まりを含み、終わりを含まない区間である（K2）。単位は、分（日 × 1440 ＋ 分）。
- 時刻は 1 分、日は 1 日。
- 月は、暦に月の定義があるとき、保存された日が入る月の、初日から末日まで。年は、1 年の日数が決まっているとき、保存された日が入る年の、初日から末日まで。季節は、季節の境界があるとき、保存された日が入る季節の、始まりから、次の境界の前まで（年をまたぐ季節を含む）。
- 求められない粒度（月の定義が無い、季節の境界が無い、1 年の日数が決まっていない、暦の設定が無い）は、保存された開始の 1 日（決定 13）。
- 改暦のある暦でも、月と年の幅は、暦から求める（K2 の文言どおり。月の定義も、年の日数も、決まっているため）。画面の側は、既にある暦の関数を使う。Native の側には、改暦の計算を足す（2 本目）。
- 終わりの日時がある出来事の幅は、開始の幅の始まりから、終わりの粒度の幅の終わりまで。終わりの粒度が「なし」か、知らない文字列のとき、または、終わりが開始より前のときは、終わりが無いものとして扱う（開始の粒度の幅）。
- K1 で、月・季節・年だけの出来事を並べるときは、幅の始まりを使う（K2 の文言どおり）。

### DR-CED-5　現在地の幅（◇11 の読み）

- 現在地の幅は、場面の作中日付の粒度の幅か、現在地を決めた出来事の、開始の粒度の幅である（K2 の本文）。
- ◇11 の問いは「開始の日だけにしてよいか」と書く。問いの対比は、「期間の全体か、開始だけか」だった。開始の粒度が月・季節・年の出来事で現在地を決めたときは、K2 の本文のとおり、その月・季節・年の全体を、現在地の幅にする。
- この読みは、ユーザーに伝えた（2026-11-22）。fixture に、この場合を明示して入れる。

### DR-CED-6　幅が接するとき

- 出来事の幅の終わりと、現在地の幅の始まりが、同じ時点のときは、重ならない（「これまで」）。現在地の幅の終わりと、出来事の幅の始まりが、同じ時点のときも、重ならない（「これから」）。幅が、終わりを含まない区間であること（K2）から決まる。

### DR-CED-7　現在地の決め方（C3・C3a・C4）

- 順は、C4 のとおり。場面の作中日付 → その場面に結び付いた、材料にできる出来事のうち、K1 の並びで最も後のもの → 読む順で手前の、現在地を持つ最も近い場面から借りる → 決まらない。
- 材料にできる出来事は、日時があり、確度が「不明」でない出来事である（C3）。C3a の条件（出来事が全部「不明」で、作中日付のある、保管済みでない場面も無い）に当たる作品では、確度が「不明」の出来事も、材料にする。
- 手前の場面から借りるときは、候補を「作中日付のある場面か、材料にできる出来事が結び付いた場面」に絞ってから、最も近い場面を選ぶ。今の `resolveSceneAnchor` は、絞らずに最も近い候補を選ぶので、材料を除くと、現在地が決まらなくなる場合がある。
- 返す値は、今の `ChronicleAnchor` の形と、出どころの名前（`scene`／`stamped`／`proxy`／`none`）を保つ。切り替えの PR で、差し替えやすくするためである。
- 保管済みの場面は、入力から除いて渡す（呼び出す側の責任）。C3a の判定のために、作中日付のある、保管済みでない場面があるかどうかを、入力で受ける。

### DR-CED-8　移行で入れる仮の日時（I2）

- 「最も後の日」は、保存された日付そのものから決める（日時のある出来事の、開始と終わりの日。保管済みでない場面の作中日付）。月・季節・年の幅の終わりは、使わない（I2 の文言どおり）。幅を使うと、移行の結果が、暦の設定で変わる。
- そのため、月・季節・年だけの出来事の幅の内側に、仮の日が置かれることがある。その出来事どうしは、「同時進行」になる。仮の日時は、確度が「不明」で、作者が年表で動かす前提である（起案の §3）。
- 置く順は、裏の並び、同じなら作った日時、それも同じなら id（決定 14）。作った日時は、形の違う文字列が混ざりうるので、既にある、時点の比較の関数を使う。
- 出来事にも場面にも日付が無い作品では、暦の起点の日（日数 0）から、1 日ずつ置く。
- この PR が足すのは、決め方の関数だけである。移行そのもの（§5 の 6）は、後の PR で、Native の側の同じ関数を使う。

### DR-CED-9　今の判定の再現の試験

- 「裏の並びで比べると、ほぼ全部の出来事が『これまで』に入る」ことを、今の関数（`resolveSceneAnchor` と `chronicleSnapshot` の導出）で再現する試験を、1 本目に入れる。今の挙動を固定する試験で、切り替えの PR（§5 の 5）で、期待値を改める。
- 同じ入力を、新しい関数に通すと、日時どおりに分かれることも、並べて確かめる。

### DR-CED-10　「終わりが開始より前」の「開始」

- DR-CED-4 の「終わりが開始より前のときは、終わりが無いものとして扱う」の「開始」は、開始の幅の始まりである。終わりの幅の終わりが、開始の幅の始まり以前のときに、終わりが無いものとして扱う。
- 開始が月・季節・年だけの出来事で、終わりが、その幅の中の、保存された日より前の日のときは、終わりを使う（幅は、開始の幅の始まりから、終わりの幅の終わりまで）。K2 が、月・季節・年だけの出来事の開始を「その幅の始まり」として扱う（K1 の並びも、幅の始まりを使う）ことに合わせた。
- fixture に、この場合を入れた（`end-inside-start-month-before-stored-day`）。

### DR-CED-11　範囲の外の値

- 粒度が「時刻」で、分が 0〜1439 の外のときは、丸めずに、日 × 1440 ＋ 分のまま使う。Native の書き込みの入口は、分の範囲を検査している。範囲の外の分は、古い行にしか残りえない。並びが単調であることを保つために、丸めない。fixture に入れた（`time-minute-above-range`、`time-minute-negative`）。
- 日は整数の前提である。画面の側は、小数の日を切り捨てる（fixture には入れない。Native は整数で読む）。
- 月・季節・年の幅を、暦から求めた結果が、有限の数にならないとき（暦の設定が壊れている）は、求められない粒度として、保存された開始の 1 日にする。
- 日の大きさの上限は、この関数では決めない。上限は、書き込みの入口の検査（§5 の 3・4）が持つ。極端に大きい日では、うるう年のある暦の計算が遅くなる（既にある暦の関数の性質）。入口の検査を書く PR で、上限を、画面の側と Native で同じ値に決める。

### DR-CED-12　作った日時の比べ方（I2 の置く順の 2 つ目の鍵）

- 作った日時は、時刻として、ミリ秒まで比べる。形の違う文字列（ISO の形と、SQLite の「年-月-日 時:分:秒」の形）は、同じ時刻なら、同じとして扱う。
- 読めない値は、読める値の後ろに置く。両方とも読めないときは、同じとして扱い、次の鍵（id）で決める。文字列としては、比べない。
- 理由：既にある共通の関数は、両方とも読めないときに、実行環境の並びの規則で文字列を比べる。その結果は、Native の文字列の比較と、同じになる保証が無い。移行（§5 の 6）は Native で走るので、画面の側と Native が、同じ結果になる決め方にする（K3）。
- fixture に入れた（`prov-created-at-unreadable-sorts-last`、`prov-created-at-identical-unreadable-id-breaks-tie`、`prov-created-at-both-unreadable-different-id-breaks-tie`）。

### DR-CED-13　日はあるのに、粒度が「なし」の出来事（I2 と I3 の関係）

- 起案の用語は、「日時がある」を、開始の日があり、粒度が「なし」でないこと、と書く。I3 は、日時はあるのに粒度が「なし」の出来事の、粒度を「日」に直す、と書く。
- I2 の関数は、I3 の読みに合わせる。開始の日があり、粒度が「なし」の出来事は、仮の日時を入れる対象にしない。その日は、「最も後の日」に数える。I3 が、同じ移行の中で、その出来事の粒度を「日」に直すので、移行の後は、日時のある出来事になる。数えないと、仮の日時が、その出来事より前に置かれることがある。
- 開始の日があり、粒度が、知らない文字列の出来事も、対象にせず（I4。想定しない値の行は飛ばす）、その日だけを数える。
- 前後の判定（K1・K2）では、粒度が「なし」の出来事は、移行の前は、日時が無いものとして扱う（DR-CED-3）。
- fixture に入れた（`prov-granularity-none-with-day-is-not-a-target` ほか）。

### DR-CED-14　C3a の「作品の出来事が全部」の数え方（切り替えの PR で決める）

- 現在地の関数は、渡された出来事だけで、C3a（全部が「不明」か）を判定する。日時の無い出来事は、「不明」として数える（B1）。ただし、日時の無い出来事は、C3a に当たる作品でも、材料にならない。
- 今の自動のまとめは、秘密の印の判定を先に掛けた出来事を、現在地の決め方に渡している。秘密の印で除く前の全部を渡すか、除いた後を渡すかは、この PR では決めない。切り替えの PR（§5 の 5）で、渡す集合とあわせて決め、この文書に足す。
- 現在地の値のうち、裏の並びの欄（`ordinal`）は、今の型を保つために埋める。新しい判定は、この欄を使わない。Native の側は、この欄を持たなくてよい。fixture の期待値にも、入れていない。

### DR-CED-15　Native の側（2 本目）の作り

- 置き場は、`grimodex-core` の `chronicle_calendar`（暦の計算。改暦は子の module）と `chronicle_order`（幅、並び、判定、現在地、仮の日時、時点の読み方）である。`lib.rs` には、`pub mod` の 2 行だけを足した。依存は足していない。N-API には出していない。MCP の写し（`grimodex-mcp` の `chronicle_snapshot.rs`）は、切り替えの PR まで変えない。
- 画面の側と同じ例（`chronicle_order_vectors.json`）の全件（幅 99、並び 14、判定 54、現在地 39、仮の日時 29）で、期待値と一致する。case の id の一覧と、期待値の欄の集合を、試験で固定した。
- 例に無い入力は、実装のときに、画面の側の実物（TypeScript を実行した値）と、乱数で突き合わせた（暦・幅で約 26 万、時点の文字列で約 68 万、並び・判定・現在地・仮の日時で 6 万。点検でも、暦 38 種の総当たり）。不一致は 0 だった。突き合わせの道具は、repo に入れていない。
- 整数は、`i128` で持つ。割り算と剰余は、画面の側の `Math.floor` に合わせた。
- 画面の側と、意図して違える所（どれも、通常のデータでは届かない）。
  - うるう年のある暦で、日から年を求める所は、画面の側の「1 年ずつ補正する」手順を、二分探索に替えた。答えは同じで、極端に大きい日でも遅くならない。
  - 季節の始まりの日に端数がある暦では、Native は、その境界を使わない（分の区間が整数にならないため）。暦の編集の画面は、整数だけを保存する。
  - 幅の端が、画面の側の数の精度（2 の 53 乗）を超える入力では、Native は、幅を「無い」として返す。開始の日が、約 6 兆日を超える場合である。
  - 暦の値が極端に大きく、計算が桁あふれする入力では、求められない粒度として、保存された開始の 1 日にする（DR-CED-11 と同じ向き）。panic しない。
- 作った日時の読み方（DR-CED-12）は、画面の側の時点の読み方（`lib/time.ts` と、それが使う Temporal の実装。版は 1.0.1）と、読める・読めないが一致するように写した。オフセットの無い「年-月-日T時:分:秒」と、日付だけの文字列は、読めない。SQLite の「年-月-日 時:分:秒」は、UTC として読む。ミリ秒より細かい桁は、切り捨てる。読み方の表は、Native の試験にだけある。Temporal の実装の版を上げるときは、表を作り直して、突き合わせる。
- 場面の確度に、知らない文字列が入っていても、読み取りは失敗させない（場面の確度の列には、値の検査が無い）。知らない確度は、「不明」でないものとして扱う（画面の側と同じ）。
- 読む順の番号が同じ場面が複数ある、壊れた入力では、借りる場面の選び方が、画面の側と変わりうる（画面の側は渡された順、Native は場面の id の順）。読む順の番号は、通常は重ならない。

- MCP の写しが、保管済みの場面を除かないことと、改暦を無視していることは、切り替えの PR で、Native の 1 つに寄せるときに直る（K3）。
- 起案の本文に、確認の後に古くなった文が、ほかに見つかったときは、台帳の一般の決まりで読まず、この文書に列挙を足す。

## 4. §5 の 3 の 1 本目：AI・MCP と原稿の読み込み（N7・N8。2026-11-25）

### DR-CED-16　入口の変更のうち、画面でない分

- **PR の分け方**：§5 の 3 を、画面でない分（N7・N8）と画面の分（N5・N6）の 2 本にする。Native はまだ日時なしを許す。
- **N7**：アプリ内の AI と MCP の `create_event` は `startTime` と `precision` を必須にし、粒度 `none` を拒む。`update_event` は `precision` を任意で受け、日時の null 化と粒度 `none` を拒む。道具の説明に「不確かなら推定の値を入れ、確度で表す」を足した。
- **暦の要約**：`get_chronicle_state` は、暦があるときだけ `calendar: { daysPerYear, startYear, months, leapRule, reform }` を足す（日の数え方に要る分。◇9 の要約の範囲を、閏と改暦を含めるとユーザーが決めた。確認 161）。曜日の名前・年号・旧暦の決まり・タイムゾーンは渡さない。
- **N8**：原稿の読み込みの出来事は、`provisionalBaseDay`（保管中でない場面の日付を含む）から読み込んだ順に 1 日ずつ、粒度「日」、確度 `unknown`。製品から呼ばれない古い取り込み（`importExtractedEvents`）は削った。

## 5. §5 の 3 の 2 本目：年表の画面（N5・N6。2026-11-26）

### DR-CED-17　入口の変更のうち、画面の分

- **N5**：作成の日は `chronicleCreateDay` で決める。選んだ位置と画面の中央は、これまでどおりの粒度で、確度 `exact`。どちらも使えないときは `provisionalBaseDay`（いま読み込んでいるこの作品の出来事と、保管中でない場面の日付）で、粒度「日」、確度 `unknown`。場面の絞り方は N8 と同じ。
- **N6 の開始の欄**：出来事の欄だけ「なし」を出さない（`requireDate`）。日時の無い出来事は「なし」を選べない状態で選択済みに見せ、選べるのは「年月日」と「日時」。原文の「「日」以上」を、日か、日より細かい粒度と読んだ。年や季節は、一度日付を入れた後で選べる。
- **N6 のまとめて消す操作**：画面に、出来事の日付をまとめて消す呼び出し元は無かった（§1.3 の【報告】の行は、実際と違った）。選択のまとめての削除は、場面は作中日付の消去、出来事は削除で、そのまま残す。型と Native の `eventClearDate` は残り、§5 の 4（Native の入口の検査）で拒む。

## 6. §5 の 4：Native の入口の検査（N1〜N4a・N9。2026-11-26）

### DR-CED-18　入口の検査

- 拒む文は `grimodex-core` の `CHRONICLE_EVENT_DATE_REQUIRED` 1 つ。画面の代役・アプリ内の AI は `electron/shared/chronicleEventDate.ts` の同じ文、MCP は core の定数を使う。
- **作成**：公開の入口（`agent_event_create_with_authority_impl`。画面の手動の `event_create` と AI の `agent_event_create` が通る）と、MCP の写し（`grimodex-mcp` の `db.rs`）で拒む。再送の確認の後で検査する（版を上げる前の再送は、保存済みの結果を返す）。共通の `apply_event_create_in_tx` には入れない。抽出の承認も同じ関数を通るためで、承認の日時は G1〜G9 の commit で Native が決める。
- **更新**：要求を反映した日付の 6 欄が保存値と 1 つでも違うときを「触れる」とし、反映後に日時が無ければ拒む。同じ値の送り直しは触れないとみなし、粒度の自動の引き上げも、値が変わるときだけにする。画面の更新、MCP、まとめての `eventSetDate`、時間の関係の取り込みに同じ決まりを当てる。
- **確度だけの更新の拒否（N4a の一部）は、まだ入れない。** 原文は「確度だけを変える更新は拒む」と「移行までは、日時の無い出来事の更新を補わずに通す」の両方があり、読みが割れる。後者を採り、移行（§5 の 6）で補う処理と一緒に入れる。
- **まとめて日付を消す**（`eventClearDate`）は拒む。画面に呼び出し元は無い。取り消し・やり直し・スナップショットの復元は journal の値を書き戻すので、通る（N9）。
- 出来事を書く箇所を数える試験は `narrative_scope_storage_authority.rs` の `chronicle_event_write_inventory`。分け方は、検査あり、抽出の承認と共有、取り消し・復元、seed と移行。
- 残る制限：開始の日が無く終わりだけ残った古い出来事では、「点にする」も拒まれる（先に開始の日付を入れる）。

### DR-CED-19　抽出の承認で入れる日時（G1・G2・G4〜G9）

- **場所**：`narrative_extraction/chronicle_approval_date.rs`。digest の照合の後、書くときの値にだけ日時を入れる（G8）。操作の中身は書き換えない。payload が開始の日と「なし」でない粒度を持つときは、そのまま使う。
- **G2**：根拠の場面を読む順（保管した node とその子孫を除く。同じ並びの鍵は id の順で、画面と同じ）で見て、最初に作中日付のある場面の日付を、**開始と、あれば終わりも**写す。分は、その端の粒度が「時刻」のときだけ写す。「日付を写す」を、場面の作中日付の全体と読んだ。
- **G4・G5**：G4 は core の `resolve_chronicle_anchor_by_date`、G5 は `provisional_base_day`。どちらも粒度「日」。小数の日は切り下げる。
- **G6・G9**：確度は `unknown`。Native が日時を入れた出来事の、開始・終わりの日・分・粒度と確度の 7 欄だけを、出所 `system` にする（schema は変えない）。ほかの欄と、payload が日時を持つ場合は、今までどおり。
- **G7**：1 件ずつ、その時点の DB から決める。取り消し・やり直し・再送では、決めた値がそのまま残る。
- **G3 は未実装**（EET/1）。**B2 は入れない**。B2 は N4a の補う処理で、移行（§5 の 6）の後に有効にする。

## 7. §5 の 5：比べ方の切り替え（K4・C1〜C5・B1。2026-11-26）

### DR-CED-20　切り替えの前に決めた読みと文言

- **C3a に渡す集合（DR-CED-14 を閉じる）**：出来事は全件を渡す。年表の秘密の印で出来事を除く段は、CSR/1 で無くなっている。hidden の Codex は、主な人物・場所の id を空にするだけで、出来事は残る。
- **場面**：現在地と読む順の入力からは、保管した node とその子孫を除く（画面の側・MCP・承認の日時で同じ）。
- **「同時進行」**：この段では「これまで」と同じ欄に入れる（K4a）。欄は足さない。
- **C5 の生死**：確度が「不明」の誕生・死亡の出来事は、生死と年齢の導出の材料にしない。死亡の出来事が「不明」で、誕生が分かる人物は、「存命」になる（設計 §3 の残る制限のとおり）。誕生が「不明」なら、死亡の出来事があっても、生死は「不明」で、年齢は出ない。取り込みで Native が日時を入れた出来事は確度が「不明」なので（G6。取り込みは今は閉じている）、その死亡は、作者が確度を直すまで生死に反映されない。
- **C1 の行の注記**：まとめの出来事の行に、確度が「おおよそ」なら「（日付はおおよそ）」、「不明」なら「（日付は不確実）」（en は ` (date approximate)`／` (date uncertain)`）を添える。今の時刻の行の注記と同じ語。
- **C1 の導入の文**：chatSystem の `chronicleSnapshotIntro` に「確度が不明（日付は不確実）の出来事の前後関係は、不確かです。」（en："The order of events whose date is uncertain is not reliable."）を足す。常に入れる。
- **変えないもの**：`get_character_timeline`・出来事の一覧の並びと、抽出の目録（K4 の列挙に無い）。

## 8. §5 の 6：移行（I1〜I7。2026-11-26〜）

### DR-CED-21　仮の日時を入れる関数（I2・I3・I4・I7。まだ呼ばない）

- **場所**：`grimodex-db` の `chronicle_date_migration::fill_missing_chronicle_dates`。呼び出し側の transaction の中で呼ぶ。版の引き上げ、完了の印、起動の配線、I5、I6 は次の段。
- **I2**：置く順と「最も後の日」は、core の `provisional_event_dates` を使う（写しを作らない）。場面の日付は、`chronicle_read` の保管済みでない場面。
- **I3**：開始の日があり、粒度が「なし」なら「日」（分があれば「時刻」）にする。確度は変えない。開始の日が無く、終わりだけが残る行は、終わりを消し、同じ書き込みで仮の日時を入れる。
- **設計に定めが無い点**：終わりの日があるのに、終わりの粒度が「なし」の行は、変えない。今も「終わりなし」の扱いなので、見え方は変わらない。
- **I4 の「想定しない値」**：知らない粒度、整数でも NULL でもない日と分、0〜1439 の外の分、絶対値が 2^53−1 を超える日（画面の側が正確に持てない）、読めない裏の並びと作った日時。その行は何も変えない。日が読める行は、「最も後の日」に数える（DR-CED-13）。
- **I7**：version・updated_at・ordinal を変えない。書くのは events と、書き込みの連番（write clock。どの表の更新でも増える）だけ。
- **返り値**：変えた出来事と列の名前（I5・I6 が使う）と、飛ばした行の id。
