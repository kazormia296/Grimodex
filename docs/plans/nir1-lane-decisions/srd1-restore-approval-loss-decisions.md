# 判断の記録：SRD/1 の RD6（スナップショットの復元の確認の文に、承認が外れる件数を出す）

確認済みの行は、台帳 `docs/plans/nir1-l6-l9-execution-plan.md` の `nir1-chronicle-scene-review-apply-delta/1#chronicle-applied-proposal-redecide`（RD1〜RD6、確認 139）。件数を出すことは確認 84 (b)、数え方と、0 件のとき・数えている間・失敗のとき・開いたときの値は、確認 133 (4) でユーザーが選んだ。下の項目は、設計が「実装で決める」「画面の PR で決める」とした起案者の読み（技術判断）。命令は足さない（既にある `project_snapshot_restore_context` の応答に欄を 1 つ足す）。

## DR-SRD-RD6-1　欄の形

`lossNotices` の 1 件にはせず、隣に別の欄 `approvalLossCount`（0 以上の整数）を足した。`lossNotices` は「復元で戻らない物」の一覧で、承認が外れることとは意味が違うため。欄が無い応答（古い Native）は、件数が分からないものとして扱い、文を出さない。

## DR-SRD-RD6-2　数え方

- 範囲に「本文・章立て」を含み、スナップショットが出来事の補助の行を持つときだけ数える。それ以外と、差が空のときは、取り込みの記録を走査せずに 0。
- 今の出来事の id の集合と、復元の正規の計画（`build_canonical_restore_plan`）が入れ直す出来事の id の集合の差を、復元の本体と同じ関数で取り、X の書き手と同じ SQL（`REMOVED_EVENT_PROPOSALS_SQL`）で、承認が外れる提案の数を数える。確認の文の件数と、復元で実際に外れる数が一致することを試験で固定した。
- 出来事の秘匿の印と開示シーンの値は読まない。

## DR-SRD-RD6-3　画面

- 文は、確認の説明の「現在の状態はスナップショットとして自動保存されます。」の次の行に出す：「年表に取り込んだ AI 抽出の出来事が無くなり、n 件の提案の承認が外れます。」（n は提案の数）。0 件のときは出さない。
- 範囲の選択を切り替えると、既にある下見（`useRestoreLossPreview`）が選んだ範囲で読み直すので、件数も一緒に読み直す。同じ範囲に戻したときは、最初に読んだ値を使う（開いたときの値。押すときに数え直さない）。
- 読んでいる間は「復元する」を押せない。件数は、戻らない物の下見と同じ読み取りで来るので、下見を読んでいる間も同じく押せない（今までは押せた）。
- 読み取りが失敗したら、「取り込んだ出来事の承認が外れるかを確かめられませんでした。」を出し、「復元する」は押せる。
- 日本語の文言はコードの既定の文に置き、`ja.json` には足さない（起動時に読まれるため。RA7 の DR-SRD-RA7-4 と同じ）。英語は `en.json` に足した。

## 計測

`measure_restore_approval_loss_context`（`#[ignore]` の試験、debug build、1 回）：本文 1.1 MiB と、取り込んだ出来事 60 件の作品で、確認を開いてから件数が出るまで（context 1 回、件数の分を含む）は、範囲に本文あり 10.3 ms、本文なしに切り替え 5.0 ms、本文ありに戻して 7.5 ms。件数の SQL だけは 0.5 ms。

設計が求めた 2,000 件では測れなかった。Native が年表の末尾に並び順のキーを足す処理が、62 件を超えると失敗する見込みで、2,000 件では実際に失敗したため（下の「見つかった別の不具合」）。2,000 件の取り込みの記録での件数の SQL の時間は未測定。命令を足す形（専用の読み取り）に改めるかの判断は、測れるようになってから。

## 見つかった別の不具合（この PR では直さない）

計測のために 2,000 件を一度に取り込もうとして、Native の並び順のキー（`narrative_extraction/chronicle_operations.rs` の `increment_integer` と `validate_order_key`）が、JS の fractional-indexing と食い違うことが分かった。

- `az` の次を `b0` にする（JS は `b00`）。`b0` は自分の検証で「短すぎる」と拒まれる。
- JS が作る正しいキー `b00` も、「整数部分の末尾が 0」として拒む。
- 結果：AI 抽出の取り込みで、年表の末尾への追記が 62 件を超えると失敗する見込み（キーの規則からの読み。試験では 60 件は通り、2,000 件は失敗した）。年表の末尾のキーが `b00` 以降の作品（画面で作った出来事が多い作品など）でも、取り込みが失敗する見込み（画面が作るキーの形は未確認）。
- 製品の既定では取り込みが閉じているので、今は表に出ない。SRA/1 で取り込みを開く前に直す必要がある。直し方の判断はユーザーに伺う。

## 残る制限

- 構造を持たない古い形式のスナップショット（範囲を選べない）は、下見を読まないので、件数も出ない。ただし、古い形式の復元は今の build では拒まれる（`PROJECT_SNAPSHOT_LEGACY_RESTORE_REQUIRES_NATIVE_AGGREGATE`）ので、件数が出ないまま承認が外れることは無い。
- ブラウザの mock は件数を返さない（古い Native と同じく、文は出ない）。
- 確認を開いた後に、別の窓で年表が変わると、件数と、復元で実際に外れる数がずれうる（開いたときの値。確認 133 (4)）。
