## 2. 判断

### DR-SRA-1　場面から提案を引く読み取り（R1〜R3）を、先に、単独の PR で出す

- §6 の 3（場面から提案を引く読み取り）は、ほかの段と file が重ならない。取り込みの単位（§6 の 1）より先に出す。
- この PR は、Native の読み取りと、IPC の命令 1 本と、画面の側の呼び出しの関数までを足す。画面（節）は足さない。製品の動きは変わらない。

### DR-SRA-2　引き方

- 提案に、場面の列は無い。場面との結び付きは、版の記録の中の、根拠の一覧（根拠ごとに、場面を指す鍵と、引用を持つ）にある。
- 既にある索引（依存の辺の、場面から版を引く索引）で、その場面を読んだ版を引き、次の 2 つで絞る。その版が、提案の現行の版であること。その版の根拠の一覧に、その場面を指す根拠が 1 つ以上あること（読んだだけの場面は、根拠ではない）。
- 新しい索引は、足さない。足す必要が出たときは、測った結果をユーザーに見せて、あらためて確認する（R3 と、台帳の「許さないもの」）。

### DR-SRA-3　返すもの（R2）

- 提案の id、現行の版の id、題、根拠（その場面の分。引用と、場面の id）、根拠がまたがるほかの場面の id、3 つの状態（確認の状態、参照元の状態、年表の状態）、重複の疑い、関連に使われない静的な理由。
- 場面の本文の全体は、返さない。返す引用は、版の記録が既に持つ、根拠の引用である（H4）。
- **「関連に使われるかの見込みとその理由」は、静的な理由だけを返す。** 関連する過去シーンの資格の判定は、「今書いている場面」を引数に取り、その場面との前後で変わる理由を含む。節には、「今書いている場面」が無い。そこで、版の記録だけで決まる理由（根拠が本文と合わない、場面の適用範囲が解決できない、秘密の印が付いている、承認されていない、など）だけを返す。「今書いている場面より前の場面であること」のような、場面によって変わる理由は、返さない。起案の S4 が出すと書いたのは、§1.4 の 2 つの場合で、どちらも静的な理由である。
- 静的な理由の判定は、資格の判定の本体と、同じ部品を使う。別の実装を作らない。資格の判定の規則は、変えない。

### DR-SRA-4　防御（H4）

- project の束縛は、Native が確かめる。場面が、その project に属さないときは、空を返す。
- ページ付きで、上限を持つ。上限は、Native の定数で持ち、画面が渡す値は、それ以下に切り詰める。
- 自分のデータを読む命令の一覧に、1 本足す（39 本から 40 本）。制限モードの外の経路からは、呼べない。
- main で、引数を、項目ごとに検証し直す。
- 上限の検証は、Main も Native と同じく、UTF-8 のバイト数（256）で行う。Native が最終の権威である。

### DR-SRA-5　実装の点検で決めたこと（DR-SRA-2〜4 の範囲内）

- **静的な理由の部品**：場面の Scope の行を読んで決める部分のうち、問い合わせ側の場面に依らないもの（有効な Scope 制御がちょうど 1 つであること、互換印が Unknown でないこと、材料の制約が Unresolved でないこと）は、`scene_scope::check_material_scope_static` に切り出した。資格の判定の本体（`check_material_constraints_with_memo`）も、同じ per-row の関数を先に呼ぶ。本体の結果（理由の種類と、行ごとの順序）は変えていない。静的な読みは、Scope の行を読めない・欠けているときの `MaterialAuthorityUnavailable` と、`statement()` が作れないときの `BindingInvalid` も返す。理由は重ねる作りで、失敗しても freshness まで評価する。
- **索引の要否（R3）**：`narrative_dependency_edges` は既にある索引で引く。`narrative_proposal_applications` には `proposal_id` の索引が無く、年表の状態の判定は、ページごとにこの表を 1 回走査する（`(proposal_id, revision_id)` の組で絞る。補償の検査は既にある索引を使う）。SQLite 3.54 の in-memory で、50 組のページを、10 万行の表に対して測ると約 13 ms（1,000 行で 0.3 ms 未満）だった。取り込みの記録は出来事 1 件につき 1 行で、10 万行は通常の作品の規模を大きく超える。そのため、索引は足さない。実行計画は試験で固定した。大きい DB で遅いと分かったときは、測定結果とともに、ユーザーに伺う（DR-SRA-2）。
- **年表の状態**：現行の版そのものが取り込まれているかで決める（取り込みの記録の `revision_id` を、現行の版と比べる）。取り込み済みの提案は、製品の経路では改版できないが、記録の束縛は、版の id に揃える（immutable child/revision）。
- **ページの鍵**：提案の id にした（版の id ではない）。ページの間で提案が改版されても、同じ提案が 2 ページ目に重ねて出ない。順序は作成順ではなく id 順である。ページの間に増えた提案は、次のページでは見えないことがあり、画面は、変化の通知を受けたら 1 ページ目から読み直す。ページの費用は、その場面の辺（歴史の版を含む）の数に比例し、上限は無い。ページごとに整列する（`USE TEMP B-TREE FOR ORDER BY`）。これらは試験で固定した。
- **返す欄**：DR-SRA-3 の列挙に無かった `proposalSetId`、`runId`、根拠の `evidenceRef` は返さない。根拠は、引用と場面の id である。
- **版の記録が読めないとき**：版の本文・封印の記録が JSON として読めない版は、ページ全体を失敗させず、その 1 件に `material-unavailable` の理由を付ける。

### DR-SRA-6　資格の判定の本体に触れた範囲と、変えていないこと

- 静的な理由を、資格の判定の本体と同じ部品で出すために、本体の関数（`scene_scope.rs` の `check_material_constraints_with_memo`）の先頭の検査を、行ごとの関数（`static_material_scope_reason`）に切り出した。関連する過去シーンの資格の判定の規則は、変えていない（SRA/1 の「IR の admission の規則は、PUB-G の後まで変えない」）。
- 切り出した関数は、Scope の権限の座標（source の鍵と、版の印）を、引数で受ける。本体は、今までどおり、問い合わせの文脈に封じた座標（`query.scope_authority_source_key` と `query.scope_authority_revision_token`）を渡す。静的な読みは、今の権限の座標を渡す。実装の途中の版は、本体の比較の値を、今の権限の座標に変えていた。起案者が差分を読んで、元の値に戻した。
- 材料の制約が Unresolved のときの検査は、切り出した関数が先に行う。本体は、その後の、問い合わせの場面との照合でも、Unresolved を同じ理由（`ScopeUnsupported`）で拒む。行ごとの結果は、変わらない。
- 確かめ方：資格の判定と抽出に関わる Rust の試験を、広く回した（`cargo test -p grimodex-db --lib narrative_extraction::` の 1,525 件、`--test narrative_nir1_retrieval_admission` の 78 件、`--test narrative_extraction` の 64 件、`--test narrative_scene_proposals` の 21 件）。どれも通った。
- 評価の準備が固定している file（`evals/nir1-graph/observation-prep.v1.json` の pins）と、この PR が変える file は、交わらない。
- 3 つの状態の定義は、起案に細かい定義が無かったので、次のとおりに決めた。確認の状態は、提案の状態（未確認、承認、却下、保留、後回し）。参照元の状態は、根拠の場面の鮮度の読み（新しい、古い、確かめられない）。年表の状態は、現行の版の、取り消されていない取り込みの記録があるかどうか（入っている、入っていない）。
