## threat model（GDX-PRECHECK-001 の security-sensitive。TASK §12 を写した）

### セキュリティの観点

- 信頼: Electron main の sender の確認、Native の grant の slot と profile の状態の store、current workspace authority。renderer の隔離（sandbox、contextIsolation、CSP、NC-1）。
- 信頼しない: renderer（乗っ取られた場合を含む）、env、設定ファイル、起動引数、MCP、ほかの窓、古い grant と handle。
- 攻撃と防御:
  1. 確認を経ない activation（renderer の IPC、env、設定、起動引数、MCP、自動）→ 要求は Main が処理し、Native の消費なしに段 4 に進めない（型と実行時の両方）。grant を伴わない N-API を消す。Negative (4)(6)。
  2. dialog の置換・誘導 → 表示文は Native の定数、digest を Native が計算して binding に入れる。既定は取消、checkbox が要る。Positive (3)。（ST1 の具体化: Main が `showMessageBox` に渡した文字列の digest を issue に渡し、Native が binding の digest と照合する。P2-3）
  3. grant の再利用、別 sender／window、同時 2 件 → 単一 slot、Consumed、Mismatch、Busy。予約中はほかの preview も拒否。Negative (4)。
  4. id の漏れ → 応答と event に previewId、grantId、epoch を出さない。Negative (5)。
  5. 一方向の破り（restricted:false の書込み、ファイルの削除）→ writer は書かない（既存の試験に新しい操作を足す）。J-1 はファイルを書き換えない。画面からの到達は SF-1（DA-1）。F-1 は Out-of-scope のまま開示。Negative (10)。
  6. 段 1〜2 と段 2 後の競合で平文が返る → 段 1 の直後に同期で閉鎖、完了時の拒否を旧 AI に広げる、非 stream も取り消す。Negative (3)(15)。
  7. activation の途中の license の key の持ち出し（DA-1 P3 (b)）→ 予約の時点から restricted の client（key の文法の検査、proxy と redirect なし）。
  8. PUB-G の前の入口の露出 → renderer の定数、Native の gate、Main の not-activated。seam は非 packaged の exact env だけ。Negative (12)。
  9. 状態や event からの推測 → 閉じた状態コードだけ。
  10. Chromium 自身の通信 → Main は spellchecker を設定しない（静的検査）。restricted の試走で「続く通信」（K3/3 の変える点 9 の一覧）の外が見つかれば [precheck]。
- 残余（開示に書く。新しい経路ではない）: 状態ファイルの削除と別の profile（F-1）、K3/2 開示 7 の残余、K3/3 の「未確認と未検証」、段 1 の前に始まった proxy を使う license の呼出し（平文を運ばない）。

### lifecycle の観点

- 待ち続け: 段 3、段 5、起動時の barrier に ≤30 s の上限。dialog は 60 s。終了の証拠は子 process の exit と lease の drop で、kill の要求や rejected promise だけを証拠にしない。
- crash と途中の失敗: 段 4 の前は unrestricted のまま、後は restricted・停止未確認で次の起動で barrier（状態ファイルの受理条件の表）。予約と grant は保存しないので再起動で消える。
- 二重の activation、再入: 単一 slot と予約、Main の in-flight の印、`activationPromise`。
- workspace の遷移との交差: D-3 の edge での失効、D-4 の途中の拒否、bind での permit の失効。同期点の試験で示す（固定の sleep に頼らない。post-B §12）。（integrator 追記で D-4 は (b)。途中の拒否は置かない）
- 窓の close と sender の消失: 段 1 の前は revoke。段 1 の後は activation を続ける（消費した grant は戻さない）。結果は残る窓に event で伝える。
- app の終了: 段の途中の終了は新しい段に進まず、状態ファイルが次の起動を決める。終了を上限の外で待たせない。
- 起動の順序: NC-1 → gate（initBackend の直後）→ CI seam、workspace の event、scheduler、renderer。DA-2 は index.ts の配線でこの順序を保つ。

### 試験で固定したこと

- **L-1**（mock の backend。`profileActivation.test.ts`）：段 2 の listener の例外、段 3 の `participant-timeout`、`participant-failed` のそれぞれで、取消の N-API が 1 回だけ呼ばれ、呼出しの順が `consume` → `activating` の通知 → 取消 → `unavailable` の通知であること。段 4／5 の失敗と段 6 の検査の失敗では呼ばれないこと。N-API が無い・`false`・例外のどれでも unavailable になり、通知が届き、invoke が拒否されること。
