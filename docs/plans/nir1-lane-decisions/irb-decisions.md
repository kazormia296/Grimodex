# IRB の判断の記録（関連場面の IR の index build が native の接続を長く握る件）

出所は PD 評価の本測定 第 5 版（`fusion-eval-data/pd-2026-11`、m-ja-2、117 Scene、2026-11-05）の抽出の失敗の調査
（読むだけ。DB の写しとコードで確かめた）。基点は `origin/master` の `d45fa7e8`、branch は `claude/irb-audit-scope-index`。

根拠は、ユーザーの依頼（2026-11-05、引き継いだ NIR-1 の作業と「CI 待ちの間も実装を進めましょう」）の範囲の不具合の修正であること。IRB が AGENTS.md の U3 の対象レーン（C-resource、C-body、C-product、D-final 追補、D-transport、D-dispatch、H-store／H-current、DI-1、E）に含まれるかは確かめられていないので、U3 は根拠にしない。委任の外の項目（閾値の緩和、新しい送信先、保存範囲の拡大、新しい契約）には当たらない。閾値・送信先・保存・契約は変えない。

## 3. 変えないもの・まだ決めていないもの

- 変えない：snapshot の source の束縛（3 回の `validateSceneScope`、`sourceRowsMatch`、`settleExternalSourceMutations`、quiescence lease）。これは安全のための fence。IR の publish の再検証と CAS。receipt の audit の検証の意味。read だけに caller timeout を付ける方針（mutation lane に timeout を付けない）。
- DR-IRB-1 の後の測定（REPS=3、dev 枝の計測の道具）：prepare は m-ja-2 で 10.2 s、m-en-1 で 12.3 s。内訳の最大は `root_material`（Run の receipt の hydrate と artifact の再生）で、receipt の検証の呼出しは receipt の数の 4.8 倍／9.2 倍だった（同じ Run の Root ごとに Run 全体を検証し直していたため）。DR-IRB-4 はこの重複を無くした。測定（同じ道具、REPS=2 の 2 回目、release、2026-11-06。前の値は別の測定で、m-ja-2 の before 10.4 s はこの道具での再計測、m-en-1 の before 12.3 s は前の REPS=3 の値）：m-ja-2 の prepare は 10.4 s → 7.4 s（hydrate 491 → 102 回＝Run の数、receipt の検証 6,934 → 1,417 回、`root_material` 5.2 s → 2.1 s）、m-en-1 は 12.3 s → 7.0 s（hydrate 509 → 59 回、検証 14,291 → 1,546 回＝receipt の数、`root_material` → 3.1 s）。prepare はなお候補の数に線形に伸びるので、前景を塞ぐ問題の根本の解にはならない（残りは下の内訳）。第二段（Run ごとに捨てる）の後の prepare は m-ja-2 で 7.4〜7.5 s、m-en-1 で 6.9〜7.0 s で、第一段（7.42〜7.43 s、6.91 s）より +65〜94 ms（約 1%、各 1 回の測定）。数える SQL 1 本の分と見られるが、分離して測ってはいない。
- 残りの内訳（m-ja-2、DR-IRB-4 の後）：`finalize.freshness` 3.1 s（候補ごとの Freshness の読み）、`root_material` の残り 2.1 s（`load_v2_context_artifact` 0.4 s、Root ごとの request の proof と material の再計算）、`root_material` の外の membership 1.7 s（revision の lineage の読み、envelope の検証）。次に効くのは Freshness の Run 単位の共有、lineage の読みの共有、または prepare を前景に譲らせる・dirty を debounce する・専用の読取接続（DR-IRB-3）。いずれも別の判断として設計する。
- DR-IRB-4 の memory（第二段で対応済み）：第一段の memo は prepare の間じゅう、全 Run の parse 済み artifact の Value を持ち、snapshot の payload は `ArtifactScan` と accepted の 2 部だった。peak RSS（試験の process 全体。`irb_prepare_timing` は prepare の後に publish 側の読みも走らせるので prepare だけの値ではない。`maxrss` を python の `resource` で取得、REPS=2、release、同じ DB の写し）：m-ja-2 は DR-IRB-1 だけ 261 MiB → 第一段 410 MiB（+148）→ 第二段 313 MiB（+52）、m-en-1 は 235 → 332（+97）→ 281 MiB（+46）。Run 1 つあたりの増分は第一段で約 1.4 MiB（m-ja-2、+148 MiB／102 Run）、第二段で約 0.5 MiB（+52 MiB／102 Run）。これを Run の数に比例させて 3,000 Run まで延ばすと第一段は約 4 GiB、第二段は約 1.5 GiB になる（直線の延長による推測で、未測定）。第二段で `ArtifactScan` を件数と検証の 4 項目に縮め、Run の残りの revision が 0 になったら Run の memo を捨てるようにした。なお +46〜52 MiB 残るのは、Run が最後の revision まで生きる分（roster の順は proposal id で、同じ Run の revision が散るので、多くの Run が走査のほぼ全体にわたって生きる）と accepted artifact の 1 部で、これ以上は roster を Run の順に並べ替える（候補の順と publish の入力の順に影響するので別の判断）設計になる。残りの内訳は未測定（推測）。
- 前景の read の lock 待ちに期限を付ける案は、関連場面の IR の窓（D=40 ms）との関係があるので、案を並べてユーザーに聞く。
- `projectSnapshotAdapter.ts` の catch が読込みの例外を `SNAPSHOT_SOURCE_CHANGED` に付け替える件は DR-IRB-2 で直した：読込み・転送の失敗と確かに分かるもの（IPC timeout、失敗した SELECT）は `SNAPSHOT_SOURCE_READ_FAILED`、message に原因の種類を足す。fail-closed は保つ。pending mutation の reject や外部 mount の衝突など、変化かもしれない例外は保守的に `SNAPSHOT_SOURCE_CHANGED` のまま残るので、「`SNAPSHOT_SOURCE_CHANGED` は実際の比較の不一致だけ」までは行かない（残りは例外の種類を型で分けられてから）。利用者（`extractionCoordinator.ts`、`codexStructureExtractionApi.ts`）は code を連ねて `Snapshot build failed: …` にするだけで、message は表示しないので、画面で見えるのは code の違いだけ。message の原因は診断を読む道具向け。
- PD 評価の harness（失敗の時刻を discard の前に取る、error の cause を残す）は、次の事前登録の版で直す。第 5 版の道具は凍結のまま。
- この修正を含む build で PD 評価を取り直すと、IR build の時間が変わるので、事前登録の新しい版が要る。

## 4. 検証

- DR-IRB-4 の試験 `nir1_chronicle_index::run_proof_memo_tests`：(a) 同じ fixture の全 roster revision で、memo ありと memo なしの preflight（Ok の中身、unavailable の理由、error）が一致すること。receipt の hydrate、artifact の digest、artifact の inline 欠落、Snapshot authority（snapshot task の output の改変）、accepted artifact（window plan の行の削除）の 5 種類の改変でも一致すること。5 種類は、それぞれ意図した分岐（`receipt-hydration-invalid`、`artifact-digest-mismatch`、`artifact-inline-binding-missing`、`snapshot-authority-invalid`、`recipe-input-binding-invalid`）に届くことを `read_revision_material_membership`（memo なし）と `read_revision_material_membership_with_memo` の Unavailable の status と issue の code で確かめ、preflight が unavailable の理由を 1 つに潰す前の段で比べる、(b) 1 つの Run に 2 つ以上の Root がある fixture で、prepare の hydrate が 1 回、receipt ごとの lifecycle／audit の検証が receipt の数だけになり、memo なしだと Root の数の倍になること、(c) 連続する 2 回の prepare で Run の検証が毎回やり直され（hydrate が毎回 1 回）、間に入った永続の変更（model binding の削除）が 2 回目に見えること。そのとき hydrate の失敗は cache されず、Root の数（2）だけ繰り返される。
- 試験 `stage_provenance::audit_count_plan_tests`：migrate 済みの DB で、2 つの SQL の実行計画が `SCAN ai_audit_events` を含まず、`idx_ai_audit_scope_` の index を `scope_id=?` で引くこと。
- receipt の再生を通る既存の試験（material roster の golden、IR の build、hydration）で、数える行が変わらないこと。
- 写しの DB（`sqlite3` の読み取りだけ）：実行計画が `SEARCH ai_audit_events USING INDEX idx_ai_audit_scope_operation (scope_id=? AND operation_id=?)` になり、同じ件数（4）を返すこと。
- prepare の段ごとの時間の実測（修正の前後）は、PD 評価の run の終了後に写しの DB で行う。
