## threat model（確認済みの actor・防御・受信先・受入れの範囲内。新しいものを足さない）

- 信頼する: Main と Native、Chromium の network stack（版の範囲で。Electron 43.5.0／Chromium 150）、利用者。信頼しない: 乗っ取られた renderer（WebRTC の接続・名前解決・dns-prefetch で、攻撃者が選んだ宛先〔host 名、IP literal、loopback の任意 port、LAN〕へ接続・解決しようとする）。
- 範囲に入れない: 同じ OS ユーザーの別プロセス（listener の port を後から取りうる残余は FC-1 で開示済み）、QUIC・mDNS・TURN の relay candidate など行列の外（draft の「未確認と未検証」）、Windows／macOS（G-pub の範囲）。
- 必須の防御: 3 機構が独立に要る（proxy、`<-loopback>`、policy、rules。外した構成を対照で検出）、許可先 0（AL-0）と RS-1 の閉じた集合、LS-1 の上界と bytes の破棄、default session の最初の接触、fail-closed の起動失敗と固定コード、製品に無効化の入口を置かない、閉じた集合の静的な固定。
- LS-1 の listener 自体の脅威: renderer（Chromium 経由）が接続の洪水・RST・half-open・巨大な書込みで Main を落とす、または資源を使い切る。防御は、socket の `error` の握りつぶし、同時 256 以下、保持 5 秒以下、超過は受けた直後に切断、受けた bytes は `resume()` で読み捨てて検査・保存・log・書込みに渡さない、返事をしない。
- 受入れ: TASK の 5 の表（K3/3 の Positive (9)、Negative (23)(29)〜(33)）。

- DR-NC1-18（DR-NC1-8 の変更。確定）: 実 Electron 43.5.0（Linux）で、`web-contents-created` の handler の同期の中で `webContents.stop()` や `app.quit()` を呼ぶと SIGSEGV する（`close()` の後でも同じ。`did-start-loading` の中の `stop()` も `loadURL` で落ちる）。`close({ waitForBeforeUnload: false })` だけなら落ちず、次の tick まで遅らせた `stop()`、`close()`、`app.quit()` は `before-quit` と `will-quit` に進んで正常に終了し、破棄された webContents の `loadURL` は `ERR_FAILED` になる。そのため `NC-SESSION`／`NC-POLICY`／`NC-LISTENER-LOST` の実行中の経路を次に改めた。(1) handler の中では判定（`session` の同一性、policy の適用と読み戻し）と「失敗の印」（`enteredTermination`）だけを同期に行う。(2) 破棄（遅らせた `stop()` と `close({ waitForBeforeUnload: false })` の best effort）と、固定コードの出力・`app.quit()` は、依存の `defer`（既定は `setImmediate`）で handler の外の tick へ回す。破棄が終了より先。(3) `did-start-loading` の listener と同期の `stop()` は外した。(4) 起動前の失敗は promise の継続から呼ばれるので同期のまま。信頼境界・閾値・時間の上限は変えない（新しい timer も `app.exit` も足さない。`setImmediate` は 1 tick の遅れで、上限ではない）。`defer` は試験が差し込む依存の面で、製品の呼出しは引数なしのまま。代替案: `waitForBeforeUnload:false` の `close()` だけを同期に呼び `app.quit()` を遅らせる（`stop()` の除外は可能だが、同期の `close()` の SIGSEGV の可能性を持ち込まないため全部遅らせた）。実機の確認: 製品の `createRendererContainment()` を esbuild で bundle した main から partition `persist:x` の BrowserWindow を作り、`start()` が true、stderr に `[grimodex-electron] NC-SESSION`、続けて `before-quit`、`will-quit` が出てプロセスが終了し（SIGSEGV なし）、`loadURL` が `ERR_FAILED` になることを確かめた（この修正の head で 1 回。記録ファイルは採らない）。試験: `rendererContainmentStartup.test.ts` に handler の同期の中で `stop`／`close`／出力／`quit` が呼ばれない対照（遅らせると呼ばれる）を足した。`rendererContainment.startupOrder.test.ts` は `index.ts` の通しで、破棄と `app.quit` が handler の返りより後・破棄が `app.quit` より先であることを固定する（`defer` を同期に戻す変更で赤になることを確認した）。**S3 の引き継ぎ（G-open の条件の一部。S4 の gate で記録する）**: probe 用 main に、default session でない BrowserWindow を作って `NC-SESSION` を起こす実機の試験を足す。SIGSEGV せず `before-quit` と `will-quit` を経て終了し、窓が読み込みを始めないことを観測する。`NC-POLICY` は実機で起こしにくいので、実機の観測は `NC-SESSION` で代表させ、`NC-POLICY` は同じ経路（`discardLater` と `failRuntime`）の単体試験で固定する。状態: 確定（実機の記録は S3）。
- DR-NC1-19（P3。確定）: `NC-LISTENER-LOST` は `server.close()` が呼ばれたときだけ起こる（Node の `net.Server` は `close()` 以外では `close` を出さない。製品のコードは server を明示的に閉じない）。listener が accept 不能になる障害（fd の異常など）は検知しない（draft の LS-1 は「listener が実際に閉じたときだけ FC-1 の対象」と定めており、draft どおり。blackhole なので到達 0 で fail-closed は保たれる）。試験は注入した `onClosed` で成立している。accept 不能の検知は別の draft の議題として扱う。また `before-quit` を一度見ると `quitting` は戻さない。終了が取り消された（close-veto などで quit が続かなかった）後の `NC-LISTENER-LOST` は出ない。この経路は扱わない（取消し後に listener が閉じる経路自体が現状ほぼ無く、出さない側に倒れても閉じ込めは保たれる）。
