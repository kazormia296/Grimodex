## PR の分け方と止める点

- 1 つの PR にする（Native の command、review の読み出しの応答、画面、試験、実機の検査）。大きくなる場合は、Native と画面を分けてよい。分ける場合、Native の PR だけでは製品の挙動は変わらない形にする（画面が新しい command を呼ばない）。
- **§6 の測定の結果をユーザーが見て判断するまで、画面のボタンを置き換える変更は merge しない。** 測定は、実装の枝の build で、評価のデータの写しに対して行う。

## 判断

| ID | 判断 | 理由 |
| -- | ---- | ---- |
| DR-BAO-1 | 新しい command の入力は、project、抽出の id、対象の一覧（提案の id と現行の版の id）だけにする。未知の項目は拒む。中身、秘密の印の値、actor、要求の識別は受け取らない | B1、B7。画面が中身を作れないこと自体が防御である |
| DR-BAO-2 | 対象の判定は、Native の 1 つの関数に置く。読み出しの応答と、書く直前の判定が、同じ関数を使う。返すのは、対象かどうかと、対象でない理由の一覧である | B2、B3、B4。2 か所で条件がずれないようにする |
| DR-BAO-3 | 「最初の版そのもの」は、提案の現行の版が、系譜の根（親を持たない、AI の解釈の版）であることで判定する。中身の比較は使わない | B2 (b) |
| DR-BAO-4 | 見せる理由の 4 つの値は、版に封印された Envelope の `assertion.payload` から読む。提案の中身の値は使わない | B2 (e)。Native は、中身と Envelope の値の一致を確かめていない |
| DR-BAO-5 | 根拠の条件は、Envelope の根拠の一覧の全件が、封印済みの根拠の記録（`evidence.resolved@1`）の項目と 1 対 1 に対応することで判定する。今の画面側の条件（確かめ方が完全一致、欠けや分断が無い）と違う提案を選ぶ場合は、違いを記録して報告する | B2 (d)、設計の §8 |
| DR-BAO-6 | 子の版と承認は、今ある 2 つの処理の本体を、同じ transaction の中で続けて呼ぶ。本体を外から呼べる形にするだけで、検査は省かない。子の版の中身は、Native が親の中身から、秘密の印だけを false にして作る。`surfaceId` は今の review と同じ値にする（系譜の検証がこの値を見る） | B5。新しい検査の抜けを作らない |
| DR-BAO-7 | 「作業中の操作」として登録し（今の承認の command と同じ包み方）、提案と提案の間で、終了と workspace の切り替えの要求を確かめる。要求があれば、そこで止めて、それまでの結果を返す | B7 |
| DR-BAO-8 | 画面は、今の 7 つの条件の計算を、Native の判定の表示に置き換える。抽出の保存の直後と、review の操作の後は、読み出しをやり直して判定を受け取る。遅ければ、操作の応答に判定を載せる形に変える（挙動は変えない） | B3 |
| DR-BAO-9 | 一覧の並びは、表示のときだけ変える（見せる理由の付く提案を上に）。画面の store の順は変えない | 実機の検査と試験が、store の順に依る箇所がある |
| DR-BAO-10 | 計画の読み込みが提案ごとに走って遅い場合は、この command の中で 1 回にまとめる。判定の結果は変えない | 設計の §3、§6 |
| DR-BAO-11 | 範囲外：1 件ずつの承認と版の作成の command の変更、IR の資格の判定、見せる理由の変更、chat の IR、作者が編集した提案や承認済みの提案を対象に入れること、組を選ぶ操作 | 候補を小さく保つ |

## 信頼境界と影響

| 面 | 影響 |
| -- | ---- |
| 画面と Native の間の契約 | command が 1 つ増える。呼べるのは画面からだけで、MCP からは呼べない |
| 書かれるもの | Native が対象と判定した提案の、秘密の印を外した子の版と、その承認。今ある 2 つの command で書けるものと同じ種類である |
| 承認の記録 | 今と同じ actor、同じ権限。新しい種類の記録は無い |
| 関連場面（IR） | 判定は変わらない。資格を持つ提案（承認済みで、秘密の印が外れた版）が増える |
| 年表 | 変わらない。取り込むと、出来事は secret で作られる |
| 評価の harness | 変わらない（このボタンを使っていない） |

外部への送信、subprocess、保存先は変えない。非同期の lifecycle は、今の承認の command と同じ調停に入る。

**測定（評価のデータの写しに対して。製品の DB と凍結した評価の材料は変えていない）。**

- 対象と判定された提案は、全体の 75.7% だった。1,086 件を承認し、失敗は 0 件だった。
- 承認した 1,086 件のうち、関連場面の資格の判定を通ったのは 1,068 件である。残りは、判定の条件（材料の再生など）で止まった。対象でないと判定された提案が承認された例は無い。
- 1 回の抽出の最大は 0.5 秒だった（評価のデータは、場面ごとの抽出で、1 回の提案が少ない）。提案が 300 件の抽出では、約 80〜95 秒と推定する。推定の根拠は、承認 1 件ごとに計画の全件を読む手間が、件数に比例して増えることである。
- 測定に使った道具は、DB の写しを未 review に戻す機能を持つので、repo に入れていない。

### 遅さの直し（DR-BAO-10、別の PR）

- 1 回にまとめたのは、封印済みの計画の名簿（計画の成果物と、Task の束縛、manifest、受領書の検証）と、Snapshot と既存の出来事の一覧の証明である。承認 1 件ごとに全件を読んで検証していた。いまは、command の最初に 1 回だけ検証し、提案ごとの承認と子の版の作成には、その結果を渡す。承認の本体は、渡された結果を使う場合も、渡されない場合も同じ関数である。1 件ずつの承認の経路は何も渡さず、今まで通り全検証をする。
- 提案ごとに残した検査は、次の通りである。取り込みの消費と、適用の記録の見張り。Run の spec。現在の版と提案の状態。子の版の題（封印済みの題との比較）。生きている scope の権威（開示の場面が 1 つの mapping に解決できること）。いずれも、その提案の書く transaction の中で読む。
- 重い検証は、command の最初の 1 回で、書く transaction の外である。設計の B5「検査を省かない」に対しては、「重い検証は 1 回、同じ行であることは毎回」とする。提案ごとの書く transaction の中で、検証した行がいまも検証した時点と同じであることを、主キーだけの 1 本の SELECT で確かめる。比べるのは、Run の project と Snapshot・既存の出来事の digest、計画の owner の Task と Attempt、Snapshot の owner の Task と Attempt の状態・version・所有関係、2 つの成果物の所有関係と payload の digest である。違えば、その提案から使い回しをやめ、書き手が全検証をする（1 件ずつの経路と同じ結果になる）。以後の提案も全検証にする。
- 不変を守っているのは、次である。版と Envelope は、DB の trigger が書き換えを拒む。Task、成果物、Run、受領書、提案の組は、書き手の条件が守る（完了済みの行は書き戻さない。更新は実行中・待機中の行だけを対象にする）。使い回しの前提は、この不変である。
- DB のファイルを直接書き換える相手は、今ある脅威モデルの範囲外である。この相手は、1 件ずつの経路も止められない（digest に鍵が無く、書き換えた内容に合わせて digest を計算し直せる）。上の照合は、同じ DB に対する別の書き手の更新や取り違えを、提案の間でも見つけるためのもので、改ざんへの防御としては数えない。
- 測定（評価のデータの写し。承認した件数 676 件と 410 件、失敗 0 件。直す前の build、直した後の build、照合を足した build を、同じ日・同じ写し・同じ道具で続けて測った）。直す前は 1 件あたり 約 38 ms と 約 29 ms で、Run の提案の件数 n に比例して増えていた（約 28 ms + 1.1 ms × n と約 25 ms + 0.8 ms × n。g の 1 件あたりは、Run が 2 件で 30 ms、16 件で 46 ms）。直した後は 約 20 ms と 約 19 ms で、件数に依らない。command の合計は、直す前の 25.4 秒と 12.0 秒が、13.9 秒と 7.9 秒になった。承認した提案の id の集合と、DB の全行（id と時刻を隠したもの）は、直す前と一致した。照合を足した分は、同じ条件の比較で 1 件あたり 約 0.3〜0.6 ms である。提案が 300 件の抽出は、1 件あたり約 20 ms として約 6 秒と見積もる。この件数の実測は無く、見積もりである。
