# EWC の判断の記録（抽出の窓と根拠の目録の食い違いによる coverage hole）

EWC は evidence window coverage。出所は PD 評価の本測定 第 5 版（m-en-1、71 Scene、2026-11-05）の抽出の失敗の調査
（DB の写しとコードで確かめた。DB の本文・題名はここに書かない）。基点は `master` の `253de53d`、branch は `claude/fix-evidence-window-coverage`。

根拠は、ユーザーの依頼の範囲の不具合の修正であること（U3 の委任ではない）。委任の外の項目（閾値の緩和、新しい送信先、保存範囲の拡大、新しい契約）には当たらない。

## 1. 事実

| 事実           | 確認の結果                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 失敗の形       | `assertEvidenceSpanCatalogCoverage`（`src/features/narrative-extraction/evidence/spanCatalog.ts`）は、目録の各 entry の `canonicalRange` が、どれかの window の `sourceView.documentRange`（owned と context の外接範囲）に完全に入ることを求める。入らない entry が 1 つでもあると、observe が LLM の前に `EVIDENCE_SPAN_CATALOG_COVERAGE_HOLE` で落ちる（run 作成時の同じ assertion でも落ちる）                                    |
| 食い違いの原因 | window planner（`windowPlanner.ts`。owned 上限 6000、cut は block 境界 → 「。！？\n」→ grapheme の順、context は左右 240 字）と、目録の分割（文の終端は 。！？!?\n、括弧の中は分割しない、1 つの文が 4096 字を超えると 4096 字の格子で分割）が別の規則で切る。6000 字を超える改行の無い段落（英語の '.' だけの文、括弧の長い引用を含む日本語）では、cut が entry の途中に来て、cut をまたぐ entry が左右の context 240 字では届かない |
| 実測           | m-en-1 の 71 Scene のうち 2 件（位置 39・59）が落ちた。m-ja-2 は 0 件。実際の原稿でも起こりうる形                                                                                                                                                                                                                                                                                                                                     |
| 再現           | 試験 `windowPlanner.evidence.test.ts` が、13,000 字の改行無しの英語の段落と、5,400 字の後に括弧の長い引用が cut をまたぐ日本語の段落で、従来の plan が同じ assertion で落ちることを固定する                                                                                                                                                                                                                                           |
| plan の消費者  | `extractionCoordinator.ts` の run 作成（source view を封印するための plan）、`source.window-plan@1` の task（snapshot から計画し直す）、評価の `observationAdapter.ts`。codex の構造抽出（`codexStructureExtractionApi.ts`）は目録を使わず、plan は変わらない                                                                                                                                                                         |
| catalog の入手 | run 作成では plan の前に catalog を作っている。window-plan の task は、封印された snapshot の companion（`evidence.catalog`）から同じ catalog を読める。評価の adapter は catalog を plan の後に作っていたので、順序を入れ替える（catalog は snapshot だけから決まる）                                                                                                                                                                |

## 3. 変えないもの・まだ決めていないもの

- 変えないもの：`spanCatalog.ts`（分割の規則、digest、sourceRef の採番、4096 字の上限、alias、coverage assertion、`visibleEntries`）。英語の '.' を目録の文の終端に入れることは今回しない。`windowId`・`sourceRef`・owned の範囲。
- context に入る本文が増えるので、cut をまたぐ entry を持つ Scene だけ、その window への入力が増える。この Scene の抽出は従来は始まらなかった。
- 他の cut と entry の食い違い（owned が entry の途中で切れること自体）は残る。その entry は window の 1 つが全体を見られる（引用できる）ことだけを保証し、observation が重複して引用される可能性は従来の context と同じ扱い。
- 隣の window と重なって見える範囲は、広げた側で従来の 240 字以下から 4,096 字以下に増える。そのため window をまたぐ重複の observation が増えうる。これは今の 240 字の重なりと同じ種類の挙動で、後段の merge と cluster が扱う（新しい処理は足さない）。
- 英語の '.' を終端にする、目録の分割を block 境界に合わせる、といった目録側の変更は、digest と事前登録に影響するので別の判断。
- 既知の制約（EWC の範囲外、修正前から同じ）：`contextForOwned` の既定半径（240 字）の端は、owned の cut（`snapToUtf16Boundary` を通る）と違って UTF-16 の境界に寄せない。window 境界から ±240 字の位置にサロゲートペア（𠮷、絵文字）があると、`buildNarrativeSourceView` が `Invalid narrative Source View range or identity` を投げる。これは coverage hole ではなく別の形の失敗で、catalog の有無に関係なく起きる。**今回は直さない**：両端を寄せると、hole の無い既存の入力でも context の範囲（source view の digest）が変わり、「hole の無い入力の plan は byte 同一」と事前登録に影響するため。広げる側の端は entry の境界（grapheme／文字の境界）に揃うので、この修正が新しい失敗を増やさないことを試験で固定した（広げた plan で失敗する window は、従来の plan でも失敗する window に限る。この入力では従来 1 window が失敗し、広げた plan は 0）。直すなら事前登録への影響を決めたうえで別レーンで扱う。
- この修正を含む build で PD 評価を取り直すと、hole のあった Scene の plan と prompt が変わるので、事前登録の新しい版が要る（hole の無い Scene は変わらない）。

## 4. 検証

- `src/features/chronicle/extraction/windowPlanner.evidence.test.ts`：13,000 字の改行無しの英語の段落と、括弧の引用が cut をまたぐ日本語の段落で、従来の plan が coverage assertion で落ち、catalog つきの plan は通ること。owned・windowId・sourceRef が変わらないこと。広げるのは hole の元になった window だけで、延長は 4,096 字以内、context が owned と重ならないこと。全 entry が既に入っている入力（複数 document、長い日本語、複数段落）で plan が従来と `toEqual`／JSON 同一であること。catalog が無いときに従来と同一であること。小さい予算で entry が複数の window にまたがる場合。決定的であること。context 半径の端がサロゲートペアの途中に当たる入力で、広げた plan が従来の plan にない source view の失敗を増やさないこと（上の既知の制約）。
- `src/application/narrative-extraction/extractionCoordinator.citation.test.ts`：長い改行無しの段落の citation-ID run が、LLM の前の coverage assertion で落ちずに完走すること。run 作成と `source.window-plan@1` の task の両方の plan が catalog を受けること（修正を外すと `EvidenceSpanCatalogCoverageError` で落ちることを確認）。既存の「coverage hole は observer の前に拒否する」試験はそのまま通る。
