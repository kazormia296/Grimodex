## 要点

- 確認済みの `history-reauthorization`（proposal/3）は記録と毎 turn の再認可を求めるが、各項目をどの既存の保存先・writer・reader に対応付けるかを決めていない。このため H-store と H-current は先へ進めない（l6-l9:24-25）。この draft はその対応付けを差分として出す。
- 保存先（推奨）：turn に一つの文脈 `HistoryTurnContextV1` を、DT-3 が予約した `binding_json` の slot に置く。値は digest、整数、閉じた enum だけにして、大きさを ID の長さや入力の数に依存させない（モデルで最大 1,893 B。HS-1 が実際の型で測る）。入力ごとの証跡（input-use と typed N/A）は、既存の入力行と資格行の JSON に、版を上げた閉じた形で置く。資格行は 1 attempt で最大 1,544 件、約 200 KB になりうる（S6）ので、binding_json（上限 64 KiB）には置けない。文脈を足すと上限を超えるときは、文脈なしで attempt を作り（その attempt は history に使わない）、送信は止めない。attempt の行の既存の session_id 列には DB で検証した chat session ID を入れ（DT-3 で実装済み）、候補はこの列と既存の index で列挙する。schema は変えない。対案の子 table は schema の変更と保存範囲の拡大にあたり、別の draftRef の確認が要る。
- 資格の完備規則：入力ごとに、7 種の kind のそれぞれについて、1 件以上の ref か、表で決めた typed N/A のどちらか一方を持つ。(kind, target) の重複は不可。記録した ref はすべて毎 turn 現行の reader で再資格化する。今の D-final の出力はどの入力もこの規則を満たさず、typed N/A を表す型も無い（S6-1）。DF+-a で直す。
- 軸：storyTime は `StoryPositionWitness`、viewpoint は `ExplicitScenePov` から取り、無ければ unavailable。未解決どうしの一致は同一とみなさない（GDX-NARR-SEMANTIC-CONTRACT-001、iron-laws.md:198-199）。witness には対象 Scene 自身の値（物語時間の key、POV の character）だけを入れ、project の scope authority の版と story の順位は入れない。POV や物語時間の設定を含め、project の tree への書込みはどれもこの版を変える（S6-5）ので、入れると、どこかを編集するたびに過去の Human 入力まで外れる。その書込みが材料に与える影響は、Revision 入力ごとの再資格化（A3）で外す。今の D-final ではどの turn も Revision を入力に持つ（pack.rs:940-943）ので、書込みの後は生成出力がこれで全部外れ（ほかの node の作成と削除だけで版が元の値に戻った場合は、現行の reader の判定に従う。S6-5）、版を入れないことで残るのは過去の Human 入力だけである（§4）。auto は turn の文脈の軸として比べ、phase と reveal は材料ごとの既存の Scope ref で再資格化する。
- 範囲：同じ chat session で、同じ target Scene（同じ incarnation）の turn に限る（推奨）。過去の Human 入力は current Human capture の lineage で、生成出力は親の再資格化と成功 receipt で扱う。1 つの Human の version に attempt は生涯 1 件までしか作れない（DT-2 の決定的な attempt ID）ので、過去の Human は、その 1 件の attempt の文脈が今回と一致するときだけ候補にする。製品の再試行は新しい user 行と新しい capture になり、失敗した turn の旧い Human は、資格の規則では候補になりうる（request に入れるかは DI-1b の packing）。同じ capture の再生成は作らない。DSN §1.10 の retry 行の第 2 文はこれを許す文面なので、DSN を DT-2 に追随させることが前提になる（下の「再試行の形」）。確認ダイアログは作らない。Artifact は unsupported、Graph 由来は Pending（外すには DI-1a の後に別の draftRef の確認が要る）。
- 今回の turn の Human：D-final の読取に加えて、create と claim の transaction の中で、capture が current のままであることを確かめ直す。a153743b の create と claim は capture を読まず（S6-4）、取り消した Human が送られうる。DT-2（commit `fc8786e9`）は create の側を閉じた（capture が current でなければ attempt を作らない）。未実装なのは、claim の側の capture の再確認と、create と claim での Scope binding の token と restore epoch の再確認と、create の transaction の中で Native の時計から作成時刻を決めること（DT-2 の owner は coordinator の値を保存している）である。claim の COMMIT から transport 開始までの取消は、claim の transaction の読み直しでは閉じない。閉じる責務は DI-1c と DD-1 に置き（capture の取消の入口と owner の `cancel()` を両方向に束ね、利用者の生成の取消が capture の取消を伴うようにする）、束ねられない書込みと、COMMIT の後の token・epoch・superseded の変化は残余とする（Mandatory defenses の「COMMIT の後の窓」と「利用者の取消と capture の取消の結束」）。
- 再試行の形（ユーザーの選択）：推奨は、再試行を新しい送信（新しい user 行、新しい capture）とし、1 つの Human の version に attempt を生涯 1 件までにすること（DT-2 の実装）。DSN §1.10 の DT-2 matrix の retry 行は、「新しい attempt は利用者の新しい操作からだけ作る」に続けて「同じ key でも前の attempt が終端していれば作ってよい（再生成を妨げない）」と書き、同じ capture の再生成を許す。DT-2 の記録 E5 はこの第 2 文から逸脱して再生成をできなくし、DSN L250 は DSN を追随させるとするが、まだ追随していない。推奨は、DSN を DT-2 に追随させる（第 2 文を改める）ことを前提条件にする。対案（同じ Human の再生成を許す）を選ぶ場合は、規則 3 を差し替えた新しい draftRef が要る（「選択肢と推奨」の「再試行の形」）。
- cold reopen を越える同一性は durable workspace identity（workspace ID と canonical locator）で、restore を越えないことは restore epoch（project の semantic epoch）で判定する。history の有効期間は作成から 30 日とし、この行で決める。
- restore と undo：資格は保存せず、毎 turn 今の状態から計算する。対象 Scene の編集（その undo を含む）、message の編集や削除、capture の取消、restore は、Scope binding の token、version の失効、capture の状態、restore epoch を先へ進めるので、戻しても旧い履歴は戻らない。一方、ほかの Scene の挿入や archive などで変わった対象 Scene の読む順の順位などが元の値に戻れば、過去の Human 入力は再び候補になる。生成出力は、現行の reader が親の Revision 入力を再び適格とする場合（別の node を作って消し、project の scope authority の版が元の値に戻った場合など。S6-5）に限って戻りうる。確認済み行の「restore／undo で旧資格を戻さない」をこのように読むことを、確認に含める（§4 の「元の値に戻る場合」）。
- 可用性の制約：
  - 物語時間と POV はどちらも既定で NULL で、人の明示の操作でしか入らない。repo の評価・試験・journey の fixture に 2 軸がそろう Scene は無い（製品同梱サンプル v2 だけが 8/8 だが、Scene Scope が Unknown なので D-final が成り立たない）。対象 Scene に物語時間と POV が無ければ、その Scene では history を使えない。
  - POV や物語時間の設定を含め、project の tree へ製品の writer で書くと（どの Scene への書込みでも。本文の保存を含む）、project の scope authority の版が変わり、承認済みの Revision は A3 で `source-revision-changed` になる（freshness cycle の後は stale）。今の D-final は Raw 1 件と Revision 1 件以上を必須にし、渡した Revision が 1 件でも不適格なら request 全体を拒否する（pack.rs:788-791、940-943、1937-1947）。そのため、書込みの後は、新しい Revision を承認するまで今回の turn も準備できない。過去の turn の生成出力は、どれも Revision を入力に持つので、すべて history から外れ、新しい Revision を承認しても戻らない（版が元の値に戻る往復を除く。S6-5）。残りうるのは過去の Human 入力だけである。生成出力を含む history を使うには、2 軸を設定してから承認し、その後は tree を書かない、という順序が要る。
  - 対象 Scene を編集すると（AI の出力の適用、POV や label の設定、Codex の名前の一括置換による本文などの書換えを含む）、Scope binding の token が進むので、その Scene の history は過去の Human 入力も含めて全部外れる（project の tree への書込みでもあるので、上の項目のとおり、新しい Revision を承認するまで今回の turn も準備できない）。確認済みの scope-storage-authority が、通常の編集で Source token を更新して旧資格を失効させること（l6-l9:113）に合わせた扱いである。
  - 対象 Scene の読む順の順位が変わっても、その Scene の history は全部外れる。順位は live な Scene だけで数えるので、前での Scene の挿入、削除、並べ替えのほか、archive／unarchive（外部 mount の同期による自動のものを含む）でも変わる（ほかの Scene の変更を戻して順位が元に戻れば、過去の Human 入力は再び候補になる）。

- Revision 入力の最小は 1 件である。D-final は、渡す Revision ID の列を 1〜512 件に限り（pack.rs:788-791）、1 件でも A2／A3 で不適格なら request 全体を拒否し（pack.rs:1937-1947）、選んだ item に Raw と accepted IR が 1 件以上ずつ無ければ拒否する（pack.rs:940-943）。prepare も 3 入力以上、Raw、accepted IR を要求する（prep.rs:1101-1106、1136-1137）。したがって、今の D-final の attempt はどれも Revision を入力に持ち、Raw だけを材料にした turn は作れない。
- Native の検査は、Source、Revision、Decision、Freshness、Scope がどれかの入力に 1 件以上あることだけを見る（prep.rs:1138-1160）。
- history の checker とは次の点で合わない。
  - 7 種を入力ごとにちょうど 1 件ずつ求める（hist.rs:56-80）。Source と Scope が複数ある Revision 入力は重複で、Index と D1 が無いので、どの入力も拒否される。
  - 明示に束縛された Human はこの検査を免除される（hist.rs:518-529）。
  - turn の tuple を保存値と完全等値で比べる（hist.rs:485）。材料は turn ごとに違うので、通常の会話の祖先は不一致で外れる。
  - storage adapter は tuple を常に None で返す（hist.rs:1148）。今は実データで常に fail-closed になる。
- S6 の実測（既存の fixture。Revision 2 件、各 Entity 2、Relation 1）：資格 ref は今回の Human 0 件、Raw 1 件、Revision 各 16 件（Revision、Decision、Freshness 各 1、Source 4、Scope 9）、計 33 件・4,997 B（行の平均は約 150 B）。D-final はまだ製品から呼ばれない（prep.rs:5 で dead_code を許し、persist の呼出しは試験だけ）。
- 完備規則（DF+-a）との差（S6 の実測）：今回の Human は 7 kind すべて、Raw は Revision・Decision・Freshness・Index・Scope・D1 の 6 kind、Revision は Index と D1 が欠ける。(kind, target) の重複が無いことと、複数の Source／Scope を保つことは、今の出力でも満たす。
- typed N/A を表す型が無い。資格行の `QualificationReference` は input_ordinal、kind、identity、version の 4 field だけで、`deny_unknown_fields` を持つ（gendb.rs:204-215）。入力行の `InputReference` も role と target だけで、input-use の field が無い（gendb.rs:185-190）。DF+-a は両方の JSON の版を上げ、final input digest の domain（`nir1-generation-inputs@1`。gendb.rs:696-704 と gen.rs:868 の 2 か所）と、history adapter の kind の写像（hist.rs:927-951）も合わせて変える。
- 明示の Human の免除（hist.rs:518-529）は、実際の adapter では条件付きで効く。lineage を解決する読取で message 行が読め、その binding が一致したときだけ `explicitly_bound` が true になる（hist.rs:1018-1033、1052）。それ以外の D-final の Human は、資格 0 件なので MissingQualification(Source) で外れる（S6 の実測）。
- 資格 ref の identity は `:` で区切った文字列の連結で、escape が無い（pack.rs:1080-1125）。ID が `:` を含むと、別の事実が同じ文字列になりうる（S6 の理論上の指摘で、再現はしていない。製品の ID は UUID）。
- 1 attempt の資格 ref の数：typed review の Revision 1 件あたり 11＋2E＋Rel 件（E は Entity、Rel は Relation の数。fixture の 16 件と一致）。Revision 入力が最大の 102 件のとき、1 attempt あたり最大 1,327 件、DF+-a の後は 1,544 件で、資格行は最大で約 200 KB になる（S6。式は typed review の producer の形による）。history はこれを祖先の attempt ごとに読む。

### S6-3 binding_json の 64 KiB と、保存先を比べる根拠

- 上限は `MAX_BINDING_JSON_BYTES`（64 KiB）で、書込みと読取の両方で検査する（gendb.rs:38、889、1042、1098）。`create_attempt` は超えると `NIR1_GENERATION_BINDING_LIMIT` を返し、attempt の作成そのものが失敗する（gendb.rs:885-891）。history の都合で生成全体が止まりうる。
- 入力行と資格行は binding_json に入らず、既存の子 table（`nir1_generation_input_refs`、`nir1_generation_qualification_refs`）に 1 行ずつ JSON（`reference_json`）で入る（migrate.rs:4143-4154、gendb.rs:898-904）。こちらは 64 KiB の対象外で、読む量は呼出し側の予算で決まる。
- DT-3（実装済み・未 merge）は、binding を v2 にし、DB で検証する `chatSessionId` と Scene の束縛（scene ID、incarnation、source token、本文の digest）を、process-local な caller（profile、caller、caller epoch、Main の caller session）と分けた。`historyTurnContext` と `durableWorkspaceIdentity` の slot は、値の入らない型で予約し（null だけを読み書きでき、値があれば parse で拒否する）、64 KiB と schema は変えていない。slot に入れる `HistoryTurnContextV1` の形は repo のどこにも無く（S6 の grep）、この draft の §2 が初めて決める。DT-3 の作業記録によると、v2 は識別子 12 個（各 4,096 B 以下）と digest 6 個で、escape の無い識別子なら最大約 49 KiB、JSON の escape では 64 KiB を超えうる（その場合は create が拒否する。DT-3 の試験）。
- 数え方：canonical JSON（key を整列、空白なし）の bytes。digest は 71 B、i64／u64 は最大の桁数、enum は最長の値。ID は典型（36 B の UUID）と、現行の検査が許す最大（4,096 B、gendb.rs:37。escape の要らない文字）の 2 通り。S6 は同じ数え方が AttemptBinding v1 の実際の struct の大きさと一致することを確かめた。DT-3 の v2 は field の名前と型を写して数えた。

- 読み方：
  - 過去の turn の数は binding の大きさに効かない（祖先は参照でたどる）。binding に効くのは、そこに置く値の形だけである。
  - turn に一つの値を digest、整数、閉じた enum に限れば、slot の大きさは ID の長さにも入力の数にも依存しない（約 1.9 KB）。典型の ID では上限に対して十分に小さく、ID が上限の 4,096 B でも収まる。
  - 識別子が escape を多く含むと、slot が空でも v2 の binding が 64 KiB を超えうる（制御文字だけの 4,096 B の ID は JSON で 24,576 B になる）。この場合は DT-3 の既存の拒否のままとし、この行は変えない。slot を足して初めて超える狭い範囲だけを、この行が扱う（§2 の「上限を超えるとき」）。
  - 入力ごとの証跡は、入力の数と ID の長さに比例し、上の不採用の行のとおり 64 KiB を超えうる。資格行そのものは 1 attempt で約 200 KB に達しうるので、binding_json には置けない。既存の子 table の行に置くか、新しい子 table を作るかの比較は「選択肢と推奨」の最初の行にまとめた。
  - 数え方の script は integrator の作業記録に残す（`size_v2.py`）。HS-1 は実際の型を canonical JSON にして、上限の組合せ（ID 4,096 B、digest、最大の整数）で測り、試験で固定する（S6 の勧め）。

### S6-5 project の scope authority の版の揮発性（POV と物語時間の設定を含む）

S6 は、renderer の IPC の裏にある Native の writer を 1 回ずつ呼んで、次を測った（ケースごとに新しい fixture。renderer と IPC そのものは通していない）。

| 書込み（製品の writer） | 対象 | project の scope authority の版 | Scene token | Scene の Scope binding の版 | 承認済み Revision の A3（直後） | Revision の canonical Freshness（freshness cycle の後） |
| ----------------------- | ---- | ------------------------------- | ----------- | --------------------------- | ------------------------------- | ------------------------------------------------------ |
| `tree_node_patch` の POV（Scene のプロパティ、chip row、Chronicle の scene-event の移動） | 対象 Scene | 変わる | updated_at だけ変わる | 進む | `source-revision-changed` | stale（rebuild-required） |
| 同上 | 別の Scene | 変わる | （対象 Scene は変わらない） | （別の Scene の版が進む） | `source-revision-changed` | stale |
| Chronicle の一括のレーン割当（`sceneSetPov`） | 対象 Scene | 変わる | updated_at だけ変わる | 進む | `source-revision-changed` | stale |
| `temporal_scene_patch` の物語時間の key、label だけの編集 | 対象 Scene | 変わる | version も変わる | 進む | `source-revision-changed` | stale |

- 理由（コード）：project の scope authority の版は、project の全ノードの id、parent、種類、並び、story_time_order、archive、version、updated_at と、全 Scene の Scope binding を取り込む（dbpsa.rs:188-212、253-265）。製品の writer はどれも updated_at を進め、Scene の Scope binding を作り直す。typed Revision の material は project の scope authority を Source として必ず含み、A3 はその版が live の版と等しいことを求める（er.rs:3523-3526 の `NIR1_SCOPE_AUTHORITY_STALE` が `source-revision-changed` として返る。er.rs:2113-2117）。
- POV の値と label そのものは版の digest に入らない。それでも製品の writer は updated_at を必ず進めるので、版は変わる。直接 SQL で POV の列だけを変えると版は変わらず、製品と逆の結果になる（S6 の改訂前の版はこの方法で「POV の設定では版が変わらない」と書き、改訂で取り下げた）。負例は製品の writer で作る。
- 版は今の行から計算する値で、単調には進まない。ほかの行を変えずに node を作ってから消すと（作成の undo を含む。renderer の undo は `tree_node_delete` を呼ぶ）、作成は新しい node とその Scene の Scope binding だけを足し（domain_writes.rs:3125-3159）、削除はその二つだけを消し（domain_writes.rs:3360-3370）、registry は変わらない（scene_scope.rs:481-503）ので、版は元の値に戻る（コードからの推定。実測していない）。scene_scope.rs:812-814 の comment は A→B→A の書込みで旧い token を作り直さないことを意図しているが、node の作成と削除の往復はこの保護に入らない。A3 の版の検査は等値比較（er.rs:3523-3526）なので、このとき書込みの前に承認した Revision を再び通しうる（canonical Freshness などほかの ref が変わっていない場合。freshness cycle が間に走ったときに canonical Freshness が元の token に戻るかは確かめていない）。既存の Scene への書込みは、その Scene の Scope binding の版を 1 上げる（scene_scope.rs:563-611）ので、Scene の編集とその undo では版は元に戻らない。これは A3 と scope-storage-authority の既存の挙動で、この行は変えない。history での扱いは §4 の「元の値に戻る場合」に書く。
- 帰結：
  - project の tree への製品の書込みは、どの Scene への書込みでも（本文の保存、POV、物語時間、label、archive を含む）、承認済みの typed Revision を A3 で使えなくする。A3 が通すのは、Revision の Entity が持つ Scope binding の authority revision が今の版と等しい Revision だけで（er.rs:3523-3526）、書込みの前の状態に束縛した Revision は通らない。新しい immutable な typed Revision の review と承認が要る（er.rs:3393-3395 の comment は「a later edit makes cold reopen unavailable until a new immutable typed Revision is reviewed」とする）。これは確認済みの scope-storage-authority と A3 の既存の挙動で、この行は変えない。
  - 今の D-final はどの turn にも Revision 入力を 1 件以上求める（S6-1）。そのため、書込みの後は次の二つが起きる。(1) 新しい Revision を承認するまで、今回の turn も D-final で止まる（渡した Revision が不適格なら `NIR1_NATIVE_A2_UNAVAILABLE`、渡さなければ件数の拒否。pack.rs:788-791、1937-1947）。(2) 過去の turn の生成出力は、どれも親 attempt が Revision を入力に持つので、§3 の Revision 入力の再資格化で全部外れ、新しい Revision を承認しても戻らない（上の node の作成と削除だけで版が元の値に戻った場合は、現行の reader の判定に従う）。history に残りうるのは過去の Human 入力だけである。
  - 物語時間と POV をそろえる操作そのものが、それまでの承認を失効させる。生成出力を含む history を使うには、2 軸を設定してから Revision を承認し、その後は tree を書かない、という順序が要る。
  - この版を history の turn の文脈（witness を含む）に入れると、過去の Human 入力まで、project のどこかを編集するたびに外れる（生成出力は、入れなくても上の (2) で外れる）。§4 はこの版を turn の文脈に入れない。

- Mandatory defenses: 次を必須にする。
  - writer は Native だけで、renderer の値を認可の根拠にしない。候補は Native が、attempt の行の session_id 列（DT-3 で DB の chat session ID に固定済み）と既存の index で、同じ project と chat session の attempt から列挙する。binding_json を parse して project 全体から探さない。renderer の選択と caller の session の申告は使わない。
  - 資格の完備規則（§3）を守る。kind ごとに 1 件以上の ref か表の typed N/A のどちらか一方を持ち、(kind, target) の重複を許さない。重複と過不足の判定は、identity の文字列の一致ではなく、型付きの組（kind ごとの成分）で行う。Revision 入力の Source と Scope は、現行の Revision と対象 Scene から導いた集合と過不足なく一致させる。表に無い N/A、未知の理由、ref と N/A の併存は不完全とする。
  - 毎 turn、D-final と同じ participant の read snapshot の中で、記録した ref をすべて現行の reader で再資格化する。保存した値は比較の目印として使い、資格そのものは保存せず毎 turn 計算し直す。DB の外の状態（profile、caller、route、lifecycle）は、snapshot の前後と、保存と送信の直前に確かめ直す（DT-2、DI-1c）。
  - 今回の turn の DB の状態は、D-final の snapshot だけで確かめたことにしない。create と claim のそれぞれの immediate transaction の中で、(1) current-turn の capture が current のままであること（同じ capture ID、owner、message version）、(2) 対象 Scene の Scope binding の token が、D-final の snapshot で読んだ値（文脈に記録する値と同じもの）と等しいこと、(3) project の現行の semantic epoch が、同じく snapshot で読んだ値と等しいこと、を読み直して確かめる。文脈を保存しない attempt（§2 の binding-limit など）でも同じく確かめる。DT-3 が同じ transaction で確かめる Scene と session の束縛（incarnation、source token、本文の digest、未 archive、session の node_id）に加える。create で違えば attempt を作らない（typed refusal、送信 0）。claim で違えば送信せず、送信していない terminal を一度だけ書く（terminal の行は native-generation-receipt の matrix のうち送信前の行。DT-2 の zero-send の writer がこの対応を決めている）。これは既存の欠けを埋める防御で、現状は次のとおり：a153743b の create と claim は capture を読まない（S6-4）。DT-2（commit `fc8786e9`）の `create_attempt_for_capture_bounded`（grimodex-db nir1_generation.rs:3978 (fc8786e9)）は、同じ transaction で capture を読み直し、current でなければ `NIR1_GENERATION_CAPTURE_NOT_CURRENT`（同 :4033 (fc8786e9)）で attempt を作らないので、create の (1) は実装済みである。DT-2 の `claim_attempt_bounded`（同 :4110 (fc8786e9)）は CAS だけで capture を読まないので、claim の (1) は未実装で、DT-2 の記録 §11-4 は dispatch 直前の再確認を DI-1c の責務として引き継いでいる。この draft の規則では、その再確認を claim の transaction の中の読み直しとして実装する（transaction の外の事前の確認では、確認から claim の COMMIT までの間の取消や新しい user 行を防げない）。(2) と (3) は create と claim のどちらにも無い。この draft が確認を求めるのはこの規則で、未実装の分を DT-2 に足すか DI-1c が足すかは含まない（「critical path への影響」）。どちらの場合も、次の 3 つがすべて、DI-1c が history の文脈を持つ attempt を製品の送信につなぐ前に merge されていること（merge 条件）：claim の capture の再確認、create と claim での Scope binding の token と restore epoch の再確認、create の transaction の中で Native の時計から作成時刻を決めること（下の作成時刻の項目）。
  - COMMIT の後の窓：claim の transaction の読み直しが守るのは claim の COMMIT までで、COMMIT から transport 開始までは守らない。DT-2 の claim は CAS で、COMMIT の後は DB の外の authority（profile の permit、route、workspace、Ready の binding、lease）だけを再検証し（`revalidate`。nir1_generation_owner.rs:493-507 (fc8786e9)）、開始判断は owner の phase mutex で `Nir1OwnerCancel::cancel()` と線形化する（同 :1000-1010）。どちらも DB の状態を読まない。capture の取消（`cancel_current_chat_input`、`cancel_current_chat_submission`。nir1_prepared_request.rs:667、797）は別の Native の入口から独立に書け、owner の `cancel()` には結ばれていない。そのため、claim の COMMIT の直後に取消が入ると、取り消した Human の request が送られうる。同じ窓で、対象 Scene の Scope binding の token（Scope 設定の保存、対象 Scene の通常の編集）、project の restore epoch（snapshot restore と integrity repair。workspace は Ready のまま epoch が進む。S6-4、§7）、capture の superseded（新しい user 行）が変わっても、lifecycle の gate や lease を動かさない限り、開始判断は止まらず、旧い token と epoch の下で組んだ request が送られうる。開始判断の lock の中で capture を DB から読み直すことは、DT-2 の lock 順（DB の mutex を owner の phase mutex の下で取らない。DT-2 の記録 §4 の L1）に反するので採らない。この窓は次のとおり扱う。(a) 製品の capture の取消の入口は、取消を受理して利用者に返す前に、その capture の owner の `cancel()` を呼ぶ（owner の cancel handle を引く方式は DI-1c と DD-1 が決める）。開始判断の前に入った取消は送信 0 の Cancelled になり、後に入った取消は transport 開始の後の取消として DT-5 が扱う（送った bytes は戻らない）。これは DD-1 の受入れ条件で、製品の入口を開ける PUB-L の前に満たす。(b) 開始判断の直前に capture、対象 Scene の Scope binding の token、restore epoch を lock の外で bounded に読み直してもよい。窓は狭まるが閉じないので、規則にはしない。(c) owner の `cancel()` に束ねられない書込み（外部 process の user 行の挿入、DB の直接編集、束ねていない入口）と、COMMIT の後の token・epoch・superseded の変化は残余として受け入れる（Out-of-scope attacks）。残余でも history の資格は壊れない（次の turn の再資格化が、取り消した Human と、それを親の current-turn に持つ生成出力を外し、記録した token と epoch が今と違う候補も外す。superseded になった Human は、claim の時点で current だった入力なので、規則 1〜4 で判定される）。この draft が確認を求めるのは、この窓が claim の transaction では閉じないことと、(a) の責務の置き場と、(c) の残余である。
  - 利用者の取消と capture の取消の結束：利用者が取り消した Human は、取消の時機によらず history の候補にならない。この保証は capture の状態（cancelled。§6 の規則 2）が担うが、owner の `cancel()` も、zero-send と Cancelled の終端を書く writer も capture に書かない（S6-4）ので、利用者の生成の取消の入口が owner だけを取り消すと、capture は current のまま残る。その場合、create の前の取消は attempt が 0 件で Human が外れるが、create の後の取消は Cancelled の終端の attempt がちょうど 1 件になり、次の user 行で capture が superseded になった後に、その Human が規則 1〜4 を満たして候補になる（同じ取消でも時機で結果が変わり、取り消したはずの文が、DI-1b の packing が採れば local の model に再び渡る）。これを次のとおり閉じる。
    - 結束：利用者が生成を止める Native の入口（K5 の draft の `nir1_local_generation_cancel`〔K5 L322。handle だけを受け取り、capture の取消を規定していない〕に当たるもの。command の形と、handle から owner の cancel handle と受理済みの submission を引く方式は DD-1 が決める）は、一つの command の中で、owner の `cancel()` を呼び、その owner の current-turn の capture を既存の capture の writer（`cancel_current_chat_input` と同じ writer。新しい writer は作らない）で cancelled にする。renderer が owner の取消と capture の取消を別の command として呼べる形にしない。逆向き（capture の取消の入口 → owner の `cancel()`）は上の (a) で、これで、どちらの入口から入っても owner と capture の両方が取り消される。K5 の command の表の役割（取消）は増やさない（capture の取消は、利用者の取消の効果として同じ command の中で行う）。
    - 順序と失敗：どちらの入口でも、owner の `cancel()` を先に呼ぶ（DB を待たずに、開始判断の前の送信を止める）。利用者の取消の入口は、capture の取消が既存の writer の終端の結果（cancelled、not-current、not-found）になってから成功を返す。capture の取消が error で終わったときは typed な拒否を返し、成功として返さない（K5 の表の「返すもの: なし」は正常の応答で、失敗は拒否で返す）。同じ command を再実行して続けられる（owner の `cancel()` は何度呼んでも同じで、capture の取消は、すでに cancelled なら not-current を返して状態を変えない）。

### 2. 保存先

保存先は二つに分ける。turn に一つの固定長の値は binding_json の予約 slot に、入力ごとの証跡は既存の子 table の行に置く。比較の根拠と対案は S6-3 と「選択肢と推奨」の最初の行にある。

history の slot（DT-3 が `historyTurnContext` として予約した slot）は、次の三つの形のどれかをとる。

- null：HS-1 より前の attempt と legacy の行。history に使わない。
- unavailable：閉じた理由だけを持つ（`d-final-incomplete`、`binding-limit`、`workspace-identity-unavailable` など。理由の集合は HS-1 が閉じた enum で決める）。history に使わない。
- `HistoryTurnContextV1`：次の field を持つ。

| field | 値 | 取得源 |
| ----- | -- | ------ |
| contract | `nir1-history-turn-context/1`。未知の版は history に使わない。値の導き方（resolver の規則など）を変えるときは版を上げ、旧い版の文脈は使わない | — |
| sendClassification | `local-only` だけ | Native の route の分類（D2a restricted の下の対応 local route） |

| restoreEpoch | project の現行の semantic epoch の ID をドメイン分離した digest と、epoch の番号。epoch の ID は TEXT で、backup restore の epoch だけが digest から作る UUID、ほかは `Uuid::new_v4`（S6-4）なので、ほかの可変長の値と同じく digest で持つ | semantic epoch の reader（`semantic_epoch.rs:77-99`） |

- durable workspace identity の slot（DT-3 が `durableWorkspaceIdentity` として予約した slot）には、workspace ID の digest と canonical locator の digest の組を置く（§7）。求められなければ null にし、history の slot は `workspace-identity-unavailable` にする。
- DB の chat session ID は attempt の行の session_id 列と AttemptBinding v2 の chatSessionId に、対象 Scene の ID と incarnation は DT-3 の Scene の束縛に置く（実装済み。§6 の列挙の鍵）。ここでは繰り返さない。
- selection digest は、estimator の版、selector の予算、使用量、残量と、採用した入力（ordinal、input-use、target）の順の列から計算する。保存した入力行とこの field だけで計算し直せる形にする（§3 の D1）。
- 可変長の値（epoch の ID と workspace ID を含む）は、domain 分離した SHA-256 の digest で持つ。そのため slot の大きさは field の集合だけで決まり、ID の長さにも入力の数にも依存しない。モデルでは history の slot が最大 1,893 B、durable identity の slot が 194 B（S6-3）。HS-1 は実際の型で測り、その最大を試験で固定する。
- 上限を超えるとき：二つの slot を足すと binding_json が 64 KiB を超える場合は、history の slot を unavailable（`binding-limit`）にし、durable identity の slot を null にして attempt を作る。その attempt は history に使わないが、送信は止めない（history の記録の都合で生成を止めない）。slot が空でも 64 KiB を超える場合（escape を多く含む識別子など）は、DT-3 の既存の拒否（`NIR1_GENERATION_BINDING_LIMIT`、attempt を作らず送信 0）のままとし、この行は変えない。
- 入力ごとの証跡は次のとおり。どちらも final input digest に含め（digest の domain の版を `nir1-generation-inputs@1` から上げる）、行の JSON の形だけを変える。table と列は変えない（`reference_json` 列は JSON を持つ。S6-3）。
  - input-use：入力行（`nir1_generation_input_refs`）の `InputReference` に、閉じた enum の field を足した新しい版で持つ。
  - typed N/A：資格行（`nir1_generation_qualification_refs`）の `QualificationReference` を、present（kind、identity、version）か not-applicable（kind と閉じた理由）のどちらかをとる新しい版にして持つ。旧い版は 4 field と `deny_unknown_fields` だけで（gendb.rs:204-215）、N/A を表せない。
  - history adapter の kind の写像（hist.rs:927-951）も新しい版に合わせる。
- 書く時点：D-final と同じ snapshot で作り、handoff で運び、`create_attempt` の同じ immediate transaction で、attempt、入力行、資格行と一緒に書く（DI-1c）。その transaction の中で、current-turn の capture、対象 Scene の Scope binding の token、restore epoch を読み直して確かめる（Mandatory defenses）。その後は変えない。
- D-final の出力が完備規則を満たさないときは、history の slot を unavailable（`d-final-incomplete`）にする（その attempt は history に使わない）。行の形が閉じた型から外れるとき（未知の enum、表に無い N/A）は、writer が保存しない（typed refusal）。
- 今回の軸のどれかが unavailable の turn（storyTime か viewpoint。対象 Scene が mapping に無ければ readingOrder、storyTime、auto も）も、unavailable を記録した文脈を付ける。その attempt は history に使えないが、理由を残す。
- 旧い形の行（v1 の binding、history の slot が null か unavailable のもの、input-use と typed N/A の無いもの）は、終端と回復のためには読むが、history には使わない。history の読取でこれらに当たったら、その候補と子孫を除外し、turn は止めない。

### 3. 資格の完備規則

1. 入力ごとに、7 種の kind（Source、Revision、Decision、Freshness、Index、Scope、D1）のそれぞれについて、1 件以上の ref か、下の表の typed N/A のどちらか一方を持つ。
2. 同じ入力の中で (kind, target) の重複は不可とする。target は ref の identity を、kind ごとの成分（例：Scope の scene-source なら Scene の ID、material scene proof なら Scene の ID と incarnation）の型付きの組として扱う。同じ target で版が違う ref が 2 件あれば不完全とする。今の identity は `:` で区切った文字列の連結で escape が無い（S6-1）ので、重複と過不足は文字列の一致で判定しない。DF+-a は、成分の境界が衝突しない形で identity を作るか、判定を型付きの組で行う。
   - Revision の sealed な material basis（source_basis と evidence_set）自体が同じ source key を別の token で持つ場合は、Revision 側の不整合として扱う。D-final（DF+-a）はその Revision を今回の request に採用せず、閉じた集合の理由コードを返す。ほかの入力と attempt の文脈はそのまま保つ。D-final の今の重複除去は (kind, identity, version) なので（pack.rs:1027-1046）、この場合は同じ identity の ref を 2 件出してしまう。A2 は live な Source から material basis を組み直して照合する（er.rs:2113-2131）ので通常は起きないが、Revision 側の不整合で、その Revision を含む turn の history が黙って消えないようにする。
   - D-final 自身の出力が規則 2 に反する場合（D-final の不具合）は、§2 のとおり history の slot を unavailable（`d-final-incomplete`）にし、その attempt を history に使わない。
3. ref の集合は、表と現行の状態から導いた集合と過不足なく一致させる。Revision 入力では、現行の Revision の material basis と Evidence の Source、対象 Scene と Revision から A3 が導く Scope の集合と一致すること。
4. 記録した ref は、毎 turn すべて再資格化する（下の表）。1 件でも current でなければ、その入力は stale で、候補と子孫を除外する。
5. typed N/A は表の欄に限り、理由も表の値に限る。表に無い N/A、未知の理由、ref と N/A の併存は不完全とする。typed N/A は「その kind がこの入力に当てはまらない」ことの宣言で、表と照合して確かめる。検査の免除ではない。

### 4. 軸と比べ方

- turn の文脈は、候補の attempt に記録した文脈と今回の文脈を等値で比べる。比べるのは、範囲（project、chat session（DB の chat session ID）、対象 Scene の ID と incarnation）、Scope binding の token、9 軸と auto、purpose、send classification、durable workspace identity、restore epoch。有効期間は §7 で確かめる。
- 入力ごとの ref は §3 で再資格化する。材料は turn ごとに違うので、材料の ref を turn の文脈として比べない（現行の checker の完全等値（hist.rs:485）はやめる）。対象 Scene の本文の token と digest も turn の文脈として比べず、入力ごとの ref で扱う。
- token と digest は不透明な文字列として等値で比べる。Scene token の時刻の書式は writer ごとに違う（S6）ので、時刻として解釈したり、大小を比べたりしない。
- 確認済み行の「exact tuple」は、「記録した各 ref が今も exact に current であること」と読む。「過去の turn の材料が今回の turn の材料と同じであること」とは読まない。この読み方は確認を求める項目の一つである（冒頭の表の (1)）。
- 既存の AttemptBinding（v1 は gendb.rs:127-143。DT-3 の v2 で caller の field にまとめた）の次の field は、turn の文脈として比べない。値が違うだけでは除外しない。
  - caller_id、caller の session（DT-3 で chat session と分けた）、workspace_binding_digest：process ごとの値で、再起動や開き直しで変わる。caller の ID と session は Main が発行する UUID（`electron/main/profileEgress.ts:638-649`）、workspace_binding_digest は authority instance と recovery generation を含む `LiveBinding` の digest（`electron/native/grimodex-node/src/nir1_generation.rs:936-940`）である。比べると cold reopen の後に履歴が外れる。workspace の同一性は durable workspace identity で比べる（§7）。
  - profile_id、caller_epoch：送信側の許可（D2a の profile と、その epoch）で、今回の turn の送信の前に DT-2 と DI-1c が確かめる（§8）。caller_epoch は再起動では進まず、D2a の activation で進む（`electron/native/grimodex-node/src/profile_egress.rs:193-206`）。履歴の資格は DB の材料と turn の文脈で決め、送信側の許可には依存させない。
  - route_revision、provider、model、api、endpoint_identity：送信先の route。履歴に効く区別は send classification（local-only）と purpose で、これを比べる（§5）。local-only の route どうしの変更（別の local endpoint や model）では履歴を外さない。今回の turn の route の検査と同意は K5、DT-2、DI-1c が行い、送信中の route の変更は turn を止める（§8）。
  - material_digest、scope_digest、d1_digest：§1 のとおり要約で、今回の turn の値とは比べない。

| 軸 | 記録する値 | 比べ方 | unavailable になる場合 |
| -- | ---------- | ------ | ---------------------- |
| scene | 対象 Scene の ID と incarnation（DT-3 の Scene の束縛） | 等値（範囲の条件） | Scene の行が無い、Scene 自身の archive、Scope binding の行が無い（DT-3 の「live」は Scene 自身の archived_at だけを見る。祖先の folder の archive は下の readingOrder、storyTime、auto で扱う） |

- 両方が unavailable でも一致としない。今回の文脈の軸が unavailable なら、その turn ではどの履歴も使わない（turn は履歴なしで続く。§8）。
- witness の比較項目は、POV や物語時間を製品の writer で設定すると project の scope authority の版が変わる（S6-5）ことを前提に、次のように決める。
  - 比べる：対象 Scene 自身の値。storyTime は raw key と、それが project の中で一意に解決していること。viewpoint は POV の character ID と、それが今も可視の character であること。readingOrder は読む順の順位（読む順には Scene ごとの key が無く、順位がその Scene の位置を表す唯一の値なので）。順位は live project Scope authority の値をそのまま使い、archive した Scene を含めて数え直したりしない。そのため、前の Scene の archive／unarchive でも順位が変わり、履歴が外れる（§10。元の順位に戻った場合は下の「元の値に戻る場合」）。story ref と reading ref は Scene の ID から作る文字列で、Scene と同じ値になる（S6-2）。
  - 比べない：project の scope authority の版。project の tree へのどの製品の書込みでも変わる（本文の保存、POV、物語時間、label、archive を含む）ので、入れると、project のどこかを編集するたびに、過去の Human 入力も外れる。物語時間を Scene ごとに設定していく作業（history を使えるようにするための作業）も、そのたびに過去の Human 入力を外す。生成出力は、版を入れなくても次の項目のとおり外れるので、版を入れないことで残るのは過去の Human 入力だけである。
  - 比べない：story の順位。ほかの Scene の key が変わるだけで変わる。対象 Scene の物語時間の位置は、その Scene の key で表す。
  - 比べない項目が材料に与える影響は、入力ごとに扱う。typed Revision の Source と Scope の ref は project の scope authority の版を含み、A3 はその一致を求める（S6-5）ので、版が変われば、Revision を入力にした turn の生成出力は §3 の再資格化で外れる。今の D-final はどの turn にも Revision 入力を 1 件以上求める（pack.rs:940-943、prep.rs:1136-1137。S6-1）ので、生成出力はすべてこれに当たり、project の tree への製品の書込みの後は全部外れる（版が元の値に戻った場合は下の「元の値に戻る場合」）。材料の ref がほかの Scene の状態に依存しないのは、過去の Human 入力だけである（その ref は message version と対象 Scene の Scope binding で、capture lineage とともに再資格化する。§3、§6。ほかの Scene の変更で変わりうる対象 Scene の読む順の順位、物語時間の key の一意性、auto の実際の軸は、turn の文脈の軸として比べる）。この行は D-final の必須文脈を変えない。別の変更で Revision を持たない attempt ができても、その生成出力は同じ規則（入力ごとの再資格化）で判定する。
  - 元の値に戻る場合（確認済み行の「restore／undo で旧資格を戻さない」（l6-l9:229）と Recovery の「旧 lineage を再利用しない」（l6-l9:235）の読み方。確認を求める項目の一つで、冒頭の表の (2)）：
    - 資格は保存せず、毎 turn 今の状態から計算する。保存した資格を戻すことは無い。
    - 単調に進む値が変わった候補は戻らない。単調に進む値は、対象 Scene の Scope binding の token（Scene への書込みのたびに binding の版が 1 上がる。scene_scope.rs:563-611）と incarnation（作り直すと新しい UUID。DT-3 の作業記録 §4）、message version の失効（ws-schema.rs:33-55）、capture の状態（S6-4）、restore epoch（S6-4）である。そのため、対象 Scene 自身の編集（移動を含む）とその undo、message の編集・削除・同じ ID の再挿入、capture の取消、restore と integrity repair の後は、元の状態に戻しても、それまでの候補は戻らない。
    - 単調でない値は、今の値と記録した値を比べる。対象 Scene の読む順の順位、物語時間の key の一意性、POV の character の可視性、auto の実際の軸（project の phase_resolution_mode と、各 Scene の key の有無で決まる。scene_axis.rs:13-64）、durable workspace identity（§7 の元の path に戻した場合）、project の scope authority の版（S6-5）、材料ごとの reveal state などである。これらは、ほかの Scene の変更を戻す操作（前に挿入した Scene を消す、挿入の undo、archive した Scene の unarchive、重複した key の解消）や、character の hidden の解除などで元の値に戻りうる。
    - 過去の Human 入力：ref（message version と対象 Scene の Scope binding）と capture lineage はほかの Scene の状態に依存しないので、文脈の軸が記録と同じ値に戻れば、その軸だけで外れていた過去の Human 入力は再び候補になる。例：対象 Scene の前に Scene を挿入して順位が変わり、次の turn で過去の Human 入力 H1 が readingOrder の理由で外れた後、その挿入を undo すると（`tree_node_delete`）、順位が元に戻り、その次の turn では H1 が再び候補になる。挿入の後の turn の Human 入力は、その時の順位を記録しているので外れる。
    - 生成出力：親の入力の再資格化（§3）は現行の reader（A2、A3、canonical Freshness など）の判定に従い、history は独自の単調な目印を足さない。元の変更も戻す操作も project の tree への書込みなので、通常は版が元と違い、親の Revision 入力は A3 で外れたままである（archive と unarchive、本文の保存とその undo など）。ほかの node の作成と削除だけで版が元の値に戻り（S6-5。コードからの推定）、現行の reader が親の Revision 入力を今の snapshot で適格とするなら、生成出力も再び候補になりうる。そのときは、今回の turn の D-final も同じ Revision を入力にできる。history の判定は、同じ snapshot での現行の reader の判定と一致させ、受入れの試験で固定する。A3 か scope-storage-authority の側で版の往復を拒むように変われば、history もそれに従い、この行の変更は要らない。
    - 理由：単調でない値が記録と同じ値に戻った turn では、候補は記録した時と同じ文脈で評価され、材料の ref も今の reader で current と確かめられる。保存した資格を戻すのではなく、今の状態から計算した結果である。history だけが厳しい扱いをするには、新しい単調な目印の保存（schema か保存範囲の変更）か、project の書込みのたびに過去の Human 入力も含めて全部を外す目印が要る。対案は「選択肢と推奨」に示す。
  - 対案（story の順位も比べる案、project の scope authority の版も比べる案）は「選択肢と推奨」に示す。
- holder・audience・timeline・worldline・layer の 5 軸は Scope binding の token にも含まれる（`narrative_scene_scope.rs:176-199`）。軸ごとに比べるのは、確認済み行の Negative が軸ごとの個別の拒否を求めるため。軸を比べた後に token を比べ、版の変化なども除外する。token は Scene の通常の編集（本文、設定、物語時間、POV、label、Codex の名前の一括置換）と registry の変更でも進む（S6-4、S6-5）ので、対象 Scene を編集すると、過去の Human 入力も含めて、その Scene の history は外れる。これは確認済みの scope-storage-authority が通常編集で旧資格を失効させる（l6-l9:113）のに合わせた扱いで、対案は「選択肢と推奨」に示す。
- auto：turn の文脈では、project の phase_resolution_mode から ADR-002 の resolver が決める軸を比べる。材料ごとの auto の制約は A3 の Scope ref（typed scope と reveal state）で再資格化する。
- phase と reveal（post-B §10.1）は turn の文脈の軸にしない。Revision 入力（と将来の Graph 由来の入力）の A3 の Scope ref を再資格化して確かめる。reveal state の token は、phase の状態、伏線の状態、query viewpoint、scope authority の版を含む（er.rs:2488-2497）。変われば、その入力と子孫が外れる。Raw と Message の入力は narrative の材料でないので phase と reveal を持たない。生成出力は、親の Revision 入力を通して確かめる。過去の Human の文章の意味は追跡しない（l6-l9:583）。

### 6. 範囲と候補

- 範囲：同じ project、同じ chat session（DB の chat_session_id。caller の session ではない）、同じ対象 Scene（ID と incarnation）の attempt に限る。chat session は Scene に束縛されている（node_id）ので、通常は session が同じなら Scene も同じ。Scene が作り直された場合や node_id が別の Scene に変わった場合は、DT-3 の Scene の束縛と capture の scene_id で外れる。
- session の鍵：DT-3 は、attempt の行の既存の session_id 列（と AttemptBinding v2 の chatSessionId）を、DB で検証した chat session ID（D-final が読んだ capture の chat_session_id）にし、caller の process-local な session は binding の caller の field（callerSessionId）に分けた（実装済み。両者が同じ値なら拒否する）。a153743b では caller の session がこの列に入る（S6-4）ので、これは計画の DT-3 行の「DB で検証する chat_session_id と、process-local な caller binding を分ける」の具体にあたる。この定義で、既存の `require_session`（gendb.rs:706-716）、message version の session_id 列、checker の読取（hist.rs:1022、1152。DT-3 が chatSessionId に変えた）は、どれも同じ chat session を指す。
- 候補の列挙：Native が、attempt の行の session_id 列と既存の index `idx_nir1_generation_attempts_session(project_id, session_id, id)`（migrate.rs:4124-4125）で、同じ project と chat session の attempt だけを読む。binding_json を parse して project の attempt から探すことはしない。読んだ attempt は、created_at_ms の降順（新しい順）、created_at_ms が同じなら attempt ID の bytes の昇順、という一つの全順序に並べて評価する。候補の検証と予算の消費、予算が尽きたときに除外される候補は、どれもこの順で決まる。session の attempt の読取（並べ替えと、規則 3 が数える ordinal 0 の入力行の読取を含む）は 1 turn の予算（K1b）に含め、読み切れなければ §8 の予算の枯渇として扱う。renderer の選択と caller の session の申告は使わない。採用するかどうかと最終予算での配置は、DI-1b の D1 が決める。
- session の ID の再利用：attempt の行の session_id 列には chat_sessions への外部キーが無い（migrate.rs:4106-4112）ので、session を消して同じ ID で作り直すと、旧 attempt も列挙される。session を消すと chat の行が cascade で消え（migrate.rs:832）、message version は失効の trigger で invalidated になり（ws-schema.rs:33-37）、capture の行も消える（ws-schema.rs:76-81）。そのため旧 attempt の Human と生成出力は規則 1 で外れる（fail-closed）。この依存を受入れの試験で固定する。
- legacy と文脈の無い attempt：v1 の行、history の slot が null か unavailable の attempt、未知の版の文脈は、候補にしない。その attempt を親や祖先に持つ候補も外す。turn は止めない（§8）。DT-3 の今の読取は v1 の行で snapshot の読取全体を失敗させる（S6-4）ので、HC-1b はこれを候補の除外に変える。
- 過去の Human（capture lineage）は、次をすべて満たすときだけ候補にする。
  1. message version の origin が human で、失効していない。
  2. その version を持つ capture が、同じ project、chat session、Scene にあり、状態が superseded である。cancelled と current は候補にしない。closed は今は writer が無いので不適格とする。
  3. その version を ordinal 0（current-turn）に持つ attempt が、同じ project と chat session にちょうど 1 件あり、その文脈が今回と一致する。数えるのは、上の「候補の列挙」で読んだ attempt である。その attempt の入力の ref を規則 4 に使う。1 つの Human の version に attempt を作れるのは、製品の writer では生涯 1 件までである（DT-2 は attempt ID を capture から決定的に導き、同じ ID の 2 件目を作らない〔commit fc8786e9〕。capture は message ごと、version ごとに 1 行）。この前提は DSN §1.10 の retry 行の第 2 文と食い違う（下の「DSN との関係」）。0 件（attempt を作らなかった turn の Human など）は候補にしない。2 件以上は、DT-2 の製品の writer が作れない形（試験用の writer の行や外部編集の DB。DSN の第 2 文どおりに再生成を入れた製品なら作れる形になり、その場合は規則 3 を差し替える）なので、どれを採るかを決めず、その Human を候補にしない（閉じた理由のコードで返す）。
  4. 自分の ref（§3）を再資格化できる。
  - `bind_human_message`（gendb.rs:2237）で束縛しただけの version、capture の無い legacy の行、表示だけの行は候補にしない。attempt が作られなかった turn の Human（§8 で create の前に止めた turn）と、文脈なしで作った attempt（§2 の binding-limit など）だけを持つ Human も規則 3 を満たさないので候補にならず、後から補修しない。
  - claim で止めた attempt（§8。送信していない terminal を持つ attempt）は、create の transaction の中で capture が current であることを確かめてから文脈を記録したものなので、送信して失敗した attempt と同じく規則 3 の attempt に数える。利用者の取消で止めた場合は、利用者の生成の取消の入口が capture も cancelled にする（Mandatory defenses の「利用者の取消と capture の取消の結束」）ので、その Human は規則 2 で外れる（この結束が無ければ capture は current のまま残り、取り消した Human が規則 1〜4 を満たしてしまう）。利用者が取り下げたのではない取消（sender の destroyed、window の close など）で止めた場合は、capture が current のままなので、その Human は送信して失敗した attempt の Human と同じく規則 1〜4 で判定する。同じ session への新しい user 行の挿入で superseded になって止めた場合は、その Human は取り消されたものではないので、規則 1〜4 を満たせば候補になる（前の turn の claim の前に次の user 行が入ったときに、前の Human を落とさないため）。どの場合も、その attempt には出力が無いので、生成出力の候補は生じない。
  - 規則 3 が attempt を 1 件に限る理由：同じ capture の再試行は無い。DT-2 は同じ submission の 2 件目の attempt を作らせず（`NIR1_GENERATION_ATTEMPT_EXISTS`。owner では `SubmissionAlreadyAttempted`）、capture も message ごと、version ごとに 1 行なので、失敗の後に同じ capture で attempt を作り直すことは起きない。製品の再試行は、利用者が同じ文を新しく送る操作で、新しい user 行、新しい capture、新しい version になる。そのため、規則 3 で attempt を選んだり順位づけたりする必要が無い。この前提は DT-2 の決定的な attempt ID に依り、DSN §1.10 の retry 行の第 2 文と食い違う（次の項目「DSN との関係」）。ordinal 0 が capture の version であることは、D-final の出力の形（pack.rs:945-951）と input-use の導き直し（§5）で確かめる。DT-2 の create は、capture の version が User の Message として入力のどこかにあることだけを確かめる（位置は見ない）。ordinal 0 に別の Human X の version を置いた attempt A（A 自身の capture の version は別の位置）があれば、X の attempt は X 自身のものと A の 2 件になって規則 3 を満たさず、A の capture の version は ordinal 0 に attempt が無くて規則 3 を満たさないので、どちらの Human も候補にならない（fail-closed）。
  - DSN との関係（規則 3 の前提は DSN §1.10 と食い違う）：DSN の DT-2 matrix の retry 行（DSN L261）は、「新しい attempt は利用者の新しい操作からだけ作る」に続けて、「同じ key でも前の attempt が終端していれば作ってよい（再生成を妨げない）」と書く。第 1 文は K5 の「DT-5 の owner/lifecycle matrix が満たす条件」の retry 行と同じ向きで、上の再試行の説明と合う。第 2 文は、同じ capture に 2 件目の attempt を作る再生成を設計として許す文面で、規則 3 と両立しない。DT-2 の記録 E5 は第 2 文から逸脱し（同じ submission での retry〔再生成〕はできない。retry 鍵〔…〕は DD-1 で決める）、DSN L250 は matrix と違えた点について「本書も追随させる」とするが、DSN は追随していない。K5 の draft は第 1 文と同じ文だけを置いている。この draft の推奨は DT-2 の側に立つので、DSN の第 2 文を DT-2 に合わせて改めることを前提条件にする（「確認の扱い」）。DSN が第 2 文のまま、DD-1 が同じ submission の再生成のための retry 鍵を入れて同じ capture に 2 件目の attempt を作れるようにするなら、規則 3 は差し替えが要る（新しい draftRef。「選択肢と推奨」の「再試行の形」）。その間に作られた 2 件目の attempt の行は、規則 3 の「2 件以上は候補にしない」により、その Human と、その Human を親の current-turn に持つ生成出力を、history から外したまま戻さない（補修しない規則）。
  - 失敗した turn の再送：A1 が出力の無い終端で終わった後に、利用者が同じ文を新しく送ると、新しい user 行 H1′ と新しい capture C′ ができ、trigger が旧い capture C を superseded にする。再送の turn（attempt A2）の候補に H1 が現れ、H1 は、規則 1〜4 を満たせば候補になる（規則 3 は A1 の文脈が今回と一致するか。A1 の後に対象 Scene を編集するなどで Scope binding の token が違えば外れる）。H1′ はその turn の current-turn の Human で、A2 が成功した後の turn では H1′ と M2 が候補になる。request に H1 と H1′ が同文で並びうるが、資格の規則は本文の同一性を見ず（l6-l9:583）、並べるか重複を避けるかは DI-1b の packing の判断である（H1 を資格の段階で外す対案は「選択肢と推奨」）。M2 の親 attempt A2 は H1′ を ordinal 0 に持つ唯一の attempt なので、生成出力の親の Human の規則 3（下）は A2 自身を指し、採用する message の集合は食い違わない。
  - 古い Human を後から新しい文脈へ付け替える経路は無い。Human の attempt は 1 件で、その文脈は、capture が current であることを読んだ D-final と同じ snapshot で作る（D-final は current の capture だけを読む。gendb.rs:2464-2506、§2 の書く時点）。create と claim の transaction の中でも capture が current のままであることを確かめ直す（Mandatory defenses。a153743b の create と claim は capture を読まないので、これが無いと snapshot の後に取り消した Human でも attempt を作れた。DT-2 は create の側を閉じ、claim の側が未実装。S6-4）。superseded と cancelled は current に戻らず（S6-4）、文脈の token と epoch は先へ進むだけである。この項目が閉じるのは、history の lineage（古い Human を新しい文脈の attempt に付け替える経路）と、create と claim の COMMIT までの送信である。claim の COMMIT から transport 開始までの取消が request の送信を止めるかは別の問題で、Mandatory defenses の「COMMIT の後の窓」で扱う。history 側は、capture の取消を次の turn が規則 2 で外す（利用者の生成の取消は、結束により capture の取消を伴う）。
- 生成出力（親の再資格化）は、次をすべて満たすときだけ候補にする。
  1. message version の origin が generated で、失効しておらず、親 attempt がある。
  2. 親 attempt の terminal receipt が succeeded かつ parsed で、出力の version がこの version と一致する。
  3. 親 attempt の文脈が今回と一致し、親の入力（その turn の Human、Raw、Revision、親が採用した履歴）を、今回の文脈の下で再帰的に再資格化できる。親の current-turn の Human には、過去の Human の規則 1〜4 も当てる（規則 3 の attempt は親 attempt 自身でなければならない。その Human を ordinal 0 に持つ attempt がほかにもあれば、この生成出力も除外する）。capture が cancelled（成功の後に取り消した場合を含む）か、capture が無ければ、この生成出力も除外する。capture は attempt が成功した後も retire か次の user 行までは current で、その間も取消ができる（S6-4）ので、この規則が無いと、取り消した Human への返答だけが採用されうる。
  4. 自分の ref を再資格化できる。
  - 生成出力に Decision も確認も付けない。receipt は来歴の検証で、開示の許可ではない（DSN §7.3 の「history 用の宣言 grant と、生成のクリック用の確認は置かない」と同じ判断）。
  - 生成出力が外れた turn の Human 入力を単独で残すか、失敗した turn の再送で H1 と H1′ が同文のまま request に並ぶことをどう扱うかは、DI-1b の packing の判断で、資格の規則は変わらない。
- Artifact：unsupported。NIR の生成 attempt が Artifact を作る writer は無く、reader は producer を None で返す（gendb.rs:322-337）。Artifact の入力を持つ候補は除外する。producer の relation は作らない。
- Graph 由来：Pending。Graph 由来の入力を持つ候補は除外する。この行が決める（確認に含める）のは、Pending の間は除外することと、Graph 由来の入力に Index の typed N/A を認めず、Index の ref を必ず持たせること（§3 の表）だけである。Index の ref の identity と version の正確な形（sealed Graph Index の generation ID と binding digest の具体）と、再資格化に使う reader は、現行の reader が無い（§3、S6-1）ので、この draft では検証できず、決めない。Pending を外す draftRef が Index の ref を必須にしない形（例：Index を Scope の ref にまとめる）を選ぶ場合は、この行の確認済みの規則の変更にあたるので、その draftRef の Delta に変更として明記して確認を得る。
  - Pending を外すことは履歴 lineage の変更にあたる（l6-l9:620）。DI-1a の後に、ref の形、reader の名前、history の snapshot の中での再資格化、正例と負例の受入れを書いた新しい draftRef を起案し、確認を得てから外す。この行の確認は Pending の解除を含まない。
  - S1 で、B の sealed binding を製品の経路で publish する呼出しが無いと分かった（計画は B-ROUTE を加えた）。Graph 由来の入力が製品の request に入るのは、B-ROUTE、CP-1／CP-2a、DI-1a の後で、Pending を外す draftRef の正例の受入れもその後になる。
  - history の PR は「Graph が Pending の限定 core」として、未完了の Graph の受入れを明示して merge する（post-B:64）。history 全体の完了は、Pending を外す確認と、その受入れの後とする。

### 7. durable workspace identity、restore epoch、有効期間

- durable workspace identity：workspace ID（`.grimodex/workspace.json` の id）の digest と、canonical locator の digest の組。authority_instance と recovery_generation は process ごとの値なので入れない。AttemptBinding v2 の durable identity の slot（DT-3 が予約）に置く。候補の値が今回と違えば除外する。cold reopen では組が変わらないので、履歴は続く。folder の copy や move では canonical locator が変わるので、外れる。
  - canonical locator：`LiveBinding` の locator は canonicalize されていない（S6-4）ので使わない。workspace が Ready になったときに、Native が workspace の root を OS の canonicalize で解決し、その path の bytes をドメイン分離した SHA-256 の digest にする。symlink は解決するので、symlink 経由で開いても同じ値になる。path が Unicode として正しくない場合と canonicalize が失敗した場合は unavailable とし、その workspace では history の文脈を記録せず（§2 の `workspace-identity-unavailable`）、使わない。path の文字列は保存しない。macOS の `/private` 配下、Windows の verbatim の形などの扱いと、大文字と小文字だけが違う綴りの扱い（OS が on-disk の綴りを返せば同じ値、返さなければ別の値で fail-closed。畳む処理は足さない）は、C-body の draft の「canonical locator」と同じにする。
  - 判定の時点：次に Ready になったときに作る locator で判定する。open している間の folder の移動や改名は、その間の判定に反映しない（app の外の操作）。
  - 元の path に戻した場合：move した folder を元の path に戻し、workspace ID も元のままなら、組は一致し、その workspace の履歴は再び候補になる。durable workspace identity は単調でない値で、今の値と記録した値を比べるので、元に戻れば一致する（§4 の「元の値に戻る場合」。確認済み行の「restore／undo で旧資格を戻さない」（l6-l9:229）の読み方として確認を求める。冒頭の表の (2)）。restore ではないので epoch は進まない。ほかの文脈（epoch を含む）と ref の再資格化は通常どおり行う。C-body の draft も、同じ規則で宣言が再び有効になることを許している。copy して編集した folder で元の folder を置き換えることは、app を通さない DB ファイルの置換にあたり、Out-of-scope である（restore epoch では検出できない）。
  - C-body の draft（`nir1-c-body-disclosure-proposal-2-draft.md` の「canonical locator」）も同じ規則を置く。実装は一つにし（integrator が所有する）、どちらの行が先に確認されても同じ値を使う。この行の確認は C-body の行の確認に依存しない。
- restore epoch：project の現行の semantic epoch（ID の digest と番号。§2）。文脈に記録し、今回と等値のときだけ使う。
  - backup restore（Safe Mode からの restore を含む）は staged DB の上で Ready の前に、snapshot restore と integrity repair は適用と同じ transaction で（workspace は Ready のまま）、新しい epoch を作る（S6-4）。どれも次の turn の読取より前に epoch が進むので、それまでの履歴は全部外れる。適用の時点で準備から送信までの間にある turn は、create と claim での epoch の再確認（Mandatory defenses）で止める（§8）。
  - Body を含む snapshot restore は、project の tree_nodes を消してから入れ直すので、既存の chat session の node_id は NULL になる（S6-4）。その session では capture が作れず、生成そのものができない。restricted の下では renderer の汎用 SQL が拒否され、既存の session の node_id を書き換える Native の製品の writer も無いので、session を Scene に束縛し直せるのは、unrestricted の間の renderer の Drizzle か DB ファイルの直接編集に限る。束縛し直しても、restore の前の履歴は epoch で外れる（Scene の incarnation が新しくなれば、それでも外れる）。この経路では capture の段階で止まり、epoch の比較まで届かないことがあるので、epoch の防御は、epoch 以外が一致したまま epoch だけが進む状況（Body を含まない scope の snapshot restore か integrity repair）と CurrentQualifier の単体の試験で確かめる（受入れに加えるもの）。
  - epoch の理由は問わず、epoch が進めば外れる（integrity repair は reason `migration` の epoch を作る。manual-rebuild なども同じ。保守的な扱い）。
  - import は新しい project ID か新しい workspace を作るので、旧い履歴とは一致しない。今後、同じ project ID と workspace に戻す import や restore を作るときは、Ready の前か、適用と同じ transaction で epoch を進めることを条件にする。
  - epoch の無い project は unavailable とする。D-final の Revision 入力は Freshness に epoch を要するので、通常は epoch が無いことはない。
- 有効期間：作成から 30 日とし、この行で決める。長い執筆期間に同じ Scene の会話を続けられる長さで、再資格化の後ろの歯止めとする。どの過去の turn を使えるかを決める履歴 lineage の規則で、K1b の対象（どれだけ読む・待つ・保持するか）ではない。K1b の history の行の「期限」は 1 turn の処理の期限で、これとは別のもの。
  - 作成時刻：attempt の行の created_at_ms と文脈の eligibleUntilMs（＝created_at_ms＋30 日）は、`create_attempt` の transaction の中で Native が一度だけ読んだ時計の値から決める。今の `FinalDispatchRequest` は作成時刻と期限を coordinator の値として運び、`create_attempt` は created ≥ 0 と expires > created しか確かめない（S6-4）ので、handoff の値は使わない。DT-2 の owner は現状この値を保存する（nir1_generation_owner.rs:707-708 (fc8786e9)）ので、この規則は DT-2 のコードの変更を要し、担当は「critical path への影響」の「追加の作業」の (3) である。attempt の行の expires_at_ms は送信用の handle の期限で、history には使わない。
  - 判定：今の時刻が［created_at_ms, 判定の終わり）の外なら除外する。判定の終わりは、保存した eligibleUntilMs と、created_at_ms＋その時点の有効期間の早い方とする（有効期間を短くしたとき、旧い attempt にも効かせるため）。時計が作成時刻より前に戻っている場合も除外する。
  - 変更：短くするのは integrator の技術判断で行える（正例の受入れを保つ範囲。理由を作業記録に残す）。長くするには新しい draftRef の確認が要る。値の選択肢は「選択肢と推奨」に示す。

### 8. 除外と turn の停止

| 状況 | 扱い |
| ---- | ---- |
| 候補ごとの不一致、stale、unknown、不完全、unsupported、Pending、有効期間の切れ、identity や epoch の違い。legacy（v1）の行、文脈の無い attempt、未知の版の文脈 | その候補と全子孫を除外する。独立した枝は残す。turn は止めない（legacy の行の型付きのエラーも、この行の除外の理由として扱う） |
| 今回の軸のどれかが unavailable（storyTime か viewpoint。対象 Scene が mapping に無ければ readingOrder、storyTime、auto も。今の D-final では後者は A3 で先に止まる） | 履歴をすべて除外し、turn は履歴なしで続ける（今回の turn 自体は有効なため） |
| 1 turn の予算の枯渇 | 検証を終えていない候補を除外し、検証を終えた独立の候補は残す。turn は続ける（K1b の表、post-B §10.3）。session の attempt の列挙（§6）を読み切れないときは、どの候補も検証を終えていないので、その turn は履歴なしで続く |
| slot を足すと binding_json が 64 KiB を超える | 文脈なしの attempt を作り、送信は続ける（§2）。その attempt は history に使わない |
| claim の COMMIT の前の turn の取消（利用者の取消は結束した入口を通す。sender の destroyed や window の close などの取消を含む）、今回の turn の準備から claim の COMMIT までの間の失効（workspace と lifecycle、D2a の permit と caller epoch、route。current-turn の capture が current でなくなったこと〔取消、新しい user 行による superseded〕、対象 Scene の Scope binding の token の変化、restore epoch の変化。DB の状態は `create_attempt` と claim の transaction の中で確かめる）、最終 payload の不一致、DB の読取のエラー（型付きの unavailable でないもの） | turn 全体を止め、送信しない。create の前なら attempt を作らない。claim で分かったら送信していない terminal を一度だけ書く（native-generation-receipt）。部分的な履歴で続けない（post-B §10.3）。claim で止めた attempt の Human は、次の turn で、送信して失敗した attempt の Human と同じく §6 の規則 1〜4 で判定する（利用者の取消なら、結束により capture が cancelled なので外れる。利用者が取り下げたのではない取消なら、capture は current のままで、規則 1〜4 で判定する） |
| claim の COMMIT の後、送信の開始判断の前の turn の取消（owner の取消の flag を立てるもの。利用者の生成の取消の結束した入口、sender の destroyed、window の close など）と、DB の外の authority の失効（profile の permit、route、workspace、Ready の binding、lease。DT-2 の `revalidate` と開始判断） | 送信しない。送信していない terminal を一度だけ書く（DT-2 の pending start）。開始判断の後の取消は DT-5 が扱う（送った bytes は戻らない） |
| claim の COMMIT の後、送信の開始判断の前に起きた DB の状態の変化（対象 Scene の Scope binding の token、restore epoch、新しい user 行による superseded、owner の `cancel()` に束ねていない書込みによる capture の取消） | 止めない（残余。Mandatory defenses の「COMMIT の後の窓」と Out-of-scope attacks）。開始判断は DB の状態を読まないので、旧い token と epoch の下で組んだ request が 1 回送られうる。history の資格は壊れない（次の turn が、記録した token と epoch を今の値と比べて変わった候補を外し、取り消された capture の Human を規則 2 で外す。superseded になった Human は規則 1〜4 で判定する） |

除外と停止の理由は閉じた集合のコードで返し、本文などの平文を含めない（post-B §4.4）。利用者への表示（例：「POV が未設定のため履歴を使えない」）は DD-1 で決める。

### 10. 失効

| 変化 | 起きること（既存の writer の同じ transaction） | history への効果 |
| ---- | --------------------------------------------- | ---------------- |
| chat の行の編集、削除、同じ ID の再挿入 | message version の invalidated が 1 になる | その version と、それを入力に持つ attempt の子孫が外れる。戻らない |

### 11. 数値（1 turn の予算は K1b、有効期間はこの行）

- 1 turn の予算は、確認済みの `nir1-defensive-resource-limits`（K1b）の規則に従い、integrator が HC-1a の実測（長い chain、diamond、fan-out、欠損、循環）から選んで、PR と作業記録に残す。厳しくするのは自由で、merge の後に緩めるには再確認が要る（K1b の規則 6、7）。C-query の 512 と 100 ms は流用しない（post-B §10.2）。
- 予算の対象：1 turn で読む attempt（session の attempt の列挙を含む。§6）と候補の数、node、edge、資格の ref（typed N/A を含む）、参照の bytes、読む本文の bytes、SQL の VM steps、1 turn の期限、busy の待ち、project authority の行（HP-1）。
- HC-1a の実測には、1 attempt の資格 ref が 1,300 件を超える場合（DF+-a の後は最大 1,544 件、資格行で約 200 KB。S6-1）と、Revision の多い turn が続く session を含める。
- 超えたときの扱いは §8 のとおり。
- history の有効期間（30 日）は K1b の対象ではなく、この行で決める（§7）。短くするのは integrator の技術判断、長くするには新しい draftRef の確認が要る。
- slot の大きさ（モデルで history の slot が最大 1,893 B、durable identity の slot が 194 B）は field の集合で決まるので、HS-1 が実際の型で測って試験で固定する。binding_json の 64 KiB は既存の値で、この行では変えない。

Required confirmation evidence is the exact statement: `I confirm draftRef nir1-d2b-history-mapping-proposal/1 for contractId history-reauthorization.`

- この行が止めているもの：DF+-a、HS-1、HC-1a／b、DI-1b／c（計画の K4 行）。critical path「K4・K5 → DF+ → DT-5／HC-1 → DI-1 → DD-1 → PUB-L」の起点の一つで、Session B では K2 と並んで先に出す。
