## 4. 判断（案）

### DR-RB-1 置き場所と authority

- grimodex-db に表 3 本を置く。名前は仮。
  - `session_work_plans`：`plan_id`、`project_id`、`chat_session_id`、`status`（`active`｜`closed`）、`version`、時刻。
  - `session_work_tasks`：`task_id`、`plan_id`、`project_id`、`position`、`title`、`criterion`（任意）、`expects_write`、`status`、`status_reason`、`done_by`（`agent`｜`author`）、`version`、時刻。
  - `session_work_task_links`：`task_id`、`kind`（`agent_run`｜`ai_audit_execution`｜`chat_message`｜`tool_call`）、`ref_id`、`effect`、`outcome`、時刻。本文を持たない。
- 唯一の正本は Native の SQLite（ADR 007 §2・§4）。会話の表への FK だけを持ち、作品の表への FK は持たない。書くのは typed N-API（main 専用）だけで、generic SQL は通さない（A3 の DR-A3-1 と同じ形）。Mastra の thread metadata には置かない。
- 会話ごとに `active` な plan は 1 つ。単発の質問では plan を作らない。作るのは、複数の手順、受け入れ条件、複数の書き換え、承認待ち、サブエージェント、会話をまたぐ継続、作者の明示のどれかがあるとき（Write-Safety Roadmap の Gate C の引き継ぎ事項）。
- Project 側の Work（ADR 012）はこの表に載せない。将来 Project 側の型を作るときに、型の対応を決める。
- すべての手順が `done` か `cancelled` になった plan は、main が自動で閉じる。作者の片付けを要らなくするため。
- 未完了の手順が残る plan は自動では閉じない。作者は 1 回の操作で plan ごと閉じられる。放置した plan に新しい依頼の手順が混ざることは残る（出口条件「恒常的な手作業の片付けを要らない」に対する残り）。

**保存する内容と削除**（保存の範囲の拡大。利用者の回答は第 10 節）

- 保存する：手順の短い題（上限 200 字）、条件（任意、上限 500 字）、状態と理由の短い文、順序、版、時刻、参照の ID。
- 保存しない：作品の本文、tool の結果、承認の中身、Task Grant（DR-RB-6）。
- 題と条件は AI が書く文なので、作品の内容（人物名や展開）が写りうる。
- 会話と project の削除で cascade。
- 写し：自動の backup、復元の前の退避、migration の前の snapshot に残り、復元すれば戻る。作品の ZIP の書き出しにも、会話と同じく入れる（利用者の回答。選んだ選択肢の説明の原文は「写しに残し、会話と同じく書き出します。書き出しと取込みの作業が増えます。」）。取込みで読み戻す形は、実装で詰める（第 9 節）。
- 作品のスナップショットを復元しても、手順は戻らない。`done` の手順の書き換えが作品に無い状態になりうる。画面は「適用した」と「今の作品にある」を分けて書く（ADR 007 の不変条件 15）。

### DR-RB-2 状態と、誰が変えられるか

状態（`WorkTaskStatus`）：`ready`、`in_progress`、`blocked`、`review`、`done`、`cancelled`。

| 遷移 | AI | 作者 |
| --- | --- | --- |
| 手順の追加・並べ替え | できる | できる |
| `ready` ⇄ `in_progress`、→ `blocked`・`review` | できる | できる |
| → `done` | DR-RB-3 の条件を満たすときだけ | できる |
| `done` → 戻す | できない | できる |
| → `cancelled` | `criterion` が無く `expects_write` が偽の手順だけ | できる |
| `cancelled` → 戻す | できない | できる |
| `title`・`criterion` の書き換え、手順の削除 | できない | できる |
| `expects_write` を真から偽に | できない | できる |

- AI が自分の条件を弱められないこと（ADR 007 の不変条件 12）は、この表を main が強制して守る。AI の申告や prompt の指示に頼らない。
- 作者が手で `done` にする操作は、書き換えの承認ではなく、何も書き換えない。画面は「作者が完了にした」と分けて出す（`done_by`）。
- `criterion` を書けるのは、手順を作るときの AI と、作者の編集。
- 1 つの Run が同時に進める手順は 1 つ。plan の中では、親の Run が進める手順と、待ちの子の Run が持つ手順が、ともに `in_progress` になりうる（DR-RB-8）。
- すべての更新は `version` を条件にする。古い版の更新は拒む（Roadmap の出口条件）。
- 承認待ち・質問待ちは、手順に別の状態として持たない。A3 の Interaction から導いて表示する。

### DR-RB-3 完了の判定（DR-ST-3 の実装の形）

「書き換えを伴う手順」を、AI の申告だけで決めない。

- main は、tool の呼出しを受け取った時点で、その呼出しを出した Run が進めている手順に結び付けて `links` に書く。子の Run は切り出した手順に固定する（`agent_runs.task_id`。親の Run が手順を移るときの記録は、呼出しごとの `links` が持つ）。`effect` は manifest から取る。
- 手順を扱う tool（`get_session_plan`・`update_session_plan`・`request_task_grant`）は、結び付けの対象にしない。結び付けると、読むだけの手順まで書き換えや提案の扱いになるため。
- `expects_write` を真にできるのは、手順を作るときの AI の申告、後からの AI と作者の操作、main（結び付いた呼出しに `mutate`・`destructive` があったとき）。真にした後、AI は下げられない。
- AI が `done` にできる条件：
  - `expects_write` が偽。
  - `expects_write` が真なら、結び付いた書き換えが 1 件以上確定していて、承認待ちや結果不明の呼出しが残っていない。
- `stage`（提案）だけで終わった手順は `review`。提案が本文に適用されたら（作者が「適用」を押しても、作品ごとの自動適用でも）、main が `done` にする。適用の経路に手順の参照を通すのは、Release B の実装に含める。
  - （追補）「適用した」の根拠は、提案の `accepted` の記録でなく、本文の保存の成功にする。今は本文の保存より前に `accepted` を確定し、保存に失敗しても戻さない（[本文の適用の起案](prose-apply-atomic-draft.md)の第 1 節。自動適用と手動の「適用」の両方）。同じ起案の段 1（自動）と段 2（手動、未設計）が入った後は、新しい経路の `accepted` を根拠にできる。
- 拒否・失敗した書き換えしか無い手順は `done` にできない。
- 限界：
  - AI が「書き換える手順」と申告せず、何も呼ばなければ、AI はその手順を `done` にできる。画面は `done` の数と、適用した書き換えの件数を分けて出す。
  - 手順に結び付けずに行われた書き換えは、この判定に出ない。その書き換えも承認の仕組み（DR-GA-3、DR-RB-6）は通る。

### DR-RB-4 AI の tool

| 名前（仮） | 内容 | 分類 |
| --- | --- | --- |
| `get_session_plan` | 今の plan と手順を返す | `read / none` |
| `update_session_plan` | 手順の追加・並べ替え・状態の変更（DR-RB-2 の範囲） | 名指しの新しい分類／`none`（作品の正本は変えない） |
| `request_task_grant` | これから行う書き換えの範囲を示して、作者の承認を求める | 名指しの新しい分類／`none`（承認の要求を作るだけ） |

- 使えるのは親の turn の agent だけ。調べ物などを任せる sub-agent には渡さない（ADR 007 の不変条件 14）。待ちの手順を続ける子の Run（DR-RB-8）は同じ agent の続きとして扱い、自分の手順に限って使える（案）。
- 経路は Mastra の経路だけ（43 本が 46 本になる）。legacy の経路には足さない（前提に MP-6・MP-9 があるため。起案者の読み）。**帰結**：今の製品の経路は legacy なので、この案では、製品で使えるには Mastra の旗 L も開いている必要がある。
- plan の内容は、毎 turn の自動の注入にしない。AI は `get_session_plan` で読む。active な plan がある会話では、「未完了の手順がある」の 1 行だけを案内に足す。DR-ST-9 の「要約から独立して注入する Task Contract は作らない」に合わせるため。
- 手順を扱う道具だけを名指しした分類を、ADR 008 の追補で足す（利用者の回答）。画面操作の `ui` は 3 本に限るので使わない。名前は追補で決める。`ui` と同じく、TS と Rust の build の検査で名指しの道具に限る形にそろえる（Mastra の担当の提案）。`get_session_plan` は `read / none`（起案者の読み）。

### DR-RB-5 F0-lite-B の 3 つの型

- `WorkTaskStatus`：DR-RB-2 の 6 値。
- `TaskContractSnapshotV1`：`{ schemaVersion: 1, planId, taskId, taskVersion, title, criterion?, expectsWrite }`。DR-ST-9 の後は、目的や制約の欄を持たない。承認の要求と完了の判定が「どの版の手順か」を固定するための内部の写しで、AI に毎 turn 送らない。
- `AnalysisReadBasisV1`：`{ consistencyModel: "capture-on-first-read", runId, entries: AnalysisReadBasisEntryV1[] }`。Entry は A3 の型を束ねるだけ。DR-RB-6 の版の照合に使う。

### DR-RB-6 Task Grant

- 対象は `mutate / task-scope` の tool だけ。`destructive` は対象にしない。
- 範囲：plan、project、会話、操作（tool の名前）、対象。対象は、更新なら AI が挙げた項目の ID の一覧。
  - （追補・訂正）元の版は続けて「作成なら項目の種類」と書いていた。これは起案者の案で、利用者には示していない。第 10 節の問い 2 の問いと選択肢が挙げたのは「書き換え」で、種類で区切る形は、選ばれなかった「操作の種類ごと」に近い。
  - （追補）利用者の回答までは狭い側にする（起案者の暫定で、決定ではない）。次は範囲に入れず、1 件ずつ確認する：作成する呼出し（`create_codex_entry`・`create_foreshadow`・`create_snippet`・`create_event`、作成を含む `apply_ai_tree_plan`）と、どの項目の書き換えに数えるかを決めていない操作（`stamp_scene_event`・`unstamp_scene_event`・`set_event_participants`・`add_event_relation`）。扱いは実装の前に伺う（第 9 節）。
- 付与：AI が `request_task_grant` で範囲を示し、作者がカードで承認する。承認の仕組みは Gate A と同じ（DR-GA-3）。範囲を広げるのは新しい承認（ADR 007 §6）。
- 実行のとき、main が呼出しごとに照らす：plan が active、project・会話・操作・対象が範囲の中、AI の利用方針、取り消されていないこと。そのうえで一回限りの Capability を出す。外れたら個別の承認に回す。
- 版：作者が見ないまま、並行の編集を上書きしないための照合を置く。形は 2 案で、**実装の前に利用者に伺う**。
  - 案 A（起案者の案）：base は「この Run で AI が最後に読んだ版」（`AnalysisReadBasisV1`）。読んでいない対象、版が分からない対象、読んだ後に版が変わった対象は個別の承認に回す。今の Mastra の経路では読んだ版が分からない（K7）ので、**MP-9 の印に版か内容の hash が入るまで、まとめて任せる承認は効かない**。
  - 案 B：承認の要求を作る時点で、一覧の項目の版を main が固定する（DR-GA-3 と同じ形）。MP-9 を待たない。AI が読んだ後から要求の前までの編集は拾えない。
  - どちらも、照合は実行中の Run の中だけで使い、終端した Run の basis は使わない。固定した版は Grant と同じく memory に置く。自分の書き換えの後の版は main が更新する。
  - （追補）版の照合は書き換えの対象についての条件。作成を範囲に入れると決まった場合も、作成には掛けない（起案者の案。上書きするものが無いため）。案 A の「版が分からない対象は個別の承認に回す」は、作成には当てない。
- 失効：作者の取り消し、Stop、plan の終了、AI の利用方針の変更、project・workspace・profile の切替、アプリの終了（利用者の回答：停止や再起動で解除）。
- 保持：**main の memory だけに置く**。再起動の後は効かず、同じ範囲を示して承認し直す（利用者の回答。DR-A3-14「保存した承認は認可に使わない」とも合う）。何を承認したかの記録は `links` に残すが、認可に使わない。
- 範囲の中では、回数の区切りで止めない（Roadmap の出口条件）。書き換えは今の Undo で戻せる形で行い、画面に件数を出す。

### DR-RB-7 止まったときは、要約して自動で続ける（DR-ST-5 の条件 2）

利用者の回答（第 10 節）：「要約して自動で続ける」。起案の推奨（「続行」を出して止まる）とは違う。

- 回数の上限の撤廃は、停止が効く経路から（DR-ST-5 の条件 1）。さらに、自動の続行の歯止めが決まるまでは撤廃しない（起案者の条件。回数の上限も予算の停止も無いと、止めるのは Stop だけになるため）。
- 入れる経路と旗：Release B の旗の内側で、Mastra の経路に入れる（案）。問いは今の製品（legacy）の挙動で説明したので、legacy にも入れるかは実装の前に伺う。
- tool の結果の予算（`limit_tokens`）と文脈の残りが尽きる前に、古い応答と tool の結果を要約に畳み、同じ Run で続ける。予算の割合そのものは変えない。
- これは DR-ST-5 の「長い読み取りの turn はこの予算で止まる」を変える（判断記録の DR-ST-5 に追記した）。
- 要約の後、AI は手順の一覧を `get_session_plan` で読み直す。手順は自動では注入しない（DR-ST-9）。
- Task Grant と読んだ版は main が持ち、要約の内容に依らない。
- 要約はもとの会話の送り先と同じ model に作らせる。要約の保存は、今の会話の要約の扱いを超えて足さない（案）。
- 歯止め（案。閾値は実装の前に伺う）：停止はいつでも効く。手順が 1 つも進まないまま要約が続いたら、本文と手順を残して「続行」を出して止める。費用と時間の上限は未決（第 9 節）。
- 要約に失敗したら、本文と手順を残して「続行」を出す。
- 要約の方式は、MP-9／10 の圧縮との関係を Mastra の担当と詰める（K10）。
- 途中再開との関係：A3 の途中再開は、tool の結果ごとに版と可視性を照らして本文を置き換える（DR-A3-6）。要約に畳んだ部分はそのままでは照らせない。条件（A3 の担当の指摘、2026-11-28）：
  - 要約に畳んでも、読んだ source の一覧（basis）は捨てずに引き継ぐ。「hidden にした項目を読んでいた実行は再開しない」の判定に使う。
  - 要約の本文は source ごとに置き換えられないので、版の変わった source があれば要約ごと外して読み直す。
  - 要約を途中再開の状態に残すのは保存の中身の変更で、利用者の確認の対象。
  - 終端の理由（`limit_tokens`・`context_window_exceeded`）の使い方も変わる。

### DR-RB-8 承認や質問を待つ間も、ほかの手順を進める

利用者の回答（第 10 節）：「ほかの手順は進める」。起案の推奨（全体を止める）とは違う。画面の試作と同じ挙動になる。

- 方式（案）：待ちが生じた手順を子の Run に分ける。2026-11-27 の A3 の担当との合意と同じ形。親は `running` のまま、待つ子だけが `waiting_user`・`waiting_approval` になる。
- 同時に待てる承認・質問は 1 件のままにする（案。A3 の「root の Run ごとに pending は 1 件」を変えない）。2 件目が要る手順は、1 件目が解けるまで待つ。ほかの手順は進む。
- 同じ手順の中では、待ちが解けるまで先へ進まない。待っている手順に依る手順も進めない。
- 子の Run が使える権限は、親の Task Grant の範囲の中だけ（ADR 007 の不変条件 14）。
- Stop は親と子の両方を閉じる。
- （追補）A2 の確定版（DR-A2-6）では、承認・質問の待ちの間も turn の枠を持つ。「ほかの手順は進める」（利用者の回答）を満たすには、Release B の版で枠の持ち方も決める必要がある（K11）。決まっていないのは方式で、進めること自体は回答済み。
- A3 の schema（今実装中の版）は変えない（A3 の担当の判断、2026-11-28）。Release B の版で次を変える（同じ担当の指摘）。
  1. 「会話ごとの active な Run は 1 つ」の部分 unique index の述語（例：root の行だけに掛ける。子の数の上限は別に決める）。pending の index は、上の案なら変えない。
  2. Native の開始の検査（同じ会話に終端でない Run があると拒む）と claim の検査。子を作る関数を足す。
  3. 回収・claim・破棄・終端の単位。親が終わるときの子の扱い。待ちだけが残ったときの親の状態。
  4. Roadmap の「root ごとの pending は最大 1 件」は、上の案なら変えない。
  5. `status`・`terminal_reason` の語は足さずに済む見込み。語を足す場合は表の作り直しになるので、実装の前に確かめる。
- 子の行と親子の紐付けは保存の追加で、1〜3 は A3 の決定の変更。**形が決まった時点で利用者に確認する**。そのとき A3 の判断記録の追補と、脅威モデルの「同じ実行の取り合い」の見直しを A3 の担当と相談する。

### DR-RB-9 画面

### DR-RB-10 旗と、開けるまでの段

## 5. owner と lifecycle（GDX-PRECHECK-001）

| 経路 | owner | 始まり | 停止・失効 | 失敗と再起動 |
| --- | --- | --- | --- | --- |
| plan・手順の書込み | main（typed N-API） | tool の呼出し、作者の操作 | Stop の後の tool の書込みは拒む | 版が違えば拒む。書けなければ AI に失敗を返し、手順の表示は前の状態のまま |
| 呼出しと手順の結び付け | main の turn owner | 呼出しを受け取った時点 | turn の終端 | 書けない場合は、その手順を AI が `done` にできない |
| Task Grant | main（memory） | 作者の承認 | DR-RB-6 の失効 | 再起動で消える。復元しない |
| 子の Run | main の turn owner | 手順が承認・質問の待ちに入る時点 | Stop・権限の失効で親子とも閉じる | 回収・破棄・終端の単位は A3 の担当と詰める。詰まるまで途中再開しない。（追補）Mastra の経路は、MP-9 と再入の実証が済むまで途中再開できない |
| 自動の要約 | main の turn owner | 予算か文脈の残りが尽きる前 | Stop で止める | 失敗したら本文と手順を残して「続行」 |
| 帯の表示 | renderer | 会話を開く | 会話の切替で取り直す | 読めなければ帯を出さず、理由を出す |

## 6. 脅威モデルへの影響（draft。利用者の確認までは確定しない）

- 信頼する：作者の操作、main、Native の DB の authority。
- 信頼しない：AI の出力（作品の本文や外部の内容に仕込まれた指示を含む）、renderer からの認可の主張、保存した手順の文（後の turn で指示として扱わない）。
- 対象の攻撃と防御：

| 攻撃 | 防御 |
| --- | --- |
| AI が条件を緩める、手順を消して完了に見せる | DR-RB-2 を main が強制 |
| 書き換えていないのに「適用した」と見せる | 書き換えると申告した手順と、書き換えを呼んだ手順は、確定が無いと AI は `done` にできない（DR-RB-3）。画面は `done` と適用の件数を分ける。申告しない手順は残る |
| 仕込まれた指示が広い Grant を求める | 付与は作者の承認だけ。範囲はカードに列挙。`destructive` は対象外 |
| Grant の下で、作者の並行の編集を上書きする | 読んだ版との照合（DR-RB-6） |
| 手順の文を介した持続的な指示の注入 | 自動の注入をしない。長さの上限。tool の結果はデータとして扱う |
| renderer や generic SQL からの書換え | typed の経路だけ、D2a の台帳に追加 |
| 要約に仕込まれた指示が残る、要約で条件が落ちる | 要約はデータとして扱う。権限は要約に依らない。手順は読み直す。残る恐れは利用者に示した |
| 子の Run が親より広い権限を持つ | 親の Grant の範囲だけを渡す |
| 自動の続行で費用が膨らむ | 停止、進まないときの停止。費用の上限は未決 |

- 対象外：OS の層の改ざん、写しのファイルを直接書き換える攻撃者。
- 受入れ（負の試験）：条件の緩和、古い版の更新、範囲の外の呼出し、失効した Grant、別 project・別会話、手順を扱う道具の sub-agent からの呼出し、親より広い子の Run が、それぞれ拒まれる。

  - 旗 L を開ける前の事情（Mastra の担当の回答、2026-11-28。条件の関数と、問 36 の原文は読んで確かめた）：旗 L を開けると、条件を満たす turn は Mastra の経路に替わる（`src/application/chat/chatTurnMastraEngine.ts` の `shouldUse`。利用者が経路を選ぶ設定は無い）。その turn では、途中再開も、再起動や 30 分の中断の後の承認の出し直しも使えない。旗 L を開ける条件（Mastra 移行計画の MP-13）に途中再開は入っていない。A2 の範囲を確定した利用者の確認（確認の記録の問 36）の説明「30 分で中断し、「続ける」で確かめ直してカードを出し直せます」は、経路を限っていなかった。
  - 旗 L の前にどこまで揃えるかは、Mastra の担当が旗 L の確認（U-16）と合わせて伺う予定。SessionTasks は旗 L の分を伺わず、その回答の後に残る分だけを伺う（回答しだいで、この点は要らなくなる）。
- （追補）まとめて任せる承認と作成の扱い（Mastra の担当の指摘、2026-11-28）。実装の前に利用者に伺う。伺う担当は SessionTasks。
  - 作成を範囲に入れるか。入れるなら何で区切るか（項目の種類、件数、作る予定の名前など）。
  - 作った項目への続きの操作（作った出来事の参加者の設定など）を、同じ承認に含むか。
  - `stamp_scene_event`・`unstamp_scene_event`・`set_event_participants`・`add_event_relation` を、どの項目の書き換えに数えるか。作成と書き換えが 1 回の呼出しに混じりうる `apply_ai_tree_plan` の扱い。

- （追補）次は起案者の案で、決定でも利用者の確認でもない（2026-11-28 に M4 の下書きの質問へ返したもの。DR-RB-2・3 の本文は変えていない）。実装の担当が決め、保存する形は実装の前に利用者に伺う（問 34）。
  1. 提案は `mutate`・`destructive` でないので `expects_write` が真にならず、DR-RB-3 の文面では、提案を作っただけの手順を AI が `done` にできる。未適用の提案がある間は、`expects_write` に関わらず AI の `done` を拒む。
  2. 戻り先は、`blocked`・`review` から `in_progress`、作者が戻す `done`・`cancelled` から `ready`。同じ状態への遷移は拒み、同じ要求の再送は書込みの層で扱う。
  3. main が `done` にするのは `review` から。提案の結び付きがあり、適用が 1 件以上で、未適用の提案・承認待ち・結果不明が 0 のとき。適用の確定は状態に関わらず記録し、`review` に入る時点でも評価する。

  5. 作者が却下した提案は解決済みとする。確定した書き換えか適用が 1 件も無ければ `done` にしない。
  6. 決めていないもの：`review` に移すのが AI か main か（AI が移さないまま Run が終わると、適用されても `in_progress` のまま）。版が古くなって `proposed` のまま残る提案の扱い。直接の書き換えと適用した提案が混じり `review` でない手順は、3 のままだと AI も main も `done` にできない。

## 10. 利用者への問いと回答（2026-11-28、AskUserQuestion）

問いと選んだ選択肢は、会話の記録から機械的に写した原文。

### 問い 1（手順の保存）

> Release B は、chat の依頼の「手順と進み具合」を会話の外の新しい表に保存します。保存するのは、AI が書く短い手順文（200 字まで）と条件（500 字まで）、状態、順番、関連する記録の ID です。作品の本文は保存しませんが、手順文に人物名や展開が写ることがあります。会話や作品を消すと一緒に消えます。この中身で保存するとして、backup などの写しはどうしますか？

- 回答（推奨と違う回答）：「ZIP 書き出しにも入れる」— 写しに残し、会話と同じく書き出します。書き出しと取込みの作業が増えます。
- 選ばなかった選択肢：「写しにも残す (Recommended)」、「写しでは空にする」

### 問い 2（まとめて承認）

> Release B では「まとめて任せる承認」が入ります（Gate A の問いでそう説明しました）。承認した範囲の書き換えは 1 件ずつ確認せず進みます。削除は含めず毎回確認します。範囲の区切りと、再起動の後の扱いをどうしますか？

- 回答（推奨どおり）：「挙げた項目だけ・再起動で解除 (Recommended)」— AI が書き換える予定の項目と操作を一覧で示し、承認します。一覧の外は 1 件ずつ確認。停止や再起動で解除し、もう一度承認します。
- 選ばなかった選択肢：「操作の種類ごと・再起動で解除」、「挙げた項目だけ・再起動後も有効」

### 問い 3（AI の道具）

> 手順を扱う AI の道具を 3 本足す案です（手順を読む、手順を書く、まとめて承認を求める）。手順を書くのは作品を変えないので確認なしにします（AI が自分の完了条件を緩めたり、手順を消したりはできません）。入れるのは Mastra の経路だけです。今の製品は古い経路なので、使えるようになるには Mastra の経路を開ける必要があります。どうしますか？

- 回答（推奨どおり）：「この形 (Recommended)」— Mastra の経路だけ。手順の書き込みは確認なし。
- 選ばなかった選択肢：「今の経路にも入れる」、「手順の書き込みも確認する」

### 問い 4（公開の凍結）

> 公開の直前に 1 回だけ、公開する版を固定して正式な測定をする（凍結）と決まっています。Release B は前提の実装もまだそろっていません。Release B と凍結の関係はどうしますか？

- 回答（推奨どおり）：「凍結の条件にしない (Recommended)」— 凍結の時点で入っていれば旗を閉じたまま含め、間に合わなければ凍結の後に入れます。凍結は Release B を待ちません。
- 選ばなかった選択肢：「凍結の前に必ず入れる」、「凍結の対象から外す」

### 問い 5（待ちの間）

> AI が承認や質問の返事を待っている間、同じ依頼のほかの手順を進めますか？以前の画面の試作では、1 つが待ちでもほかの手順は進んでいました。なお、まとめて承認した範囲の書き換えは、もともと待ちません。

- 回答（推奨と違う回答）：「ほかの手順は進める」— 待ちの手順を別の実行に分けて並行で進めます。保存側の決定を変える作業と確認が増えます。
- 選ばなかった選択肢：「最初の版は全部止まる (Recommended)」

### 問い 6（止まった時）

> 今の仕組みでは、1 回の依頼で読める量の上限に達すると AI が最後に一言返して「続行」ボタンが出ます。文脈が一杯になった場合は送信の失敗になり、そこまでの本文が残らないことがあります。道具の呼び出し回数の上限をなくす条件として、止まったときの扱いを決める必要があります。どうしますか？

- 回答（推奨と違う回答）：「要約して自動で続ける」— AI が自分で要約して続けます。止まりにくくなりますが、要約で条件が落ちる恐れと費用の増加があります。
- 選ばなかった選択肢：「本文と手順を残して続行 (Recommended)」、「今の扱いのまま」

### 問い 7（提案の適用）

> 本文の提案は今、作者が「適用」を押すか、作品ごとの自動適用の設定（既定はオフ）で本文に入ります。この適用を承認の仕組みとして整理する別の作業（Write-Safety の A3）には担当がいません。Release B の「提案が適用されたら手順を完了にする」はここに関わります。どうしますか？

- 回答（推奨どおり）：「今の適用の仕組みを使う (Recommended)」— 別の整理はせず、提案が適用されたら（手で押しても自動適用でも）手順を完了にします。結び付けは Release B の実装に含めます。
- 選ばなかった選択肢：「担当を決めて整理してから」、「作者が手で完了にする」

### 問い 8（道具の分類）

> 手順を書く道具は確認なしと決めていただきました。ただ、道具の分類の決まり（ADR 008）には「作品は変えないが記録は残す」道具の欄がありません（画面操作の欄は 3 本に限る約束です）。実装の時に決まりをどう直しますか？

- 回答（推奨どおり）：「名指しの分類を足す (Recommended)」— 手順を扱う道具だけを名指しした分類を、ADR 008 の追補で足します。
- 選ばなかった選択肢：「提案の分類に入れる」
