## 0. 一枚目：推奨と残る問い

**何を決める案か。** 今の「まとめて承認」の 7 つの条件は、評価データの全件が満たし、何も絞らない。この案は、作者に個別に見てほしい提案を決まった条件で選び、「まとめて承認」の対象から外す。

**推奨**
1. 見せる理由を 4 つ置く（§2）。語りの枠が地の文の出来事でない／語り手が登場人物か不明／重要度が major／試みた・阻止された出来事。
2. 理由が 1 つも付かない提案だけを「まとめて承認」の対象にする。理由の付く提案は一覧の上に寄せ、理由を 1 行で出す。
3. 材料は、保存済みの版がすでに持つ値を読む。新しい保存、送信、AI の呼出しは足さない。
4. 開ける前に、理由の付かなかった提案の中身を作者の目で抜き取って確かめる（§5）。

## 1. 確かめた事実

- 今の「安全」の条件は 7 つで、画面側だけが計算する（`src/features/chronicle/chronicleExtractionStore.ts:239-285`）。見るのは、根拠の一致、actuality が決まっていること、重複の可能性、作者の編集の有無である。【確認済み】
- 「まとめて承認」は、未 review・未取り込み・版あり・7 条件を満たす提案に、承認の記録を 1 件ずつ続けて書く（`src/features/chronicle/chronicleExtractionApi.ts:1913-1938`）。【報告】
- 版に封印された Envelope は、`assertion.payload` に `attribution`、`narrativeFrame`、`actuality`、`significance` を持つ。評価 DB の 884 件と 551 件のすべてに値がある。【確認済み】
- Envelope の `attribution` と `narrativeFrame` は、統合後の観測の先頭 1 件の値である（`src/application/narrative-extraction/chronicleV2Production.ts:494-495`）。評価 DB では、提案 1 件の統合後の観測は全件 1 つだった。【確認済み】
- 値の種類：`narrativeFrame` は `story-world`、`flashback`、`dream`、`reported`、`hypothetical`、`unknown`。`attribution` は `narrator`、`character:…`、`unknown`（`src/features/narrative-extraction/ir/observations/eventOccurrence.ts:22-31`）。【確認済み】
- 評価 DB の値の内訳：枠は story-world 697／428、reported 146／103、flashback 41／20。語り手は narrator 734／444、登場人物 150／106、unknown 0／1。【確認済み】
- 提案の中身（payload）に項目を足すと、Native が未知の項目として拒む（`src-tauri/crates/grimodex-core/src/narrative_ir.rs:1674-1690`）。【確認済み】この案は payload を変えない。
- review の画面は、再起動の後は保存済みの計画から一覧を作り直す。提案を組み立て直さない（`chronicleExtractionApi.ts:1369`）。【確認済み】
- review の一覧に並べ替えは無く、印は「重複の可能性」と「安全一括承認の対象」だけである（`src/features/chronicle/ChronicleProposalCard.tsx:21-48`）。【報告】
- review の画面が版の Envelope の中身を今受け取っているかは確かめていない。受け取るのは digest と版の番号である（`chronicleExtractionApi.ts:283-284`）。【未確認】

## 2. 見せる理由

| ID | 理由 | 条件 | 作者に出す 1 行（例） |
| -- | ---- | ---- | -------------------- |
| R1 | 語りの枠 | `narrativeFrame` が `story-world` 以外 | 「回想の中の出来事です」「伝聞です」 |
| R2 | 語り手 | `attribution` が `narrator` 以外 | 「登場人物の発言の中の出来事です」 |
| R3 | 重要度 | `significance` が `major` | 「物語の大きな出来事です」 |
| R4 | 起こり方 | `actuality` が `attempted` か `prevented` | 「試みたが成らなかった出来事です」 |
| R0 | 材料なし | 版が Envelope を持たない、または値が読めない | 「確かめられませんでした」 |

- 理由は足し算で、1 つでも付けば「まとめて承認」の対象から外れる。
- 今の 7 条件は残す。7 条件に落ちる提案は、今と同じく対象外である。
- R0 は、判定できないときに見せる側へ倒すための理由である。
- 根拠の場面が複数ある提案は、理由に入れない。場面 1 つの抽出では起きず、評価データでも 0 件だった。【確認済み】

## 3. 動作

- 一覧：理由の付く提案を上に寄せる。カードに理由を 1 行で出す。理由の中での順は今のままにする。
- 「まとめて承認」：理由なしの提案だけを対象にする。件数の表示も同じ条件で数える。
- 理由の付く提案の承認・却下・保留は、今と同じ 1 件ずつの操作のままにする。
- 承認と確認を分ける表示は作らない（2026-11-10 の決定）。
- 作者が見送った印は保存しない。印は表示のたびに計算し直す。

## 4. 判定の置き場

- 材料は版の Envelope の値とする。Native が検証して封印した値で、secret だけを外した子の版は 4 つの値を親と同じに持つ（評価 DB の 884 件と 551 件のすべて）。【確認済み】題や根拠を編集した子の版でどうなるかは確かめていない。編集した提案は、今の 7 条件で「まとめて承認」の対象外である。
- 画面側：一覧の表示と件数のために理由を計算する。
- Native：「まとめて承認」の対象の検査（取り込みの規則の下書きの §5 の必須の防御）に、同じ条件を足す。画面側の計算だけに頼らない。
- 新しい保存先は足さない。review の画面が Envelope の値を受け取っていない場合は、読み出しの応答に 4 つの値を足す。これは既存の IPC の応答の項目の追加で、新しい command ではない。【要否は未確認】

## 5. 限界と、開ける前に確かめること

- 4 つの値は、抽出のときに model が付けた分類である。誤りうる。理由なしの提案の中に、作者が見るべきだった提案が混じる割合は測っていない。【未確認】
- 複数の観測に由来する提案では、先頭の 1 件の値しか見ない。場面 1 つの抽出では、評価データの全件が観測 1 つだった。フォルダ単位の抽出では別である。
- 件数は 2 作品（うち 1 作品は AI が書いた原稿）の値である。製品の経路の値ではない。
- **開ける前の確かめ方（案）**：理由なしの提案から 50 件、理由ありの提案から 50 件を抜き、根拠の本文と並べた表にして作者が見る。数えるのは、理由なしのうち「個別に見たかった」件数と、理由ありのうち「見なくてよかった」件数である。合格の線は置かず、結果を見て決める。

## 6. 脅威モデルへの影響（draft）

「まとめて承認」の脅威モデル（取り込みの規則の下書きの §5）に、次を足す案である。確認まで draft とする。

- **範囲内の誤りと攻撃（追加）**：model が、発言や伝聞の中の出来事を地の文の出来事と分類し、理由が付かずに「まとめて承認」に入る。本文に埋めた指示が、その分類を誘導する。
- **効くもの**：承認で開くのは関連場面に出す資格だけである。年表の出来事は secret のままで（取り込みの規則）、年表から AI への秘密と Graph の本文の開示の拒否は変わらない。関連場面に出るのは根拠の本文で、根拠が本文と完全に一致することは 7 条件に含まれる。
- **必須の防御（追加）**：理由の判定を Native でも行う。判定できない提案は見せる側に倒す（R0）。
- **受入れへの影響**：理由の付く提案が「まとめて承認」で承認されないこと、Envelope の無い版が対象に入らないことを試験で固定する。
