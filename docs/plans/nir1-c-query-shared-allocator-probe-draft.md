## Purpose and non-claims

The existing observer counts Rust requested bytes after allocation, separately samples SQLite, and uses baseline subtraction. It cannot reserve a shared quota before allocation or distinguish a baseline free from a query free. The diagnostic helper currently creates `Nir1GraphRequest` before its window, samples before reader close, and does not cover final observation/frame construction.

Q2 was Available in 4.637208 ms; Q513 was Unavailable in 5.040748 ms before A3 evaluation (receipts `b3b5493e8`, `bfeb2f555`). Neither is product acceptance, an attributable simultaneous total, or proof that Q513 hit the record limit. Functional checks subsequently passed (Rust 38 default / 47 diagnostic-feature, IPC refusal 2, real Native refusal 1; production 8 ms test ignored). These do not resolve the resource Hold.

The proposed experiment asks only: **can one isolated diagnostic process make Rust and SQLite share a pre-allocation admission counter and fail safely when it is exhausted?** It does not replace the conservative material reservation, change canonical qualification, select a product worker/baseline/budget split, or establish the product's 2,097,152-byte bound. The minimum useful outcome is a verified diagnostic rejection, not another claimed PASS.

## Accounting and lifetime rules

1. Every intercepted block carries immutable origin information and its allocation layout. Blocks born before the epoch are baseline blocks; freeing them never credits the query. Their bytes and the /3 process ceiling are reported separately, without a product allowance claim.
2. For managed Graph cases, after registered `READY`/`CONTINUE`, start one irreversible epoch **before constructing/copying query request fields**. It covers every subsequent intercepted allocation on every thread, not only the query call: source snapshots, response and observations, reader/participant teardown, fixed-frame construction/write, final drops and exit. There is no reset, renewed quota, end-at-snapshot, or exclusion for diagnostic reporting. Legacy observer timing stays unchanged.
3. Use a checked, allocation-free atomic reservation before calling `System`. Pending reservations count against the same ceiling; failed system allocation releases only its own reservation. Invalid size/alignment, integer overflow or accounting invariant failure fails closed. Preserve Rust alignment/zeroing and SQLite `xSize`/`xRoundup` contracts; no fabricated pointers or exception unwinding through C callbacks.
4. Growing `realloc` admits a full replacement while the old allocation remains charged, then copies and actually frees the old block before releasing its charge. Failure preserves the old pointer/content/charge. Reallocating a baseline block after epoch start charges the entire new query block, not its delta; freeing the old baseline block gives no query credit. In-place shrink may retain capacity and its full charge, never claim memory was freed merely because logical length shrank. Deallocation credit follows the real system deallocation.
5. SQLite quota/system-allocation failure returns NULL with the original allocation intact where required. Propagate SQLite failure as Unavailable/error, never partial Graph. If subsequent Rust error handling cannot allocate, `_exit` remains the terminal path. Rust quota rejection exits 90 before making that allocation; system failure exits 91; invariant failure exits 92. These are fixed diagnostic exit categories, not proof of an unobserved memory peak or reason for a canonical query rejection.
6. Keep the epoch armed through actual process exit. Snapshot fields describe their named instant only; a frame sent before exit cannot attest later frees or a whole-lifetime observed peak. A nonzero current counter at the final frame is not fabricated into zero. The surviving manager and parent establish terminal release; no final measurement frame is required or adopted after the forced-exit case.
