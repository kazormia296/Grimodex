### 打ち手 4：関係の呼び名を結ばない

- 何が変わるか。「姉ちゃん」「ダンナ」「おじいさん」のような語は、新しい人物の提案にならない。候補画面に別名ボタンも出ない。「さん」「ちゃん」を外して名簿の人に近づける処理も、語の一部だけが当たる候補も、この語には出さない。作者が自分で別名に入れた語は、今までどおり結ばれる。
- 手間がどう減るか。呼び名が原因の誤った提案と、誤って全体の別名にする操作が減る。減る量は、呼び名が実際に提案へ出ている数による。まだ数えていない。
- 危険。呼び名がそのまま名前になっている人物の新規作成の提案が出なくなる。候補画面の「+」では作れる。候補画面で AI が別名を勧めても、呼び名の語ではボタンが出ない。その別名は Codex の編集画面で足す。落とした件数と表記は、まず診断に残す。画面に出すかは作者に伺う（Q2）。

### 打ち手 2：完全一致の既存への結び付けを一括承認できるようにする

- 何が変わるか。次の条件を全部満たす結び付けは、まとめて承認できる。名前または別名に完全に一致する。該当が 1 つの Entry だけ。結び先が人物の Entry。語の一部だけが当たる他の Entry が無い。別名の追加も関係の依存もない。承認を実行するとき、その時点の Codex でも条件を確かめ直す。今は「新規作成」だけがまとめて通る。カードには「既存 · K0001」ではなく、結び先の名前を出す。
- 手間がどう減るか。名簿を整えるほど増えていた「1 件ずつ確かめる」件が、一括で通る。
- 危険。読まずに通る範囲が広がる。同姓の別人が名簿に 1 人だけいると、原稿の別人を結び先の確認なしに結ぶ誤りが入りうる。Codex の行は書き換わらない。関係・Phase の端点になる結び付けは一括から外す。
- 危険。承認してから Apply までのあいだに、結び先の Entry を別の画面で編集すると、Apply が丸ごと失敗する。今の 1 件ずつの承認にもある。一括で件数が増えると目立つ。対策は Q4 で伺う。
- 未確認。結び付けが保存された後に誰に読まれるかを、まだ確かめていない。確かめるまで着手しない。

### 打ち手 1：作者が選んだ結び先の表記を、確認つきで別名に残す

- 何が変わるか。review で結び先を選んだ表記を、「『X』を別名にも足す」の 1 行で確認して、その Entry の別名に残す。別名は作品全体のすべての場面で効く。次の抽出から、同じ表記は完全一致で自動に結ばれる。結ばれた提案の承認は、引き続き要る。打ち手 2 と組むと、以後は一括で通る。
- 効く範囲。敬称を外せば名簿の人に当たる表記だけに限る。愛称や呼び方の違い、語の一部だけが当たる表記は足さない。作者が選ぶ負荷の大半はその外にあるので、「同じ判断が戻る」問題の一部しか解けない。
- 危険。誤って足すと、その表記が出るたびに別人の Entry が強調され、以後は一括で通る。確認の行にそれを書く。足した別名を消せるか（Codex の編集と undo）は、着手の前に実機で確かめる。
- 危険。同じ Entry に別名を足す提案が同じ抽出に 2 件あると、今の構成では保存が丸ごと失敗する。そのため、1 つの抽出で 1 つの Entry に別名を足せる提案は 1 件に制限する。同じ Entry への他の結び付けが同じ抽出にあるときも、別名の確認を出さない。
- 足さない表記。呼び名、短い表記、別の Entry と衝突する表記、除外した表記、場面で指す人が変わりうる表記（役職の呼称・一人称）。

### 打ち手 3：名簿に無い表記を、一度却下したら覚えて畳む

- 何が変わるか。候補画面で却下した表記は、構造抽出でも出さない。畳んだ件数は「見送り済み N 件は出していません［戻す］」と見せる。
- 手間がどう減るか。名簿に無い表記の雑音が、却下した分だけ戻らなくなる。
- 危険。却下は表記だけのキーで、文脈も時刻も持たない。ある場面で人物ではないと却下した表記が、別の場面や後の章で本当に人物でも消える。候補画面の「却下」を「二度と出さない」の意味にしてよいかは、作者の判断（Q7）。
- 「戻す」は、候補画面の却下の状態と同じ入口を通して書く。候補画面の状態が古いまま残らないようにするため。
- 注意。構造抽出の review で「拒否」した表記は、今の構成では却下の記録に入らない。それを足すかは別の判断（保存の意味が増える。Q7）。

### 5：話者推定は作らない

台詞ごとの話し手を決める処理は、今の製品に無い。作るなら、最小は「本文で手で結ぶ（mark を同定が読む）」だけにする。AI で話し手を推定するには、台詞の前後と場面の人物名を送る新しい送信が要り、作者の確認が要る。ここでは設計に進めず、検討の記録だけにする（Q9）。

### 3.2 変更

   - (e) 1 字以下（照合は 2 字以上、`extraction/existingEntityMatcher.ts:84-103`）。
   - (f) 場面で指す人が変わりうる表記（役職の呼称・一人称）。一覧で完全には判定できないので、確認の行に警告を出す。除外するかは Q6。
   (b)(b')(c) には catalog に全 Entry の名前・別名と `excludedAliases` が要る（今の `buildCodexStructureCatalogs`、`codexStructureExtractionApi.ts:824-905` に `excludedAliases` は無い）。**足しても AI へは送らない**（ローカルだけ）。
5. 同じ Entry に別名を足せる提案は、1 つの抽出で 1 件に制限する（本線）。2 件目以降には、別名の確認の行を出さない（解決時に、同じ抽出の他の提案との衝突として検査する）。同じ Entry への他の bind-existing が同じ抽出にあるときも、別名の確認の行を出さない。理由：
   - 同じ Entry への patch が 2 件あると、1 件目が Entry の版を上げ、2 件目は同じ `baseVersion` のまま失敗する。失敗する場所は版の不一致の検査（`agent_writes.rs:2309`）で、追加のみの検査（`codex_operations.rs:468-473`）より前。
   - patch の後に、同じ Entry への bind-existing（`baseVersion` 付き）が続いても失敗する。bind が apply 時に版を再検査する（`codex_operations.rs:691-708`）。bind を先、patch を後に並べれば通るので、提案の並びで結果が変わる。
   - 打ち手 2 で bind-existing が増えると、打ち手 1 の確認が出る場面は減る。この効きの減りは測る（§4.7）。
   取り下げた案：「apply の組み立てで同じ Entry の patch を 1 つにまとめる」。commit は各 op の payload を、承認時に固定した revision の `compiledOperation.payload` と digest で照合する（`commit.rs:2862-2868`、:3163-3193）。1 つの op は 1 つの提案・版に結ばれるので、まとめた op はどの版とも一致せず、`NEX_PROPOSAL_PAYLOAD_MISMATCH` で拒否される（`tests/codex_narrative_commit.rs:752-778`、:1204-1268 が payload 不一致の拒否を固定している）。
   本線にしない案：「承認時に同じ Entry の別名をまとめて固定する」。承認時の固定は run 時点の catalog の別名と版だけで組まれる（`codexStructureExtractionApi.ts:3688-3750`）ので、2 件目の版は +1、別名の集合は 1 件目を含む形になり、承認の順と取り消しで壊れる。採るなら、連鎖の固定（版 +1、集合は和）、承認の順、取り消しの扱いを設計する。不変条件：op に入れるのは承認済みの提案の別名だけ（承認していない別名を、承認済みの提案の op に混ぜて保存しない）。
   別の解き方：bind から `baseVersion` を省く（Rust は省略を受ける。TS は必須）。順序の問題と、Apply 時の版の古さ（§3.4）を同時に解くが、挙動の契約の変更なので Q4 で伺う。patch 同士の衝突は、この案でも制限が要る。
6. 安全 flag `aliasesAllExplicit`（:1673、:2818）は未確認の別名があれば false。さらに `reviseProposalFields` が true に固定している点（Store :972）を、payload から作る形に直す（§3.2 の 2）。未確認の別名を持つ提案は一括の対象外のまま。

### 4.3 条件

確認した表記だけを別名にする。呼び名・短い表記・衝突・除外済みは足さない。承認済み（apply 済み）の run は触らない（`assertProposalNotApplied`）。別名の追加は次の apply から効く。足した別名を消せること（Codex の編集と narrative の undo）を実機で確かめるまで、打ち手 1 の着手の条件を満たさない。

### 4.4 危険と防御

| 危険 | 防御 |
|------|------|
| **同じ Entry への patch が 2 件で commit が丸ごと失敗する**。patch の後の bind-existing も失敗する（並びで結果が変わる）。transaction の境界が 1 commit という点は読んだだけで実測していない（推測） | §4.2 の 5 の制限（1 抽出で 1 Entry に別名を足せる提案は 1 件、同じ Entry への他の bind があれば確認を出さない）。先に Rust の統合試験で、今のコードの失敗 3 通りを再現して固定する（§4.6）。まとめる案は commit の payload 照合で拒否されるので採らない |

### 4.5 契約と作者の確認が要る点

- 新しい表・列・op は要らない（`codex_entries.aliases` は既存の列）。保存範囲は広がらないが、「何が別名の保存に至るか」が変わる（今は AI の明示の別名だけ。これに「作者が結び先を選び確認した表記」を足す）。この規則の変更を確認する。
- 改訂案 §6 は「別名での解決」を、規則（★2）と独立に先に入れてよい範囲とみなす。ただし §6 は推測付きで、改訂案自体が未確認の draft。§6 は、場面で指す人が変わる表記（例は「先生」）を規則が要る側に置き、別名は作品全体で 1 人だけを指す表記に限る。打ち手 1 はその限りの範囲に収まるかが、役職の呼称・一人称の扱い次第で決まる（Q6）。作者の確認まで「先に入れてよい」とは言わない。
- ADR 005（決定的な Core は同一性を推測しない）：作者の明示の選択と確認が元なので推測ではない。既定 ON にするなら、結び先を選ぶ操作を確認とみなすと明記する。ADR 006：既存の `codex.entry.patch` の経路で、新しい経路は無い。
- 効く範囲：Q6 の推奨（敬称除去だけ）のとき、選ぶ負荷の大半（愛称・呼び方の違い・語の一部だけの一致）は対象外。広げるなら、愛称類を別名にする条件と危険（別人の強調）を別に立てて伺う。
- 確認が要る：(1) 既定 ON/OFF と文言（Q5）、(2) 別名にしてよい結び方の範囲（Q6）、(3) 版の検査（Q4）。

### 4.6 試験と実機の検査

- 単体：2 か所の変換が同じ結果になる／正規化で一致する表記は足さない／衝突・除外（除外が足す表記を含む場合を含む）・呼び名・1 字は足さない／他の Entry の語の一部になる表記は足さない／未確認 → 確認で `aliasesToAdd` に入る／`aliasesAllExplicit` が未確認の間、live・復元・編集後のすべてで false（`proposalPlanner.test.ts`、`codexStructureExtractionApi.test.ts`、`codexStructureExtractionStore.test.ts`）／cold-start 復元で未確認・確認済みの別名が戻る（`codexStructureExtractionApi.coldStart.test.ts`）／同じ抽出で 2 件目の別名の確認が出ない。
- compile と apply：承認していない提案の別名は、どの op にも入らない。
- Rust の統合試験（`codex_narrative_commit.rs` の既存の流れ）で、今のコードの失敗を 3 本で先に再現して固定する：patch → patch、patch → bind-existing、bind-existing → patch（最後だけ通る見込み）。制限が効く側（2 件目の確認が出ない）は TS の単体試験で固定する。
- コンポーネント：picker 選択後に確認の行が出てチェックの切替が revision に反映される（happy-dom で足りる）。
- 実機・実 DB：(i) 敬称付きの表記を picker で結ぶ → 確認 → Apply → Codex の別名が増える、(ii) 同じ Entry に 2 表記を結ぶとき、2 件目の確認が出ず、Apply が通る、(iii) もう一度抽出して同じ表記が exact-alias で resolved になる、(iv) エディタで別名が強調される（作品全体の副作用の目視）、(v) narrative の undo と Codex の編集で別名が戻る。
- 品質ゲート：prompt・IPC・schema に触れないので Quality（Node 22 の `verify:quality`）で足りる見込み。

### 4.7 測ること

事前登録の試走 (e)（§7.1 末尾の「解決後に Apply した結果の Codex の変化」）と「表記を残す下限」の列を、打ち手 1 の前後で別に取る。§1.3 のとおり、「別名欄の編集 1」の定義の訂正が先。同じ Entry への制限（§4.2 の 5）で確認が出なくなった件数も数える。

## 7. 打ち手の順と依存

```
4（呼び名の一覧） ─┬→ 2（完全一致の一括承認）─┐
                   └→ 1（別名に残す）────────┴→ 組んで効く

```

- **4 が先**：一覧は 1 と 2 が読む。4 は保存も記録も要らず、確認が最も軽い。測定の基準線の前後だけ決める。
- **1 と 2 は組む**：1 で表記が別名に残ると、次の抽出で同じ表記は exact-alias で resolved になり、2 を入れると別名の追加なしの bind-existing として一括承認に入る。1 だけだと 1 件ずつの確認が増え、2 だけだと 1 で増える分を吸収できない。2 を先に入れると、1 が増やす 1 件ずつの確認を最初から吸収できる（推奨）。ただし 1 と 2 を組むと、確認 1 回が、以後の抽出ごとに読まずに通る決定になる。確認の行にそう書く（Q5）。
- 2 の「名前と別名を通して該当が 1 Entry」は、1 が別名を足すと衝突で崩れうる。1 の追加しない条件 (b) が 2 の前提を守る。ヒューリスティックは resolved の method を常に `exact-name` と書く（:983）ので、2 は exact-alias でも同じ扱いにする。
- 1 で別名を足す提案は `aliasesToAdd` が空でなく、2 の (c) で一括の対象外。足す 1 回だけが確認になる。
- 3 は名簿に無い表記、1・2 は名簿にある表記を扱う。同じ表記は両方に入らない。
- 1 は、同じ Entry への patch が失敗する問題を先に Rust の再現試験（3 本、§4.6）で固定し、制限（1 抽出で 1 Entry に別名を足せる提案は 1 件、§4.2 の 5）を入れてから着手する。足した別名を消せることの実機の確認も着手の条件。2 と 4 を先に出す。2 で bind-existing が増えるほど、1 の確認が出る場面は減る。
- AGENTS.md の作業範囲：この作業は NIR-1 の残レーンの委任に含まれない通常の作業。各打ち手の実装は、作者の確認の後に `[precheck]`（保存範囲・脅威モデルに触れるものは GDX-PRECHECK-001）を通す。確認が要る契約の変更は、台帳に `draftRef#contractId` の行を新しく作って確認を取る。いずれも別々の PR にする。
