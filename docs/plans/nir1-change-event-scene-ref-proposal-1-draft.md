## 0. 作者から見える変化

**何を決める案か。** 執筆の記録（`change_events`）は、各行に「どの場面か」（`scene_id`）を持ち、鎖の hash の計算に入れている。この欄は場面への外部キー（ON DELETE SET NULL）で、場面の削除（ゴミ箱に入れた時点）、章の削除、本文を含むスナップショットの復元のたびに、過去の行が NULL になり、hash が合わなくなる。この案は、場面の削除に引きずられない控えを、同じ行に持たせ、すでに空になった行も、hash が証拠になる範囲で戻す。

### 1.3 基点のコードの事実

- **DDL と書き手**【読み】：`migrate.rs` L2095-2118 が change_events の CREATE TABLE（`scene_id TEXT REFERENCES tree_nodes(id) ON DELETE SET NULL`）、L2139 が `event_uid` の `add_column_if_missing`。製品の INSERT は `grimodex-db/src/change_events.rs` の `append_change_events_in_tx` と `grimodex-core/src/change_events.rs`（基点 `2a473ff79` の L147。この file は master まで差が無い）の 2 か所だけ（ほかは test の中）。両方とも列名を指定して INSERT する。HashInput は serde_json の camelCase で、`project_id`、`scene_id`、domain、op_type、…、prev_hash の順（db の同 file の `struct HashInput` と `compute_event_hash_hex`）。`live_scene_id` は、tree_nodes に行が無い id を NULL にして、列と hash の両方に入れる。
- **scene_id は entity_id と同じとは限らない**【読み】：`prose.propose`（MCP の `tools/scene.rs`）は scene_id=場面、entity_id=stagingId で、場面は payload の `sceneId` にある。chat と layout は renderer 側で `sceneId` を必ず null にする。修復の候補は entity_id だけでは足りない（H3）。
- **場面を DELETE する本番の経路は 3 か所**【読み】：`domain_writes.rs` L3584（tree_node_delete）、L6162（AI の plan の undo）、`project_snapshots.rs` の復元（Body scope のとき、`delete_for_project` が `DELETE FROM tree_nodes WHERE project_id = ?1` を実行する）。親の folder と projects の CASCADE は別。`DELETE FROM tree_nodes` を非 test で書く所は、`git grep` でこの 3 か所だけ。**外部マウントの削除は、Rust 側に tree_nodes を消す経路が見つからない**（設計担当は「覆う経路」に数えたが、根拠が無いので数えない。反証担当の指摘を、`git grep` で確かめた）。復元は change_events に INSERT も DELETE もせず、`MAX(sequence)` を読む（`project_snapshots.rs` の復元の no-op の分岐）。**`UPDATE` は、PR-A〔#1029〕の `RestoreSceneIdParking`（退避と戻し。§2.1）だけ**。
- **trigger の発火**【実行（設計担当）】：`AFTER UPDATE OF scene_id` の trigger が、章の削除（CASCADE）、復元の型（DELETE の後に同じ id で INSERT）、手での NULL 化で発火し、控えに元の id が入った。`recursive_triggers` の ON／OFF で結果は同じ。作品の削除は行ごと消える。外部キーを OFF にした削除では `scene_id` は NULL にならず、trigger は発火しない（hash は元のまま合う）。wf53 の確かめ直しも、同形の trigger の発火を確かめた。**rusqlite 同梱の SQLite での確認は、どちらも未確認。**
- **checkpoint**【読み】：`workspace_schema.rs`（`grimodex-core/src/`）L797 の `has_current_schema_checkpoint_invariants` は、change_events については索引（`idx_change_events_project_domain_op_entity_seq`。基点で L1446）だけを見て、列や表の SQL を比べない。trigger は `has_timelapse_creation_baseline_triggers`（L1512）が、契約（`schema-contract.json`）から期待値を読んで比べる。データの移行は `schema_data_migrations` の marker で判定し（C2-ZB など。完了を exact な contract_version で見る）、marker は `migrate.rs` が書く唯一の書き手（`protected-writers.json` の `schema.migration`）。`schema_data_migrations` は列が `migration_id`・`contract_version`（CHECK > 0）・`applied_at` だけで、詳細・件数を持てない（`migrate.rs` L3685）。判定の前例は 2 型：`>=`（v28・v30・v31。`workspace_schema.rs` L2690-2770）と、exact（v32。「将来の版は未対応として full DDL に落とす」と書く）。
- **移行 supervisor**【読み。改稿 3。基点の `migration_supervisor.rs`】：DB を開く入口は `open_or_migrate_workspace_db`（`open.rs` L1103 が呼ぶ。N-API の `open_workspace` は `lib.rs` L11607 で await される前景）。**版が同じでも、quick_check か checkpoint（`live_invariants_ok`）が偽なら `shadow_migrate` に入る**（L297-300・L384-388）。手順：排他 lease → 空き容量の確認（DB の 3 倍＋WAL＋64 MB。`ensure_disk_budget` L1091。足りなければ `MIGRATION_INSUFFICIENT_DISK_SPACE`）→ snapshot（`<作品フォルダ>/backups/migrations/` に VACUUM INTO。削除の処理は見つからなかった）と checksum → staged への `fs::copy` → staged で `migrate_for_restore_preflight`（full 強制）と lineage の再発行 → `verify_migrated_db`（L1067。user_version・**checkpoint が真であること**・quick_check・全表の `foreign_key_check`）→ seal → 入れ替え。**いずれかが失敗すると `safe_mode_after_snapshot`（L513）で Safe Mode（復元だけの session。live の DB は無傷）。DB 全体が対象で、作品ごとではない**。したがって、**marker を checkpoint に足すと、marker の無い既存の v46 の DB は全部この経路に入る**。公開版 v2.0.10（schema 2）からの利用者は、版が違うので元からこの経路に入る（固定費は元からあり、この案の増分は書き直しの分）。固定の予算は空き容量だけで、時間の予算は無い。既存の性能 gate（`scripts/runtime-performance-budget.mjs` L16-17：coldStartMs 4,000 ms・projectOpenMs 3,000 ms）は、小さい seed の fast path だけを測り、この移行を覆わない。前例 45→46 の移行は 202〜511 ms（`db-connection-decisions.md` L282）。

## 3. 残る制限と、作者から見える残る点

- **戻せない行は戻らない。** §1.5 の源を全部広げても、候補のどれにも元の値が無い行（公開版より前に壊れ、id がどの源にも残らない行。undo_journal・trash・snapshot が刈り込まれた作品）は、hash が証拠にならず戻せない。「証拠が無い」行と、「読んでいない源（§1.5 の JSON の中）にだけ在る」行は、実行時に区別できない。実在の作者の DB で何件かは未確認。**作者は、戻せなかった件数を、画面で見られない**（残るのは完了の印と、数え直す関数だけ。ログ〔tracing〕は本番で捨てられる見込み。H8、Q8）。
- **鎖は、書き換え全体には無力**（既存の性質）。DB の書込み権限がある者は、`scene_ref` を NULL や別の値に直せば、hash が合わなくなり**検出はされる**が、場面の削除による旧い壊れ方と**見分けがつかない**。trigger は DROP もできる。戻せなかった行の sequence を覚える場所を足せば区別できるが、その記録も書き換えられる（C1。足さない。Q5 の先）。
- **`scene_id` は、復元で場面が無くなった行では NULL のまま**（確認 131 の Q9 で確認 115 の範囲を広げると決まったので、`scene_ref` に控えが残る）。DB を直接見る人や、将来 `scene_id` だけを引く SQL の読み手は、復元の前の履歴を取りこぼす。写像の漏れが再発しうる（H4、T8）。
- **外部キーを OFF にした削除**は trigger に当たらず、`scene_id` が dangling のまま残る（hash は合う。検証が `scene_id` を優先する限り問題ない）。今の本番にその経路は見つからない（`migrate.rs` の FK OFF の区間に `DELETE FROM tree_nodes` が無い【読み】）が、将来の経路は覆えない。
- **削除した場面の id が、change_events に残り続ける**（元から entity_id や payload に入っている行が多い。id だけで、本文ではない）。
- **接頭辞の範囲（`__grimodex_restore_park_` で始まる）の id の場面を、通常の削除で消すと、保険のため、控えが残らない。** 製品は uuid の id だけを作る見込み（PR-A のコメントの記述。この案は確かめていない）で、PR-A の復元は、親の表にこの範囲の id があれば、書く前に拒否する（`ensure_no_reserved_ids`）。IPC は任意の文字列を取りうるので、起きえない前提ではない。起きたとき、その場面の過去の記録は、削除の後で hash が合わなくなる（検出はされる。H3 の修復が、源に id が残っていれば拾う）。
- **ゴミ箱から戻した場面は別の id になる**（`restorers/scene.ts` L29）。この案の後も、削除の前の記録は旧い id に結び付いたままで、戻した場面（新しい id）の履歴とは**分かれる**。控えの値を新しい id に書き換えると、控えは hash の入力の値なので、鎖の検証が合わなくなる（確認 131 の Q4 で、旧い id のままと決定）。タイムラプスの書き出しで、旧い id の場面が別の場面として出て、場面の数が増える見込み（未確認。state_snapshots は FK が無く残るので、再生はできる見込み）。
- **trigger が無かった期間の行は、marker があるので再修復されない**（trigger を DROP した DB、trigger を持たない写しの取り込み。full DDL で trigger は戻るが、その間に NULL になった行の控えは入らない）。**受け入れる制限**（確認 131 の Q6 (2)）。後の公開版が版を上げたときの 1 回の再走査で、源が残っていれば拾える。**起動のたびの再走査は作らない**（移行の仕組みの中では作れない。marker が済めば checkpoint が真で fast path になり、修復が走らないため。毎回走らせるには、起動時の別の処理か、毎回 shadow migrate が要る）。
