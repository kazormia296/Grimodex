## 3. 名簿の作り方

- 名簿は人物（character）と場所（location）の表。実体ごとに、正式名・別名・型・初出場面を持つ。**原稿を読んで作り、抽出器の seed からは作らない**（循環を避ける）。ただし系統 B の扱いは下のとおり。
- **0 回目の目録（凍結前）**：本番と同じ prepass と候補抽出を script から呼べるかを確かめ、呼べれば表記の目録（表記・出現場面・出現数）を作る。呼べなければ目録を作らず、照合の列を省く。**目録から名簿の実体数と別名数を先に見積もる**（§4 の標本の設計の前提）。
- **系統 A（実体系）**：作品を場面番号つきの chunk（約 4.5 万字、約 5 万 token まで）に分け、順に読み、前の名簿を持ち回して実体・正式名・別名・型を作る。
- **系統 B（表記系）**：chunk の切れ目を半分ずらし、名簿を引き継がず、**原文の chunk だけ**を入力に、表記を束ねて実体にする。**目録は B の入力に入れない**（目録は抽出器の seed と同じ源で、入れると B も seed 由来になる）。目録との照合は、突合の後に別の列で行う。
- 読む側は Sonnet（effort は指示書に明示し、値を decisions に記録）。subagent には Read と Write だけを許し、書込み先は名簿の dir に限る。**これは指示書の記述で、強制ではない**（§11）。本文の中の指示には従わないと指示書に書く。
- script が A と B を突き合わせ、実体の分割・併合・型・主名・別名の違いだけを抜き出す。**Opus**（Agent ツールで model を明示して起動。workflow の agent は model 指定が効かない）が、食い違いの前後数場面だけを読んで調停する。全文は読ませない。
- g-ja-1 だけ、生成時の設計図（outline）の人物表を最後の照合に使う。**これは設計役の AI が書いたもので、人による独立の照合ではない**（§11）。2 系統の入力には入れない。
- **主名**：作中で最も正式な形。役職でしか呼ばれない人物は、最も確定的な呼称を name にし、`nameIsRole` を付ける。最頻形は別列（`frequentSurface`）。
- **別名の段**（1 つの名簿から複数の写しを作る）：
  - L0：name だけ。
  - L1：L0 に正式名の別表記（旧字・表記ゆれ・フルネームの別形）。
  - L2：L1 に略称・姓だけ・名だけ・愛称。
  - L3：L2 に、作品全体で 1 人に固定される関係呼称と役職名。
  - 変種 L2−1字：L2 から 1 字の別名を除く（部分一致の review が増えるため）。
- **別名に入れないもの**：一人称（語り手が誰かを 1 行で記録するだけ）、敬称付きの形、場面で指す人が変わる表記。
  - 敬称付きの形は、**敬称の対応表**（`honorificSurfaces`：表記→実体。別名としては登録しない。名簿との一致を見るための表で、Gold ではない）に持つ。構造抽出の unresolved のうち敬称除去が理由のものに、名簿の結び先を付けるため。
  - **敬称の接尾辞の規則**：抽出器の敬称リスト（`existingEntityMatcher.ts:13-24`。さん・様・君・くん・ちゃん・殿・氏・先生・隊長・殿方）で終わる表記は、前に固有の部分がある形（X＋接尾辞）なら敬称の対応表に入れる。接尾辞だけで単独に呼ばれる役職名は L3 の別名にしてよい。同じ表記の分類が名簿作成者の裁量で変わらないよう、**この分類を script が機械的に検査する**（敬称の対応表と別名が重ならないこと。作者の確認には回さない）。
  - 場面で指す人が変わる表記は、`ambiguousSurfaces`（表記・場面範囲・実体）に持つ。
  - **衝突は 2 種に分けて記録する**。(i) 同じ表記が 2 つの実体の別名（または 2 つの実体の名前）になる場合：構造抽出は ambiguous を出す（`existingEntityMatcher.ts:225-245`）。(ii) ある実体の名前が、別の実体の別名と同じ表記になる場合：名前が 1 件だけ一致すれば、その実体へ即 resolved になり、別名側の実体は見られない（`:225-229`）。期待する挙動は (i)＝ambiguous、(ii)＝名前側に結ぶ。
- **名簿の形**は（表記，場面）→ 実体。名簿にも敬称の対応表にも無い表記は**未判定**（誤りにも名簿どおりにも数えず、別に数える）。
- **名簿の範囲**：人物と場所の全員。**A は切らない名簿で測る**。**B だけ**、実体数が 200 を超える作品で出場面数の少ない順に切って 200 にした名簿を使う（Entry の窓が先頭 200 のため。§6）。切った数を記録し、A と B の両方の表に載せる。登録するのは全行（作者が確認した行だけの感度分析は副に付けない。§13 の 5 で聞く）。**全実体を登録した状態は実作者の Codex の状態ではなく、中間の状態（上位の実体だけ登録）は測らない**（§11）。
- **登録**：renderer の `createCodexEntry`（`src/features/codex/api.ts:231`。aliases は作成時に渡す）。Entry は manual（人が作った扱い）で写しに残る。測定専用の写しに限る。
- **置き場**：repo 外に新しい 0700 の dir（案 `/home/grimodex/identity-review-load-2026-11/`。評価データ dir は変えない）。ファイルは 0600。

## 4. 作者の確認

- **目的**：名簿の大きな誤りを拾うこと。品質の根拠にしない。
- **行の単位**は実体（名前・型・別名と各段・根拠の場面番号と段落番号・短い抜粋）。作者向けの表は記入式の md で、先例（`render-annotation-sheet.mjs`）と同じく匿名 ID・seed 固定で混ぜ、取り込みは記入済み md の ingest で行う。**層の種類と、A と B の一致の印は、作者の応答の後まで見せない。**
- **全数確認**：名簿を確定した後の実体数（A・B の突合と調停の後）が **30 以下**の作品は、全実体を確認する（標本にしない）。31 以上は次の標本にする。0 回目の目録の見積りは目安で、確定数と違えば確定数で分け直す（標本の作品が全数になる場合は乱数の行を使わず全行を見る。逆の場合は、同じ種で乱数の行を引き直す）。
- **標本**（作品ごと。種は `identity-review-load-2026-11/seed-1`、選び方は `sha256(種|作品 key|実体 id)` の昇順）：
  - **乱数の行：10**（先に引く。区間を付ける行はこれだけ）。
  - **層別の行：最大 14**（乱数の行と重ならない実体から。別名の多い上位 3、A と B の食い違い 4、場面で変わる表記 3、衝突 2、場所 2。足りなければ少なくなる）。
  - 合計は最大 24 行（全数確認の作品は最大 30 行）。層別の行は**見つかった誤りの件数**だけを出し、率にしない。
- **区間**：乱数の行だけに付ける。Wilson 95％。**0/10 の上側限界は約 27.8％**（`z²/(n+z²)`、z=1.96）。0/8 は約 32.4％、0/9 は約 29.9％。これが言えるのは「作者が 1 行 3〜4 分・短い抜粋で**検出できた誤り**の率が 28％以下」までで、名簿の真の誤り率の上限ではない。別名の取りこぼし、場面で指す人が変わる表記、衝突は、行と抜粋を見ても見つけにくく、数えられない（漏れは未検査。目録との照合は別列で、独立の検査ではない）。提案の件数への波及も言えない（行は実体単位の一様抽出で、出現の多い実体の重みとは別物）。有限母集団の補正はしない（実体 31〜40 では 10 行が約 1/3 で、区間は保守的）。区間は**作者が直す前の名簿**の値。名簿の品質の証拠にならない。
- **判定の語彙**（固定）：そのまま／名前を直す／別名を足す／別名を外す／別人が混ざる／分けるべき／わからない。
- **直しの扱い**：作者の直しは名簿に反映して名簿を確定する（凍結前）。測定の後に分かった漏れは、名簿を直さず**別列**に併記する（§14）。
- **見えた食い違い**（件数だけ。偏りの検出ではなく記述）：A と B が一致した行の誤り件数と、食い違った行の誤り件数を、**行数（分母）とともに**別に出す。層別で食い違いの行を意図的に増やすので母数が違い、行数が各 4〜10 では傾向も言えない。率の比較はしない。
- **測定 B の後の確認（副）**：次の 2 種を、測定の後に作者へ見せる。**2 種の合計で作品あたり最大 10 行**。見ないなら未確認と書く。
  1. AI が出した別名の結び先が名簿と違った行（名簿と AI のどちらが誤りか分からないため）。
  2. 名簿に無い表記のうち、別名ボタンが出たもの。**作者が「別名ではない」と確認した行だけを負例にする**。確認しない行は未判定のまま残し、名簿の漏れを AI の誤りに数えない。
- **時間**：本確認は 1 作品 24 行（全数確認の作品は最大 30 行）で、4 作品で 96〜120 行。副は最大 10 行／作品で 40 行。1 行 3〜4 分とみると、本確認 約 4.8〜8.0 時間、副 約 2〜2.7 時間で、**合計 約 5〜11 時間**（副が少なければ下側。推測）。1 行の時間は、**別の作業（precision の確認）の 1 query 約 4 分を仮に流用した推測**で、根拠が弱い。最初の作品の最初の 5 行で実測してから確定する。1 回は 60 分以内に区切る。**減らす場合は層別の行から減らし、乱数の行は作品ごとに 8 を下回らせない。**減らした後の標本は凍結前に書き直す。
- 作者が原稿を覚えているかは分からない（m-ja の 3 作は公開の作品、g-ja-1 は AI 生成）。覚えていない作品は 1 行の時間が伸びる（§13 の 5）。

  | 単独 | 1 作品（m-ja-2）だけ、L2 で F25・F50・F75 を新しい workspace で単独に流す（累積の列が前の run の影響を受けていないかの確認） | 3 |

  4 作品で **44 run、32 process**（作品ごとに行列 5・基準 1・決定性 1 の 7 process と、累積の列の 1 process）。さらに単独の 3 run・3 process で、**合計 47 run・35 process**。累積の列の最後（F100）、行列の L2、決定性の 2 回目は、**表記集合（表記×提案の種類）で一致するはず**で、一致を検査する（提案 id・scene id は run ごとに変わるので比べない）。累積の F25・F50・F75 は単独 run と表記集合で比べ、**違えば場面数の依存は単独 run の値を主**にし、累積の列は ★8 の参考値だけに使う。
- **読み出し**：**一括承認できるか・blocked は、実行直後の戻り値の projection（live。提案ごとの `safety`・`applicability`・binding）から読む。**DB から組み直す経路（restore）は `hasProperNameMention` を常に true にし、`hasRelationDeps` を渡さないので、値が違いうる。DB 側（`narrative_proposals` の current revision の `reviewPayload`）の再計算は、**別列（restore 列）**に出し、live と違う件数を記録する。主は live。
- **提案の分け方**（entity の提案だけを分ける。重ならない。順に判定）：
  0. 提案の表記が、名簿にも敬称の対応表にも無い → 「**名簿に無い提案**」（抽出のノイズ。同定の負荷ではない）。以降の分類から外し、種類別（unresolved／create-new／bind-existing）に件数だけ別枠に出す。
  1. binding が **unresolved** → 「解決が要る提案」。さらに 3 つに分ける：**名簿の実体が候補に入っている**（順位つき。同点は同順位）／**候補に無い**。理由（完全一致が複数／敬称除去／前方一致／部分一致）も数える。
  2. create-new で型が未解決 → 「型を決める提案」（blocked）。
  3. bind-existing → 「**1 件ずつ確かめる結び付け**」（一括承認の対象外）。
  4. create-new で型が解決済みかつ一括承認可 → 「**一括承認で通る提案**」（作者が読まずに承認される。負荷が 0 になるのではない）。
  5. 残り（create-new で一括承認不可） → 「手で見る create-new」。
- **名簿との食い違い（仮）の列**（精度に読めない名前にする）：
  - 名簿と違う結び先（仮）：bind-existing の結び先が、名簿の（表記，場面）の実体と違う。
  - 結び残し（仮）：名簿で既存の実体の表記なのに、create-new、または**名簿の実体が候補外**の unresolved。**名簿の実体が候補内の unresolved は含めない**（解決が要る提案と二重に数えない）。
  - **後始末の列**：一括承認で通る提案のうち、名簿で既存の実体の表記だった数（重複の予備。作者がのちに統合する負荷になりうる）を別に出す。
  - 型の食い違い（仮）：名簿が場所の表記を、person の create-new として出したもの。**一括承認で通る提案に入る場合は別に数える。**型の決まり方は catalog の `coarseClassHints` による（固有名詞らしい seed は person、それ以外は型未解決。写しの `codex_types` の hints を記録する）。
  - **自動で結ぶのは完全一致 1 件だけ**なので、「名簿と違う結び先」は名簿の衝突・場面で指す人が変わる表記以外ではほぼ起きない。**この列は抽出器の性能ではなく、名簿の設計から決まる値として別枠に書く。**
- **主な指標**：unresolved の候補に名簿の実体が入っている割合（順位つき）／部分一致の候補のうち別人の割合（**分母は名簿に載る表記の unresolved 提案**。未判定は別。提案単位の割合を主とし、候補 slot の合計を併記する。候補の件数に上限があるかは試走で確かめる。1 文字の別名〔L2−1字〕は候補を増やす）／blocked の割合／場面で指す人が変わる表記と名簿の衝突での挙動／敬称除去が理由の unresolved の件数。
- **操作の数**：§7 の表の規則。**「entity の提案だけの下限」**と書き、関係・Detail・Phase の提案は種類別に件数だけ出す。L 段をまたぐ比較に使わない（別名を足すほど create-new が bind-existing に変わり操作が増えるため、単調でない）。件数は**表記単位と実体単位**の両方で出す（1 人が 5 つの表記で出ると 5 件になる）。**AI なしの経路では、解決しても表記が別名として保存されない**ので、操作数は「承認の下限」と「表記を残す下限」の 2 つで出す（§7.1）。
- **前の回の未 review の提案（★8 の参考値）**：累積の列で、前の回の未 review の提案のうち、**最新の run に同じ表記で残る**件数と、各表記が未 review のまま何 run 分たまるか。**これは seed の安定性で、作者が 1 回決めた後に再抽出で同じ表記がどれだけ再び出るかではない**（それは決定を入れない設計では測れない。場面が入れ子なので、残る割合は構成上ほぼ決まる。表記は 1 run に 1 提案なので、1 run 内の N はほぼ 1）。**「上限」とは呼ばない**（承認で作られた Entry が次の run の seed を bind-existing に変え、件数が増える種類もあるため）。製品に run 間の引き継ぎは無く（seed は毎回作り直される。製品側は未完了 run の復元だけで、limit 8）、この数は seed と catalog が決める。凍結前に 1 作品の F25→F50 で、**前の run の提案が置換・重複・並存のどれになるか**を確かめる（結果で定義を確定。§14）。
- **注意（凍結前に実測）**：(1) 1 作品で seed 数・出現数・request／response のバイト数を測る。制限は **request 8 MiB・response 8 MiB・source view 900・seed 10,000・出現 100,000**（`extraction/schemas.ts:6-11`。900 は sources、10,000 は seeds、100,000 は occurrences）。**request 側と source view 数の超過は、応答を待たず RangeError で投げる**（`entityCandidatePrepass.ts:133-135, 332-341`）ので、失敗の理由コード（request-bytes／response-bytes／sources／seeds／occurrences）を決めて記録し、§8-2 の完了率と区別する。超過した作品は「構造抽出が通らない範囲」の観測として記録し、作品を縮めて通さない。(2) 上限は 4 作で当たらない見込み（推測）。(3) 最初の 5 run で 3 件以上失敗なら止めて原因を調べる。(4) **AI なしの経路では、planner は seed を飛ばさず、`seeds[Math.min(index, seeds.length−1)]` の index はずれない**（seed の form は必ず固有名詞か別名で、どちらも名前になる形のため。`codexStructureExtractionApi.ts:1603-1609, 1671`、`proposalPlanner.ts:12-17`。読みで確認）。試走では飛ばした件数 0 を assert する。(5) prepass の `status` が complete でないと、seed が空のまま提案 0 件で返る（エラーにならない。`codexStructureExtractionApi.ts:1574`）。run ごとに prepass の status と seed 数を記録し、0 件の run は完了に数えず別に報告する。(6) 構造抽出の全経路を実 DB で通す試験は無く、測定で製品の不具合が見つかる可能性がある（記録し、直さない）。

## 6. 測定 B（候補画面）

- **対象**：候補画面（`CodexCandidatesReport`）の AI 判定 `judgeCandidates`（`src/features/codex/candidateJudgment.ts:65`）。**構造抽出とは別の数字**。DOM は使わず、**entry から製品のモジュールを直接呼ぶ**。候補は IPC の `extract_codex_candidates`（ラッパは失敗を [] に潰すので、IPC を直接呼んで失敗と 0 件を区別する）。画面の active／visible は `activeCandidates`・`candidateKey`・`loadDismissedCandidateKeys` で製品と同じ式。Entry は filterType=null・検索語なしで `loadEntries` した全件。
- **arm**：
  - **B1（主）**：**画面どおり**。候補の上位 50（`MAX_CANDIDATES`）・Entry の先頭 200（`MAX_ENTRIES`）・1 要求。作品×段（L0〜L3）×**3 回**＝4×4×3＝**48 要求**。**3 回は同じ候補・同じ名簿への AI の揺れだけ**を見る（どの作品・どの 50 件かの標本の揺れは言えない）。上位 50 は count 降順で頻出に偏る。登録段が進むほど既知の名前が候補から外れ（出現 2 未満と既知名を除外。`codex_candidates.rs:408-413`）、**段ごとに候補の集合と分母が変わるので、段をまたぐ比較はしない**。段ごとの N・判定数を必ず併記する。
  - **B2（副）**：L2 だけ。模擬作者が名簿どおりに上から受理・別名・却下し、残りを判定し直す（`ceil(N/50)` 回）。1 回だけ。**名簿に無い候補（未判定の表記）は、画面を進めるために却下として扱い、却下の件数を別に数える**（名簿に無い表記を誤りにも名簿どおりにも数えない方針は変えない。触らず残すと候補が減らず、`ceil(N/50)` の進みが決まらない）。扱いを変えると要求数と以後の候補が変わる。**処理の分岐は製品の handler と同じ引数で store を呼んで写す**（受理＝`codex_create`、別名＝entry の aliases 更新、却下＝却下キー集合）。乖離のリスクを事前に書き、1 作品 1 回、DOM を駆動する小さな確認と突き合わせる。却下キーは本文由来の表記なので、**件数だけ記録する**。
  - **N（候補数）は AI なしで先に測る**（作品×段。`extract_codex_candidates` だけ）。要求数と費用はその値から再計算してから、上限を凍結する。
- **AI の設定**：
  - **偽 AI の env（`GRIMODEX_PRODUCT_JOURNEY_FAKE_AI`）を node 側と main 側で立てない**ことを assert する。
  - `judgeCandidates` は、policy が off か未ライセンスだと**エラーなしで空の Map を返す**（`candidateJudgment.ts:71`）。**送信前に policy・license・言語（ja）を assert する。**
  - **各要求の後に `ai_usage` の行を確かめる。`judgeCandidates` は `void recordAiUsage(...)` で書込みを待たない**（`candidateJudgment.ts:116`）ので、件数が増えるまで poll（上限つき）してから読む。台帳は書込みの失敗を握りつぶし、tokens が null でも行を残す（`recordAiUsage.ts:83-115`）ので、**「行なし」「tokens が null」「tokens が 0」は別の失敗理由として数える**。surface が `codex_judgment` で tokens が正の行が成功。空の Map・要求 0 件は「判定 0 件」でなく「失敗」として別に数える。
  - **各 B の process の終了時に、AI audit と `ai_usage` の surface・pathId の集合が `codex_judgment` だけであることを assert する**（要約・題名・保守・Agent など他の AI 経路が起動していないことの確認。project の AI policy は、欠損時に full へ倒れる fail-open のため）。
  - 判定の一部欠落（入力に無い surface の黙った破棄）の件数も数える。
  - **主 arm は再送しない**（製品は自動再送しない）。通信の失敗（429／5xx）に限り 1 回再送し、別列に数える。判定の中身の失敗は再送せず失敗として数える。
  - key は keyring／製品の `ai-keys.json` から **FIFO** で渡し、値は表示・記録しない。隔離した profile の safeStorage の backend が `basic_text` でないことを試走の前に確かめる。実行後に `delete_api_key` で消し、userData ごと削除する。前後で製品の `ai-keys.json` のハッシュを比べる。
  - `ai_usage` の `model` は renderer の設定の値で、実際に送ったモデルの証拠にならない。**AI audit（repo 外の写し）で確かめられるのは、送信時の指定（`request.prepared` の `body.model`・`route.model`）**。既存評価の audit（件数・キー名だけの確認）では、解決された model（`effectiveModel`・`modelFingerprint`）は常に null で取れなかった。`codex_judgment` の経路の audit は標本に無く未確認で、取れるかは推測。取れなければ records に「resolved model: 取得不能」と書く。試走 (f) で `codex_judgment` の audit を 1 件見て確定する。
  - 使うモデルの案は **Sonnet 5.5**（§9、§13 の 4）。役割 `structured` は未設定にして `settings.model` を使う。
- **記録（件数のみ）**：N／判定された数（最大 50）／51 件目以降で判定なしの数（候補としては画面に見える）／別名ボタンが出る数（`aliasOfId` が実在 id）／**名簿どおりの別名**／**名簿と違う別名（仮）**／**結び残し（仮）**（名簿で既存の実体だが `aliasOfId` が null か 51 件目以降）／**名簿に無い表記への別名**（未判定。負例に数えず、副の確認で作者が「別名ではない」とした分だけ負例）／候補に出ない既存名（完全一致の除外・出現 2 未満。結び残しの対象外）／`suggestedType` と名簿の型の不一致／`aliasOfId` の 3 回の自己一致／失敗・部分欠落（失敗の理由コード別）／tokens／切った Entry の数（B は 200 に切った名簿を使うので、窓の外は 0。`listCodexEntries` は ORDER BY が無いが、200 以下なら順は影響しない。Entry 数が 200 以下であることを assert する）。
- **名簿の形**：(表記，`firstSceneId`)→ 実体。候補の文脈は初出箇所の 1 文（前後 50 字）だけ。場面で指す人が変わる表記は、初出場面の写像で決める。
- **操作の数**：§7 の表の規則。候補 1 件 1 クリック（受理・別名・却下）。「開く」「AI 判定」は固定の操作として別に出す。
- **候補画面の別名ボタン**は、AI が決めた結び先にだけ出る。作者は結び先を選べない（構造抽出の結び先の選択画面とは構造が違う）。「名簿と違う別名」は、作者が却下・新規作成・画面の外での修正のどれかを選ぶことを意味する。
- **候補画面が製品に残るか**：`recordAiUsage.ts:24` のコメントは `codex_judgment` を「retired」としているが、`CodexManagementPanel.tsx:1067` で常設されている（調査での確認）。方針が変わるなら B の位置づけだけが変わる。

## 7. 指標の定義と ★ との対応

### 7.1 操作の数（凍結前に UI で確かめ、表を埋める）

「最小の操作数」は、**考える時間・読む時間・誤りの取消を含まない下限**。下の値は調査での読みで、UI（`CodexEntityProposalReview.tsx`と、`:288` が使う `CodexEntityResolutionPicker.tsx`）で確かめるまで推測。**AI なしの経路では、seed は別名を持たない**（`codexStructureExtractionApi.ts:1603-1620`）。このため、完全一致の bind-existing も、unresolved を既存の項目に解決した結果も、別名の追加が空になる（`proposalPlanner.ts:126`、`codexStructureExtractionStore.ts:787-822`）。別名も要約も変わらない場合、Codex の項目は変わらず、結び付けの記録だけが残る（`compiler.ts:183-188`）。**表記を Codex に残す（次の run で同じ表記が unresolved のまま出ない）には、別名欄を編集する操作が別に要る**。そこで操作数は **「承認の下限」**（表の第 2 列）と **「表記を残す下限」**（第 3 列。別名欄の編集 1 を足した値）に分けて出す。完全一致の bind-existing は、承認しても Codex が変わらないので別枠で数える。

| 提案の種類 | 承認の下限（案） | 表記を残す下限（案） | 備考 |
|---|---|---|---|
| 一括承認で通る提案 | 全体で 1 | — | まとめて 1 回 |
| bind-existing（完全一致。Codex は変わらない） | 承認 1 | 承認 1＋別名欄の編集 1＝2 | 別枠で数える。一括承認の対象外 |
| unresolved（名簿の実体が候補内） | 解決 1＋承認 1＝2 | ＋別名欄の編集 1＝3 | 解決で unreviewed に戻る |
| unresolved（名簿の実体が候補外） | 新規作成 1＋承認 1＝2 | 同左 | 重複を作る。後始末は別に数える |
| create-new で型が未解決 | 型の選択 1＋承認 1＝2 | 同左 | |
| 手で見る create-new | 承認 1 | 同左 | |
| 名簿に無い提案（種類を問わない） | 件数のみ | — | 別枠。参考の下限は却下 1（主指標に入れない） |
| 関係・Detail・Phase | 件数のみ | — | 主指標に入れない |

試走 (e) の UI の確認に、**解決後に Apply した結果の Codex の変化（別名が増えるか）を見る項目**を足す。

- **開く・実行・取り込み**は A と B で**同じ規則**：主の指標から外し、**固定の操作**として列を分けて出す。A は「開く 1、解析の実行 1、取り込み（Apply）1」。B は「開く 1、AI 判定 1／要求、取り込みは決定ごとに反映のため 0」。
- クリック数は 1 つの値にまとめず、**判断の種類別の件数を主**にする。**件数から作者の負荷（時間）へは換算しない**（種類別の時間は測らない）。

- 出し方：A は 1 cell 1 run なので **run 間の範囲は無く**、決定性の 2 回目との差（表記集合で比べる）を記録し、範囲は作品間の値の並べ方で示す。B は作品ごと・段ごとに 3 回の最小〜最大を示す。作品間は平均しない。A と B は別の表で、**合算も優劣づけもしない**。分母が小さい指標は件数を併記する。

### 7.3 ★ との対応

| ★ | 測定で決まるか | 材料にする指標 | 言えないこと |
|---|---|---|---|
| ★4 最初の組（must-link-surface だけか、cannot-link-entries も同時か） | 決まらない（参考値） | 解決が要る提案のうち**名簿の実体が候補内**の件数＋**結び残し**／cannot-link の適用先の見込み＝**衝突**と**別人の候補**の件数 | 規則を作っても 1 表記 1 規則で、同じ run の中では節約にならない。節約は再抽出・場面追加の後にだけ出て、今は測れない。cannot-link の適用先（merge の提案）は今は無い |

## 8. 判断不能の条件（案。値は §13 の 6 で確認）

次のどれかなら、その範囲は結論を出さず「判断不能」と書く。

1. 名簿：作者の確認が未了。**標本の作品**（乱数の行 10）は、(a)「別人が混ざる」または「分けるべき」が **2 行以上**、(b)「わからない」が **3 行以上**のどちらか → その作品は ★の材料に使わず、別に報告する。(c)「別名を足す」が **4 行以上** → その作品の結び残し（仮）と名簿と違う別名（仮）は使わない（別名の漏れが多い）。**全数確認の作品**（乱数の行が無い）は、全行に対する割合で、(a) 20％ 以上、(b) 30％ 以上、(c) 40％ 以上を同じ扱いにする。**★5**：層別の「場面で変わる表記」「衝突」の行で「別人が混ざる」「分けるべき」が 2 行以上の作品は、★5 の材料に使わない。
   - 閾値の目安（n=10 の乱数の行。真の誤り率ごとに、その条件に当たる確率）：

     | 真の率 | (a) 2 行以上 | (b) 3 行以上 | (c) 4 行以上 |
     |---|---|---|---|
     | 5％ | 8.6％ | 1.2％ | 0.1％ |
     | 10％ | 26.4％ | 7.0％ | 1.3％ |
     | 15％ | 45.6％ | 18.0％ | 5.0％ |
     | 25％ | 75.6％ | 47.4％ | 22.4％ |
     | 40％ | 95.4％ | 83.3％ | 61.8％ |

     許容する誤り率を本書で先に決める根拠は無く、判断不能が半ば偶然に決まりうる（真の率 15％でも (a) は約 46％）。値の確認は §13 の 6。
2. A：その作品の run のうち **80％ 未満**しか完了していない。**prepass の status が complete でない run と提案 0 件の run は完了に数えない。**応答・request が上限を超えた場合は、判断不能でなく「構造抽出が通らない範囲」の観測（§5 注意 (1)）。
3. A：live と restore の列が、一括承認で通る提案で食い違う場合は判断不能にせず、両方を出す。
4. B：主 arm の失敗（空の Map・有効な結果なし・要求 0 件）が、その作品×段の **3 回中 2 回以上**。または自己一致を出すのに成功した回が 2 回未満（1 回の失敗は記録して残りで出す）。
5. ★5：場面で指す人が変わる表記が 4 作の合計で 5 未満なら「材料なし」と書く（5 は便宜の値で根拠は無い。結論を出さないための印）。
6. ★8：凍結前の確かめで前の run の提案の扱いが決まらなかった場合は、定義を確定するまで測らない。
7. 実行の途中で停止線（§9）に当たった範囲。

## 11. 言えないこと

- **名簿は仮の正解で、品質を言わない。**作者の確認は乱数の行 10 と層別の行だけで、確認外は未確認。乱数 0/10 でも、言えるのは**検出できた誤り**の率の上側限界（約 27.8％）まで。名簿の真の誤り率でも、提案の件数への波及でもない。層別の行は名簿全体の誤り率の推定に使えない。
- **自己選好と共有された誤り**：名簿の 2 系統（A・B）と調停は同じ Claude 系で、**同じ向きの偏りが残る**。A と B が一致した誤りは調停で拾えない。**測定 B の AI が同じ系列なら、名簿と AI が同じ誤りを共有し、「正しい別名」が過大に出る**。g-ja-1 の原稿の生成も同じ系列。
- 系統 B は、読む対象が原文だけで目録を入れない。それでも抽出器の seed と同じ源の目録との照合は別列で、独立の確認ではない。
- subagent への「書込み先を限る」「本文の指示に従わない」は**指示書の記述で、強制ではない**。
- g-ja-1 の設計図の人物表は、設計役の AI が書いたもの。**人による独立の照合ではない。**
- 名簿の漏れ（別名の取りこぼし）は「結び残し（仮）」を過大にしうる。名簿に無い表記は未判定で、正誤を言わない。敬称付きの形は敬称の対応表にあるが、別名としては測っていない。**場面で指す人が変わる表記と衝突は、名簿を作る AI が定義する**。作者が確かめるのは層別の 5 行だけで、取りこぼしを検出できない（★5 の件数は名簿作成の癖を反映しうる）。
- **別名の登録段（L0〜L3）は、Codex に別名をどこまで登録してあるかの軸で、原稿の呼び名の揺れの大きさではない**（原稿は固定）。測るのは全実体を登録した状態だけで、実作者の Codex（一部だけ登録、途中まで）の中間の状態は測っていない。実作者への外挿の根拠は無い。
- **名簿に無い提案は同定の負荷ではなく抽出のノイズ**。別枠に件数だけ出す。「一括承認で通る」は負荷が 0 になることではなく、通した後の統合・修正（重複）は後始末の列で別に数える。
- **名簿を作る AI と B で測る AI は同じ系列**で、GDX-NARR-EVAL-001 の Gold の規則（model が自分の Gold を作らない）の例外にあたる（§10、§13 の 3）。指標は「名簿との一致」で、正解率ではない。
- 測定用の写しの Entry は manual、AI 生成原稿は human 相当で作るため、**AI 由来の記録（source metadata）は実態と違う**。AI 帰属の出力は使えない。
- B の 3 回は同じ候補・同じ名簿への AI の揺れだけで、候補の標本の不確実性は言えない。段ごとに候補の集合が違うので、段をまたぐ比較はしない。
- 「名簿と違う結び先（仮）」「結び残し（仮）」は**名簿との不一致で、誤りの確認ではない**。どちらが誤りかは分からない（作者の副の確認が見た範囲だけ）。
- 評価の写しの決定は harness の自動承認・模擬で、**人の review の結果ではない**。測定 A は決定を入れない（★8 は参考値）。B2 は名簿どおりの模擬作者。

1. **原稿の一部を Anthropic へ送ってよいか。**
