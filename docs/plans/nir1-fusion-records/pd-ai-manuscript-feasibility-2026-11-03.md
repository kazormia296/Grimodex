# 実原稿なしで融合の枠を測れるか（PD／AI 生成原稿の調査まとめ）

調査だけで、何も実行・取得していません。根拠は `origin/master` と `origin/claude/nir1-contracts` の git object です。

## 1. 結論

- **Raw 満杯率（Raw が 8 件満杯になる割合）は測れます。** PD でも AI 生成でも、LLM も人の承認も要りません。ただし、原稿を入れるための新しい入口の script が要ります。
- **IR の共通枠の使用率は、条件つきで測れます。** 手段は「手書きの対応表」か「実 LLM での抽出」のどちらかです。前者の数字は表の設計を反映するだけで、実際の抽出結果ではありません。
- **Graph の候補の有無は、PD でも AI 生成でも測れません。** 原稿の問題ではありません。Graph の公開 gate が閉じていて（`PRODUCT_GRAPH_PUBLISHED=false`）、実原稿の複製を Graph の評価に載せる入口も無いからです。
- **Graph の材料の件数のうち、自然な値は作者の実原稿でしか出ません。** PD では pin と承認済み Revision と本文宣言が 0 件になります（「入力が無い」という結論）。
- **得られるのは「作者の実利用の分布」ではなく、「作品の性質ごとの範囲（感度）」です。** 枠を「変えない」判断の根拠には使えます。「変える」判断の根拠には使えません。

## 2. 方式の比較

| 項目 | PD だけ | AI 生成だけ | PD ＋ AI 生成 |
|---|---|---|---|
| Raw 満杯率 | 測れる。独立した作品を 5 つ以上そろえられる | 測れるが参考値。テンプレ展開だと満杯率が上振れしうる（推測） | PD を主、AI 生成を補助にする |
| IR の枠の使用率 | 対応表か抽出が要る（下記） | 同左。生成時に意図を仕込めるが、偏りが出る | 同左 |
| Graph の材料 | 0 件（構造的） | 仕込めるが「準備状態」の層で、自然な値ではない | PD は使わない |
| LLM の要否 | Raw は不要。IR は表または抽出 | 生成に LLM が要る（repo に前例なし）。Raw は不要 | 同左 |
| 費用の目安 | Raw は 0 円（ローカルの埋め込みだけ）。IR 抽出をクラウドで行うと数ドル規模（外挿による推測） | 生成と抽出の費用。実測なし | 合算 |
| 作者の時間 | 取得の確認、分割規則の決定 | model・prompt・Scene 数の決定 | 両方 |
| 確認が要る点 | 取得、置き場所、IR の抽出先 | 生成元、費用、偏りの扱い | 全部 |
| 代表性の限界 | 古典は文体や Scene の粒度が作者の現代小説と違う。Codex や pin が無い | 正解が生成規則から作られ、循環が起きる。偏りがある | 両方の限界が残る |

IR の手段は 2 つあり、性質が違います。

| IR の手段 | 内容 | 注意 |
|---|---|---|
| 手書きの対応表 | Scene ごとに summary／actuality／attribution／narrativeFrame を書く（既存の評価と同じ方式） | 承認は harness が代行する。数字は「表の設計」の反映で、実 LLM の挙動ではない |
| 実 LLM での抽出 | ローカル Ollama、またはクラウド | ローカルで抽出が成立するかは未確認。クラウドは新しい送信先になる |

## 3. 推奨の方式と最小の手順

**推奨は「PD を使った Raw 満杯率の測定」だけを先に行うことです。** IR は別途、確認を取ってから進めます。

1. **Scene の分割規則と目標の長さを先に決めて記録する。** Raw は「上位 30 チャンク」から Scene を数えるため、分割の仕方が満杯率に直接効きます。
2. **PD の作品を 5 つ以上選ぶ。** 日本語と英語の両方が望ましいです。著作権の保護期間が切れていることを確認し、取得物の hash を記録します。
3. **前処理を行う。** 青空文庫なら、ヘッダ・フッタ・注記・外字を除き、Shift_JIS を UTF-8 に直し、ルビは親文字だけにします。Gutenberg なら、行の折り返しを解き、START／END を除き、章見出しを整えます。
4. **原稿を repo の外の使い捨てディレクトリ（`mktemp -d`）に置く。** 通常の書込み API（`tree_node_create`）で Scene として入れます。
5. **Raw の検索だけを走らせる。** ローカルの ONNX 埋め込み model（ruri／bge）を使います。Raw が 8 件満杯になった割合を作品ごとに集計します。
6. **記録には件数と ID だけを残し、本文は書かない。** すべてに「CP-4 の証拠ではない」の印を付けます。
7. **結果は「この作品群での範囲」として報告する。** 作者の使い方には一般化しません。

その後に続ける場合の順序は次のとおりです。

- IR の測定が必要かをユーザーが決める。
- Graph の測定は、作者の実原稿ができてから、または「Graph 用の入口を作る」確認を取ってから行う。

## 5. 調査どうしの食い違い

- **決定論 provider を PD に使えるか。** 調査によって表現が違いました。
  - 一方は「provider は Scene 本文が一致したときだけ答えるので、PD にはそのままでは使えない」。
  - もう一方は「対応表を差し替えれば使える。CP-4 の方式が前例にいちばん近い」。
  - 両者は両立します。ここでは「表を新しく書けば使えるが、表が IR の中身そのものになる」と整理しました。
- **直接 SQL で入れる既存 seed の扱い。**
  - 一方は通常の書込み API（`tree_node_create`）による入力を前提にしました。
  - もう一方は SQL の seed もあると指摘しましたが、評価の規則は SQL による材料の注入を禁じています。
  - 正式な入口は書込み API を採りました。SQL の seed は試運転や件数集計の確認にだけ使えます。
- **ローカル LLM について。**
  - 一方は「外部送信は増えない」と読みました。
  - もう一方は「ローカルで Chronicle 抽出が動いた記録は無い。評価用の script は OpenRouter 固定で、改変が要る」と述べました。
  - 送信先の面では前者、実際に動くかどうかでは後者が根拠として強いので、「送信は増えないが成立は未確認」と書きました。
- **AI 生成原稿の位置づけ。** どちらも「Raw の代表値には使えない」で一致しました。違いは補足にとどまります。
  - 一方は偏りの面から「Graph の統制実験向き」と述べました。
  - もう一方は「テンプレ展開が満杯率を上振れさせうる」と述べました。
