- **snapshot と listEvents の失敗（m-ja-2 の 11、m-en-1 の 10）は model の出力ではない。** どれも run が付く前に落ちた。原因は、関連場面の IR の index build（承認のたびに全 reviewed revision を再生する）が native の単一の DB 接続を長く握り（m-ja-2 の写しで revision 249 件で約 10 s、483 件で約 37 s）、その間の renderer の read が 10 s で timeout したこと。snapshot の adapter は、その例外を `SNAPSHOT_SOURCE_CHANGED` などに付け替えていた（Scene の行は一度も変わっていない）。失敗の窓の終わりが IR build の prepare の終わりと 13〜21 ms で一致した（m-ja-2 の写しの DB で確かめた）。製品の不具合として扱い、DR-IRB-1（PR #805）・DR-IRB-2（PR #806）で直し始めた。記録は `docs/plans/nir1-lane-decisions/irb-decisions.md`（branch `claude/irb-audit-scope-index` 等。未 merge）。
- `<long>` は harness が 32 字以上の英数字の列を伏せたもので、長さから `SNAPSHOT_SCOPE_VALIDATION_FAILED`（1 回目の scope の検証の失敗、32 字）と**推定**する。実際の code は記録に残っていない。
- m-en-1 の listEvents の失敗が m-ja-2 より早い位置から出ているのは、m-en-1 の Scene あたりの提案が多く（509/71 ≒ 7.2。m-ja-2 は 491/117 ≒ 4.2）、reviewed revision が早く増えたことと整合する（**推測**。位置ごとの revision の数は確かめていない）。
- m-en-1 の `Evidence span catalog coverage hole`（39・59）は、LLM を呼ぶ前の決定的な検査（根拠の span の目録の一部が、どの抽出の窓にも入っていない。`spanCatalog.ts` の `assertEvidenceSpanCatalogCoverage`）で落ちた。DB の接続の件とは別の、製品の不具合の候補。**原因は未調査**。

## この結果で言えないこと（事前登録 §10 に加えて）

- **抽出の失敗で、IR の入力が設計どおりでない。** 設計は「全提案を非 secret で承認した下での最大の IR」だが、失敗した Scene（m-ja-1 で 33/88、m-ja-2 で 11/117、m-en-1 で 12/71）は提案も承認も 0 なので、後ろの位置の IR はその Scene の revision を持たない。決まりどおり失敗は除かずに数えたが、主指標はこの欠けを含んだ値。
- m-en-1 の「IR の admitted が 0 件」が多い（168/210）理由は分かっていない。失敗だけでは説明しない（m-ja-2 は 11 件の失敗で 0/348）。英語の floor（0.66）か、作品・model の性質か、は**推測**にとどまり、原因の診断は別に行う。
- 作品ごとの値の違い（m-ja-2 の 86.7％ と m-en-1 の 11.8％、m-ja-1 の 23.1％）は、作品・言語・抽出の条件（m-ja-1 は修正前の prompt）・build の違いを分けられない（事前登録 §10）。
- 採否の閾値は置かない（事前登録 §6）。枠の案の採否はユーザーが結果を見て決める。

### 公開の文献から足す限界（2026-11-05、記録の後に追記。指標・判断規則・読みは変えない）

出典は integrator の調査の文書 `/home/grimodex/fusion-eval-data/design-notes/nir-prior-art-2026-11-05.md`（repo の外。§3 の V4〜V6、§7 で本文と照合済みのもの）。

- **標本の実効の大きさは sample の数より小さい。** 表の件数は 3 の倍数で、同じ query の 3 回の反復を数えている。D0 の 219 は約 73 query・3 作品にあたり、Wilson の区間は sample の数で計算しているので実効の n は約 1/3 になる。作品が 3 つだと、作品を単位にした bootstrap も不安定になる（multiway bootstrap、Bowyer 2025、Smucker 2009）。値は「この 3 作品の中の値」で、作品をまたぐ一般化は主張しない。D0 の数え方は事前登録どおり sample の数のまま変えない。
- **1 回の run の値で、非決定性の分散を含まない。** 抽出の失敗の数・提案の数・IR の admitted は、run ごとに変わりうる。
- **「全提案を非 secret で承認」は、IR が最大に出る条件であると同時に、不忠実な解釈も通す条件。** 枠に入った IR の中身の正しさ（その 1 件が関連場面として適切か）は測っていない（FABLES：要約の claim の忠実さは 69〜91％）。枠の使用率は「IR が枠を使う機会」で、関連場面の改善を示す値ではない（事前登録 §1 の目的どおり）。
- **言語の間で比べない。** 日英の差は、IR の floor（ja 0.813、en 0.66。`policies/narrative/nir1-related-scenes-ranking.json`）の校正の差を含む。m-en-1 の「IR の admitted 0 件」の診断では、floor の校正と、IR の build の preflight を通る revision が 509 件中 318 件だったこと（IRB の計測。理由は調査中）の両方を候補にする。
