# 融合の枠の測定：設計（統合版）

対象は `origin/master` `39ac13c8` と記録用 branch `origin/claude/nir1-contracts` の git object です。これは設計だけで、測定も実装もしていません。「確認済み」は 3 案と 2 つの批判が file:line まで読んだ事実です。「推測」「未確認」は実物で確かめていません。数値の閾値は、すべて「提案」で、測定の前にユーザーが決める値です。

## 1. 結論

1. **まず費用ゼロの再集計をします。** L0 の受領書では、Raw が 8 件になったのは 24 query 中 1 件（en-05）だけでした。ただし 22 Scene の合成 corpus なので、実原稿の割合には使えません。
2. **次に、実原稿の複製を使い、標準 build で Raw と IR だけを測ります（段階 1）。** 測るのは Raw 満杯率、IR が共通の 1 枠を使う割合、枠を広げた場合に動く query の割合の上限です。Graph の測定は含めません。
3. **Graph の候補の有無と精度は、段階 1 では測れません。** 実原稿の複製を評価 build の Graph arm に載せる入口が今は無く、作るのは新しい authority です。段階 1 で出せる Graph の値は、pin などの入力の件数（天井）だけです。
4. **Graph 専用枠、Graph を 2 件以上にする arm、Raw を押し出す案は、ユーザーの確認が出るまで着手しません（段階 2）。** 段階 1 では、枠を広げた場合の上限を計算するところまでです。
5. 結果は CP-4 の証跡にも判定にもしません。全記録に `not-cp4-evidence` を入れます。

## 3. データと正解ラベル

### 3.1 データ

| 区分 | 使い方 |
|---|---|
| 作者の実 project（ローカルのみ） | 主。DB を一時ディレクトリ（`mktemp -d`。repo の外）へ複製し、読み取り専用で使う。終了後に消す。`.artifacts/` は一部が git の管理下なので使わない |
| 公開作品（青空文庫など） | 使わない（段階 1）。IR に Chronicle 抽出が要り、LLM への送信先の問題が出る。Graph の入力は人工になる |
| L0 の合成 corpus、G-case、dev fixture | 試運転と手順 A の参考だけ。母集団としては使わない（Graph に有利に設計されている） |

**記録に残してよいもの**：件数、割合、run ごとの salt でハッシュ化した不透明な ID、等級。
**残さないもの**：本文、題名、`chunkText`（L0 の受領書は `results[].chunkText` に抜粋を載せる書式なので、そのまま使うと記録 branch に原稿が載ります）。複製、salt、ラベルのシートは repo の外に置き、worktree の片付け前に退避します。

### 3.2 正解ラベル（段階 1：B3）

作者の負担を、時間で見積もります。**どれも推測です。作者に実際の速度を聞いて決めます。**

| 作業 | 件数 | 時間 |
|---|---|---|
| B3 の関連度ラベル（IR が足した Scene と Raw 6〜8 位） | 最大 60〜100 件 × 約 20 秒 | 約 20〜35 分 |
| 再ラベル（約 20%、7 日以上空ける） | 12〜20 件 | 約 5〜10 分 |
| 任意：実行前に挙げる「出てほしい場面」（30 query × 3 件まで） | 30 × 約 2 分 | 約 1 時間 |
| 合計 | | 約 1〜2 時間（任意分を含む） |

**ラベルの付け方**
- **付ける人：** 作者 1 名。外部の LLM や第三者に原稿を渡しません。
- **質問：** 「いまこの場面を書いている（直している）とき、この前の場面を関連場面で見たいか」。
- **等級：** 0＝無関係、または見て損する。1＝関係はあるが無くても書ける。2＝見ると役に立つ。3＝必ず見たい。有用は 2 以上。
- **カードの形式：** query 側は本文末尾 500 文字（UTF-16）と全文。候補側は題名、冒頭 200 字、全文。**どの系が出した候補でも同じ形式・同じ情報量にします。** 製品の excerpt は系ごとに形式が違い、出所が漏れるので使いません。
- **盲検：** 順序は乱数で混ぜ、順位・score・出所・path は見せません。出所の対応表はラベルの封印まで開きません。作者は自分の設計を知っているので、完全な盲検にはなりません。限界として記録します。
- **再ラベル：** 食い違ったら両方保持します。指標は初回で計算し、再ラベル版は感度分析として併記します（後から良い方を選ばない）。
- **一致率：** 重み付き κ と、有用かどうかの二値 κ を出します。下限は提案 0.6 で、割ったら「ラベルが不安定」と記録して結論を一段下げます。この値はユーザーが決めます。

**観測後のラベルは、事前に固定した Gold とは言えません。** 出力から候補を選んで付けるラベルは、事前に固定した Gold ではありません。「Gold を観測の後に変えない」規則を満たすかは、ユーザーの判断です（§6）。独立した Gold と呼べるのは、実行前に作者が封印する「出てほしい場面」（hash で封印）だけです。これを recall の分母に使います。pool 内のラベルから出す recall は下限にすぎません。

## 4. 測る値の定義、arm、事前登録

### 4.1 測る値

単位は query Scene（その Scene を現在の編集 Scene とみなし、製品と同じ builder で query を作る）です。本文が空でなく、読書順で前に 1 件以上ある Scene が対象です。

| 値 | 定義 | 段階 |
|---|---|---|
| M1 | Raw 件数（0〜8）の分布。「満杯」は 8 件。`≤6`、`≤5` も併記。層別：過去 Scene 数 1〜7／8〜29／30〜99／100 以上 | 1 |
| M1' | 取得した上位 30 チャンクのうち、後ろの Scene が占めた数と、1 Scene が複数チャンクを占めた数（歪みの大きさ） | 1 |
| M2 | IR が共通の枠を使った割合（結果に `kind:"ir"` の行がある）。分母は IR が `available` の query。`unavailable` の割合と閉じた理由も別に報告 | 1 |
| M2' | Raw 満杯のとき、IR に Raw に無い候補があったか | 1（B0 の観測器の確認が通れば） |
| M3a | query Scene が pin を 1 件以上持つ割合（Graph の seed の天井。製品の規則は最初の pin を seed にする：`nir1GraphSeed.ts`） | 1（SQL） |
| M3b | pin・承認済み Revision・Relation・本文宣言の件数（入力の漏斗） | 1（SQL） |
| M3c〜 | Graph の適格な候補の有無、適格な候補が枠で捨てられた割合、Graph 候補の precision | 2 |
| L | §3.2 の等級。precision は有用（2 以上）の割合に Wilson の 95% 区間をつける。project ごとに別に出す | 1（IR のみ） |

**M3b は適格性の測定ではありません。** Native の判定（承認、Freshness、Scope、reveal、本文宣言）を SQL で再実装すると、第二の実装になり、結果が Graph の候補と一致する保証がありません（DR-CB3-1 が同種の案を却下しています）。入力の有無を知るだけの参考値です。実原稿で作者が宣言していなければ、製品が出せる Graph 候補は 0 件になります。その場合も「Graph は何も足せない」と一般化せず、「入力が無かった」と報告します。

**Raw 満杯の歪みへの対策（M1 の補正）：**
- 主：読書順の 3〜4 か所の地点（例：原稿の 25%、50%、75%、100%）で、それより後ろの Scene を除いた複製を作り、各地点の末尾付近の Scene を query にして測ります。再 index は地点数分で済みます（実行可能性は B0 で確認）。
- 補助：完成原稿の複製での値と M1'。両者の差を、歪みの大きさとして併記します。
- 完成原稿の値だけで「満杯率は低い」と結論しません。

### 4.2 arm と、段階 1 で出せる「天井」

枠の規則は 3 か所（renderer の `slotOpen`、IR の `find`、Native の `compose`）に 1 件で固定されています。policy の数値（`maxAdditionalScenes`）だけを 2 にしても動かないので、arm を実際に走らせることはせず、記録から決定的に再計算します。表示の合計は 8 件以内、Raw は全件保つ前提です。

| arm | 現行より動く query の上限（天井） | 段階 1 | 段階 2 |
|---|---|---|---|
| 現行（共通 1 枠） | — | 観測そのもの | 同左 |
| 共通 2 件 | 2 件目が入るのは Raw ≤6 の query。上限は P(Raw ≤6 かつ Raw に無い IR 候補が 2 件以上) ≤ P(Raw ≤6) | M1 から。IR 候補の数は観測器が通れば | — |
| 共通 3 件 | 3 件目が入るのは Raw ≤5。上限は P(Raw ≤5 かつ候補 3 件以上) ≤ P(Raw ≤5) | 同上 | — |
| Graph 専用枠（+1、合計 8 以内） | IR が枠を使い、かつ Raw ≤6 の query だけ。上限は P(IR 使用 かつ Raw ≤6)。IR 使用で Raw が 7 のときは合計 9 になり入らない。IR が枠を使っていなければ、Graph は現行の枠で出るので変化なし | M1、M2 から | 実際の比較（候補の有無と precision） |
| Graph を 2 件以上 | — | 扱えない | wire、click registry、走査の変更が要る |
| 9 件目に足す案 | — | 扱わない（表示上限 8 の変更） | 別 lane |
| Raw の押し出し、dense pool の昇格 | — | 扱わない | 別 lane（post-B §7.2「押し出さない」の撤回を伴う） |

**天井は上限です。効果と読みません。** 候補の precision が 1 だったとしても、天井を超える割合の query は変わりません。天井が小さければ、arm の実装は不要です。大きくても、効果があるとは限りません。

### 4.3 事前登録するもの

実原稿の複製を開く前に、次を文書にして commit し、hash を記録します。

- 母集団の定義（query Scene の条件）、分母、層、抽出の規則と乱数 seed、M1 補正の地点の決め方
- M1〜L の定義、Wilson 区間、天井の式（§4.2）、解析 script の hash
- ラベルの rubric v1、カードの形式、対象の選び方と件数の上限、再ラベルの規則
- 判断規則（§5）と、閾値を決めたユーザーの確認
- 除外の規則（不一致・失敗は除外せず記録）
- 実行環境：L0 と同じ隔離（`scripts/local-ci-xvfb.mjs`、Wayland／D-Bus／proxy の変数除去）。Chromium の辞書取得は env の proxy では止まらないため、egress の証跡（`egress.mjs` の socket 採取と net log）を取る

## 5. サンプルサイズと、枠の判断への進み方

### 5.1 サンプルサイズ

**同じ project の query は独立ではありません。** 同じ物語・同じ pin・同じ Raw の候補を共有します。設計効果は `1+(m−1)ρ` で、m=50、ρ=0.1 なら約 5.9、m=100、ρ=0.2 なら約 21 です。独立を仮定した区間は狭すぎます。

- 1 つの project を全 Scene で測る場合は census なので、その project の値に標本誤差はありません。**project が 5 未満なら、project をまたぐ推論はしません。** project ごとの値を並べるだけにし、プールした区間は出しません。作者 1 名の project 1〜2 個なら、結果は「この project の記述」にとどまります。
- Wilson の 95% 区間の半幅（p=0.5）：n=30 で ±0.17、n=100 で ±0.10、n=200 で ±0.07、n=400 で ±0.05。
- precision の例：20/40 で 0.35〜0.65、28/40 で 0.55〜0.82。**precision の下限を閾値に使うには、有効なラベルが 40 件前後は要ります。**
- 0 件の場合の Wilson 両側 95% 上限は `3.84/(n+3.84)`。上限を 0.05 未満と言うには n が 73 以上、0.10 未満なら 35 以上です。n=60 では約 0.06 で足りません。
- IR の補完の標本は M2 に従属します。M2 が低ければ、precision の標本はほとんど集まりません。その場合は「判断不能」と報告し、数を増やすために設計を変えません。

### 5.2 判断規則

結果から枠の判断に進むかを、測る前に決めます。**閾値の数値は、すべて提案です。** 確認台帳の現行閾値（CP-4 の品質の条件）の緩和ではなく新設ですが、ユーザーが測定の前に決めるまで確定しません。

| 規則 | 条件 | 結論 |
|---|---|---|
| D0 判断不能 | 分母の query が少ない（提案 200 未満、census なら全件）、または有効な IR ラベルが少ない（提案 40 未満） | 「判断不能」。枠は現状維持。追加の project や期間の延長を提案する |
| D1 入力が無い | pin 付き query が 73 件以上あり、その 0 件（M3a の上限が 0.05 未満） | Graph が動く以前に入力が無い。枠の再設計より先に、入力（pin、本文宣言）の lane を提案。**枠は変えない** |
| D2 天井が小さい | 各 arm の天井の Wilson 上限が提案 5% 未満 | その arm は実装しない |
| D3 天井が大きい | 天井が 5% 以上 | 段階 2 の確認に進む理由にはなるが、効果の根拠ではない。段階 2 の費用と得られる情報を示して、ユーザーが選ぶ |
| D4 IR の補完の質 | IR の補完 1 件の precision の下限が提案 0.40 未満 | 共通枠を増やす案（2・3 件）は採らない |

**比較の作り方：** precision の比較は、同じ query の中での対の差だけを根拠にします。母集団が違う値の点推定同士（枠が空いた query の Graph と、Raw が満杯に近い query の Raw 下位など）の大小を、規則に使いません。

**この測定は枠を自動で変えません。** 規則は、別 lane での設計・確認に進むかを決めるためのものです。進む場合は、新しい Gold の版を測る前に固定します。

## 7. 危険と、確かめていないこと

### 危険

| 危険 | 対応 |
|---|---|
| **代表性：** 実原稿は作者（保守者）の project に限られる。pin や承認の量が、一般の作者より多い可能性（推測）。project が少なければ、結果は記述にとどまる | project ごとに別に出す。一般化しない（§5.1） |
| **天井を効果と読む** | 天井は上限。効果として報告しない（§4.2） |
| **Raw 満杯率の歪み：** 完成原稿の replay は Raw を少なく見せうる | §4.1 の補正。完成原稿の値だけで結論しない |
| **replay と実利用の差：** 製品のパネルは編集中の本文の末尾から query を作る。replay は完成した本文で測る | 地点ごとの複製で近づける。限界として明記 |
| **ラベル：** 標本が小さく区間が広い。作者 1 名で、盲検は不完全 | 形式の統一、順序の乱数化、再ラベル（§3.2）。0.5 と 0.7 の区別は、大きな標本が無いとできないと明記 |
| **「入力が無い」と「枠が原因」の混同：** Graph 候補 0 件を「枠が悪い」「Graph は無価値」と読む | D1 で分ける。M3b は適格性の測定ではない |
| **原稿の漏洩：** 受領書に `chunkText` が入る書式の流用、log、会話への混入 | ID と件数だけを記録する。driver に「出力に秘密が無い」型の検査を置く。Claude は集計だけを読む。ignore 対象の記録は、worktree を消す前に退避する（`worktree-cleanup-ignored-files`） |
| **事前登録の抜け道：** ラベルを付ける前に arm の指標を見る、結果を見てから閾値や rubric を動かす | §4.3 の順序。解析 script の hash を記録 |
| **CP-4 との混同** | 全記録に `not-cp4-evidence`。frozen な harness の file は変更しない |
| **判断不能に終わる可能性が高い：** 実 project が 1〜2 個で、Graph の入力が少ないと、D0 か D1 が結論になる | その結論も有用な結果として扱う（段階 2 に進む理由が無い、と分かる）。段階 1 の費用は小さく抑えてある |

### 確かめていないこと

- §2 の B0 の 4 点：固定検査に触れないか、複製先で IR と index が有効か、観測器で `ir.scenes` の全件が読めるか、既存部品を転用できるか。
- 実原稿の project に、pin、承認済み Revision、本文宣言、Chronicle の sealed generation が、どれだけあるか（B1 の結果に依存）。
- `admitDevPreview` の固定 purpose（`diag-registration`、`hook-check` など）が、実原稿の複製を技術的に許すか。許すとしても、集計に使わない前提（「integrator only, never aggregated」）。
- Graph の「適格な候補があったが枠で捨てた」割合は、評価専用の seam が無いと測れない（段階 2）。
- 作者のラベル付けの速度と、払える時間。
- すべての時間・行数の見積もり（推測）。
- 3 案と 2 つの批判が読んだ範囲以外の、材料文書の主張は下書きとして読んだ。
