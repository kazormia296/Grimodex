## C4 ★ 脅威モデル（rev1 §6 の draft）の確認

**(1) 何を決めるか**
段 1 は「DB が変わったか」を DB の中の連番で判定する。この連番が、誰に・どう壊されうるかの想定（誰を信頼し、何を守り、何を守らないか）が §6 の draft。これで良いか。

draft の中身：
- 信頼しない：renderer（任意の SQL を authorizer の下で実行できる）。
- 信頼する：Native。
- MCP：別 process。typed な tool だけで DDL は持たない。書込みは DB 側の TRIGGER で覆うので、MCP の規律には頼らない。
- 範囲外：DB の file そのものを書き換えられる local の攻撃者。今と同じで、検出できるのは監査の chain だけ。
- 範囲内の攻撃と防御：
  - 連番の偽造・巻き戻し → 直接の書込みを拒否し、TRIGGER が使う書込みだけ名前の完全一致で許す。
  - TRIGGER の削除 → DDL を拒否する。
  - restore での取り違え → lineage を作り直す。
  - 書込み tx 内で読んだ値の再利用（ABA）→ proof に使う値は Read の tx か autocommit で読んだものだけにする。
- 連番は失効の合図にすぎず、scope・registry・宣言の authority ではない。

**(2) 選択肢**
設計文書に選択肢は無い。判断は「承認」か「修正の指示」の 2 択。承認する前に見てほしい点が 3 つある。
- 範囲外の「file を書き換えられる攻撃者」は今も範囲外のままで、連番はその攻撃者には偽造できる。今より悪くはならないが、連番だけを守る追加策は無い。
- TRIGGER が 1 本でも欠けると、その表の書込みで連番が進まず、古い結果を新しいと誤る（fail-open）。防御は生成関数・本文の全文比較・自己修復・全経路の試験で、残るのは開発者の誤り。
- 不変条件が落ちると全量の shadow migration が走る。MCP が常駐していると排他 lease の待ち 10 s で open が失敗しうる。軽い修復（in-version repair）を持つかは承認後に決める、と書いてある。
- 設計文書が確かめていない点：MCP が app に同梱か、利用者が別に置く copy か（§9）。MCP が別 copy なら「MCP は TRIGGER で覆われる」は成り立つが、古い MCP が常駐して lease で競合する場面が増える。

**(3) 推奨と理由**
承認する。ただし「MCP の同梱状況は PR-1 の前に read-only で確かめる」を条件にする。理由：
- MCP のコードを変えずに、DB 側の TRIGGER で全経路を覆える。
- 範囲外の攻撃者の扱いは今と同じで、新しい弱点を足さない。
- 同梱状況は C1（古い binary の扱い）の運用にも効くので、先に事実を固めたほうが手戻りが少ない。

**(4) 決めないと止まるもの**

今決めると、PR-1 の authorizer と台帳の仕様が固まる。

# 質問票 2：chat の IR（agent の `search_events` を拡張する案）

回答済みで再質問しないもの：正式な試験は当面しない、設計を先に起こす、IR の要約・quote を chat の送信先へ送る、使った IR の ID と作者の訂正・却下を local に保存する、閾値は held-out の試験で決める、agent の tool で使い分ける。

## (a) 作者の年表の event にも「後の Scene を除く filter」を掛けるか

**(1) 何を決めるか**
今の `search_events` は、secret の event を開示の Scene より前でだけ隠す。secret でない後の event は返す。IR 由来の結果には「今の Scene より後を除く filter」が必須。作者が自分で作った年表の event にも同じ filter を掛けるか。

事実：
- 承認済みの IR の提案は、適用されて初めて年表の event になる。
- 適用された event は evidenceSceneLinks で Scene に結ばれる。quote は写らない。
- 年表だけにある event には、Scene に結ばれていないものがありうる。そのとき位置が無いので、filter は掛けられない。

**(2) 選択肢**
- (A) 掛けない。IR 由来の結果にだけ filter を掛ける。
  - 効果：既存の tool の挙動は変わらない。
  - リスク：1 つの tool に 2 つの規則が混ざる。設計 v2 は、この場合は専用の tool に切り替える余地があるとしている。
- (B) Scene に結ばれた event にだけ、IR と同じ規則を掛ける。結ばれていない event は今のまま返す。
  - 効果：規則が IR と揃い、後の筋の混入を減らせる。
  - リスク：既存の tool の結果が変わる（AI の挙動資産で、品質ゲートの対象）。年表の計画の質問には後の event が要ることがある【推測】。
- (C) 全 event に掛ける。
  - 効果：規則が最も単純。
  - リスク：位置が無い event の扱いを別に決める必要がある。年表の将来の計画（後の event）を問えなくなる。

**(3) 推奨と理由**
(B)。理由は、IR と同じ向きの規則で作者の「まだ書いていない後の筋」への混入を抑え、位置が無い event は今のまま返して既存の使い方を壊さないから。
実装の前に決める細部：複数の Scene に結ばれた event は、いちばん前の Scene で見るか、いちばん後で見るか。今の Scene が無いときの扱い。

**(4) 決めないと止まるもの**
S1（閉じたまま実装）の `search_events` の拡張が止まる。(A) なら専用の tool に切り替えるので、設計の形（1 つの tool か 2 つか）が変わる。
今決めると、「1 つの tool か 2 つか」と、AI 挙動資産の変更範囲（説明文）が固まる。
印：無印。送信範囲は狭まる側。ただし既存の tool の挙動変更なので確認はしてほしい。

## (c) tool の結果が会話の履歴に残ることの扱い

**(1) 何を決めるか**
tool が返した IR の quote や要約が、local の会話の履歴に残る場合、承認済みの保存の範囲（使った ID と作者の訂正・却下）を超えてよいか。

確かめた事実（コード上の読み。試験では未確認）：
- 履歴に永続化されるのは、assistant メッセージの metadata の `tool_calls` で、中身は tool 名・params（query）・`resultSummary`・tokensUsed（`chatTurnStoreActions.ts:1410`、`agentTypes.ts` の `ToolCallRecord`）。
- tool の結果の本文（`tool_result`）は、その turn の中のメッセージ配列に積まれる。metadata には入らない。
- `resultSummary` は executor が決める文字列で、今の `search_events` は「N events found」程度。
- 最終の回答は assistant メッセージとして保存される。IR の内容を言い換えていれば、それも残る。これは今も Raw の内容で起きていて、新しい保存ではない。
- 未確認：audit の記録、tool cache、debug log に結果の本文が残るか。次の turn で `tool_result` が再送されるか。
- query は model が書く文字列なので、原稿の語句が含まれうる。

**(2) 選択肢**（設計文書に選択肢は無い。以下は上の事実から私が整理した）
- (A) 本文は残さない。履歴には tool 名・query・件数と、使った ID（承認済みの範囲）だけ。`resultSummary` は件数のみにする。
  - 効果：承認済みの範囲で収まる。
  - リスク：次の turn で、model は前の tool の結果を見られない（必要なら再度呼ぶ）。履歴の再描画で、出典の引用は出せない（ID から引き直す）。
- (B) quote と要約も履歴に残す。
  - 効果：再描画と次の turn で使える。
  - リスク：IR の本文が local の履歴に残る。保存範囲の拡大。
- (C) 要約（summary）だけ残し、quote は残さない。
  - 効果：再描画に最低限使える。
  - リスク：保存範囲の拡大が小さくても発生する。要約が誤りだったときも履歴に残る。

**(3) 推奨と理由**
(A)。理由は、承認済みの範囲内で済み、IR が誤っていたときの影響が履歴に残らないから。
実装の前に、audit・tool cache・debug log・次 turn の再送を、試験で確かめて固定する（これは S1 の項目にする）。

**(4) 決めないと止まるもの**
S1 の「ID と訂正・却下の local の記録」と executor の `resultSummary` の設計が止まる。
今決めると、保存の仕様と GDX-PRECHECK-001 の記録（保存範囲の項目）が固まる。
印：(A) は無印。(B)(C) は★（保存範囲の拡大）。
