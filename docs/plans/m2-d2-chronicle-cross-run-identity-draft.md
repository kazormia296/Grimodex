## 0. 要点

- 今は、抽出をやり直すと同じ出来事が別物になる。作者が「同じ出来事」と確かめても、その相手はどこにも記録されない。
- 同一性の根拠は**作者が確かめて結んだもの**だけにする。題の一致などで自動に結ばない（ADR 005・ADR 004、M4 契約案の carried-forward と同じ考え方）。
- **「結んだ記録を残す」だけでは、抽出をやり直しても聞かれ続ける。** 次の run の提案を前の結びにつなぐ手がかり（§3.2）と、作者の「同じ」「違う」の両方を覚えることが要る。これは ERM（ADR 015 の must-link／cannot-link、M3）と同じ型なので、M3 と合わせる。
- 結ぶ記録の置き場所は 3 案（§3.1）、次の run での当て方は §3.2。どれも新しい契約か保存の拡大で、利用者に伺う。
- 今の製品で見える小さな不具合：重複の疑いのカードが、候補の既存の出来事を生の id の 1 件目だけで出している（§1.1）。契約は要らない。年表の担当に共有した。
- 効き目が出るのは、年表の取り込みが製品で開いた後（SRA/1 の P1）。実装は SRA/1 の D2・D3 と同じ PR 群か、その後にする。

## 1. 確かめた事実

### 1.1 今の動き
- 提案の `eventId` は、抽出のたびに `createId()`（既定は `crypto.randomUUID()`）で振られる（`proposalPlanner.ts:166-172`）。提案の key（`{eventId}:{index}`）も run ごとに変わる（`repository.rs:3958-3989`）。
- 既存の出来事との一致の判定（`existingEventMatcher.ts:87-133`）は 3 値。
  - `already-satisfied`：根拠の指紋の一致、または題と根拠の場面の集合の一致。提案ごと捨てる。
  - `probable-duplicate`：題だけが一致（題の正規化は trim・NFC・小文字化だけ）。新しい id の提案のまま、候補（既存の `events.id`）を付ける。
  - `none`：題の一致が無い。
- **製品の経路では `already-satisfied` に届かない。** 製品が渡す既存の出来事の目録（`existingEventCatalog.ts:17-33`、Native 側 `repository.rs:2540-2590`）は、場面と根拠の手がかりを空にしている。そのため一致は題だけで、題が少し揺れれば `none` になり、二重に作られる。
- 一致の結果は、run に封じた plan の成果物（`planned[].match`）にだけ残る。提案の payload にも版にも入らない。
- 作者の重複の選択は 3 つ（`chronicleExtractionApi.ts:1899-1926`）。
  - `create-as-new`（別の出来事として作る）＝承認。
  - `skip-as-same`（同じものとしてスキップ）＝却下。
  - `hold`（保留）。
  - 決定に残るのは `decisionJson.probableDuplicateChoice` の値だけで、**どの既存の出来事と同じかは残らない**（Native の検査 `repository.rs:6341-6399`、`commit.rs:2599-2705`）。
  - 画面は候補の 1 件目の生の id を出すだけで、題を引かず、複数の候補から選べない（`ChronicleProposalCard.tsx:143-170`）。
- 取り込みは提案の `eventId` で新しい出来事を作る。同じ id が既にあれば失敗する（`commit.rs:2304` の `ensure_event_id_available`）。取り込みの記録（Application）は、作った `events.id` と 1 対 1。

### 1.2 確認済みの起案と ADR の制約
- **SRA/1 の A5**：重複の選択は 3 つのまま。相手の id を残すとは書いていない（年表の担当の確認）。
- **SRA/1 の D2・D3**（未実装）：取り込みの時の年表全体の照合（`NEX_CHRONICLE_RESUME_LIVE_CATALOG_DRIFT`）を外し、Native が取り込む時点の年表に対して題で重複を調べ直す。返すのは疑いの有無だけで、相手を特定する前提ではない。題の正規化の値は未定。残る制限は「題が違う同じ出来事は見つけられない」。
  - 今の照合は、候補の既存の出来事が取り込みの時にも残っていることを暗黙に保証している。D2 の後は保証されない。
- **SRD/1**：出来事が消えると、それを作った Application の提案の承認を外す（X）。承認し直し（RA）も Application が作った `events.id` を使う。**結んだだけの提案（Application が無い）は、どれの対象にもならない。** 確認 87 は、承認し直しの時に今の出来事の中身と照合しないと決めている。
- **SRA/1 §2.8・ERA/1**：取り込み済みの提案は編集できない。人の手直しで変えてよいのは 4 項目だけ。
- **SRA/1 の U3 と :223（確認済みの残る制限）**：「同じ場面を抽出し直すと、同じ内容の提案がまた出ることがある」「題が違う同じ出来事は、見つけられない」。この起案は、この 2 つの制限を変える提案になる。
- **CED/1**：既存の出来事の目録（`chronicle.existing-events-catalog@1`）の形を変えると、凍結した抽出の結果と評価の digest に触れる。
- **ADR 015**：通常の Codex の同一性は同じ Codex ID だけ。Merge／Split の対応は ERM の側で記録し、M2 の identity 契約の代わりにしない（:62）。M2-D2〜D4 の identity 契約をどの段で確定するかは未決（:247）。脅威モデルは「AI は提案を出すだけ。規則の作成は作者の画面の操作だけで、chat の AI の道具と外部の MCP に載せない」。
- **ADR 005（:409-410）**：「Stable identity がない場合、Deterministic Core が heuristic matching で identity を捏造してはならない」（起案者が原文で確認）。
- **ADR 004（:118-121）**：「候補生成・ranking に使う決定論処理は残してよいが、Apply 許可条件にはしない（同一語の再登場、exact name／alias、時刻表現検出、Scene 間共起など）」（起案者が原文で確認）。→ 根拠の指紋や題の一致は、**候補を出す・並べる**のには使ってよいが、同一性を決めたり取り込みを許したりする条件にはしない。
- **書き手の固定**：決定や Application の表に新しい書き込み・欄を足すと、書き手の指紋を固定した試験（`proposal_decision_writer_inventory`）と `change-feed-writers.json` の登録に当たる。新しい authority の扱いになる（年表の担当の指摘）。
- **AWA/1**：取り込んだ出来事は、アプリ内の AI の道具と MCP が更新・削除できる。

## 2. 何を「同じ出来事」とするか

起案者の読み：
- 安定した key になるのは、**既に年表にある `events.id`** だけ。提案の `eventId` は、作る予定の新しい id で、同一性の key にならない。
- したがって同一性は「提案が、既存の出来事 E と同じだと作者が確かめた」という**結び**として表す。結べない提案（新しい出来事）は、M2-D1 の「まだ Entry でない新しい候補」と同じく同一性なし。
- key の綴りは `chronicle-event:{events.id}`（Change Feed の objectKey・Contribution の台帳と同じ）を推す。M2-D1 の `codex:` は Feed の `codex-entry` と別の第 3 の綴りになった。同じことを避ける。
- 結びは作者の画面の操作だけで作る。AI の道具・MCP・背景の処理の経路には載せない（ADR 015 §3 と同じ）。
- 結びの中身は AI に送らない。版も書き換えない。

採らない案と理由：
- 提案の `eventId` を既存の E にそろえる：取り込みが `ensure_event_id_available` で失敗する。chat の IR の A1 が「events の行がある＝取り込み済み」と見て、未取り込みの提案を取り込み済みと誤る。
- 目録に結びを入れて、一致の判定の `already-satisfied` を通す：目録の版を上げることになり、凍結した digest に触れる（CED/1）。
- 題の一致で自動に結ぶ：ADR 005・ADR 004 に反する。
- M2-D1 型の policy の宣言だけにする：その宣言は挙動を動かさないので、再抽出の抑止にも比較の根拠にもならない。

## 3. 結びの置き場所と、次の run での当て方

### 3.1 結びの置き場所（3 案）

- **案 A：既存の `skip-as-same` と封じた候補から結びを導く。**
  - 作者が「同じものとしてスキップ」を選び、候補がちょうど 1 件の時だけ、その候補を結び先とみなす。新しい保存は無い。
  - 候補が 2 件以上の時は結べない。取り込みの後に結ぶこともできない。
  - 読む側（変更レビュー・再抽出）が、決定と封じた plan の成果物を合わせて読む新しい読みが要る。
- **案 B：決定に、検証つきの `existingEventId` を足す。**
  - `skip-as-same` を選ぶ時に、作者が候補から 1 件を選ぶ。Native は、封じた候補に含まれることと、今その project に存在することを確かめて記録する。
  - 決定の形（`decision_json`）と書き手に触るので、**新しい契約・authority**。重複の選択は SRA/1 の A5 で確認済みなので、選び方の追加も伺う。
  - 画面は、候補の題と日時を引いて、複数から選べるようにする（UI は Claude が持つ）。
  - 取り込みの前にだけ働く。
- **案 C：別の台帳に結びを持つ。**
  - 「提案（または run の出来事の key）→ 既存の `events.id`」を新しい表に置く。取り込みの後から結ぶこともできる。
  - **保存範囲の拡大と新しい契約。** writer の登録・スナップショットの復元・profile egress の登録も要る。
  - 決定・Application の表を変えないので、SRD/1 の 1 対 1 の前提を崩さない。

起案者の読み：置き場所だけなら案 B が小さい。ただし §3.2 のとおり、案 B だけでは「やり直しても聞かれない」は成り立たない。

### 3.2 次の run での当て方（決め手）

起案の上で 3 つの場面を通した（起案者の読み）：
- **(1) 同じと結んだ後の 3 回目**：P1 を取り込んで E ができ、再抽出の P2 を作者が E に結んだ。3 回目の P3 は、今の一致の判定では題が同じなら `probable-duplicate` で**また聞かれる**。P2→E の結びは、P3 を P2 や E につなぐ手がかりにならない。
- **(2) 題が揺れた時**：判定は `none` で、封じた候補が空になる。案 A・B は封じた候補から選ぶので、**結べない**。
- **(3) 作者が「違う」と選んだ時**：覚えるのが「同じ」だけなら、次の run で**また聞かれる**。

したがって、効かせるには 2 つが要る。
- **run をまたぐ手がかり**：P3 を前の結びにつなぐもの。候補は、根拠の指紋（場面と引用）や、題と根拠の場面の集合。ADR 004 の Signal／Prefilter として「候補を出す・並べる」にだけ使い、同一性の確定と取り込みの許可は作者の選択による。今の目録はこの手がかりを空にしているので、目録の外から読む形にする（目録の版は上げない）。
- **作者の「同じ」と「違う」の両方を覚える**：ADR 015 の must-link／cannot-link と同じ型。M3（ERM の担当）の回答（2026-11-26）：
  - ERM の PR 1 の表（設計草稿、未 push）は、規則の対象を Codex の Entry の ID で持つ。出来事は抽出ごとに ID が変わり、照合の key が出来事の手がかり（参加者・場面・日時など）になるので、**保存の形は別にした方が素直**。
  - 共通にできるのは原則：書き換えない版の履歴、規則の中身を AI に送らない、モデルの出力の後にアプリが決定的に当てる、食い違いは勝者を選ばず確認待ち、取り消しは新しい版。
  - ERM の表に対象の種類の列を足して出来事も入れる案は、版上げが 1 回で済むが、対象が増える**新しい契約**。決めるなら ERM の PR 1 の schema を固める前（数日内）。
  - 「ERM を Codex に限る」と決めた利用者の回答は、M3 の手元の回答の原文には見当たらない（contracts の全文は未確認）。
  - ADR 015 :247：D2〜D4 の同一性の契約そのものは **M4 の持ち物**。:247 を閉じるのは M3 だが、M4 の契約が決まってから。ERM の PR 2 は年表への影響を「列挙できない＝未解決」として止める形で先に進められるので、M4 を急がせない。
  - 起案者の読み：年表は ERM と**別の保存の形**にし、上の原則を共通にする。
- 候補を出す範囲を封じた候補の外（その project の任意の出来事）に広げるなら、Native が project と存在を確かめる。信頼境界が広がるので、脅威モデルに書く。

## 4. 決めること

- **結び先が消えた時**：結び先の出来事が消えた（作者・AI・MCP・復元）時、結びを「失効」として残すか、SRD/1 の X と同じ transaction で外すか。Core は他の出来事に付け替えない。
- **SRD/1 との関係**：結んだ提案は Application を持たない。X・RA・RD の対象に入れるか、入れないと明記するか。作者が呼べる却下の入口を作らない（X6）・作者の却下を覆さない（RA6）と突き合わせる。
- **取り込む時の再確認**：SRA/1 の D2 の後は、結び先の生存が暗黙には保証されない。結びを使う時点で、Native が transaction の中で確かめる規則を置く。SRA/1 の D3 と同じ PR 群で扱う。
- **D3 の範囲**：Native の題の照合が相手の id を返すなら、SRA/1 の D3 の範囲が広がる。年表の担当と合わせる。
- **再抽出での使い方**：結びを持つ前回の提案と同じ key で比べる（D1 の変更レビューと同じ比較）。再抽出の時に、結んだ出来事への提案を「既に年表にある」と出すか。目録の外から一致の判定が結びを読む形にする。

## 5. 使い道（製品の経路での到達）

- **SRD/1 の重複と再提示**：同じ場面を抽出し直した時に、作者が同じと確かめた出来事を何度も出さない。**§3.2 の手がかりと「同じ／違う」の記憶がそろった時だけ効く。** 案 B の置き場所だけでは効かない。
- **年表の変更レビュー**：D1 と同じ「同じ key を含む、直前の承認済みの版との比較」が使える。結びが無い限り、全部が新しい出来事として出て差は出ない。年表の版を読む reader と画面は新しく作る。
- 効かないもの：Chronicle の index・Graph・関連場面（key は提案・版）、Contribution の台帳（既存の出来事を更新する書き手が無い）。

## 7. 未確認

- 決定の `decision_json` に未知の key を足した時、Native が拒むか（自由形式の JSON と報告されたが、検査の全数は読んでいない）。
- 復元で `events.id` が戻った時に、結びを復活させてよいか。
- 複数の run で同じ既存の出来事に結んだ時の扱い（1 つの出来事に結びが何本も付く）。
- 年表に統合・分割の操作が無いこと（ADR 015 の Merge／Split は Codex の Entry 向け）。
