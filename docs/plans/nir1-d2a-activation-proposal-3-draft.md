## 事実

### Y-1 の finding（接続）

- 再現条件（実機）: Electron 43.5.0（Chromium 150）、Linux、sandbox 有効。窓は本体の `buildWebPreferences()`（`electron/main/windows.ts:234-240`）と同じ webPreferences で、本体の `protocol.ts` の `app://bundle` と CSP の下で動く。env の proxy と Wayland／D-Bus の変数を外し、Xvfb を host namespace で動かした（`unshare -n` は使わない）。renderer の任意の JS が `new RTCPeerConnection({ iceServers: [{ urls: "turn:host:port?transport=tcp" }] })` か `turns:host:port` で ICE の収集を始めるだけで、Chromium は host 名を解決して TCP に接続し、`turns:` では TLS の ClientHello（SNI）まで送る。CSP の `connect-src` も permission handler も止めない。
- 同じ probe で、fetch、XHR、WebSocket、EventSource、sendBeacon、img、form、`window.open`、同梱の worker と service worker、HTML 以外の応答と 404 を開いた iframe は、canary への接続が 0 件だった。Main の設定（`setWebRTCIPHandlingPolicy` 単独、`--force-webrtc-ip-handling-policy`、CSP の `webrtc 'block'`、`--disable-webrtc`、`--disable-blink-features=RTCPeerConnection`）は塞がなかった。`--proxy-server` を blackhole にすると塞がるが、更新と spellchecker を含む Chromium の通信が全部止まる（`d4`）。

- 到達した宛先の種類: 試験の受け手は loopback と LAN の受信 socket（canary）と、試験用の DNS 観測だけで、攻撃者が受け手になりうる外部サーバーへは送っていない。Chromium が接続・送信・解決を試みた宛先は、(a) 名前の解決と TCP／TLS、(b) IPv4／IPv6 literal の TCP／UDP（loopback の任意の port、LAN を含む）、(c) remote candidate の IP と port である。

### K3/2 の O-2 の前提が崩れていた点

- K3/2 は「production の CSP が外部への接続を許さないので、renderer は外へ直接通信できず、読めても外へ出せない」を O-2 の前提にし、WebRTC と DNS 先読み・preconnect は「CSP の対象外と理解しているが、実機では見ていない」として Y-1 に預けた。実機では、WebRTC の接続と名前解決、dns-prefetch が外へ出せた。

## 設計

### NC-1: 機構（実機で閉じた構成）

renderer 窓が使う default session と Chromium の process に、次の 3 つを同時に当てる。

1. default session に `setProxy({ mode: 'fixed_servers', proxyRules: 'socks5://127.0.0.1:<LS-1 の port>', proxyBypassRules: '<-loopback>' })` を当て、続けて `closeAllConnections()`。`proxyBypassRules` は `<-loopback>` だけで、許可先を書かない（AL-0）。`<-loopback>` は、loopback を Chromium の暗黙の bypass から外して proxy（blackhole）へ向ける。
2. すべての webContents に、`app.on('web-contents-created')` で `setWebRTCIPHandlingPolicy('disable_non_proxied_udp')` を当て、`getWebRTCIPHandlingPolicy()` で読み戻す。
3. `app.commandLine.appendSwitch('host-resolver-rules', buildHostResolverRules())` を、app が ready になる前に 1 回だけ当てる。規則の exact な文字列は `MAP grimodex-rule-sentinel.invalid 127.0.0.1, MAP * ~NOTFOUND, EXCLUDE github.com, EXCLUDE objects.githubusercontent.com, EXCLUDE release-assets.githubusercontent.com, EXCLUDE 127.0.0.1, EXCLUDE localhost`（`al0-final-real` の `resolverSwitch` と同じ。`EXCLUDE` は RS-1 の 4 名〔3 host と `localhost`〕と `127.0.0.1` の 5 つで、`localhost` は 1 回だけ）。RS-1 に無い名前（sentinel を除く）と、`127.0.0.1`（別形式を含む）以外の IP literal は `ERR_NAME_NOT_RESOLVED` になる。`EXCLUDE 127.0.0.1` は proxy の listener を IP literal で書くため、`EXCLUDE localhost` は `localhost` 名の local proxy を使う利用者の更新のために要る。sentinel（`grimodex-rule-sentinel.invalid`）は規則が届いたかを確かめる固定名。`EXCLUDE` は書く順序に関わらず `MAP` に優先する（作業記録での観察。JSON 未収録。`x1`／`x2` は prefix の合成の記録で、順序の優先の直接の記録ではない。文字列が exact であること〔順序を含む〕は (31) の単体試験、優先の意味は自己確認 (a)(b) と (23b) の実機の解決で固定する）。

### AL-0 と RS-1: 許可先の閉じた集合

- 許可先は `electron/main` のコードに置く 1 つの module の定数にする。`proxyBypassRules` と `host-resolver-rules` はこの定数から組み立てる。定数の中身を exact に固定する試験を置き（Negative (31)）、増減には新しい draftRef が要る。実行時に外から（env、設定、IPC、renderer の値）足す入口を作らない。OS による分岐も作らない（全 OS で同じ定数）。
- AL-0（直接通信を許す先）: **0 件**。`proxyBypassRules` は `<-loopback>` だけ。renderer の Chromium の通信は、すべて blackhole の proxy へ向かう。
- RS-1（名前解決を許す名前）: `github.com`、`objects.githubusercontent.com`、`release-assets.githubusercontent.com`（electron-updater の確認と取得。exact な 3 host で wildcard にしない）、`localhost`（固定名）。加えて `EXCLUDE 127.0.0.1`（proxy の listener のため）。実測で確かめた `github.com` と `release-assets.githubusercontent.com`、固定名の `localhost`（と `EXCLUDE 127.0.0.1`）に、**予備の `objects.githubusercontent.com`** を加えた集合である。予備は GitHub の旧来の release asset の redirect 先として入れた host で、`al0-updater` の実測の redirect 先は `release-assets.githubusercontent.com` であり `objects` は観測していない。入れる根拠は旧来の挙動の推定で実測ではない（外すのは閉じた集合の変更で、新しい draftRef。現行は残す）。`github-releases.githubusercontent.com` は観測しておらず含めない（未確認の項目）。`api.github.com` も含めない（electron-updater 6.8.9 の `GitHubProvider` は、host が未指定か `github.com` のとき API でなく `github.com` の `/releases/latest` を使う〔`out/providers/GitHubProvider.js:158-163`〕。publish は provider `github`、owner、repo だけで host の指定がない〔`electron-builder.yml:108-111`〕。`resolveHost(api.github.com)` が `ERR_NAME_NOT_RESOLVED` になることは `al0-dict`）。`github.com` を除くと更新の確認が、asset の host を除くと取得が `ERR_NAME_NOT_RESOLVED` で止まる（`u3`、`v3`）。`u2`／`u3`／`v2`／`v3` は AL-1 の旧構成（bypass に `https://*.gvt1.com:443`、rules に `EXCLUDE redirector.gvt1.com`／`*.gvt1.com` を含む）での記録で、GitHub の host の `EXCLUDE` の有無だけを変えた対照である。AL-0 の構成では `al0-updater` が asset の取得で 200 を示す。`localhost` を入れる理由: env の proxy が `http://localhost:PORT` の環境で、`EXCLUDE localhost` が無いと更新の session が proxy の host 名を解決できず `ERR_PROXY_CONNECTION_FAILED` になった（`w1`）。入れると更新の確認が proxy に `CONNECT github.com:443` として届いた（`w2`）。`w1`／`w2` も AL-1 の旧構成で、`localhost` の `EXCLUDE` の有無の対照である。
- RS-1 の名前は、renderer が TURN の host に書いても、接続は `<-loopback>` と proxy の既定で blackhole へ向き、UDP は policy が止める（`nl-al0-final` の RS-1 の 4 名 × {STUN、TURN-UDP、TURN-TCP、TURNS} の 16 行: canary へ 0、TURN-TCP と TURNS の 8 行は proxy の listener へ 2 件ずつ、STUN と TURN-UDP の 8 行は proxy へも 0）。名前そのものは固定なので、載せられる文字がない。選び方（4 通りの名前と port）で運べる情報は極小で、名前は resolver の cache にも阻まれる（推定）。
- 近い名前の扱い: `gvt1.com`、`a.gvt1.com`、`a.b.github.com`、`github.com.evil.test`、`evil.release-assets.githubusercontent.com`、`api.github.com`、`x.localhost`、`localhost.` などは解決されない（`al0-nearnames`: 列挙した名前と `foo.local`、`[::1]`、`169.254.169.254` の全部が `ERR_NAME_NOT_RESOLVED`。`127.1`、`0x7f.0.0.1`、`2130706433`、`127.0.0.1.` は `127.0.0.1` に正規化されて解決され、TCP は `<-loopback>` で proxy へ向く）。
- 辞書（`*.gvt1.com`）は RS-1 にも AL にも入れない。Chromium の辞書の取得は `redirector.gvt1.com` から `rr<N>---sn-*.gvt1.com` へ redirect するので、許可するには glob が要り、glob は攻撃者が選べる label を許す（「選択肢と推奨」の AL）。

### LS-1: blackhole の受け口

- Main が `127.0.0.1` の ephemeral port で TCP の listener を持つ。SOCKS5 の挨拶を受けても返事をせず、受けた bytes は読み出して即座に捨てる（検査、保存、log への出力をしない）。固定 port（`1`、`9`）は、その port で SOCKS5 を話す別の local プロセスに host 名が渡りうるので使わない。listener を持たず閉じた port を指す案（LS-2）も到達 0 だったが（`g2`、`al0-closed-proxy`）、別のプロセスがその port を後から取りうるので推奨しない。
- 有限にする（K1b の共通の規則）。上界を確認の対象として固定する（緩めるには新しい draftRef。DA-1 はこれより小さい値を試験から選んでよい）: 同時の接続数は 256 以下、1 接続の保持は 5 秒以下、上限を超える接続は受けた直後に切断する（待ち行列を持たない）。観測した最大は 1 つの行で 60 程度（30 件の TURN server）。
- accept した socket の `error`（ECONNRESET など）は握りつぶして `destroy` する。Chromium は TURN／SOCKS の job の取消しや `pc.close()` で接続を即座に落とすので RST は通常の動作で、error handler がないと Node で未処理例外になる（作業記録での観察。JSON 未収録。(30a) の試験で固定する）。server の `error`（EMFILE などの一時的な accept の失敗を含む）も握りつぶして継続し、listener が実際に閉じたときだけ FC-1 の対象にする。
- **通常の終了と消失の区別**: アプリの終了（`before-quit` の開始）の後に listener が閉じても、`NC-LISTENER-LOST` に数えない。終了の開始より前に閉じたときだけ数える（試験は (30a) の 1 件）。再 bind はしない。listener は製品のコードから明示的に閉じず、process の終了で OS に閉じさせる（`before-quit` から終了までの間に port が空く窓を作らない）。

### MD-1 と適用の順序

- 範囲: 窓が `app://bundle` を読む起動すべてで、mode を問わず適用する。packaged build は常にこれ。適用しないのは、非 packaged かつ `ELECTRON_RENDERER_URL` ありの開発の起動だけ（`<-loopback>` と名前解決の閉じ込めで、loopback の Vite dev server が読めなくなるため）。この例外では policy の handler も登録しない（NC-1 の全段を適用しない）。述語は、master に入っている `electron/main/devRendererUrl.ts`（DA-1 の ST1。#676。判断の記録は `da1-decisions.md` の DR-DA1-6）の `shouldRegisterAppProtocol()` の 1 つ（内部は `resolveDevRendererUrl({ isPackaged, env })`。packaged は env があっても `undefined`）で、NC-1 の適用はこの関数が true のときだけ。NC-1 を含む各所は `process.env.ELECTRON_RENDERER_URL` を直接読まない（env を読む file が `devRendererUrl.ts` だけであることは、既存の `rendererIsolation.static.test.ts` の (e) が固定している。(31) は再掲しない）。
- 順序（**起動手順** (0)〜(6)。NC-1 の節の手順 1〜3 とは別の番号で、FC-1 の期限と (30a) はこの番号で指す）: 起動手順 (2)〜(4) は、`app.whenReady()` の中で、**default session への最初の接触より前**に始める。**default session の接触**は、次の呼出しの列挙で定義する（列挙にない API の接触は未検証）。(A) `session.defaultSession` の参照: 製品では `applySessionPermissionPolicy()`（`index.ts:240`。`security.ts:126,145`）、`installProductDownloadGuard()`（`index.ts:242`。`downloadGuardElectron.ts:44`。同じ関数が `app.on('session-created')` も登録する）、NC-1 の `setProxy`。(B) Electron が暗黙に default session へ委譲する `protocol.*`（`protocol.handle`、`unhandle`、`isProtocolHandled`、`register*Protocol`、`intercept*Protocol` など 19 個）: Electron 43.5.0 の binary の JS で、これらが `session.defaultSession.protocol.*` へ転送されることを確かめた（`registerSchemesAsPrivileged` は ready 前の別の binding で、この転送の一覧にない）。製品では `registerAppProtocolHandler()`（`index.ts:246`。`protocol.ts:188` の `protocol.handle`）。NC-1 の `setProxy` 自身が default session の最初の接触になる。NC-1 は、(A)(B) のどの呼出しより前、かつ `initializeNarrativeMaintenanceStartup()` の呼出し（`index.ts:248`。中で `initBackend`〔`index.ts:120`〕と `createProfileEgressGate`〔`index.ts:124`〕が走る）より前に完了させる。置き場所は `performance.mark("grimodex:electron-when-ready")`（`index.ts:235`）の直後で、`resolveAppVersion` の動的 import（`index.ts:238`）より前。(0) `host-resolver-rules` の `appendSwitch` を、app が ready になる前（`index.ts:201` の `registerAppProtocolScheme()` の近く）で呼ぶ。(1) `web-contents-created` の policy の handler を、最初の webContents が作られる前に登録する（`index.ts:232` の `registerSecurityHandlers`、`security.ts:111-122` に並べる）。(2) `app.whenReady()` の後に LS-1 の listener を起動して port を得る（default session に触れない）。(3) `await setProxy(…)`（default session の最初の接触）と `await closeAllConnections()`。(4) 自己確認（FC-1）。(5) その後に既存の起動: `applySessionPermissionPolicy()`、`installProductDownloadGuard()`、`registerAppProtocolHandler()`（この 3 つの順は現状のまま）、`initializeNarrativeMaintenanceStartup()`（`initBackend`）。(6) 最後に `BrowserWindow` を作る（`windows.ts:306`、`374`。`createMainWindow` の呼出しは `index.ts:730`）。
- この位置にする理由: 起動前の失敗（FC-1）の `app.quit()` が、Native の backend の起動の前に起きるようにするため。`will-quit` の finalizer（Native の終了 receipt を待つ。`index.ts:568` で作り `index.ts:669` で登録する。どちらも backend の初期化の後）は、その時点で未登録で、待つ Native の状態もない。`registerImeShutdown`（`index.ts:216`）の `will-quit` は、backend が `null` なら何もしない（`imeShutdown.ts`）。NC-1 を `initBackend` の後に置く構成は許さない（Negative (30a) の順序の試験で固定する）。
- default session の最初の接触にする理由と、辞書の要求の測定（**この要約が唯一の正本**で、他の節は MD-1 を指す。実機。Linux、Electron 43.5.0、窓は `about:blank` の scratch main。`ord-*`）: spellchecker の辞書の要求は、旧い順序の 18 回で ready から 33〜132 ms に始まった。旧い順序（最初の接触が (A) の permission 相当の 9 回か、(B) の `protocol.handle` の 9 回で、NC-1 は 3 秒後を模擬）では、18／18 回が `setProxy` の前に出て、OS／環境の proxy がなければ rules の名前拒否（`ERR_NAME_NOT_RESOLVED`）で止まり（6 回）、env の proxy（`127.0.0.1`／`localhost`）があればその proxy へ `CONNECT redirector.gvt1.com:443` が届いた（12 回）。NC-1 を最初の接触にした 35 回（環境の proxy なし・`127.0.0.1`・`localhost` 各 5、NC-1 の開始を ready から 20／50／100／300 ms 遅らせた 12、24 個の busy loop を並走させた 8）、(A) の直後に NC-1 を当てた 15 回、(B) の直後に NC-1 を当てた 3 回、NC-1 の後に (B) と (A) を呼んだ 9 回は、すべて要求が `setProxy` の完了後に始まり blackhole（`SOCKS5`）へ向き、env の proxy への CONNECT は 0、`Dictionaries/` は空だった。この記録が支えるのは、接触の直後に NC-1 を当てても、NC-1 が最初でも 0 だったこと、接触から `setProxy` までが 3 秒空くと要求が前に出ることまでで、『NC-1 が最初』である必要性は示していない（安全側の規則として置く。接触と NC-1 の間に長い `await` を挟まない保証が起動手順にないため）。要求が前に出る仕組み（Chromium が最初の proxy 設定を待つのか時間差か）は特定していない。Windows／macOS、GNOME／KDE の設定による proxy、PAC／WPAD、実アプリの `index.ts` は未測定。
- 窓の作成前に効かせる理由: 起動直後に作られた窓が、設定の前に作った接続を持ち続けると塞がらない。窓を作った後で `setProxy` する構成は試していない（未検証）。
- profile の mode、gate の構築、activation とは独立に適用する（`createProfileEgressGate`〔`index.ts:124`〕より前に終わり、その結果を待たない）。mode を問わない理由: activation は再起動なしで restricted になり、`host-resolver-rules` は ready の前にしか当てられないので、restricted のときだけ適用する案は切り替えられない。
- network service を SIGKILL して再起動させた後も proxy と rules は維持された（AL-0 は `al0-netservice-kill`、AL-1 の旧構成は `k2`）。

### FC-1: 失敗時の扱い（fail closed）

どちらも、独自の終了を作らず、既存の終了の経路を通す。**この draft は、実行中の既存の graceful な終了の保証を弱める新しい時間の上限も、`app.exit` も置かない。** 起動前の待ちの期限（下の「起動前の待ちの期限」）は、窓も Native の状態もない段階だけの規則である。

- 失敗の通知（**表示の契約**。起動前と実行中で同じ）: 固定コードを stderr（`console.error`）に 1 行出すだけで、OS の表示 API（`dialog.showErrorBox`、`showMessageBox`、`showMessageBoxSync`）は呼ばない。理由: 独立のレビューが Electron 43.5.0／Linux／Xvfb（GTK）で確かめた報告（記録は本測定の外）では、`showErrorBox` の直後に `app.quit()` を書くと `showErrorBox` が戻らず 12 秒後も process が生存し、`await` しない `showMessageBox` の直後に `app.quit()` を呼ぶと 90 ms で終了して利用者は表示を見られない。前者は無期限の待ちで K1b の規則 1 に反し（無人の journey や CI で終了しない）、後者は表示が届かない。表示を出して有限に待つ方式は新しい上限と機構になり、Windows／macOS を含めて未検証なので、この draft は置かない（引き継ぎ H10）。起動前の文言は固定の 1 行（コードと「原稿は変更されていません」。窓も Native もなく、原稿は読み書きされていない）、実行中はコードだけ（実行中は未保存の原稿を既存の経路で保存するので「変更されていません」とは書かない）。log directory は Rust 側の logging が書く場所で、起動前（Native の起動前）に使えるかは未確認なので契約にしない（使える手段があれば追加してよい。書込みの失敗や待ちで終了を遅らせない）。
- 固定コード（renderer や設定の値を含まない列挙値。Negative (30a) と 1 対 1）: 起動前: `NC-LISTEN`（listener の起動）、`NC-PROXY`（`setProxy`）、`NC-CLOSE`（`closeAllConnections`）、`NC-SELF-RESOLVE`、`NC-SELF-PROXY`、`NC-TIMEOUT`（起動前の共有の期限の超過）。実行中: `NC-POLICY`、`NC-SESSION`（default session でない webContents）、`NC-LISTENER-LOST`。
- 自己確認（起動前。窓の作成前）: (a) `resolveHost(sentinel)` が `127.0.0.1`。(b) **`EXCLUDE` していない IP literal（`1.1.1.1`、`127.0.0.2`）の `resolveHost` が `ERR_NAME_NOT_RESOLVED`**。(c) `resolveProxy(<固定の URL 3 件: https://turn.attacker.invalid:443/、https://example.invalid:8443/、http://127.0.0.1:1/>)` が `SOCKS5 127.0.0.1:<port>`。(b) が要る理由: 規則（`MAP * ~NOTFOUND` と `EXCLUDE`）が部分的にしか効いていない状態は、(a) と (c) だけでは検出できない。sentinel の `MAP` だけの構成は (a) と (c) を通し、IP literal と名前を解決した（`al0-selfcheck-sentinel-only`）。最終構成では (a)〜(c) が通り、IP literal は失敗した（`al0-selfcheck-final`）。IP literal の判定はネットワークを要さないので、オフラインの CI でも判別できる（`.invalid` や未知の名前の失敗は規則がなくても起きるので、判別に使わない）。**起動前の待ちの期限**: 起動手順 (2)〜(4)（listener の起動、`setProxy`、`closeAllConnections`、自己確認）は、起動手順 (2) の開始から 5 秒の 1 つの期限を共有する（K1b の規則 1（有限。無期限の待ちを作らない）に従う。再試行はしない）。超過した時点で `NC-TIMEOUT` とし、後で返った結果は捨てる（窓は作らず、二重の終了も起こさない）。期限の判定は Main の timer 1 つで、各 `await` を個別に打ち切る機構は足さない。この期限は起動前だけの規則で、実行中の graceful な終了には新しい上限を置かない。5 秒は、Linux の実測の最大値（負荷下の 152 ms、自己確認を除く）の約 30 倍の余裕を見た値で、Windows／macOS の実測はない。それらの遅い初回起動で network service の最初の応答が 5 秒を超えると `NC-TIMEOUT` で毎回終了する誤検知がありうる（未確認。G-pub で各 OS の NC-1 の所要と 5 秒に対する余裕を記録し、余裕が小さければ値を /4 で見直す。引き継ぎ H7）。
- policy の判定（`NC-POLICY`）: 適用が例外を投げた場合に加え、`getWebRTCIPHandlingPolicy()` の読み戻しが `disable_non_proxied_udp` でない場合。
- 起動前（窓がない）の失敗: 窓を 1 つも作らず、固定の 1 行を stderr に出し（上の表示の契約）、`app.quit()` で終了する。OS の表示は出さないので `app.quit()` は表示を待たない。窓がないので close-veto も未保存の原稿もない。NC-1 は `initBackend` より前（MD-1）なので、Native の backend は未起動で、`will-quit` の finalizer（`index.ts:669` で登録）も未登録であり、`app.quit()` は Native の終了 receipt を待たずに終わる（終了で証明すべき Native の状態がない）。
- 起動前の待ちが 5 秒で終わらない場合: `NC-TIMEOUT`（上）。窓も Native の状態もないので、`app.quit()` は未登録の finalizer を待たずに終わる。返らない `await` の promise は捨てるだけで終了を妨げない見込み（窓がなければ `app.quit()` が待つものはない。実機では再現していない。(30a) で返らない promise を注入し、fake timer で期限と終了を示す）。
- 実行中（窓がある）の失敗: (i) 閉じ込めの外の webContents は、何も読み込ませずその場で破棄する。(ii) そのうえで既存の終了の経路（`app.quit()`。close-veto〔`windowChrome.ts` の `createCloseVetoController`、`CLOSE_VETO_TIMEOUT_MS` = 1.5 秒〕と strict persistence drain と `will-quit` の finalizer〔Native 観測の予算 30 秒・最大 3 回の再試行。証明できないときだけ既存の `options.exit(1)`〕）をそのまま使い、未保存の原稿は既存どおり保存を試みる。(iii) 固定コードは stderr に出す（上の表示の契約。OS の表示 API は呼ばない）。graceful な終了は renderer に保存（flush）を頼む経路でもある（local の保存で外への送信ではない）。
- 既存の終了の間の閉じ込めの状態: 破棄した webContents は何も実行しない。listener を失った場合は proxy の port が閉じ、Chromium の接続は失敗する（`g2`、`al0-closed-proxy`: 到達 0）。ただし、その間に別のプロセスがその port を取って SOCKS5 を話すと名前が渡りうる（確率は低いと見るが、推定）。この間の長さは既存の経路の上限に従い、この draft は短くも長くもしない（分単位になりうる。既存の経路の値は、close-veto 1.5 秒、strict persistence drain、`will-quit` の Native 観測の予算 30 秒×最大 3 回の再試行）。残余として開示する。
- 失敗しても窓を開く案（FC-2）は、塞がない状態で O-2 の読取が開くので採らない。固定コードと失敗した段だけを書く（上の表示の契約。renderer や設定の値を含めない。保存先の拡大ではない）。
- 無効化の入口を製品に置かない: packaged build では env、起動引数、設定、IPC のどれからも閉じ込めを止められない。対照（閉じ込めを外した構成）は probe 用の main だけが持つ。

### 補助の層の位置づけ

- 既存の CSP（`connect-src 'self'` など）は、fetch などの通常の経路の第 1 の層として残す。NC-1 は CSP の対象外の経路（WebRTC の接続と名前解決、dns-prefetch）を塞ぐ。CSP が効かない realm が将来できた場合も、AL-0 の下では default session の通信は blackhole へ向く（設計上の帰結。独立のレビューの報告では、CSP を外した `app://` の応答の同一 origin の realm で fetch／XHR／img／beacon／WebSocket／worker を試し、ベースラインは 56 行中 42 行が到達、NC-1 は 0 到達で 42 行が proxy 側へ向いた。記録は本測定の外で、この draft の根拠にしない）。
- 実機で効かなかったので防御に数えず、足さないもの: preload で main world の `RTCPeerConnection` を消す（iframe の `contentWindow.RTCPeerConnection` で回避でき 19 probe が漏れる。`e1`）、CSP の `webrtc 'block'`、`--disable-webrtc`、`--disable-blink-features=RTCPeerConnection`、`setWebRTCUDPPortRange`、`session.webRequest`（WebRTC の socket を観測できない）、`app.setProxy`（`net.fetch` の proxy を変えるが renderer の WebRTC に効かない）、`x-dns-prefetch-control: off`、`Connection-Allowlist` 応答 header（Electron 43 の binary に実装の文字列は実在するが、どの構成でも漏れは変わらない。`f1`）。
- WebRTC の policy は補助でなく NC-1 の一部（policy だけでは塞がらない。`h3`）。

**推奨: AL-0**。理由: ユーザーの案 1（構造的に塞ぐ）に沿い、許可先を置かないので、label や平文の経路が残らない。辞書の停止の代償は限定的と見る（小さいとは断じない）: 製品の `editor.spellCheck` の既定は `false` だが、言語 `en` のプロジェクトは既定で `true`（「unrestricted の挙動への影響」の 2）なので、辞書が未取得の新規 install（Windows／Linux）の `en` のプロジェクトは、spellcheck が有効でも何も検査されない。取得済みの辞書の file が既存の利用者に残ることは、独立のレビューの Linux の報告（影響表 2。記録は本測定の外）にとどまる。AL-3 は redirect 先（`rr<N>---sn-*.gvt1.com`）が止まるため辞書の利益が得られず、残余だけが残る（`al3-dict`）。AL-1 は残余が重い。辞書を Main 側で取得する案、同梱する案、取得先を exact host に固定する案は、未検証で別の課題（引き継ぎ H2）。

### 名前の漏れ（NL）の定義（名前の合否の述語はここだけ）

冒頭の 1、変える点 6、(23b)、(32)、(34)、選択肢の表の「名前の解決 0」は、この述語を指すだけで、別に定義しない。

- 観測する host: `getaddrinfo` の記録層の name、DoH の canary の qname、Chromium の net log の `HOST_RESOLVER_MANAGER_REQUEST`／`JOB` の host。正規化: scheme、port、末尾の dot、IPv6 の角括弧を外し、小文字にする（net log の生の形は `https://~notfound`、`http://~notfound:35057`、`app://github.com`、`127.0.0.1:39035` など。`nl-al0-final`）。
- 許容集合 A: RS-1 の 4 名（`github.com`、`objects.githubusercontent.com`、`release-assets.githubusercontent.com`、`localhost`）、sentinel（`grimodex-rule-sentinel.invalid`）、`127.0.0.1`（`127.1`、`0x7f.0.0.1`、`2130706433` などの別形式は `127.0.0.1` に正規化されて同じ）、net log に限って `~notfound`（rules が拒否した名前の書換え先）、DoH の canary の qname に限って `www.gstatic.com`（DoH を有効にした観測の構成で出る Chromium の到達性確認の名前。`al0-doh`: 28 件、ほかの名前は 0。固定名で攻撃者が選べない。帰属は未確認で、製品の通常の起動で出る通信とは主張しない）。A の限定つきの要素はこの 2 つだけで、実行者が試験ごとに除外を足さない。
- 合格: 観測した host の正規化した集合が A の内側であること。A の外の host、または試験が行ごとに生成する nonce を含む名前が 1 件でもあれば漏れ。nonce を含む名前だけを数えることはしない（RS-1 外の名前の取りこぼしを見逃すため）。
- 不活性の行（RJ）は、`getaddrinfo` の記録 `dnsNames` が許容集合 A の内側であること（末尾 dot と大文字小文字を正規化。道具が行の種類を問わず見る）を行の判定にする。これは NL の `getaddrinfo` の分の部分集合で、DoH と net log の観測を含む全体の合否はこの定義のままである。
- RS-1 の名前の行（RS-1 の 4 名を STUN／TURN の host にした行と、その名前への dns-prefetch）の解決は期待値で、漏れに数えない（`nl-al0-final`: 解決の記録がある行は 6）。行ごとの合否は「その行で観測した host が A の内側」で決め、「`dnsNames` が空」は使わない。canary への到達 0 は別に数える。

### 行ごとの合否（RJ）の定義（行の合否の述語はここだけ）

冒頭の 7、(23)、(29)、(34) は、この述語を指すだけで、別に定義しない。合否は**行ごと**に決め、集計値（canary 到達の合計、proxy 宛の合計）は合格の根拠に使わない（記録の参考値）。不合格だけを足す必要条件は下の「記録全体の必要条件」。集計値では、canary を置けない宛先や、`<-loopback>` を外して DIRECT に落ちた行が、他の行の proxy 宛の合計に紛れて見逃される。DA-1 が行を足しても、この規則が自動的に効く。

**行の区分（TCP と UDP の ICE 行。1 つの行は次の表の 1 つだけに入り、区分は閉じ込めなしの対照の同じ行の観測だけで決まる）**: 対照は、同じ行列を閉じ込めなしで、**判定する構成と同じ名前解決の環境**で走らせたベースライン（G-open は対照を必須で走らせる。対照なしの判定は参考で合否に使わない）。環境は 2 通りある。(23a) の形は、名前を `127.0.0.1` の canary へ写す対照で、**末尾 dot つきの名前も写す**（WebRTC は FQDN の remote candidate と STUN／TURN-UDP の名前を `rcu-<n>.probe.test.` のように末尾 dot つきで事前解決するので、dot なしの `MAP *.probe.test` だけでは一致せず、名前が `MAP * ~NOTFOUND` で拒否される）。この対照では、名前を宛先とする行（ICE server の名前、FQDN の remote candidate）も canary に届く。(23b) の形は実 DNS の対照で、`*.probe.test` は解決できず、ICE server の名前の行は canary に届かないが名前の解決が試みになる。対照での「接続の試み」は、canary への到達、ICE の進行中（`gathering:gathering`／`ice:checking`）、ICE server の行の名前の解決のどれか。**remote candidate の行は、名前の解決だけでは試みに数えない**（隣の行の名前が時間窓に入って解決の記録が付く行があるため）。このため、非 mDNS の FQDN の remote candidate の 5 行は、(23a) の対照では canary に届いて**活性の行**になり（`fm-baseline`）、(23b) の実 DNS の対照では名前の解決だけで `ice:new` のまま接続しない**不活性の行**になる（`fq-baseline`）。後者は対照の環境（名前が解決できない）の性質で、経路の性質ではない。**(23a) の対照の成立条件**: 名前を宛先とする行（STUN／STUNS／TURN-UDP／TURN-TCP／TURNS／TURNS-TCP の名前、FQDN の remote candidate）が対照で canary に届いて活性の行にならなければ、対照の写しの欠陥で、(23a) を通さない。

| 区分 | 対照での観測 | 合否 |
| ---- | ------------ | ---- |
| 活性の行 | canary に到達する | 下の「行の種類」の合格条件で判定する |
| canary を置けない宛先の行 | canary には届かないが、接続の試みが観測できる（link-local の `169.254.169.254`、(23b) の対照の実 DNS で解決先のない名前、公開名など） | 活性の行と同じ合格条件。canary 0 は最終構成でも見かけの 0 で根拠にならず、TCP は proxy 宛、UDP は ICE の状態だけが合否を決める |
| 不活性の行 | 接続の試みが観測できない。`[fe80::1]`、localhost の TURN-TCP／TURNS（RS-1 の行）、(23b) の対照の FQDN の remote candidate など | **正常時は合否に数えず**、列挙して理由を記録に残す。ただし次のどちらかがあれば**不合格の行として判定に移る**（判定の件数に入る）: canary 到達、行の `getaddrinfo` の記録 `dnsNames` に許容集合 A の外の名前（行の種類を問わない。末尾 dot と大文字小文字を正規化）。名前の全体の合否は NL と (32) |

区分の件数（活性、canary を置けない宛先）は TCP／UDP の行の内訳で、DNS だけの行と不活性の行は別である。不活性の行は判定の件数の外にあり、区分の件数を合否の分母に使わない。

**行の種類ごとの合格条件**（活性の行と canary を置けない宛先の行に適用する）:

| 行の種類 | 該当する行 | 合格の条件 |
| -------- | ---------- | ---------- |
| TCP | `turn-tcp`／`turns`／`turns-tcp`、`remote-candidate-tcp`（IP literal と FQDN）、TURN-TCP を載せる行（30 件・8 URL・約 200 文字の名前、RS-1 の名前、`gvt1`、公開名の行）、`sx.multi-url.*`（複数 URL を混ぜた server。TURN-TCP を含む。id に proto がなく outcome は `multi`）、`sx.setconfiguration.turn-tcp.*`（outcome は `setconf`） | canary 到達 0 **かつ** その行の時間窓で blackhole の listener への接続が 1 以上 |
| UDP | `stun`／`stuns`／`turn-udp`、`remote-candidate-udp`（IP literal と FQDN） | canary 到達 0 **かつ** ICE が policy で止まった形（行の outcome が `gathering:complete` または `ice:new`。閉じ込めなしでは IP literal の行と、(23a) の形の名前を写した行が `gathering:gathering`／`ice:checking` で進行する） |

| `.local` | `.local` の行 | RJ では判定しない。合否は (23) の `.local` の規則だけ（観測は UDP 5353 の multicast の受信 socket で、DA-1 が足す。道具は `.local` の行を `mdns` として判定から外すだけで、`.local` の観測を持たない）。canary への到達があれば「記録全体の必要条件」で不合格 |
| 対象外（道具の `classify` が返す `n/a`） | `control.*`、Main 側の通信の確認（`main.net-fetch*`、`main.updater-style-net-request`、`main.node-fetch`）、`realm.worker-rtc-defined`、`sx.webtransport.*`（outcome は `wt:WebTransportError`）、`sx.bundled-worker-rtc`（outcome は `w:worker-ok:rtc?`。この 2 種は outcome が下の接頭辞で始まらないので id で対象外にする。ICE の行ではなく CSP と handler の対照）、outcome が `error:`／`no-window`／`rtc-undefined`／`setRemoteDescription-failed` で始まる行（blob の iframe の `SecurityError`、`window.open` の `no-window`、worker の `worker-error` が代表例。CSP と handler で ICE まで届かない） | 合否は判定しない。列挙して記録に残す。**canary への到達があれば不合格**（下の「記録全体の必要条件」） |
