用語
- 「日時」：出来事の、作中の開始の日（暦の起点からの日数）と、分。
- 「確度」：日時の確かさ。画面の文言で「確定」「おおよそ」「不明」の 3 つ。
- 「裏の並び」：出来事ごとに保存している順番の値（コードでは ordinal）。画面には出ない。
- 「作中の現在地」：今書いている場面が、作中のいつに当たるかを表す値（コードでは anchor）。
- 「自動のまとめ」：チャットに毎回自動で入る、年表の要約。
- 「Native」：Rust で書いた本体の側。

## 0. 一枚目

**何を決める案か。** 年表の出来事は、必ず日時を持つ。日時が分からないことは、確度で表す。出来事の前後は、日時で比べる。

**なぜ要るか。**
- 年表の画面は、出来事を日時で並べる。ところが、AI 向けの前後の判定は、裏の並びを使っている。画面で作った出来事は、裏の並びが全部同じ値になる。そのため、AI 向けの判定は、日時に関係なく、ほぼ全部の出来事を「これまで」に入れている見込みである（コードの読み。実行していない）。
- 日時の無い出来事があると、前後を決める物差しが 2 つ要る。抽出の提案を承認して年表に入れると、日時の無い出来事が増える。

**形**
1. 出来事を作る・変える入口で、Native が、日時の無い出来事を拒む。
2. 前後の比べ方は、1 つにする。日時と分、同じなら裏の並び、それも同じなら id。
3. 既にある日時の無い出来事には、移行で日時を入れる。年表の画面で今見えている位置を、そのまま日時にする。確度は「不明」にする。
4. 抽出の提案を承認して年表に入れるときは、出来事に日時を入れる。提案が日時を持たないときは、根拠の場面から機械的に決める。
5. 確度が「不明」の出来事も、前後は日時で比べる。ただし、場面の「作中の現在地」を決める材料にはしない。
6. AI に年表の出来事を渡すときは、確度も渡す。

**変えないこと**
- 保存済みの裏の並びは、書き換えない。並べ直さない。
- 作者が付ける印（Codex の hidden、年表の出来事の秘密の印）の判定は、変えない。
- 場面の作中日付は、今までどおり、入れなくてもよい。

## 1. 確かめた事実

### 1.1 ユーザーの決定（2026-11-22）

1. 年表の画面の並びと、AI 向けの判定の食い違いは、「比べ方をそろえる」形で直す。保存済みの裏の並びは書き換えず、前後を比べる箇所を全部、年表の画面と同じ 1 つの比べ方に通す。
2. 「日時の無い Event を禁止しましょう。不明な日時は日付の確度で表現することができますし。」（原文）。日時の無い出来事を並べ替える操作は、足さない。
3. 確度が「不明」の出来事の前後は、ほかと同じく日時で比べる。AI に渡すとき、確度も渡す（原文「2で確度も注入」）。
4. 既にある日時の無い出来事には、移行で日時を与える。画面で今見えている仮の位置を、その出来事の日時として保存する。確度は「不明」にする。
5. AI や MCP が、日時を指定せずに出来事を作ろうとしたときは、拒んで、日時を指定させる。
6. 抽出の提案を承認して年表に入れるときの日時は、根拠の場面から取る。取れなければ、AI が、その場面のほかの場面や出来事も使って推定する（原文「1+3。1で取れなければ、AIがそのSceneだけでなく他のSceneやEventなども活用して推定抽出を行います。」）。
7. AI による推定は、「抽出のときに AI が推定する」形にする。選択肢の説明は、次のとおりだった。抽出の指示と提案の形を変え、提案が最初から推定の日時を持つ。評価の凍結した材料に触れ、60 を超える file が変わる見込みである。公開の直前に 1 回だけ凍結する方針と、時期がぶつかる。
8. 確度が「不明」の出来事は、場面の「作中の現在地」を決める材料にしない。

起案者の読み（決定ではない。◇2 で確認する）：決定 6 の「取れなければ」は、「根拠の場面に作中日付が無ければ」と読む。手前の場面の日付や年表の出来事は、AI の推定の材料として渡す。

### 1.2 年表の 2 つの並び

- 年表の画面は、出来事を、日時で横に並べる。日時の無い出来事だけ、日付の範囲の後ろに、裏の並びと id の順で、仮に置く。全部の出来事に日時が無いときだけ、裏の並びで並べる。【読んだ（`src/features/chronicle/chronicleAxis.ts:38-75`）】
- 年表の画面で新しく作る出来事は、裏の並びを渡さずに保存される。Native が、既定の同じ値（`a0`）を入れる。アプリ内の AI と MCP が作る出来事も、同じである。【読んだ（`ChroniclePanel.tsx` の `handleAdd`、`src/features/agent-writes/event.ts:574-585`、`agent_writes.rs:7942`）】「既存の最後の次」を入れる関数は、古い抽出と、原稿の読み込みだけが使う。【読んだ（`src/features/chronicle/api.ts:173-204` と、その呼び出し元）】
- AI 向けの前後の判定は、裏の並びが「作中の現在地」以前かどうかで決める。【読んだ（`chronicleSnapshot.ts:101-104`、`:183-201`）】同じ比べ方を、人物の所在・未回収の因果・本文未描写の背景・人物の選び方でも使う。MCP 側（Rust）にも、同じ処理の写しがある。【報告】
- 「作中の現在地」は、場面に作中日付があれば、その日付で決まる。無ければ、その場面に結び付いた出来事のうち、裏の並びが最も後ろのもので決まる。それも無ければ、読む順で手前の場面から借りる。【読んだ（`resolveSceneAnchor.ts:73-191`）】
- 年表の整合の検査（因果の逆転、二か所に同時に居る、年齢、季節）と、人物の生死の導出は、日時を見ている。裏の並びが食い違っても、誤らない。【報告】

### 1.3 日時の無い出来事ができる経路

- 年表に、日時のある出来事が 1 つでもあれば、画面で新しく作る出来事には、必ず日時が入る。選んだ位置の日時か、無ければ画面の中央の日時である。【読んだ（`ChroniclePanel.tsx:1135-1195`、`:1490-1510`）】
- 日時の無い出来事ができるのは、次の場合である。
  - 年表の出来事が、全部日時なしの間に作ったとき（年表が空のときを含む）。【報告】
  - 作者が、出来事の日付の欄を消したとき。【読んだ（`EventDateFields.tsx:140` に、日時を消す書き込みがある）】
  - 画面の、複数の出来事の日付をまとめて消す操作。【報告】
  - アプリ内の AI か MCP が、日時を渡さずに作ったとき。【読んだ（`src/features/chat/agent/chronicleWriteTools.ts:112-150`。日時は任意）】
  - 抽出の提案を承認して、年表に入れたとき。【読んだ（`commit.rs:3129-3139`、`src/features/chronicle/extraction/compiler.ts:118-140`）】
  - 原稿の読み込みで出来事を作ったとき。【報告】
- 公開済みの版（v2.0.10）にも、年表と、日時の無い出来事ができる経路があった。利用者の作品に、日時の無い出来事があり得る。どれだけあるかは、分からない。【報告】

### 1.4 取り消しと復元

- 取り消し（undo）は、出来事の行を、記録してある前の値で、まるごと書き戻す。作品のスナップショットの復元は、出来事の表を、スナップショットの値で入れ直す。どちらも、書き戻した後に、値を整える処理は無い。【報告】
- そのため、移行の後でも、移行の前に取った記録を使うと、日時の無い出来事が戻ることがある。【報告】

### 1.5 抽出と、評価の凍結

- 抽出の提案は、今は日時の欄を持たない。本文の中の時間の表現を、文字列で持つだけである。抽出の AI への指示は、「推測の暦日へ変換しない」と明記している。抽出の AI に送っているのは、場面の本文だけで、既存の出来事・場面の日付・暦は送っていない。【報告】
- 取り込みの出来事は、画面の側と Native が、同じ決まった値（日時なし・確度「不明」）で組み立て、Native が照合する。【読んだ（`compiler.ts:118-140`、`commit.rs:3129-3139`）】
- 凍結に束ねる評価の道具は、年表への取り込みを呼ばない。取り込みの中で日時を決める変更は、評価の材料に触れない。抽出の指示と提案の形を変える変更は、触れる見込みである。【報告】

## 2. 規則

### 2.1 日時の必須化（N1〜N9）

- **N1**　年表の出来事は、開始の日と、「なし」以外の粒度を、必ず持つ。日時が分からないことは、確度「不明」で表す。場面の作中日付は、今までどおり、入れなくてもよい。
- **N2**　守る場所は、Native の書き込みの入口である。出来事を作る共通の処理、出来事を変える処理、複数の出来事の日付をまとめて変える処理の 3 つと、時間の関係を取り込む処理（今は製品から届かない【報告】）である。保存の形そのものには、制約を入れない（理由は §1.4。N9）。
- **N3**　作るときに、日時が無いか、粒度が「なし」なら、拒む。拒むときの文は、Native・アプリ内の AI・MCP で同じにし、日時を指定してやり直せるように書く。「日時が不確かなら、推定の値を入れて、確度で表す」と案内する。
- **N4**　変えるときに、変えた後の出来事が日時を持たなくなるなら、拒む。
- **N5**　年表の画面で新しく作る出来事には、常に日時を入れる。年表に日時のある出来事か、作中日付のある場面があれば、今と同じ決め方（選んだ位置、無ければ画面の中央）を使う。どちらも無ければ、暦の起点の日に置き、確度を「不明」にする。
- **N6**　出来事の日付の欄から、「なし」を外す。複数の出来事の日付をまとめて消す操作は、無くす。日付を消したいときは、確度を「不明」にする。
- **N7**　アプリ内の AI と MCP の、出来事を作る道具は、日時を必須にする。確度を指定できるようにする。変える道具では、日時を消せないようにする。道具の説明に、「日時が不確かなら、推定の値を入れて、確度で表す」と書く。日時の尺度が分かるように、年表の状況を読む道具の返り値に、暦の要約を足す。
- **N8**　原稿の読み込みで作る出来事は、読み込んだ順に 1 日ずつ置き、確度を「不明」にする。製品から届かない古い抽出の取り込みは、削る。
- **N9**　取り消しと復元は、日時の無い出来事を書き戻しても、拒まない。記録は書き換えない。戻った出来事は、§2.7 のとおりに扱う。

### 2.2 比べ方（K1〜K4）

- **K1**　出来事の前後は、次の順で比べる。開始の日と分。同じなら、裏の並び。それも同じなら、id。日時の無い出来事（§2.7）は、日時のある出来事の全部の後ろに置く。年表の画面の並べ方と、同じ規則である。
- **K2**　この比べ方と、「作中の現在地」の決め方と、前後の判定は、画面側と Native に、1 つずつ置く。MCP 側にある写しは、Native の 1 つに寄せる。画面側と Native が、同じ試験用の例（fixture）を読んで、同じ結果になることを確かめる。
- **K3**　前後を比べている箇所は、全部、K1 に通す。自動のまとめの 5 か所（これまでの出来事、人物の所在、未回収の因果、本文未描写の背景、人物の選び方）、「作中の現在地」の決め方、道具と MCP が返す出来事の並びである。抽出が使う既存の出来事の目録の並びは、変えない（前後の判定に使っていないため）。年表のまわりで、裏の並びを直接比べる書き方を、試験で禁じる。
- **K4**　裏の並びは、書き換えない。役割は、同じ日時の出来事の間の順だけになる。

### 2.3 承認して年表に入れる出来事の日時（G1〜G5）

- **G1**　抽出の提案を承認して年表に入れるとき、出来事には、必ず日時を入れる。
- **G2**　提案が、推定の日時を持つとき（§2.4 が入った後の提案）は、それを使う。
- **G3**　提案が日時を持たないときは、取り込みの中で、Native が次の順で決める。(1) 根拠の場面のうち、読む順で最初に作中日付のある場面の、日付。(2) 無ければ、読む順で最初の根拠の場面の、「作中の現在地」の日時。(3) それも無ければ、年表の出来事と、作中日付のある場面の、最も後の日の翌日。(4) 年表にも場面にも日付が無ければ、暦の起点の日。
- **G4**　G3 で決めた日時の確度は、「不明」にする。場面の作中日付を写したときも、「不明」にする。回想の場面などで、場面の日付が、出来事の日付とは限らないためである。
- **G5**　1 回の取り込みで複数の出来事を入れるときは、取り込みを始めた時点の年表から、全部の日時を決める。同じ場面の出来事は、同じ日時になり、前後は裏の並び（入れた順）で決まる。

G3 は、画面の側の組み立てと、提案の形を変えない。日時を決めるのは Native だけである。そのため、評価の準備が作る提案と、凍結に束ねる評価の道具には、触れない。【報告】

### 2.4 抽出のときに AI が日時を推定する（別の起案にする）

決定 7 による。抽出の指示・提案の形・Native の検証は、NIR-1 の評価をまとめているセッションの持ち場で、凍結の段取りと合わせる必要がある。2026-11-22 に、そのセッションに相談し、暫定の返事を得た（下の「段取り」）。この節は、骨子だけを書く。規則は、別の起案に書き、そのセッションが評価との整合を見た後で、確認をいただく。

- 抽出のとき、AI が、出来事の提案ごとに、作中の日時と確度を推定する。提案は、推定の日時を持つ。
- 根拠の場面に作中日付があるときは、その日付を使う。無いときに、AI が推定する（起案者の読み。◇2）。
- 推定の材料として、AI に送る内容が増える。暦、場面の作中日付、年表の出来事の題・日時・確度である。今の抽出は、場面の本文だけを送っている。作者が秘密の印を付けた出来事と、hidden の Codex は、送らない。何を、どれだけ送るかは、別の起案で決めて、確認をいただく。
- AI が返す値は、コードが検査する。暦の範囲に合わない値は、捨てる。その提案は、日時を持たない提案として、G3 で扱う。
- 抽出の指示の版、提案の形の版、Native の検証、評価の材料が変わる。提案の形は、今の形に日時の欄を足した、新しい版にする。別の処理に分けるより、契約が 1 つにまとまる。【担当の意見】

段取りと、別の起案で伺う点（評価をまとめているセッションの暫定の返事、2026-11-22）：

- 起案と実装は、この lane のセッションが持つ。ユーザーに見せる前に、評価をまとめているセッションが、評価・凍結・関連する過去シーンの資格との整合を見る。
- 関連する過去シーンは、確認済みの指示の版で作った解釈だけを使う。Native に、その版の一覧がある。新しい版を一覧に足さないと、新しく抽出した解釈は、承認しても、関連する過去シーンに出ない。一覧に足すと、関連に使える解釈の集まりが変わる。ADR 013 は、関連の資格の規則を、公開の後まで変えないと置いている。一覧に足すことが、これに当たるかは、読みだけで決めず、ユーザーに伺う。【報告と、担当の意見】
- 抽出の AI に送る内容が増える。SRA/1 の「測定を待たない」（承認した出来事の印についての決定）を、この変更にも当てるかは、別に伺う。
- 既に凍結した材料が、今の抽出の指示の出力に、どこまで頼っているかは、確かめていない。頼っていれば、取り直しの費用と時間が要る。評価をまとめているセッションが調べる。それまで、いつ入れられるかは、決められない。

### 2.5 移行（I1〜I7）

- **I1**　保存の形の版を 1 つ上げ、全部の作品の、日時の無い出来事に、日時を入れる。公開済みの版から上げる作品も、対象である。
- **I2**　入れる日時は、年表の画面で今見えている位置と、同じ順にする。日時のある出来事と、作中日付のある場面の、最も後の日の翌日から、裏の並びと id の順に、1 日ずつ置く。出来事にも場面にも日付が無い作品では、暦の起点の日から、同じ順に 1 日ずつ置く。粒度は「日」、確度は「不明」にする。
- **I3**　日時はあるのに、粒度が「なし」の出来事は、粒度を「日」（分があれば「時刻」）に直す。確度は変えない。
- **I4**　移行は、2 回走っても、2 回目は何も変えない。想定しない値の行は、飛ばして、止まらない。移行を済ませた印を残し、前の版からの近道が、移行を飛ばさないようにする。【近道があることは報告】
- **I5**　移行で日時を入れた出来事について、変更の記録の連なりの「先頭の印」を消す。記録そのものは消さない。消さないと、その出来事の次の編集が、「連なりが合わない」として失敗する。【報告】防御に触れるので、◇3 で確認する。
- **I6**　移行で入れた日時の欄には、「機械が入れた値」という持ち主の印を付ける。付けないと、作者が書いた値として扱われ、後から AI が直せない。作者が直すと、作者の値に変わる。列は足さない。【報告】新しい権限の使い方に当たるかを、◇3 で確認する。
- **I7**　移行は、出来事の版の番号を上げない。裏の並びと、取り消しの記録は、書き換えない。進行中の抽出は、既存の出来事の目録が変わるので、作り直しになる。

### 2.6 確度と、「作中の現在地」（C1〜C5）

- **C1**　AI に年表の出来事を渡すときは、出来事ごとに、確度を渡す。自動のまとめは、確度が「おおよそ」「不明」の出来事の行に、その旨を添える。道具と MCP の返り値には、確度の欄を足す。まとめの導入の文に、「確度が不明の出来事の前後は、不確かである」と書く。
- **C2**　確度が「不明」の出来事も、前後は、K1 で比べる（決定 3）。
- **C3**　確度が「不明」の出来事は、場面の「作中の現在地」を決める材料にしない（決定 8）。その場面に結び付いた出来事から選ぶときも、手前の場面から借りるときも、除いてから選ぶ。場面の作中日付は、今までどおり使う。
- **C4**　「作中の現在地」は、次の順で決める。場面に作中日付があれば、その日付。無ければ、その場面に結び付いた、確度が「不明」でない出来事のうち、日時が最も後のもの。それも無ければ、読む順で手前の、現在地を持つ最も近い場面から借りる。どれも無ければ、決まらない。
- **C5**　年表の整合の検査（因果の逆転、二か所に同時に居る、年齢、季節）と、人物の生死の導出は、確度が「不明」の出来事を、対象から外す。仮の日時が、誤った警告や、誤った生死を出さないようにするためである。前後の比べ方（C2）とは、別の扱いである。

### 2.7 日時の無い出来事が戻ったとき（B1〜B2）

- **B1**　取り消しや復元で、日時の無い出来事が戻ったときは、次のように扱う。前後は、日時のある出来事の全部の後ろ（K1）。「作中の現在地」の材料にしない。整合の検査の対象から外す。年表の画面は、今の仮の位置の表示を残す。
- **B2**　戻った出来事は、次にその出来事を変えるときに、I2 と同じ決め方で、日時を補う。確度は「不明」にする。起動のたびに全部を調べ直すことは、しない。

## 3. 残る制限

- 保存の形に制約を入れないので、取り消しや復元の後に、日時の無い出来事が、一時的に残ることがある（B1・B2）。
- 保存された裏の並びは、日時の順にならない。値そのものを読む人（保存のファイルを直接見る人）には、順が合って見えない。
- 移行で入る日時と、G3 で決める日時は、仮の値である。年表の画面では、ほかの出来事の後ろや、根拠の場面の日付に置かれる。作者が、年表で動かして、確度を直す。
- 確度が「不明」の出来事は、「作中の現在地」の材料にならない（C3）。承認して入れた出来事しか結び付いていない場面は、手前の場面から現在地を借りる。借りる先も無ければ、現在地は決まらない。
- 確度が「不明」の出来事は、整合の検査に掛からない（C5）。
- 日時と裏の並びが食い違っていた作品では、自動のまとめに入る出来事が、今と変わる。変わる向きは、年表の画面の並びに合う方である。
- MCP を使う外部の道具は、日時を付けずに出来事を作る今の呼び方では、失敗するようになる（決定 5）。
- 年表の出来事が全部日時なしの作品は、今は「並びの順」の表示である。移行の後は、暦の日付の表示になる。
- 要らなくなる画面の部品（並びの順の表示、仮の位置の表示、「シーンから取込」と「スタンプ」のボタン）は、この案では触らない。日時の無い出来事が戻ったときの表示に使うものがあるためである。整理は、公開の後に、別に決める。

変える防御・足す防御は、6 つある。どれも、ユーザーの確認まで draft である。

| 変えるもの | 信頼する相手 | 信頼しない相手 | 範囲内の攻撃・事故 | 必須の防御 | 受入れへの影響 |
| ---------- | ------------ | -------------- | ------------------ | ---------- | -------------- |
| Z1 日時の必須化を、Native の入口で守る（N1〜N8） | Native、作者の画面の操作 | アプリ内の AI の出力、MCP の外部の利用者、取り込みの操作の値 | 日時の無い出来事を作る。変えて日時を消す。まとめて日付を消す | 作る・変える・まとめて変える、の入口の検査。出来事を書く箇所を数える試験を置き、検査を通らない新しい入口が増えたら、試験が落ちる | 入口ごとに、拒むことの試験を足す。AI の道具の定義の、固定した期待値が変わる。MCP の入力が変わる |

## 5. 順番

PR は 1 本ずつ出す。

1. **記録と、起案の書き直し**（文書だけ）。
2. **比べ方・現在地・仮の日時の決め方**（K1・K2、C3・C4、I2）。新しい file だけを足す。画面側と Native に 1 つずつ。試験用の例。既にある処理は、まだ切り替えない。
3. **移行**（I1〜I7）。保存の形の版を上げる。公開済みの版からの上げ方の試験。
4. **Native の入口の検査と、取り込みで日時を決める処理**（N1〜N4・N9、G1〜G5、B2）。同じ PR にする。分けると、取り込みが、日時が無いとして失敗する。
5. **入口の変更**（N5〜N8）。年表の画面、アプリ内の AI、MCP、原稿の読み込み、設計書。
6. **切り替え**（K3、C1〜C5、B1）。前後を比べている箇所を、全部、新しい比べ方に通す。画面側・Native・MCP を、1 本で切り替える。年表のまとめの file に触れるので、道具の作り直しの lane（Mastra への移行）が、その file を共有の場所へ移す前に入れ、その lane の担当に知らせる。
7. CPL/1（位置の区別）の実装。6 の後。
8. SRA/1 の、取り込みを既定で有効にする段。3・4・6・7 の後。
9. 抽出のときの AI の推定（§2.4）。別の起案の確認と、評価をまとめているセッションとの段取りの後。時期は、既に凍結した材料への影響が分かってから決める。

2〜6 は、8 の前提である。取り込みを開けると、仮の日時の出来事が増える。比べ方と現在地の規則が、先に要る。

## 7. 未確認と限界

- この文書の【報告】は、2026-11-22 の read-only の調査の結果である。起案者は、該当の行を読んでいない。実装の前に、基点のコードで読み直す。結果は、repo の外の `design-notes/editor-scene-interpretation-2026-11-21/wf16.json`・`wf17.json` にある。
- どの挙動も、実行して確かめていない。「AI 向けの判定が、ほぼ全部の出来事を『これまで』に入れている」（§0）は、実装の最初に、試験で再現する。
- 移行で入れる位置が、年表の画面の今の位置と、1 件も違わないことは、確かめていない。画面の計算は、小数の日を使う。保存する日は、整数である。時刻つきの日付が最も後にある作品では、1 日未満のずれが出る見込みである。順は変わらない。【報告】
- 「変更の記録の連なりの先頭の印」と、「欄の持ち主の印」の仕組みは、調査の報告による。I5・I6 は、実装の前に、起案者が読み直す。
- 取り込みで入れる日時の欄に、I6 と同じ印を付けるかは、決めていない。取り込みが今、欄の持ち主をどう記録しているかを、確かめていない。
- 日時が同じ出来事の前後は、裏の並びで決まる。画面で作った出来事は、裏の並びが同じ値なので、id の順になる。同じ日の出来事の順が、意味のある順にならないことがある。分まで入れれば、決まる。
- 期間のある出来事（終わりの日時を持つ）と、粗い粒度（年・季節・月だけ）の出来事の、前後の判定は、開始の日だけで比べる。今の扱いと同じである。【報告】
- 抽出の指示を変えると、既に凍結した材料のどれを取り直すことになるかは、分かっていない（§2.4）。この案の 1〜8（§5）は、抽出の指示を変えずに進められる。
- 別件の不具合（この案の範囲外）：製品の取り込みの呼び出しが、年表の末尾の値を渡していない（SRA/1 で直す）。原稿の読み込みが付ける裏の並びの値の形によっては、その後の新規作成が失敗しうる。【報告】
