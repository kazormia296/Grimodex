用語
- 「日時」：出来事の、作中の開始の日（暦の起点からの日数）と、分。「日時がある」とは、開始の日があり、粒度が「なし」でないことをいう。
- 「粒度」：日時の細かさ。時刻、日、月、季節、年。
- 「確度」：日時の確かさ。画面の文言で「確定」「おおよそ」「不明」の 3 つ。
- 「裏の並び」：出来事ごとに保存している順番の値（コードでは ordinal）。画面には出ない。
- 「作中の現在地」：今書いている場面が、作中のいつに当たるかを表す値（コードでは anchor）。
- 「自動のまとめ」：チャットに毎回自動で入る、年表の要約。
- 「道具」：チャットの AI が、自分で呼び出して年表を読み書きする仕組み（tool）。
- 「Native」：Rust で書いた本体の側。

## 0. 一枚目

**何を決める案か。** 年表の出来事は、必ず日時を持つ。日時が分からないことは、確度で表す。出来事の前後は、日時で比べる。

**なぜ要るか。**
- 年表の画面は、出来事を日時で並べる。ところが、AI 向けの前後の判定は、裏の並びを使っている。画面で作った出来事は、裏の並びが全部同じ値になる。そのため、AI 向けの判定は、日時に関係なく、ほぼ全部の出来事を「これまで」に入れている見込みである（コードの読み。実行していない）。
- 日時の無い出来事があると、前後を決める物差しが 2 つ要る。抽出の提案を承認して年表に入れると、日時の無い出来事が増える。

**形**
1. 出来事を作る・変える入口で、Native が、日時の無い出来事を拒む。
2. 前後の比べ方は、1 つにする。日時で比べる。今の場面と同じ日時の出来事は、「これまで」でも「これから」でもなく、「同時進行」として扱う。
3. 既にある日時の無い出来事には、移行で日時を入れる。年表の画面で今見えている位置を、そのまま日時にする。確度は「不明」にする。
4. 抽出の提案を承認して年表に入れるときは、出来事に日時を入れる。根拠の場面の作中日付を使う。無ければ、提案が持つ推定の日時を使う。それも無ければ、Native が機械的に決める。
5. 確度が「不明」の出来事も、前後は日時で比べる。ただし、場面の「作中の現在地」を決める材料にはしない。出来事が全部「不明」の作品だけは、材料にする。
6. AI に年表の出来事を渡すときは、確度も渡す。

**変えないこと**
- 移行と取り込みは、保存済みの裏の並びを書き換えない。並べ直さない。
- 作者が付ける印（Codex の hidden、年表の出来事の秘密の印）の判定は、変えない。
- 場面の作中日付は、今までどおり、入れなくてもよい。
- 年表の出来事の一覧を読む処理の並びと、抽出が使う既存の出来事の目録の形は、変えない。凍結に束ねる評価の道具が、これを呼ぶためである。

## 1. 確かめた事実

### 1.1 ユーザーの決定（2026-11-22）

1. 年表の画面の並びと、AI 向けの判定の食い違いは、「比べ方をそろえる」形で直す。保存済みの裏の並びは書き換えず、前後を比べる箇所を全部、年表の画面と同じ 1 つの比べ方に通す。
2. 「日時の無い Event を禁止しましょう。不明な日時は日付の確度で表現することができますし。」（原文）。日時の無い出来事を並べ替える操作は、足さない。
3. 確度が「不明」の出来事の前後は、ほかと同じく日時で比べる。AI に渡すとき、確度も渡す（原文「2で確度も注入」）。
4. 既にある日時の無い出来事には、移行で日時を与える。画面で今見えている仮の位置を、その出来事の日時として保存する。確度は「不明」にする。
5. AI や MCP が、日時を指定せずに出来事を作ろうとしたときは、拒んで、日時を指定させる。
6. 抽出の提案を承認して年表に入れるときの日時は、根拠の場面から取る。取れなければ、AI が、その場面だけでなく、他の場面や出来事も使って推定する（原文「1+3。1で取れなければ、AIがそのSceneだけでなく他のSceneやEventなども活用して推定抽出を行います。」）。
7. AI による推定は、「抽出のときに AI が推定する」形にする。選択肢の説明は、「抽出の指示と提案の形を変え、提案が最初から推定の日時を持つ。評価の凍結した材料に触れ、60 を超える file が変わる見込みである。公開の直前に 1 回だけ凍結する方針と、時期がぶつかる」という内容だった。
8. 確度が「不明」の出来事は、場面の「作中の現在地」を決める材料にしない。
9. 「作中日時は時間まで設定できるので同日同時刻の場合と読みます。同時刻の場合、これはこれまででもこれからでもない、同時進行の物事と扱うべきです。それが不可能であれば、読み順で判定してください。」（原文）。
10. 出来事が全部、確度「不明」で、作中日付のある場面も無い作品に限り、確度が「不明」の出来事を、現在地の材料にする。
11. 抽出のときの推定は、暦、前後の場面の作中日付、年表の出来事も AI に見せて、AI が判断する形（起案 EET/1）を、最初から入れる。選択肢の説明は、「AI に送る内容が増え、費用は約 25% 増える。要約の文を通じて守りが崩れないことを測る評価と、評価の準備の直しが要り、最後の凍結と公開が遅れる。送る内容は、起案で見せて確認をいただく」という内容だった。
12. 抽出のときに AI が推定した日時の確度は、「おおよそ」を許す。本文の表現がはっきりしているときは「おおよそ」、幅があるときは「不明」である。「おおよそ」の出来事は、場面の「作中の現在地」の材料になる。
13. 期間のある出来事は、始まりから終わりまでを幅とする。季節だけの出来事は、その季節を幅とする。暦に、月や季節の定義が無い作品では、月や季節だけの出来事の幅を、保存された開始の 1 日とする。
14. 移行で日時を入れるとき、裏の並びが同じ出来事は、作った順に置く。年表の画面の今の並び（内部の id の順）とは、変わる。決定 4 の「画面で今見えている仮の位置」を、この点で改める。
15. 抽出のときの推定の質が、測った結果、足りなかったときは、結果を見て決める（開けるか、直して測り直すか、閉じたまま公開するか）。

起案者の読みと提案（2026-11-22 に、まとめて確認いただいた。§6）
- 決定 6 の「取れなければ」は、「根拠の場面に作中日付が無ければ」と読む（G2〜G5 の順）。
- 決定 9 の「同時刻」を、出来事の幅で読む（K2）。日だけの出来事はその 1 日、月・年だけの出来事はその月・年、期間のある出来事は始まりから終わりまで、季節だけの出来事はその季節を、幅とする。ここまでは、確認いただいた（決定 13 と、14 点の確認）。期間のある出来事で現在地を決めたときの、現在地の幅（開始の日だけにする）は、まだ伺っていない（◇11）。
- 決定 9 の「それが不可能であれば、読み順で判定」を、手前の場面から現在地を借りた場合に当てる。借りた現在地は、今の場面そのものの日時ではないので、同時かどうかを決められない。その場合、借りた先の日時と重なる出来事は、読む順で手前の場面のものとして、「これまで」とする（K2a）。
- 年表の状況を読む道具の返り値に、暦の要約を足す（N7）。AI が、日時の尺度を知るためである。
- 年表の整合の検査と、人物の生死の導出から、確度が「不明」の出来事を外す（C5）。

### 1.2 年表の 2 つの並び

- 年表の画面は、出来事を、日時で横に並べる。日時の無い出来事だけ、日付の範囲の後ろに、裏の並びと id の順で、仮に置く。全部の出来事に日時が無いときだけ、裏の並びで並べる。【読んだ（`src/features/chronicle/chronicleAxis.ts:38-104`）】同じ日時の出来事どうしの順は、画面は決めていない。【報告】
- 年表の画面で新しく作る出来事は、裏の並びを渡さずに保存される。Native が、既定の同じ値（`a0`）を入れる。アプリ内の AI と MCP が作る出来事も、同じである。【読んだ（`ChroniclePanel.tsx` の `handleAdd`、`src/features/agent-writes/event.ts:574-585`、`agent_writes.rs:7942`）】「既存の最後の次」を入れる関数は、古い抽出と、原稿の読み込みだけが使う。【読んだ（`src/features/chronicle/api.ts:173-204` と、その呼び出し元）】
- AI 向けの前後の判定は、裏の並びが「作中の現在地」以前かどうかで決める。【読んだ（`chronicleSnapshot.ts:101-104`、`:183-201`）】同じ比べ方を、人物の所在・未回収の因果・本文未描写の背景・人物の選び方でも使う。MCP 側（Rust）にも、同じ処理の写しがある。【報告】
- 「作中の現在地」は、場面に作中日付があれば、その日付で決まる。無ければ、その場面に結び付いた出来事のうち、裏の並びが最も後ろのもので決まる。それも無ければ、読む順で手前の場面から借りる。【読んだ（`resolveSceneAnchor.ts:73-191`）】場面の日付による現在地は、今は「その日以前で最も後の出来事の、裏の並び」に直してから比べている。同じ日の出来事は「これまで」に入る。【読んだ（同 `:106-134`）】
- 年表の整合の検査（因果の逆転、二か所に同時に居る、年齢、季節）と、人物の生死の導出は、日時を見ている。日時の無い出来事は、飛ばしている。【報告】
- 裏の並びは、場面の「作中の順」とも関係がある。年表の画面の「スタンプ」は、出来事の裏の並びを、場面の作中の順へ写す。「シーンから取込」は、場面の作中の順を、出来事の裏の並びへ写す。【読んだ（`ChroniclePanel.tsx:1986-2008`）】

### 1.3 日時の無い出来事ができる経路

- 年表の画面は、年表が日付の表示になっていて、画面の幅が測れているときは、新しく作る出来事に必ず日時を入れる。選んだ位置の日時か、無ければ画面の中央の日時である。【読んだ（`ChroniclePanel.tsx:1135-1195`、`:1490-1510`）】年表が日付の表示になるのは、日時のある出来事か、作中日付のある場面が、1 つでもあるときである。【報告】
- 年表が空の状態から、画面で作り始めると、最初の 1 件が日時なしになる。日時なしの出来事だけでは、年表は日付の表示に切り替わらない。作者が横に動かして日時を決めない限り、その後に作る出来事も、全部日時なしになる。【報告】
- そのほかに、日時の無い出来事ができるのは、次の場合である。
  - 作者が、出来事の日付の欄を消したとき。【読んだ（`EventDateFields.tsx:140` に、日時を消す書き込みがある）】
  - 画面の、複数の出来事の日付をまとめて消す操作。【報告】
  - アプリ内の AI か MCP が、日時を渡さずに作ったとき。【読んだ（`src/features/chat/agent/chronicleWriteTools.ts:112-150`。日時は任意）】
  - 抽出の提案を承認して、年表に入れたとき。【読んだ（`commit.rs:3129-3148`、`src/features/chronicle/extraction/compiler.ts:118-140`）】
  - 原稿の読み込みで出来事を作ったとき。製品の画面から届く。【報告】
- 公開済みの版（v2.0.10）にも、年表と、日時の無い出来事ができる経路があった。利用者の作品に、日時の無い出来事があり得る。どれだけあるかは、分からない。【報告】

### 1.4 取り消し・復元・欄の持ち主

- 取り消し（undo）は、出来事の行を、記録してある前の値で、まるごと書き戻す。作品のスナップショットの復元は、出来事の表を、スナップショットの値で入れ直す。どちらも、書き戻した後に、値を整える処理は無い。移行の後でも、移行の前に取った記録を使うと、日時の無い出来事が戻ることがある。【報告】
- 出来事の欄には、「持ち主」の記録がある。作者が書いた値、AI が書いた値、機械が入れた値、不明、の区別である。作者が書いた値の欄は、AI と MCP が書き換えられない。機械が入れた値の欄は、書き換えられる。抽出の取り込みは、出来事の欄を、承認した人の値として記録する。【報告】
- 出来事を変えるたびに、変更の記録が 1 件ずつ連なる。出来事ごとに、連なりの「先頭の印」がある。次の変更のとき、今の値と印が合わないと、変更が拒まれる。保存の形の移行は、走るたびに、この印を作り直す。【報告】

### 1.5 抽出と、評価の凍結

- 抽出の提案は、今は日時の欄を持たない。本文の中の時間の表現を、文字列で持つだけである。抽出の AI への指示は、「推測の暦日へ変換しない」と明記している。抽出の AI に送っているのは、場面の本文だけで、既存の出来事・場面の日付・暦は送っていない。【報告】
- 取り込みの出来事は、画面の側と Native が、同じ決まった値（日時なし・確度「不明」）で組み立て、Native が照合する。【読んだ（`compiler.ts:118-140`、`commit.rs:3129-3139`）】
- 評価をまとめているセッションの調べ（2026-11-22）：凍結に束ねる評価の道具は、年表への取り込みを呼ばない。評価の準備が作る作品には、年表の出来事が 0 件である。関連する過去シーンは、出来事の日時を読まない。この案の移行と、取り込みで日時を決める変更は、評価に触れない。【担当の報告】

## 2. 規則

### 2.1 日時の必須化（N1〜N9）

- **N1**　年表の出来事は、開始の日と、「なし」以外の粒度を、必ず持つ。日時が分からないことは、確度「不明」で表す。場面の作中日付は、今までどおり、入れなくてもよい。
- **N2**　守る場所は、出来事を書く入口の全部である。Native の、出来事を作る共通の処理、変える処理、複数の出来事をまとめて変える処理、時間の関係を取り込む処理（今は製品から届かない【報告】）である。画面の試験で Native の代わりをする部品も、同じ動きにそろえる。使われていない書き込みの処理（MCP の側に残っている写し【報告】）は、削るか、同じ検査を通す。保存の形そのものには、制約を入れない（理由は §1.4。N9）。
- **N3**　作るときに、日時が無ければ、拒む。拒むときの文は、Native・アプリ内の AI・MCP で同じにし、日時を指定してやり直せるように書く。「日時が不確かなら、推定の値を入れて、確度で表す」と案内する。
- **N4**　日付の欄とは、開始と終わりの日・分・粒度をいう。確度は含まない。保存済みの値と違う値を送る更新を、「日付の欄に触れる更新」とする。触れる更新で、変えた後の出来事が日時を持たなくなるなら、拒む。日だけを入れて、粒度が「なし」のままの更新も、拒む。
- **N4a**　日付の欄に触れない更新（題だけを直すなど）で、変える前から日時の無い出来事は、拒まない。同じ処理の中で、I2 と同じ決め方で日時を補う。粒度は「日」、確度は「不明」にする。補った欄は、「機械が入れた値」として記録する（G9 と同じ）。確度だけを変える更新は、日時の無い出来事では拒み、先に日時を指定するよう案内する。複数の出来事をまとめて変えるときは、日時の無い出来事を、裏の並びと id の順に、1 日ずつ置く。出来事を変える入口の全部で行う。取り消しと復元は、補わない（N9）。補う処理は、移行（§5 の 6）の後に有効にする。それまでは、日時の無い出来事の更新を、補わずに通す。
- **N5**　年表の画面で新しく作る出来事には、常に日時を入れる。決め方は、次の順である。(1) 作者が選んだ位置。(2) 画面の中央（年表が日付の表示で、幅が測れているとき）。(3) どちらも使えないときは、I2 と同じ「最も後の日の翌日」。年表にも場面にも日付が無ければ、暦の起点の日。確度は、(1) と (2) が「確定」（今と同じ）、(3) が「不明」である。
- **N6**　出来事の開始の日付の欄から、「なし」を外す。場面の作中日付の欄と、出来事の終わりを「点にする」操作は、残す。複数の出来事の日付をまとめて消す操作は、無くす（場面の日付をまとめて消す操作は、残す）。取り消しや復元で戻った、日時の無い出来事の欄は、「なし」を選択済みとして見せ、選べる値は「日」以上にする。
- **N7**　アプリ内の AI と MCP の、出来事を作る道具は、日時と確度を必須にする。既定の値は置かない。今は、確度を指定できず、AI が入れた推定の日時が「確定」として保存される。【報告】変える道具では、確度を任意で指定できるようにし、日時を消せないようにする。道具の説明に、「日時が不確かなら、推定の値を入れて、確度で表す」と書く。日時の尺度が分かるように、年表の状況を読む道具の返り値に、暦の要約を足す。
- **N8**　原稿の読み込みで作る出来事は、I2 と同じ「最も後の日の翌日」から、読み込んだ順に 1 日ずつ置き、確度を「不明」にする。製品から届かない古い抽出の取り込みは、削る。
- **N9**　取り消しと復元は、日時の無い出来事を書き戻しても、拒まない。記録は書き換えない。戻った出来事は、§2.7 のとおりに扱う。

### 2.2 比べ方（K1〜K5）

- **K1　物差し。** 出来事は、開始の日と分で並べる。分は、粒度が「時刻」のときだけ数え、無ければ 0 分とする。同じなら、裏の並び。それも同じなら、id。日時の無い出来事（開始の日が無いか、粒度が「なし」の出来事。§2.7）は、日時のある出来事の全部の後ろに置く。年表の画面は、同じ日時の出来事どうしの順を決めていない。裏の並びと id は、この案が足す、同点の決め方である。
- **K2　前後の判定。** 出来事の「幅」と、現在地の「幅」を比べる。幅は、始まりを含み、終わりを含まない区間である。出来事の幅は、開始から、終わりの日時があれば、その終わりの粒度の幅の端までである（終わりが「日」なら、その日の終わりまで）。終わりが無ければ、開始の粒度の幅である（時刻なら 1 分、日なら 1 日、月・季節・年は、暦から求めたその月・季節・年）。幅を暦から求められるかは、粒度ごとに決める。月は、暦に月の定義があるとき。季節は、季節の境界があるとき。年は、1 年の日数が決まっているとき。求められない粒度の出来事の幅は、保存された開始の 1 日とする（決定 13）。暦の設定そのものが無い作品でも、同じである。月・季節・年だけの出来事を K1 で並べるときは、保存された日ではなく、その幅の始まりを使う。現在地の幅は、場面の作中日付の粒度の幅か、現在地を決めた出来事の、開始の粒度の幅である（期間のある出来事で決めたときも、開始の粒度の幅だけを使う。◇11）。出来事の幅の全部が、現在地の幅より前なら、「これまで」。全部が後なら、「これから」。重なるなら、「同時進行」である（決定 9）。
- **K2a　現在地を借りたとき。** 手前の場面から借りた現在地では、「同時進行」を使わない。借りた現在地の幅と重なる出来事は、「これまで」とする（決定 9 の後半の読み）。
- **K3　置き場。** K1・K2 と、「作中の現在地」の決め方（C4）は、画面側と Native に、1 つずつ置く。MCP 側にある写しは、Native の 1 つに寄せる。画面側と Native が、同じ試験用の例（fixture）を読んで、同じ結果になることを確かめる。Native の関数は、取り込み（G4）からも呼べる場所に置く。【今は MCP の側にしか無いことは報告】
- **K4　通す箇所。** 前後を比べている箇所は、全部、K1・K2 に通す。自動のまとめの 5 か所（これまでの出来事、人物の所在、未回収の因果、本文未描写の背景、人物の選び方）、「作中の現在地」の決め方、道具と MCP が返す年表の状況である。年表のまわりで、裏の並びを直接比べる書き方を、試験で禁じる。年表の出来事の一覧を読む処理の並び（裏の並び、id）と、抽出が使う既存の出来事の目録は、変えない。
- **K4a　「同時進行」の数え方。** 人物の所在と、載せる人物の選び方は、「これまで」「今の場面」「同時進行」の出来事から選ぶ。未回収の因果は、原因が「これまで」「今の場面」「同時進行」のどれかで、結果が「これから」の組だけを出す。本文未描写の背景は、どの場面にも結び付いていない、「これまで」「同時進行」の出来事から選ぶ。現在地が決まらない場面では、今までどおり、人物の所在を出さず、どの場面にも結び付いていない出来事から、前後に関係なく、本文未描写の背景を最大 3 件出す。人物の生死は、今までどおり、日で比べる（同じ日の死亡は「死亡」）。比べ方を切り替える段（§5 の 5）では、「同時進行」の出来事を、「これまで」と同じ欄に入れる。欄を分けるのは、CPL/1 である。
- **K5　裏の並び。** 移行と取り込みは、裏の並びを書き換えない。出来事どうしの前後の判定では、裏の並びは、同じ日時の出来事の間の順だけに使う。「スタンプ」と「シーンから取込」（§1.2）は、この案では触らない。

### 2.3 承認して年表に入れる出来事の日時（G1〜G9）

- **G1**　抽出の提案を承認して年表に入れるとき、出来事には、必ず日時を入れる。決め方は、G2 から G5 の順である。
- **G2**　根拠の場面のうち、読む順で最初に作中日付のある場面の、日付を写す。粒度も写す。分は、粒度が「時刻」のときだけ写す。
- **G3**　G2 で決まらず、提案が、推定の日時を持つとき（§2.4 が入った後の提案）は、それを使う。
- **G4**　それも無ければ、読む順で最初の根拠の場面の、「作中の現在地」（C4）の日時を使う。粒度は「日」にする。
- **G5**　それも無ければ、I2 と同じ「最も後の日の翌日」を使う。年表にも場面にも日付が無ければ、暦の起点の日を使う。
- **G6**　G2・G4・G5 で決めた日時の確度は、「不明」にする。場面の作中日付を写したときも、「不明」にする。回想の場面などで、場面の日付が、出来事の日付とは限らないためである。G3 の確度は、提案が持つ値（「おおよそ」か「不明」）を使う（決定 12、EET/1 の TE12）。
- **G7**　取り込みは、1 件ずつ行う（SRA/1 の D1）。日時は、その 1 件を入れる時点の年表から決める。G5 で決まる日時は、1 件入れるたびに、1 日ずつ後ろへ進む。
- **G8**　日時を決めるのは、Native だけである。画面が組み立てる操作の値は、日時については、今のまま（なし）にする。Native は、取り込みを行うときに日時を決めて、出来事に書く。この案は、提案の形を変えない。提案に推定の日時の欄を足すのは、EET/1 である。【操作の照合を変えずに済むかは、2 つの調査で書き方が分かれた。実装の前に、起案者が読む】
- **G9**　取り込みで入れた日時・粒度・確度の欄は、「機械が入れた値」として記録する。今の取り込みは、出来事の欄の全部を、承認した人の値として記録する。日時・粒度・確度の欄だけを、例外にする。ほかの欄は、今までどおり、承認した人の値である。承認した人の値として記録すると、AI と MCP が、後から直せない。作者が直すと、作者の値に変わる。

### 2.4 抽出のときに AI が日時を推定する（起案 EET/1）

決定 7・11 による。規則は、起案 EET/1（`nir1-chronicle-extraction-event-time-proposal/1`）に書いた。EET/1 は、日時の推定を、出来事の要約を作る AI の呼び出しとは別の、AI の呼び出しに分ける。暦、前後の場面の作中日付、年表の出来事は、その呼び出しにだけ見せる。要約を作る呼び出し、関連する過去シーンの資格が見る版の一覧、評価の準備は、変えない。この節は、規則を持たない。

### 2.5 移行（I1〜I7）

- **I1**　保存の形の版を 1 つ上げ、全部の作品の、日時の無い出来事に、日時を入れる。公開済みの版から上げる作品も、対象である。
- **I2**　「最も後の日」は、日時のある出来事の、開始と終わりの日時と、保管済みでない場面の作中日付の、最も後のものである。日時の無い出来事を、その翌日から、1 日ずつ置く。置く順は、裏の並び、同じなら作った日時、それも同じなら id である（決定 14）。画面で作った出来事は、裏の並びが同じ値なので、作った順になる。年表の画面の今の並び（内部の id の順）とは、変わる。出来事にも場面にも日付が無い作品では、暦の起点の日から、同じ順に 1 日ずつ置く。粒度は「日」、確度は「不明」にする。
- **I3**　日時はあるのに、粒度が「なし」の出来事は、粒度を「日」（分があれば「時刻」）に直す。確度は変えない。開始が無く、終わりだけが残っている出来事は、終わりを消す。
- **I4**　移行は、2 回走っても、2 回目は何も変えない。想定しない値の行は、飛ばして、止まらない。移行を済ませた印を、既にある「データの移行の印」の表に書く。出来事が 0 件の作品と、新しく作る作品にも書く。起動のときの確認が、この印を読むようにし、前の版からの近道が、移行を飛ばさないようにする。【今の仕組みと合うことは報告（点検）】
- **I5**　移行で日時を入れた出来事は、変更の記録の連なりの「先頭の印」（§1.4）が、今の値と合わなくなる。合わない印を消す。記録そのものは消さない。消さないと、その出来事の次の編集が、「連なりが合わない」として失敗する。移行は、走るたびに印を作り直すので、消す処理は、作り直しの後に、毎回走る形にする。消す対象は、印の値が、出来事の今の値と合わないものだけである。移行で日時を入れた出来事と、取り消しで前の値に戻った出来事が、これに当たる。作者が、その後に正しく編集した出来事の印は、消えない。どの出来事に日時を入れたかを、別に記録することは、しない。【印の値を、出来事の今の値から計算し直せるかは未確認。できなければ、小さな記録を足す案を、あらためて伺う】防御に触れるので、◇3 で確認いただいた。
- **I6**　移行は、日時を入れた出来事の、日時・粒度・確度の欄に、「機械が入れた値」の印を書く。作者の値の印が既にあっても、上書きする（その値は、移行が入れたものだからである）。移行が日時を入れなかった出来事は、確度が「不明」でも、印を触らない。作者が直すと、作者の値に変わる。列は足さない。新しい権限の使い方に当たるかを、◇3 で確認する。
- **I7**　移行は、出来事の版の番号を上げない。上げると、取り消しの記録の連なりが、合わなくなる。【報告】裏の並びと、取り消しの記録は、書き換えない。進行中の抽出は、既存の出来事の目録が変わるので、作り直しになる。

### 2.6 確度と、「作中の現在地」（C1〜C5）

- **C1**　AI に年表の出来事を渡すときは、出来事ごとに、確度を渡す。自動のまとめは、確度が「おおよそ」「不明」の出来事の行に、その旨を添える。道具と MCP の返り値には、確度の欄を足す。まとめの導入の文に、「確度が不明の出来事の前後は、不確かである」と書く。
- **C2**　確度が「不明」の出来事も、前後は、K1・K2 で比べる（決定 3）。
- **C3**　確度が「不明」の出来事は、場面の「作中の現在地」を決める材料にしない（決定 8）。その場面に結び付いた出来事から選ぶときも、手前の場面から借りるときも、除いてから選ぶ。場面の作中日付は、今までどおり使う。確度が「おおよそ」の出来事は、材料になる。AI が推定した日時を持つ出来事も、確度が「おおよそ」なら、材料になる（決定 12）。
- **C3a**　作品の出来事が全部、確度「不明」で、作中日付のある場面（保管済みを除く）も無いときに限り、確度が「不明」の出来事を、材料にする（決定 10）。現在地には、「日付は不確実」と添える。
- **C4**　「作中の現在地」は、次の順で決める。場面に作中日付があれば、その日付。無ければ、その場面に結び付いた、材料にできる出来事のうち、日時が最も後のもの。それも無ければ、読む順で手前の、現在地を持つ最も近い場面から借りる。どれも無ければ、決まらない。
- **C5**　年表の整合の検査（因果の逆転、二か所に同時に居る、年齢、季節）と、人物の生死の導出は、確度が「不明」の出来事を、対象から外す。仮の日時が、誤った警告や、誤った生死を出さないようにするためである。作者が、自分で確度を「不明」にした、日付つきの出来事も、外れる。今の挙動からの変更である。起案者の提案で、◇4 で確認する。

### 2.7 日時の無い出来事が戻ったとき（B1〜B2）

- **B1**　取り消しや復元で、日時の無い出来事が戻ったときは、次のように扱う。並びは、日時のある出来事の全部の後ろ（K1）。前後の判定は、「不明」。確度は、保存された値が何であっても、「不明」として扱う。「作中の現在地」の材料にしない。整合の検査の対象から外す。年表の画面は、今の仮の位置の表示を残す。
- **B2**　戻った出来事は、次にその出来事を変えるときに、日時を補う（N4a）。起動のたびに全部を調べ直すことは、しない。

## 3. 残る制限

- 保存の形に制約を入れないので、取り消しや復元の後に、日時の無い出来事が、一時的に残ることがある（B1・B2）。
- 保存された裏の並びは、日時の順にならない。値そのものを読む人（保存のファイルを直接見る人）には、順が合って見えない。
- 移行で入る日時と、G4・G5 で決める日時は、仮の値である。年表の画面では、ほかの出来事の後ろや、手前の場面の日付に置かれる。作者が、年表で動かして、確度を直す。
- 根拠の場面に日付が無いとき、G5 の仮の日時は、承認のたびに、1 日ずつ後ろへ伸びる。100 件入れると、年表の末尾に、100 日ぶんの仮の出来事が並ぶ。
- G2・G4 で、手前の場面と同じ日付になった出来事は、同じ日付を現在地とする、根拠でない場面から見ると、「同時進行」になる。根拠の場面より前の場面でも、そうなる。自動のまとめの「同じ頃の出来事」に入る。行には、「日付は不確実」と添える。
- G5 で入れた出来事は、根拠の場面を除いて、作中日付のある場面から見て、常に「これから」である。自動のまとめの「これまで」には入らない。AI が道具で引けば、確度つきで見える。
- 確度が「不明」の出来事は、「作中の現在地」の材料にならない（C3）。承認して入れた出来事しか結び付いていない場面は、手前の場面から現在地を借りる。借りる先も無ければ、現在地は決まらない。そのときも、その場面に結び付いた出来事は、「今の場面」として、自動のまとめに出る（CPL/1 の W2・M1）。作中の時刻は、「未確定」と書く。
- 出来事が全部「不明」の作品（C3a）では、仮の日時が現在地になる。現在地には、「日付は不確実」と添える。公開済みの版から上げた、日時が全部なしだった作品では、今は、ほぼ全部の出来事が「これまで」に入る（裏の並びが同じ値のため）。移行の後は、仮の日時の順に並び、現在地より後の出来事は「これから」になる。
- C3a の条件（出来事が全部「不明」）は、次のどれかで、成り立たなくなる。出来事 1 件の確度を直す（場面に結び付いていない出来事でも）。「おおよそ」の推定を持つ提案を承認する。取り消しで、日時の無い出来事が戻る。成り立たなくなると、作品全体の自動のまとめが変わる。現在地が決まらない場面が増え、その場面では、結び付いた出来事と、本文未描写の背景のほかは、位置が「不明」になる。
- 場面の作中日付を写して入れた日時は「不明」で、現在地の材料にならない。AI が推定した日時は、「おおよそ」なら、材料になる（決定 12）。AI の推定が誤っていると、その場面と、後ろの場面の「これまで」がずれる。作者は、提案のカードと、年表で、推定を確かめる。
- 移行の後、年表の画面で、日時の無かった出来事の並びが、今と変わる（決定 14）。今は内部の id の順で、移行の後は作った順である。
- G2 で写す日付が、最初の根拠の場面より、読む順で後ろの場面の日付のことがある（根拠が複数の場面にまたがる提案）。その間の場面から見ると、既に書かれた出来事が、「これから」になることがある。行には、「日付は不確実」と添える。
- 手前の場面から現在地を借りた場面では、「同時進行」は出ない（K2a）。
- 比べ方の切り替え（§5 の 5）から、移行（§5 の 6）までの間は、既にある日時の無い出来事の位置が、「不明」になる。5 と 6 は、同じ release に入れる。
- 確度が「不明」の出来事は、整合の検査と、生死の導出に掛からない（C5）。作者が、死亡の出来事の確度を「不明」にしていると、その人物は、今は「死亡」だが、この案の後は「存命」側になる。
- 同じ日時の出来事は、「これまで」から「同時進行」に移る（K2）。今の挙動からの変更である。
- 日時と裏の並びが食い違っていた作品では、自動のまとめに入る出来事が、今と変わる。変わる向きは、年表の画面の並びに合う方である。
- MCP を使う外部の道具は、日時と確度を付けずに出来事を作る今の呼び方では、失敗するようになる（決定 5）。
- 年表の出来事が全部日時なしの作品は、今は「並びの順」の表示である。移行の後は、暦の日付の表示になる。
- 要らなくなる画面の部品（並びの順の表示、仮の位置の表示、「シーンから取込」と「スタンプ」のボタン）は、この案では触らない。日時の無い出来事が戻ったときの表示に使うものがあるためである。整理は、公開の後に、別に決める。

## 5. 順番

PR は 1 本ずつ出す。道具の作り直しの lane（Mastra への移行）との前後は、担当との取り決めによる。新しい file は、その lane が年表のまとめの file を共有の場所へ移した後に出す。移行の PR は、保存の形の定義の正本が移った後の master から作る（2026-11-22 に移った）。その lane は、こちらを待たずに進める。移した後の file を直すときの決まり（共有の場所の中では、ほかの共有の file だけを使う、など）は、担当から受け取っている。

1. **記録と、起案の書き直し**（文書だけ）。
2. **比べ方・現在地・仮の日時の決め方**（K1〜K3、C3・C3a・C4、I2）。新しい file だけを足す。画面側は、道具の作り直しの lane（Mastra への移行）が整えている共有の場所に置く。その lane が、年表のまとめの file を共有の場所へ移した後に出す。Native 側は、取り込みからも MCP からも呼べる場所に置く。試験用の例。既にある処理は、まだ切り替えない。
3. **入口の変更**（N5〜N8）。年表の画面、アプリ内の AI、MCP、原稿の読み込みが、日時を必ず渡すようにする。Native は、まだ日時なしを許す。年表の設計書の、日時の必須化の部分を直す。
4. **Native の入口の検査と、取り込みで日時を決める処理**（N1〜N4a・N9、G1〜G9、B2）。画面の試験の代役と、日時なしで出来事を作っている実機の検査の手順 1 本を、同じ PR で直す。年表の設計書の、取り込みの部分を直す。
5. **切り替え**（K4、C1〜C5、B1）。前後を比べている箇所を、全部、新しい比べ方に通す。画面側・Native・MCP を、1 本で切り替える。年表の設計書と、AI に渡す文脈の説明書の、比べ方の部分を直す。
6. **移行**（I1〜I7）。保存の形の版を上げる。公開済みの版からの上げ方の試験。5 の後にするのは、移行で入れた仮の日時が、確度なしで、検査や AI に出ないようにするためである。5 と 6 は、同じ release に入れる。6 が master に入るまで、5 を含む release を切らない。N4a の、日時を補う処理は、この PR で有効にする。
7. CPL/1（位置の印）の実装。5 の後。視点の人物だけは、5 を待たずに出せる。
8. SRA/1 の、取り込みを既定で有効にする段（SRA/1 の §6 の 5）。前提は、SRA/1 の §6 の全体の列に置く。
9. 抽出のときの AI の推定（起案 EET/1 の PR 4 本）。EET/1 の受け皿の PR は、4 の後。閉じた状態で入れ、日時の推定の質を測ってから、開けるかを決める。

2〜6 は、8 の前提である。取り込みを開けると、仮の日時の出来事が増える。比べ方と現在地の規則が、先に要る。SRA/1 と CPL/1 を合わせた全体の列は、SRA/1 の §6 に置く。

## 7. 未確認と限界

- この文書の【報告】は、2026-11-22 の read-only の調査と点検の結果である。起案者は、該当の行を読んでいない。実装の前に、基点のコードで読み直す。結果は、repo の外の `design-notes/editor-scene-interpretation-2026-11-21/wf16.json`〜`wf19.json` にある。
- どの挙動も、実行して確かめていない。「AI 向けの判定が、ほぼ全部の出来事を『これまで』に入れている」（§0）は、実装の最初に、試験で再現する。
- この版は、点検の指摘を受けて書き直した後、もう一度の点検を受けていない。全体の確認の前に、点検する。
- K2 の「粒度の幅」を、月・季節・年について計算する関数が、今あるかは、確かめていない。無ければ、日より粗い粒度の出来事は、開始の日だけで比べる。
- 移行で入れる位置が、年表の画面の今の位置と、1 件も違わないことは、確かめていない。画面の計算は、小数の日を使う。保存する日は、整数である。時刻つきの日付が最も後にある作品では、1 日未満のずれが出る見込みである。順は変わらない。【報告】
- 取り込みで、操作の照合を変えずに、Native が日時を決められるかは、2 つの調査で書き方が分かれた（G8）。
- 「全部が不明の作品」（C3a）の判定を、どこで、どれだけの手間で行うかは、決めていない。
- 評価をまとめているセッションの、4 本目の起案の 2 案についての意見は、まだ届いていない。
- 別件の不具合（この案の範囲外）：製品の取り込みの呼び出しが、年表の末尾の値を渡していない（SRA/1 の D9 で直す）。原稿の読み込みが付ける裏の並びの値の形によっては、その後の新規作成が失敗しうる。【報告】AI と MCP が作る出来事が、裏の並びの先頭に置かれ、現在地が先頭に寄る件は、この案で、前後の判定が裏の並びを使わなくなるので、起きなくなる見込みである。
