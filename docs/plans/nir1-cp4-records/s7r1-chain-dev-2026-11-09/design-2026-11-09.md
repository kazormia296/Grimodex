## 0. 要約

1. **連鎖の 1〜4 はコードの上で成り立つ**（§1）。食い違いは 2 点。

   - (ii) Verify を奪う foreground の正体は、まだ確定していない。
2. **新しく分かったこと（3 点）**
   - **LP-GATE（DR-CQD-GATE-1〜10）の穴**【事実】。LP-GATE は「Graph の窓の間に main 接続の commit が入ると答えが drift する」問題への対策だが、対象は Freshness だけである。maintenance は明記したうえで対象外にしている（`cq-deferred-decisions.md:377`）。今回 commit を出していたのは Verify の run／task／attempt の作成と取消しで、ちょうどこの穴に当たる。

   - **奪い手の候補**【推測・中】。周期的に Verify を奪っている候補として、Related Scenes の reconciler が見つかった。250 ms ごとに、live な lease があれば主接続で read transaction を開く。lease の TTL は 300 s。
3. **推奨は (c)**。維持の cycle に「連続 preempt の backoff」を入れる（DR-CP4-L-27 が PUB-G の前提として名指しした製品側の候補）。

   - 本番の作者の機械でも、無駄な書込み（WAL、CPU）が減る。

4. **次の手は dev の結果しだい**。

5. **やらないこと**

   - (d) 取消しの書込みを減らす。
   - (e) setup の seal で止める。
6. **S4 との関係**

## 1. 連鎖の確認

### 1.1 段 1：cold DB に `running` の dependency-verify の行が残る

【事実】
- setup の seal は維持の静止を待つが、待ち切れても setup を止めず、開示するだけである（DR-CP4-T-5 の「実装後の追記」(2)）。
  - Fable は `frozen-setup-driver.mjs:2773-2783` を挙げている。私は読み直していない。
- running の行の有無は a1／a2 で分かれた（results.md §2）。
- 測定の process を開くと、running の行は `failed／NEX_MAINTENANCE_INTERRUPTED: process interruption` に回復される（results.md §2）。回復の経路は `maintenance_runtime.rs:5017-5031`。
- 起動時の中断は、有界の失敗の方針（retry の予算、使い切ると manual）を通る（`maintenance_runtime.rs:3788-3800`）。

【推測・中】running の行がほぼ常にある理由
- 連打の間は、次の繰返しになる（§1.2）。
  1. 作成
  2. Verify
  3. preempt
  4. 行を running のまま process の memory に退避
  5. 10 ms 後の次の cycle の始めで取消し
  6. 次の作成
- このため、どの瞬間にも running の行がほぼ 1 つある。session がいつ終わっても残りやすい。
- a2 の seal の `session-end` で running が 0→1 になったことと合う。

### 1.2 段 2：dependency-verify が `PREEMPTED` で取り消され続ける

**PREEMPTED の出所は 2 つ**【事実】
- (i) **no-wait の取得**（`grimodex-db/src/lib.rs:436-467`）。maintenance の no-wait の scope の中で、foreground の waiter が 1 つでもいるか、mutex が使用中なら、`NEX_MAINTENANCE_CONNECTION_PREEMPTED` で即座に失敗する。文言は 3 種（`foreground waiter owns…`、`maintenance connection is busy`、`foreground waiter arrived…`）。
- (ii) **実行中の割込み**。maintenance の SQL の progress hook が foreground の waiter を見て、`ForegroundPreempted` で SQL を割り込む。
  - hook：`narrative_maintenance_connection.rs:1053-1058`
  - Graph の control の check：`:609-617`
  - progress callback：`:625-646`

**foreground とは何か**【事実】
- no-wait の scope の外で `Database::lock_conn_with_check` を通る呼出しは、すべて foreground になる。`ForegroundConnectionWaiter` を立てる（`lib.rs:468-521`）。
- participant の read transaction もこれに当たる。経路は `with_participant_read_transaction` → `with_participant_sql_scope_fenced` → `lock_conn_with_check`（`narrative_maintenance_connection.rs:1233-1250`、`:1519`）。
- **read だけの照会でも維持を奪う**。

**取消しの書込み**【事実】
- preempt された run は、process の memory に退避される（`defer_preempted_run`、native `lib.rs:4385`）。
- 次の cycle の始めに、`try_cancel_preempted_maintenance_run` が取消しを行う（native `lib.rs:9157-9190`、文言 `retrying deferred cleanup`）。run／task／attempt を 1 つの transaction で cancelled／failed にする（`maintenance_lifecycle.rs:1800-1852`）。
- その後、同じ WorkKey の新しい run が作られる。`:1794-1799` の comment に「The next durable wake starts a fresh Run」とある。

**再開の間隔**【事実】
- Rust の cycle は、preempt を `mark_deferred` して `accepted(true)` を返す（`maintenance_runtime.rs:3545-3556`）。
- Main は既定の `nextDelayMs = NARRATIVE_MAINTENANCE_BACKLOG_DELAY_MS`（10 ms）で次の cycle を出す（`narrativeMaintenance.ts:295`、`:3222`、中断の分岐 `:3919-3972`、`:4261`）。

**preempt の印**【事実】
- `preempted: true` を付けるのは native の 2 経路だけである。
  - `lib.rs:7621-7625`：退避の取消しが接続を取れなかった。
  - `:9900-9907`：body の Err が preempt だった。
- Rust の cycle が `Ok(accepted(true))` を返す経路（`maintenance_runtime.rs:3556`）には、この印が無い。
- 【未確認】Main がこの経路を、attempt の receipt の state で中断と見分けているか。どちらの場合も遅れは 10 ms のままである。

**1 cycle の commit**
- 【推測】少なくとも 2 回（取消し 1 回、作成 1 回）。a2 の取消しは 4.7 回/秒なので、約 9 commit/秒になる。
- 【未確認】作成が 1 transaction か。wake_outbox などほかの書込みがあるか。

**誰が奪うか**【推測・中】
- 候補は Related Scenes の reconciler である。
  - 間隔は 250 ms（`electron/main/relatedScenesReconciler.ts:1`）。IR が pending の begin の ticket を track する（`ipc.ts:2662-2675`）。
  - native の `related_scenes::reconcile`（`related_scenes.rs:378`）は、live な lease ごとに `current_operation`（`:159`）を呼ぶ。`:182` で participant の read transaction を開くので、foreground に当たる。
  - lease の TTL は 300 s（`related_scenes.rs:36`）。release か TTL まで止まらない。
- T-5 の記録（idle の session でも取消しの間隔の中央値が 258 ms、harness の poll が無くても同じ）とよく合う。
- 合わない点もある。a2 の約 213 ms は、250 ms に実行時間を足した値より短い。ほかの奪い手（sample の begin の IR の scoring など）もいるはずで、確定はしていない。
- 【事実】readyProbe が読む `nir1GraphEvalStatus`／`Diagnostics` は奪い手ではない。DB を読まないことを確かめた（`nir1_graph_eval/mod.rs:643-713`）。

**Verify が完了しない理由**【推測・中】
- Verify の 1 回の所要が、奪い手の間隔より長い。
- a1 の Verify は、最初の sample の前（reconciler が動き出す前）に完了した可能性がある【推測・低】。

### 1.3 段 3：worker の registration が refused になる

`register_with_control_observed`（`nir1_graph.rs:587-704`）は identity を 3 回見る【事実】。

| 段 | 読み | 不一致のとき | owner の分類 |
|---|---|---|---|
| preflight（`:604-605`、BEGIN の前） | `read_unpinned`。`data_version` を前後 2 回読み、違えば None | None → `Err(NIR1_GRAPH_REGISTRATION_DRIFT)` | worker-unavailable |
| pinned（`:637-642`、`BEGIN DEFERRED` の最初の読みで snapshot が決まる） | `read` が `before` と同じか | `Err(DRIFT)` | worker-unavailable |
| postflight（`:683-687`、read transaction の後） | `read_unpinned` が `before` と同じか | **`Ok(false)`** | **registration-unavailable** |

- **ReadIdentity の中身**は、connection_epoch・total_changes・data_version・main と temp の schema_version・user_version（`read_identity.rs:11-71`、`lib.rs:163-186`）。worker の接続は別 process の read-only なので（`bin/nir1-c-query-worker.rs:199-207`）、本体のどの接続が commit しても data_version は変わる。
- **Err の経路**は次のとおり。
  1. worker の stage が `CanonicalRegistration` になる。
  2. stderr に `…_CANONICAL_REGISTRATION` が出る。
  3. owner で `WORKER_EXIT_BEFORE_READY` になる。
  4. `WorkerStartup` に分類され、worker-unavailable になる。
  - 根拠：`nir1-c-query-worker.rs:89-116, 224-250`、`c_query_worker.rs:3003-3044`、`nir1_graph_product.rs:2941-2958`。
- **refused（registration-unavailable）になるのは次の場合だけ**。
  - (i) postflight の不一致。snapshot の後から postflight までの間に main 側の commit が入った場合。
  - (ii) 非正の rowid。
  - (iii) `is_complete_registered_with_scratch` が false（`:648-659`）。
  - (iv) `verify_complete_source_index` が false（`:661-663`）。
  - (v) worker の maintenance control が `Ok(None)`（`:769-772`）。worker 自身の接続なので起きにくい。
  - (vi) `…_REVISION_INPUT_LIMIT`。marker は別だが、同じ分類になる。
- **a2 の読み**。begin 15 のうち、pending の 5 が prepare に進み、5 回とも失敗した。即答の 10 は registration-unavailable だった。
  - backoff の間の即答の理由は、直前の失敗の理由（`last_failure`、`nir1_graph_product.rs:1789-1799`）である。Suspended の答えはその reason である。
  - したがって、少なくとも 2〜5 回目の失敗は refused と読める。worker-unavailable は 0 だった。
- 【推測・中】5 回とも (i) である。
  - (iii)(iv) の材料（consumer freshness、edge states、epoch、digest）は、a1 と終了時に同じだった。
  - (vi) は、同じ fixture の a1 が通っている。
  - 決め手になる内訳の記録は無い【未確認】。
- 【未確認】窓の長さを決める registration の本体の所要。prepare の失敗は約 1 s で来る（results.md §3）。
- **query の時も同じ照合がある**【事実】。
  - `nir1_graph.rs:1020-1026`：registration の identity と比べる。
  - `:1095-1141`：後の stamp と比べる。不一致は `RegistrationDrift`。
  - worker は 1 query で終わる（bin の 1 行目 "one-query"）。次の sample は、新しい worker の registration から始まる。

### 1.4 段 4：slot が Suspended になり、出られない

【事実】
- **既定の設定**（`GraphOwnerConfig::default`、`nir1_graph_product.rs:92-102`）は、backoff が 2 s から倍々で上限 60 s、`failures_before_suspend` が 5。
  - `Count` の失敗で `consecutive_failures` を足す。5 以上で `Phase::Suspended { ready_generation, reason }` になる（`:2378-2399`）。
- **`prepare_failure` の分類**（`:2941-2958`）
  - registration-unavailable と worker-unavailable は、どちらも `Count`。
  - Busy と BindingLost は `DoNotCount`。
  - CleanupUnproved は quarantine。
- **時刻**。失敗の時刻（約 1、4、11、22、39 s。results.md §3）は、backoff（2、4、8、16 s）と `rebuild_not_before`（`:2985-3000`）で説明がつく。
- **出口は 3 つだけ**。時間で出る経路は無い。
  1. `ReadyPublished` の edge で `ready_generation` が進み、次の demand で Empty に戻る（`:1122-1128`、`:1708-1718`、`:1874-1884`）。
  2. B の build の commit の後の hook。`note_maintenance_work_completed` → `resume_after_graph_index_change` で、ledger を 4 にする（`:1366-1390`、CP2a-D47／D49）。
  3. prepare の最中に B の publish があった場合（D48、`:2184-2197`）。
- **既知の現象**。K6/4 の draft に「2 s ごとの保存（60 s）では owner が suspended に残り、編集を止めた 3 s 後も Graph は戻らなかった」とある（`nir1-final-request-eval-proposal-4-draft.md:126`）。
- **結論**。`OWNER_READY_WAIT_MS` を延ばしても効かない（results.md と同じ結論）。

### 2.1 (c) 維持の cycle の連続 preempt の backoff（推奨）

**何を変えるか**
1. **native**：preempt で続きになった cycle の結果に、必ず印を付ける。
   - `maintenance_runtime.rs:3545-3556` の `accepted(true)` を、通常の backlog と見分けられるようにする。
   - 方法は 2 案。`MaintenanceCycleResult` に `preempted: bool` を足すか、native が `work_deferred` の呼出しを数えて `lib.rs:9900` の付近の JSON に `preempted: true` を付ける。
2. **Main**（`electron/main/narrativeMaintenance.ts`）：binding と project ごとに「連続の preempt の回数」を持つ。
   - 中断の分岐（`:3919-3972`）と preempted つきの継続で、`nextDelayMs` を `preemptionBackoffMs(streak)` にする。
   - 1〜2 回目は 10 ms のまま。1 回の奪い合いは今と同じ速さで戻る。
   - 3 回目からは 250 ms × 2^(streak−3) で、上限を置く。例は 5 s で、値は dev で決める。
   - 0 に戻す契機：preempt でない cycle（成功・coalesced・空）、workspace の切替、dispose。
   - 新しい enqueue（編集）では 0 に戻さない。戻すと、編集のたびに連打が再開する。

**量**
- native 30〜60 行、Main 40〜80 行、試験 150〜250 行。

**正しさの risk**
- 次のものは変えない。
  - drift の検査。
  - Graph の READY の条件。
  - lifecycle の帳簿の意味（cancelled／failed、retry の予算に数えないこと）。
  - 変わるのは「いつ次の cycle を出すか」だけである。stale な Graph を READY にする経路は増えない。
- 残る性質（悪化はしないが、改善もしない）
  - 退避された run は、次の cycle の始めまで running のまま残る。backoff の間も残る。
  - 今も連打の間はほぼ常に running の行があるので、段 1 と起動時の interruption の予算（`maintenance_runtime.rs:3788-3800`）の扱いは今と同じ。【未確認】予算の上限値。
- Verify は完了しないままでありうる。奪い手が Verify の所要より短い間隔で来る限り、Verify は終わらない。(c) は無駄を減らすだけで、その場合の次の手は (f)。
- 遅れの閾値の確認が要る。Verify の再開は最大で上限まで遅れる。確認台帳に Verify の遅れの閾値が無いことを、着手の前に確かめる。LP-GATE の §9.1 (a) で Freshness について行ったのと同じ確かめ方をする【未確認】。
- owner/lifecycle matrix（GDX-PRECHECK-001）に載せる項目。backoff の timer（最大で上限まで）が、次の 3 つとどう絡むかを決める。
  - workspace の切替：backoff の timer を捨て、streak を 0 にする。
  - dispose と quiesce（`quiesceForWorkspaceSwitch`、`narrativeMaintenance.ts:4354`）：timer を待たずに止める。
  - CI の quiescence seam（`getQuiescenceState` の `timerScheduled`、`:4564-4590`）：backoff の timer も `timerScheduled` に出る。このため、静止の判定が最大で上限まで延びうる。harness の T-1／T-5 の待ちは製品の timer を見ないので、影響は開示だけで済む見込み【未確認】。

**必要な試験**
- Main の vitest（fake timer）で次を固定する。
  - 連続 3 回で backoff になる。
  - 上限で止まる。
  - 成功で 0 に戻る。
  - 切替で 0 に戻る。
  - 1 回の preempt は 10 ms のまま。
  - 通常の backlog（preempt でない hasMore）は 10 ms のまま。
- native の試験：`accepted(true)` の preempt の経路で印が付く（既存の `lib.rs:19682`、`:23123` の形）。
- 既存の maintenance と journey の試験が通る。
- 変異の試験：印を落とす、0 に戻さない、上限を外す。どれも落ちること。
- lifecycle の試験：次の 3 つを固定する。
  - 切替で timer が消える。
  - dispose・quiesce が backoff を待たない。
  - `getQuiescenceState` が backoff の間の `timerScheduled` を正しく返す。

**dev での確かめ方**
- §6.2 の a2 型の並び（running の行がある setup）で、V-10 が消えるかを見る。

**本番の挙動**
- Related Scenes を開いたまま書く作者の機械では、Verify の取消しの書込みが毎秒数回（推測）から、数秒に 1 回まで減る。
- Graph（PUB-G の後）は、連打の間も registration と query が通りやすくなる。ただし確率的であり、決定的にするには (g) が要る。

### 2.2 (g) LP-GATE に維持の cycle を section として加える

**何を変えるか**
- **g-1（入口）**
  - native の maintenance の cycle の始めで、Freshness と同じ section に入る。場所は no-wait の guard（`lib.rs:9157`）と `try_cancel_preempted_maintenance_run` の前。`enter_freshness` は一般化する。

- **g-2（進行中）**

- drift の検査は変えない。commit を窓の外へ寄せるだけである。

**限界**

**試験と dev**

- dev：gate の counters（`deferred`、`graph_wait_expired`、`overridden`）を見る。あわせて、sample ごとの `registration-unavailable` と `driftAtQuery` が a1 型と同程度まで減るかを見る。

**規則**

### 2.3 (f) Related Scenes の reconciler を no-wait にする

**何を変えるか**

**正しさ**

- CP-4 の trace の失効や窓外率に効く可能性があるので、開示する。

**前提と効き**
- 前提：reconciler が主な奪い手であることを、dev で確かめる。外れていれば効かない。

**試験と dev**

### 2.4 (a′) refused を drift と incomplete に分け、drift では Suspended にしない

### 2.6 (b) drift の判定を狭める（やらない）

**なぜ drift の判定があるか**
- registration は、B の index が完全で current だと検証した snapshot を、その committed state の identity に結び付ける。query もその identity と比べる。
- どの commit でも identity が変わる。このため「検証した状態から何も変わっていない」ことを、安く保証できる。
- 表単位の情報が無いので、run／attempt の行の書込みだけを見分けることはできない。

**緩めると壊れるもの**
- 検証から query までの間に、Graph の入力（edge、consumer freshness、revision の承認、scope）を変える commit が入っても、READY になり回答が返る。これは stale な Graph であり、G-05 current-revision-freshness が測るものそのものである。

**安全に狭める条件**
- 表ごとの書込みの版が、別 process から見える形で要る。DB 段 1（commit の連番と TRIGGER）と 1c（除外する表の決定）のことである。
  - 1c の前提は、脅威モデルの改訂と C6 (b)。
  - 1c には「Graph の集合は、登録から query の後の比較と開示の再検証までに読む全表の和以上」とある（`stage1-design-rev1.md:179-184`）。
- V-6 の audit-only の引継ぎは使えない。V-6 は process の中の接続ごとの列で、Graph は明記したうえで対象外にしている（DR-CP4-V-6 (d)）。worker は別 process なので、同じ方法が使えない。

**今やらない理由**
- `cq-deferred-decisions.md:5` に「鮮度の判定（ReadIdentity、registration と query の drift の検査）は変えない」とある。
- ユーザーの C6「CP-4 の失効は今の定義（どの commit でも）で測り続ける」とぶつかる。
- memory の禁止（data_version を接続をまたいで比べる、二重の物差しを置く）に当たる。
- → 段 1c に送る。

### 2.7 (d) 取消しの書込みを減らす（勧めない）

- **案**：preempt された run を取り消さず、次の cycle で同じ run／attempt を再開する。作成も取消しも書かない。
- **risk**：次のものに触れる。lifecycle の契約の改訂に近い。
  - 三つ組の意味（cancelled は「接続の奪い合いで閉じた」で、retry の予算に数えない）。
  - 起動時の回復。
  - retry の予算。
  - ACK の流れ。
  - 長く続く「durable な帳簿と process の memory の対応」。
- **量**：300 行以上。
- **結論**：(c) で回数を減らせば、効果の大半は得られる。

## 6. 推奨と、確かめる順

### 6.1 推奨：(c) 維持の cycle の連続 preempt の backoff

**理由**
- 段 2 を断つ。drift の検査・Graph の READY の条件・帳簿の意味は、どれも変えない。stale な Graph を READY にする経路は増えない。
- 本番の製品（PUB-G の前）にも効く。Related Scenes を開いている間の、Verify の無駄な取消しと作成の書込みが減る。
- L-27 と T-5 がすでに名指しした候補である。委任の前例（DR-MPS）もある。
- 製品の file だけで済む（S4 の pin の外）。8 回目の S4 は要らない。

**限界（正直に書く）**
- V-10 への効きは確率的である。窓の長さ（registration の本体の所要）に対して、commit の間隔が十分に開けば通る。
- Gold の各 sample の欠落も確率的に残る。
- Verify は、奪い手が残る限り完了しない。

### 6.2 実装の前に dev で確かめること

**目的**
- (i) 段 3 の内訳を確定する。
- (ii) 奪い手を特定する（(f) が要るかの判断）。
- (iii) (c) の効きを測る。

**場所と時期**
- 新しい dev の worktree（`new-worktree.sh <path> --detach <基点>`）で行う。今走っている正式の測定が終わってから。

**計装**（dev の枝だけに置き、merge しない）
- eval の cfg は eval module の中だけに置く。ほかは env で開く普通の code にする。§3.2 の native-architecture を避けるため。
1. worker の registration の段ごとの時刻（preflight、BEGIN、semantic index、source index、seal、postflight）と、refused の内訳（drift／incomplete／source-index／非正の rowid／input-limit）。worker の stderr は、owner が allowlist の marker しか読まない。このため、env で指した path へ追記する。
2. gate の counters を `diagnostics_json`（eval module）に serialize する。
3. foreground の waiter の出所。`ForegroundConnectionWaiter::new` を呼ぶ箇所に label（reconciler、related scenes の begin の scoring、Freshness、その他）を付ける。label ごとの回数と、そのとき維持を奪ったかを数える。
4. 1 cycle の commit 数。watcher で `data_version` の差を取る（別接続の read-only、100 ms ごと）か、cycle の前後の `total_changes` を取る。

**手順**
- **A/B が成り立つか**【事実。コードの読み】：同じ cold DB で A/B ができる。
  - dev の run は `admitted.candidate` が null で（`frozen-k64-run.mjs:1632`）、setup の受領書の候補の照合（`:259-268`）を飛ばす。照合されるのは fixture の path・sha256・variant だけである（`:253-258`）。このため、修正した build でも a2 の受領書を使える。
  - ただし受領書の `coldDatabase.path` は ROOT からの相対 path で（`.artifacts/cp4/s7r1-dev-a2-setup/…/grimodex.db`）、Gold は sha256 を照合した byte copy を作る（`:520-532`）。
  - そこで、修正版の worktree には `.artifacts/cp4/s7r1-dev-a2-setup/` を同じ相対 path に写す。写すのは cp で、mv はしない。元は消さない。
  - 【未確認】dev の run が、受領書のほかの欄（launch、build の識別）を照合するか。照合する場合は、setup を作り直し、running の行の有無で層に分ける（回数が増え、費用は倍程度になる）。
- **成功の指標**：次の 3 つを、正式の判定が使う量にそろえる。「measured で 70 sample」だけでは、Graph arm の sample が drift で欠けていても満たされてしまうため。
  - (i) V-10 の率。
  - (ii) Graph arm の pool の欠落と、窓の中の定常の sample の数（K6/6・品質判定 v2 の読みで受領書から計算する）。
  - (iii) sample ごとの `registration-unavailable` と `driftAtQuery` の数。
  - 比べる基準は、a1 型（running の行が無い setup。新しく作るか、`s7r1-dev-a1-setup` を使う）の同じ量である。
- **a. 基準**
  - 残っている `s7r1-dev-a2-setup`（running の行あり）の cold DB に、同じ setup で dev の Gold を 5 回あてる。
  - a1 型にも 3 回あてて、(ii)(iii) の基準を取る。
  - あわせて、refused の内訳、取消し/秒、奪い手の内訳を取る。
- **b. 修正**
  - (c) を入れた dev build で、a2 型に 5 回、a1 型に 3 回あてる。
  - 成功の条件：
    - a2 型で V-10 が 0/5。
    - a2 型の (ii)(iii) が、a1 型の基準と同程度。
    - a1 型で退行が無い（READY が最初の probe で来る。(ii)(iii) が基準と同じ）。
    - 取消しが、最初の数秒の後は数秒に 1 回以下。
- **c. 判定**
  - (c) だけで V-10 が消え、(ii)(iii) が a1 型と同程度 → (c) で取り直しへ進む。
  - V-10 は消えるが (ii)(iii) が a1 型より悪い → (g) を足す（ユーザーに 1 行確認）。正式で HOLD になる危険を、ここで捕まえる。
  - 奪い手が reconciler と確定し、Verify が完了しない → (f) を PUB-G の前提に足す。取り直しの前に入れるかは費用で決める。
  - refused の内訳が drift でない → 連鎖の読みが違う。ここで止めて報告する。

**費用**
- build 約 11 分×2、Gold（5＋3 回）×2 で、合わせて約 1〜1.5 時間。

### 6.3 実装の順（推奨が決まった後）

1. **記録**：decisions 文書に記録する（新しい lane の文書か、`maint-precutover-stall-decisions.md` に追記）。
   - 中身：判断、信頼境界、代替案（この文書の §2 の表）、owner/lifecycle matrix、advisor の結論。

2. **実装と試験**：§2.1 の試験と、既存の maintenance と journey の試験。
3. **独立 review**。
4. **merge**：Quick と PR の ci.yml が通ったら merge する（squash でよい。pin の外）。
5. **取り直し**：新しい候補で取り直す。runbook の §1.3 の候補の決め方に従い、build の間は master を止める。
