## 0. 一枚目

**何を決める案か。** 「まとめて承認」は、見せる理由の無い提案の秘密の印を外して承認する操作である。この案は、その操作を Native の新しい command 1 つとして置き、今ある画面のボタンを置き換える。

**なぜ新しい command か。** 今は、「秘密の印を外した版を作る」と「承認を記録する」が別々の command で、画面側が提案の数だけ 2 回ずつ呼ぶ。この形だと、対象を選ぶのも、版の中身を作るのも画面側になり、途中で止まると「版だけできて承認が無い」提案が残る。新しい command では、Native が対象を判定し、提案ごとに 2 つをひとまとめに行う。

**形**
1. 対象かどうかは、Native だけが判定する。画面は、Native が返した可否と理由を表示する。
2. 画面は、作者に見せた対象の一覧（提案と版の id）だけを渡す。版の中身は渡さない。
3. Native は、一覧の中で、今も対象と判定する提案だけを処理する。一覧に無い提案は処理しない。
4. 提案ごとに、秘密の印だけを外した子の版を作り、その版に作者の承認を記録する。2 つは 1 つの transaction である。
5. 今あるボタン「安全な提案をまとめて承認」を、この操作に置き換える。
6. merge の前に、評価のデータで測り、結果を作者に見せる。作者が結果を見て判断してから merge する（§6）。

**作者にとって変わること**
- 今のボタンは、押しても提案が関連場面に出ない（秘密の印のまま承認する）。置き換えの後は、押すと、対象の提案の根拠の本文が、後の場面の関連場面に出るようになる。
- 年表に入れたいだけで、関連場面には出したくない提案は、1 件ずつ承認すれば、今と同じ（秘密の印のまま）になる。
- 年表の出来事は、どちらの場合も秘密の印つきで作られる（CAS/1）。

## 1. 確かめた事実

- 今あるボタン「安全な提案をまとめて承認」は、製品に出ている。未 review・未取り込みで 7 つの条件を満たす提案の、AI が出したままの版（秘密の印つき）に、承認を 1 件ずつ記録する。秘密の印は外さない。押しても関連場面（IR）には届かない。実機の検査と評価の準備は、このボタンを使っていない。【報告】
- IR の資格に要るのは、承認と、今の版の秘密の印が外れていることである。年表への取り込みは要らない。【確認済み（SSE/1 の実機の検査の後の DB に、Native の判定を当てた）】
- 秘密の印を外した子の版を作る command は、親の版が現行であること、受け付ける 4 項目の変更だけであることを確かめ、scope の投影を今の値で取り直す。版、材料、依存の辺、鮮度、提案の現行の版と status（未 review に戻す）を、1 つの transaction で書く。次の場合は失敗する：開示の場面が今の場面の一覧に無い、project の意味の世代の記録が無い、親の版の封印の記録が無い。【報告】
- 承認を記録する command は、未取り込みであること、組が取り込み済みでないこと、重複の可能性の判断があること、版が現行であることを確かめる。actor は作者（`electron:human-review`）である。秘密の印と、提案の status は見ない。【報告】
- 2 つの command は、Native の入口の包み方が違う。承認は「作業中の操作」として登録され、終了や workspace の切り替えと調停される。版の作成は登録されない。【報告】
- 子の版の作成と承認を 1 つの transaction にまとめる今ある command は、今の形式（V2）の版を拒むので使えない。同じ transaction で 2 つを続けて書く作り自体には前例がある。【報告】
- 子の版の Envelope は、判定の材料（語りの枠、語り手、重要度、起こり方）を親と同じに持つ。Native の系譜の検証が、親との一致を確かめている。【報告】
- 提案の中身（payload）の重要度と起こり方が、Envelope の値と同じであることを、Native は確かめていない（確かめているのは画面側だけである）。【報告】
- review の画面は、版の系譜と、Envelope の語りの枠・語り手を受け取っていない。再起動の後は、提案の中身と計画の比較だけで「最初の版のまま」を判定している。題を直して元に戻した版などで、Native の系譜による判定と食い違う。【報告】
- 重複の可能性は、抽出のときの結果が封印済みの計画にあり、Native が今も読んでいる。抽出の時点の出来事の一覧に対する判定で、後から足された出来事は見ない（今ある挙動）。【報告】
- 根拠の確かめ方の種類（完全一致かどうか）は、画面側が付ける値である。Native の検索の材料の側は、その値を読まず、根拠の引用が今の本文と完全に一致するかを、その場で確かめ直している。今の形式では、提案の根拠の一覧と、Envelope の根拠の一覧が一致することを、Native が検査している。【報告】
- 承認や版の作成のたびに、検索の材料の作り直しは走らない。作り直しが要る印を付けるだけである。承認 1 件ごとに、封印済みの計画の全件を読んで検証する。【報告。数百件のときの時間は測っていない】
- 年表への取り込みは、組に未 review・保留・延期の提案が 1 件でもあると拒まれる。取り込みが、作者が編集した版（秘密の印を外した版を含む）を受け付ける変更は、PR #864（merge 済み）と PR #866（未 merge）である。【確認済み】
- 取り込みのあった組には、子の版も承認も足せない。【確認済み】
- 古い形式（V1）の版は、判定の材料を持たず、子の版も作れない。今の製品の抽出は V2 である。【報告】
- 場面の scope の既定は、場面を作るときにだけ受け継がれる。既定を後から設定しても、今ある場面には当たらない。scope の印が「移行前からある場面」（`legacy-absent`）の場面は、関連場面の判定で不可にならない。印が未設定（`unknown`）の場面は、不可になる。【報告】
- 関連場面の結果は、今は chat や AI への送信に使われていない。この 2 つの command は、MCP からは呼べない。【確認済み／報告】

## 2. 規則

- B1. **新しい command を 1 つ足す。** 入力は、project、抽出（組）、作者に見せた対象の一覧（提案の id と、その現行の版の id）である。版の中身、秘密の印の値、actor は入力に無い。
- B2. **対象かどうかは、Native だけが判定する。** 提案が対象になるのは、次の全部を満たすときである。
  - (a) 未 review で、未取り込みである。組が取り込み済みでない。
  - (b) 現行の版が、今の形式（V2）の、AI が出した最初の版そのものである（版の id で判定する。中身の比較では判定しない）。作者が 1 度でも編集した提案は、元に戻していても、対象にしない。
  - (c) 抽出のときの重複の判定が「重複なし」である。
  - (d) 根拠が 1 件以上あり、その全件が、封印済みの根拠の記録と 1 対 1 に対応する。
  - (e) 見せる理由（RR/1）が 1 つも付かない：語りの枠が地の文の出来事、語り手が地の文、重要度が major でない、起こり方が「実際に起きた」。4 つの値は、すべて、版に封印された Envelope から読む。
  - (f) 値が読めない、または古い形式の版は、対象にしない（R0）。
  - (g) 秘密の印を外した子の版を、今、作ることができる（開示の場面が今の場面の一覧で 1 つに決まる、ほか、今ある版の作成の前提を満たす）。
- B3. **Native は、review の読み出しの応答で、提案ごとに、対象かどうかと、対象でない理由を返す。** 画面は、それを表示する（件数、カードの印、見せる理由の 1 行）。画面は、対象かどうかを自分では計算しない。読み出しの command は増やさない（応答の項目の追加である）。
- B4. **Native は、渡された一覧の中で、今も対象と判定する提案だけを処理する。** 一覧に無い提案は、対象であっても処理しない。一覧にあって対象でなくなった提案（別の窓で編集された、ほか）は、処理せず、理由をつけて応答で返す。判定は、提案ごとの transaction の中で、書く直前にやり直す。
- B5. **提案ごとに、秘密の印だけを外した子の版を作り、その版に承認を記録する。** 2 つは 1 つの transaction で、片方だけが残ることは無い。子の版は、今ある版の作成と同じ検査と、同じ scope の取り直しを通る。変えるのは秘密の印だけで、題、メモ、開示の場面、根拠は変えない。
- B6. **承認の記録は、今と同じ作者の操作として、提案ごとに 1 件残す。** 新しい actor、新しい権限は作らない。
- B7. **1 件が失敗しても、残りを続ける。** 失敗した提案は、何も書かずに飛ばし、理由をつけて応答で返す。応答は、承認した件数、対象でなくなった提案、失敗した提案を持つ。終了や workspace の切り替えの要求が来たら、提案と提案の間で止まる。同じ要求が 2 回届いても、2 回目は、承認済みの提案を対象と判定しないので、何も書かない（要求の識別は保存しない）。
- B8. **今あるボタンを置き換える。** 「安全な提案をまとめて承認」は、この操作を呼ぶ。秘密の印を外さずにまとめて承認する操作は、製品から無くなる。1 件ずつの承認（秘密の印のまま）と、1 件ずつ秘密の印を外す操作は、今のままである。
- B9. **画面の表示。** ボタンには対象の件数を出し、押す前に何が起きるかを示す（趣旨：「見せる理由の無い提案 N 件の秘密の印を外して承認します。根拠の本文が、後の場面の関連場面に出るようになります」）。見せる理由の付く提案は一覧の上に寄せ、理由を 1 行で出す。終わった後、承認した件数、飛ばした提案と理由、個別に決める提案の残りの件数を出す。
- B10. **この操作は、今ある 2 つの command でできることの組み合わせである。** 新しい保存先、新しい送信先、新しい種類の記録は足さない。1 件ずつの「版の作成」と「承認」の command は、今のまま残す。
- B11. **merge の順。** 取り込みが、秘密の印を外した版を受け付ける変更（PR #864、#866）の後に merge する。先に入ると、まとめて承認した組を、画面から年表に取り込めない。

## 3. 残る制限

- 1 件ずつの経路は今のまま開いている。画面側を乗っ取った攻撃者は、今も、1 件ずつの command で秘密の印を外して承認できる。この案の Native の判定が防ぐのは、画面の誤り、古い画面、画面と Native の条件の食い違いである。
- 見せる理由の判定の材料は、抽出のときに model が付けた分類である。誤りうる。2 作品の AI による再判定では、理由なしの 1,086 件のうち 11 件（約 1%）が、場面の外の出来事と判定された。作者が見たのは、その 11 件である。理由なしの提案からの無作為の抜き取り（RR/1 の確かめ方にあった約 20 件）は、行っていない。
- 作者が 1 度でも編集した提案は、対象にならない。秘密の印を自分で外して、まだ承認していない提案も、1 件ずつ承認する。
- まとめて承認の後も、見せる理由の付く提案（評価のデータで約 25%）と、対象でない提案は、1 件ずつ決める。それを決め終えるまで、その組は年表に取り込めない。関連場面には、承認だけで届く。
- 場面の scope が未設定の場面（取り込みで作った project の場面など）からは、承認しても関連場面に届かない（今ある挙動）。
- 取り込みのあった組には、この操作は使えない。
- 重複の判定は、抽出の時点の出来事に対するものである。抽出の後に年表に足された出来事との重複は、見ない（今ある挙動）。
- 版の数は、対象の提案の分だけ増える。
- 秘密の印を外した版は、scope の投影を、その時点の値で持つ。その後に場面を足したり並べ替えたりしたときに、関連場面の資格や取り込みで古くなる場合があるかは、確かめていない（ERA/1 の残る制限は、開示の場面を変えた版についてのものである）。§6 で測る。
- 数百件を続けて処理したときの時間は、測ってから決める（§6）。遅ければ、この操作の中で計画の読み込みを 1 回にまとめる（挙動は変えない）。

## 4. 脅威モデル（draft）

CAS/1 の §5 と RR/1 の §6 の脅威モデルを、新しい command に当てはめる。信頼する側としない側、範囲外、漏れの許容（0）は変えない。

- **新しい command が開くもの。** 今ある 2 つの command（子の版の作成、承認）で既にできることだけである。入力から中身と秘密の印の値を外したので、この command で書けるのは、「Native が対象と判定した提案の、秘密の印を外した版と、その承認」だけである。呼べるのは画面からだけで、MCP からは呼べない（今ある 2 つの command と同じ）。
- **範囲内の誤りと攻撃。**
  - 画面が、対象でない提案（見せる理由の付く提案、作者が編集した提案、重複の可能性のある提案、取り込み済みの組の提案、別の抽出の提案）を一覧に入れる。
  - 画面が古い。画面が一覧を出した後に、提案が変わる（別の窓での編集、承認、取り込み）。
  - 同じ要求が 2 回届く。途中で止まった後に、もう一度届く。処理の途中で、終了や workspace の切り替えが来る。
  - 本文に埋めた指示が、model の分類を誘導して、理由が付かないようにする（RR/1 の §6。この案は変えない）。
- **必須の防御。**
  - 対象の条件の全部を、Native が保存済みの値で判定する（B2）。画面は判定しない（B3）。
  - 一覧に無い提案は処理しない。一覧にあっても、書く直前の判定で対象でなければ、書かない（B4）。
  - 子の版は、今ある版の作成と同じ検査を通る。今ある 2 つの command の検査を、合成で省かない（B5）。
  - 子の版と承認は、1 つの transaction である（B5）。
  - actor と権限は、今の承認と同じである（B6）。
  - 作業中の操作として登録し、終了や workspace の切り替えと調停する（B7）。
- **変えないもの。** 年表の出来事は secret で作る（CAS/1）。年表から AI への秘密と、Graph の本文の開示の拒否は変わらない。IR の資格の判定は変えない。関連場面に出るのは根拠の本文である。
- **受入れ。**
  - 正例：対象の提案が、操作 1 回で、秘密の印を外した版と承認を持つ。後ろの場面からの問い合わせで、IR の資格の判定を通る。その後、取り込むと、年表の出来事は secret である。
  - 負例：見せる理由の付く提案、作者が編集した提案、重複の可能性のある提案、根拠の対応が欠ける提案、古い形式の版、取り込み済みの組の提案、別の抽出の提案は、一覧に入れても、書かれない。応答に理由が返る。
  - 一覧に無い対象の提案は、書かれない。
  - 1 件が失敗しても、残りが処理される。片方だけ（子の版だけ、承認だけ）が残る提案が無い。同じ要求がもう一度届いても、子の版と承認が二重にできない。
  - 1 件ずつの承認と版の作成は、今の試験がそのまま通る。
  - 前の場面を書いているときの AI の文脈、chat の tool、MCP に、後ろの出来事が渡らない（CAS/1 の負例。この案で変わらないことを確かめる）。

## 5. 変える場所の見込み

- Native：新しい command（対象の判定、子の版と承認の合成）、review の読み出しの応答への項目の追加（提案ごとの可否と理由）。
- 画面と Native の間の契約：command の一覧（`electron/shared/ipcContract.ts`）、N-API の binding、関連の一覧への登録（画面から呼べる内部の command の一覧、関連場面を起こす command の一覧、変更の通知を出す command の policy、物語の IR の契約の policy）。
- 画面：ボタンの置き換え、今の画面側の 7 つの条件の計算を Native の応答の表示に置き換える、一覧の並びと理由の表示、終わった後の表示。
- 試験：Native の試験（§4 の受入れ）、画面の試験、実機の検査（今ある年表の抽出の検査に段を足す。足りなければ、検査を 1 本足すことを別に伺う）。

## 6. merge の前の測定

実装の後、merge の前に、評価のデータ（場面ごとに抽出した 2 作品の DB の写し）で次を測り、結果を作者に見せる。合格の線は置かない。**作者が結果を見て判断してから merge する。**

- 操作 1 回で対象になる提案の割合（RR/1 の件数の表と合うか）。対象にならない理由の内訳。
- 対象になった提案が、後ろの場面からの問い合わせで IR の資格を通る割合。通らないものの理由の内訳。
- 数百件を処理したときの時間（組が大きいとき、小さい組を続けたとき）。
- 漏れ 0 件：秘密の印のままの提案と、見せる理由の付く提案が、IR の資格を通らないこと。年表の出来事が secret のままであること。
- まとめて承認の後に、場面を足す・並べ替える操作をしたとき、承認した提案の関連場面の資格と、取り込みが、どうなるか（§3 の未確認）。

手順：測る前に、写しの場面の scope の印（未設定か、移行前からある場面か）を確かめる。未設定の場面は、この操作の前に、場面ごとに「本筋」の設定を入れる（今ある場面には、既定を設定するだけでは当たらないため）。測定は写しに対して行い、製品の DB と、凍結した評価の材料は変えない。

## 8. 未確認と限界

- §1 の【報告】の項目は、調査と独立のレビューの報告のままである。実装のときに、変える箇所はコードで読み直す。
- 子の版の作成と承認を合成するための Native の部品は、今は外から呼べない形である。合成の仕方は実装で決める。今ある 2 つの command の検査を省かないことを、試験で固定する。
- B2 (d) の「封印済みの根拠の記録と 1 対 1 に対応する」が、今の画面側の条件（根拠が完全一致の方法で確かめられている、欠けや分断が無い）と同じ提案を選ぶかは、実装で確かめる。違いがあれば、記録して報告する。
- 評価のデータの写しの場面の scope の印は、確かめていない。
- 数百件のときの時間は測っていない。

## 9. 改訂 2 の変更点と、CAS/1 の §3 との違い

改訂 2（独立のレビューの指摘）：

- 対象の判定を、Native だけが行う形にした（改訂 1 は、画面も同じ条件を計算し、食い違えば全体を拒むとしていた）。画面は版の系譜を受け取っておらず、正常な状態でも食い違う場合があった。
- 一覧と食い違ったときは、全体を拒むのではなく、一覧の中で今も対象のものだけを処理する。一覧に無いものは処理しない。
- 1 件の失敗で止めるのではなく、飛ばして続ける。止める形だと、同じ提案で止まり続けて、後ろが処理されない場合があった。
- 「最初の版そのもの」を、版の id で判定する。中身の比較では、作者が付け直した秘密の印を、この操作が外してしまう場合があった。
- 判定の材料の 4 つの値を、すべて Envelope から読む。
- 根拠の条件の定義を直した（Native は、根拠の確かめ方の種類を読んでいなかった）。
- 「まとめて承認」の操作そのものが、CAS/1 の確認に含まれていなかったことを、冒頭と §7 に書いた。
- 作者にとって変わること、merge の順、測定の手順（場面ごとに scope を入れる）、終了との調停を足した。

CAS/1 の §3（O1〜O5）との違い：

- O1 の「今の 7 つの条件」は、B2 の (b)〜(d) と (g) に置き換えた。RR/1 の理由（B2 の (e)、(f)）を足した。
- O3（子の版だけできて承認が無い提案を、次の回に拾う）は、無くした。子の版と承認が 1 つの transaction になり、その状態がこの操作からは生じないためである。作者が自分で秘密の印を外して承認していない提案は、対象にしない。
- O2、O4、O5 は、B5、B9、B6 に引き継いだ。
