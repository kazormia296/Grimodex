## 0. 一枚目

**何を決める案か。** 「まとめて承認」は、見せる理由の無い提案の秘密の印を外して承認する操作である（CAS/1 の O1〜O5、RR/1）。この案は、その操作を Native の新しい command 1 つとして置き、今ある画面のボタンを置き換える。

**なぜ新しい command か。** 今は、「秘密の印を外した版を作る」と「承認を記録する」が別々の command で、画面側が提案の数だけ 2 回ずつ呼ぶ。この形だと、対象を選ぶのも、版の中身を作るのも画面側になり、途中で止まると「版だけできて承認が無い」提案が残る。新しい command では、Native が対象を自分で選び、提案ごとに 2 つをひとまとめに行う。

**形**
1. 画面側は、対象の一覧（提案と版の id）だけを渡す。版の中身は渡さない。
2. Native が、保存済みの値で対象の条件を判定する。画面の一覧と 1 件でも食い違えば、何も書かずに拒む。
3. 提案ごとに、秘密の印だけを外した子の版を作り、その版に作者の承認を記録する。2 つは 1 つの transaction である。
4. 今あるボタン「安全な提案をまとめて承認」を、この操作に置き換える。
5. merge の前に、評価のデータで測り、結果を作者に見せる（§6）。

## 1. 確かめた事実

- 今あるボタン「安全な提案をまとめて承認」は、製品に出ている。未 review・未取り込みで 7 つの条件を満たす提案の、AI が出したままの版（秘密の印つき）に、承認を 1 件ずつ記録する。秘密の印は外さない。押しても関連場面（IR）には届かない。実機の検査と評価の準備は、このボタンを使っていない。【報告】
- IR の資格に要るのは、承認と、今の版の秘密の印が外れていることである。年表への取り込みは要らない。【確認済み（SSE/1 の実機の検査の後の DB に、Native の判定を当てた）】
- 秘密の印を外した子の版を作る command（`narrative_extraction_create_human_derived_revision`）は、親の版が現行であること、受け付ける 4 項目の変更だけであることを確かめ、scope の投影を今の値で取り直す。版、材料、依存の辺、鮮度、提案の現行の版と status（未 review に戻す）を、1 つの transaction で書く。【報告】
- 承認を記録する command（`narrative_extraction_append_human_decision`）は、未取り込みであること、組が取り込み済みでないこと、重複の可能性の判断があること、版が現行であることを確かめる。actor は作者（`electron:human-review`）である。秘密の印は見ない。【報告】
- 子の版の作成と承認を 1 つの transaction にまとめる今ある command は、今の形式（V2）の版を拒むので使えない。【報告】
- 子の版の Envelope は、判定の材料（語りの枠、語り手、重要度、起こり方）を親と同じに持つ。Native の系譜の検証が、親との一致を確かめている。【報告】
- review の画面が受け取っていない判定の材料は、語りの枠と語り手の 2 つである。重要度と起こり方は、提案の中身にもあり、画面に届いている。【報告】
- 7 つの条件のうち、重複の可能性は、抽出のときの結果が封印済みの計画にあり、Native が今も読んでいる。根拠の一致の方法は、封印済みの記録にあり、Native の別の箇所（検索の材料）が読んでいる。「最初の版のまま」は、系譜から分かる。Native は、保存済みの値だけで、対象の条件の全部を判定できる。【報告】
- 秘密の印を外した子の版は、画面側の今の 7 つの条件を満たさなくなる（「最初の版のまま」でなくなるため）。【報告】
- 承認や版の作成のたびに、検索の材料の作り直しは走らない。作り直しが要る印を付けるだけである。承認 1 件ごとに、封印済みの計画の全件を読んで検証する。【報告。数百件のときの時間は測っていない】
- 年表への取り込みは、組に未 review・保留・延期の提案が 1 件でもあると拒まれる。【報告】
- 取り込みのあった組には、子の版も承認も足せない。【確認済み（CAS/1 の §3）】
- 古い形式（V1）の版は、判定の材料を持たず、子の版も作れない。今の製品の抽出は V2 である。【報告】
- 関連場面の結果は、今は chat や AI への送信に使われていない。【確認済み】

## 2. 規則

- B1. **新しい command を 1 つ足す。** 入力は、project、抽出（組）、対象の一覧（提案の id と、その現行の版の id）、要求の識別である。版の中身、秘密の印の値、actor は入力に無い。
- B2. **対象の条件は Native が判定する。** 提案が対象になるのは、次の全部を満たすときである。
  - (a) 未 review で、未取り込みである。組が取り込み済みでない。
  - (b) 現行の版が今の形式（V2）で、次のどちらかである：AI が出した最初の版そのもの。または、最初の版から秘密の印だけを外した、未承認の子の版（前の回に途中で止まった分）。
  - (c) 抽出のときの重複の判定が「重複なし」である。
  - (d) 根拠のすべてが、本文と完全に一致する方法で確かめられている。
  - (e) 見せる理由（RR/1）が 1 つも付かない：語りの枠が地の文の出来事、語り手が地の文、重要度が major でない、起こり方が「実際に起きた」。値は、版に封印された Envelope から読む。
  - (f) 値が読めない、または古い形式の版は、対象にしない（R0）。
- B3. **画面の一覧と食い違えば、何も書かずに拒む。** Native が判定した対象と、画面が渡した一覧（提案と版の id の集合）が一致しないときは、子の版も承認も書かない。画面は読み直して、作者に件数を見せ直す。作者が見た対象と違うものを承認しないためである。
- B4. **提案ごとに、秘密の印だけを外した子の版を作り、その版に承認を記録する。** 2 つは 1 つの transaction で、片方だけが残ることは無い。子の版は、今ある版の作成と同じ検査と同じ scope の取り直しを通る。変えるのは秘密の印だけで、題、メモ、開示の場面、根拠は変えない。既に秘密の印を外した未承認の子の版がある提案（B2 (b) の後者）は、承認だけを記録する。
- B5. **承認の記録は、今と同じ作者の操作として、提案ごとに 1 件残す。** 新しい actor、新しい権限は作らない（CAS/1 の O5）。
- B6. **途中で失敗したら、そこで止める。** それまでに終えた提案は残る（提案の単位で完結している）。応答で、終えた件数と、止まった提案と理由を返す。もう一度押すと、残りを処理する。
- B7. **今あるボタンを置き換える。** 「安全な提案をまとめて承認」は、この操作を呼ぶ。秘密の印を外さずにまとめて承認する操作は、製品から無くなる。1 件ずつの承認は今のままである。
- B8. **画面の表示。** ボタンには対象の件数を出し、押す前に何が起きるかを 1 行で示す（例：「見せる理由の無い提案 N 件を、後の場面の関連場面に出せるようにして承認します」）。見せる理由の付く提案は一覧の上に寄せ、理由を 1 行で出す（RR/1 の §3）。終わった後、個別に決める提案が残っていれば、その件数を出す。
- B9. **判定の材料を画面に渡す。** review の読み出しの応答に、語りの枠と語り手を足す。画面は、表示と件数のために、Native と同じ条件を計算する。応答の項目の追加で、読み出しの command は増えない。
- B10. **この操作は、今ある 2 つの command でできることの組み合わせである。** 新しい保存先、新しい送信先、新しい種類の記録は足さない。1 件ずつの「版の作成」と「承認」の command は、今のまま残す。

## 3. 残る制限

- 1 件ずつの経路は今のまま開いている。画面側を乗っ取った攻撃者は、今も、1 件ずつの command で秘密の印を外して承認できる。この案の Native の判定が防ぐのは、画面の誤り、古い画面、画面と Native の条件の食い違いである（CAS/1 の §5 の「信頼しない actor」のうち、この範囲）。
- 見せる理由の判定の材料は、抽出のときに model が付けた分類である。誤りうる（RR/1 の §5）。2 作品の再判定では、理由なしの 1,086 件のうち 11 件が、場面の外の出来事と判定された（RR/1 の確かめの記録）。
- まとめて承認の後も、見せる理由の付く提案（評価のデータで約 25%）と、条件を満たさない提案は、1 件ずつ決める。それを決め終えるまで、その組は年表に取り込めない。関連場面には、承認だけで届く。
- 場面の scope が未設定の project（取り込みで作った project、最初からある project）では、承認しても関連場面に届かない（今ある挙動）。
- 取り込みのあった組には、この操作は使えない。
- 版の数は、対象の提案の分だけ増える。
- 数百件を続けて処理したときの時間は、測ってから決める（§6）。遅ければ、この操作の中で計画の読み込みを 1 回にまとめる（挙動は変えない）。

## 4. 脅威モデル（draft）

CAS/1 の §5 と RR/1 の §6 の脅威モデルを、新しい command に当てはめる。信頼する側としない側、範囲外、漏れの許容（0）は変えない。

- **新しい command が開くもの。** 今ある 2 つの command（子の版の作成、承認）で既にできることだけである。入力から中身と秘密の印の値を外したので、この command で書けるのは、「Native が対象と判定した提案の、秘密の印を外した版と、その承認」だけである。
- **範囲内の誤りと攻撃。**
  - 画面が、対象でない提案（見せる理由の付く提案、作者が編集した提案、重複の可能性のある提案、取り込み済みの組の提案）を一覧に入れる。
  - 画面と Native の条件が食い違う（片方だけが新しい）。
  - 画面が一覧を出した後に、提案が変わる（別の窓での編集、承認、取り込み）。
  - 同じ要求が 2 回届く。途中で止まった後に、もう一度届く。
  - 本文に埋めた指示が、model の分類を誘導して、理由が付かないようにする（RR/1 の §6。この案は変えない）。
- **必須の防御。**
  - 対象の条件の全部を、Native が保存済みの値で判定する（B2）。画面の計算に頼らない。
  - 画面の一覧と食い違えば、何も書かない（B3）。
  - 子の版は、今ある版の作成と同じ検査を通る。現行の版が変わっていれば、その提案で止まる（B4、B6）。
  - 子の版と承認は、1 つの transaction である（B4）。
  - 既に秘密の印を外した子の版がある提案に、子の版をもう 1 つ作らない（B4）。
  - actor と権限は、今の承認と同じである（B5）。
- **変えないもの。** 年表の出来事は secret で作る（CAS/1）。年表から AI への秘密と、Graph の本文の開示の拒否は変わらない。IR の資格の判定は変えない。関連場面に出るのは根拠の本文で、根拠が本文と完全に一致することは、対象の条件に含まれる。
- **受入れ。**
  - 正例：対象の提案が、操作 1 回で、秘密の印を外した版と承認を持つ。後ろの場面からの問い合わせで、IR の資格の判定を通る。その後、取り込むと、年表の出来事は secret である（ERA/1、CAS/1）。
  - 負例：見せる理由の付く提案、作者が編集した提案（秘密の印だけを外した未承認の子を除く）、重複の可能性のある提案、根拠が完全一致でない提案、古い形式の版、取り込み済みの組の提案は、一覧に入れると、全体が拒まれて何も書かれない。
  - 一覧と Native の判定が食い違うと、何も書かれない。
  - 途中で失敗した後、片方だけ（子の版だけ、承認だけ）が残る提案が無い。もう一度の操作で、残りが処理され、子の版が二重にできない。
  - 1 件ずつの承認と版の作成は、今の試験がそのまま通る。
  - 前の場面を書いているときの AI の文脈、chat の tool、MCP に、後ろの出来事が渡らない（CAS/1 の負例。この案で変わらないことを確かめる）。

## 5. 変える場所の見込み

- Native：新しい command（対象の判定、子の版と承認の合成）、review の読み出しの応答への 2 項目の追加。
- 画面と Native の間の契約：command の一覧（`electron/shared/ipcContract.ts`）、N-API の binding、関連の policy の一覧（変更の通知を出す command の一覧、物語の IR の契約の一覧）への登録。
- 画面：ボタンの置き換え、一覧の並びと理由の表示、件数、終わった後の残りの表示。
- 試験：Native の試験（§4 の受入れ）、画面の試験、実機の検査（今ある年表の抽出の検査に段を足す。足りなければ、検査を 1 本足すことを別に伺う）。

## 6. merge の前の測定

実装の後、merge の前に、評価のデータ（場面ごとに抽出した 2 作品の DB の写し）で次を測り、結果を作者に見せる。合格の線は置かず、結果を見て決める。

- 操作 1 回で対象になる提案の割合（RR/1 の件数の表と合うか）。
- 対象になった提案が、後ろの場面からの問い合わせで IR の資格を通る割合。通らないものの理由の内訳。
- 数百件を処理したときの時間（組が大きいとき、小さい組を続けたとき）。
- 漏れ 0 件：秘密の印のままの提案と、見せる理由の付く提案が、IR の資格を通らないこと。年表の出来事が secret のままであること。

測定は、評価のデータの写しに対して行う。写しの scope は、測定のために、作成ダイアログの「本筋」と同じ既定に設定する（評価の準備は scope を設定していないため）。製品の DB と凍結した評価の材料は変えない。

## 8. 未確認と限界

- §1 の【報告】の項目は、調査の報告のままである。実装のときに、変える箇所はコードで読み直す。
- 子の版の作成と承認を合成するための Native の部品は、今は外から呼べない形である。合成の仕方は実装で決める。今ある 2 つの command の検査を省かないことを、試験で固定する。
- 根拠の一致の方法を Native で判定する関数は、今は検索の材料の側にある。同じ判定を使えるかは、実装で確かめる。
- 数百件のときの時間は測っていない。
- 見せる理由の判定の誤り（理由なしの中に、個別に見るべき提案が混じる割合）は、2 作品の AI による再判定の値で、作者の目での抜き取りは行っていない（RR/1 の確かめの記録）。
