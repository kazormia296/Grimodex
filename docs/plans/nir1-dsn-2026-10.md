## 0. 要約

1. C-query の製品 owner は grimodex-node の新しい module に置き、AppState が1つ所有する。worker 1世代につき専用の owner thread を1本使い、prepare と query を同じ thread で行う。reader thread は prepare を呼んだ thread しか起こさないため（§1.1 F9）。lease は owner thread の中で DTO へ投影してから drop し、N-API の非同期境界には持ち越さない。
2. pre-warm は需要駆動とし、READY は process 全体で最大1個にする。READY の worker は、workspace の DB に commit が1件入った時点で使えなくなる（registration-drift、§1.1 F10）。そこで parent 接続の `ReadIdentity` 相当の stamp（`SqliteSourceRevision` と schema の版）で鮮度を判定し、古い READY には query を投げずに作り直す。編集中に Graph が D の窓へ間に合う割合は、この鮮度に大きく左右される。S2 で実測する。
3. quarantine の影響は Restore の阻止にとどまらない。その workspace の新しい participant をすべて拒否する。capacity permit も process 寿命で保持されると推定され、その場合は process 全体で C-query が使えなくなる。W1 の Restore は admission の後、無期限の待機に入る（§1.6）。shutdown でも Native は Closed に到達せず、process は Main の有界な観測（30 s の予算と3回の試行上限）の後の `exit(1)` で終わる。製品では Restore を入口で typed に拒否し、再起動を案内する。
4. join は既定どおり worker の中で行い、NQG2 で Scene association を返す（原稿本文は載せない）。worker は資源内で完全に列挙した後、tuple の順で先頭 N_F 件だけを frame に載せる。N_F は 8 とする（候補 §6 と計画 CP-1 のとおり）。parent は frame を tuple の順に必要な件数まで資格判定し、採用した association だけを再検証する。資格判定を8件に絞る前に置く案（N_F を 8 より大きくする）は候補 §6 と CP-1 からの逸脱なので、K1 の「8」の意味と CP-0 の期待値の導出に入力し、K1 で確認されるまで採らない（判断 D-08）。parent 側で join する案は snapshot の整合と予算の扱いで劣るため、採らない。
5. 既存の合流 helper をそのまま延長して Graph を deadline まで待つと、IR が窓内に揃っていても timeout として捨ててしまう（`awaitNir1RelatedScenes.ts:49-73`）。成分ごとの到着と最終公開を分ける新しい helper が要る。遅れて届いた結果は、単一 entry の次 query 用 cache と `graph-ready` 通知で次の query に使う。
6. D2a の現行の `plaintext-publication` は「unrestricted なら通し、restricted なら拒否する」という意味である。このため D2a を成立させると、Related Scenes と A2 review が閉じる。K3 には、restricted 下で caller の束縛と Native の再認可を条件に通す区分2種類（両 mode 可、restricted のみ）を提案する。restricted 下では `fts_search` も拒否されるので、Raw の sparse 成分が落ちて R が変わる（推定）。この扱いも K3 で決める。
7. P-12 の Native baseline は、`selectContextItems` の除去順を Rust に移す。両 arm とも Native の renderer と `nir1-context-estimator-v1` で測る。TS の fixture（合成 token、window 64）は Native では再生できない。
8. Main の一回限り grant は、Native が binding（u64 を含む）を保持し、Main は opaque な id だけを扱う。こうすれば u64 は JS を通らない。grant の型は C 本文宣言、D2a activation、local 送信 consent の3つに分け、どれも writer の前に消費する。

### 1.2 構成

- **配置**: `electron/native/grimodex-node/src/nir1_graph_product.rs`（名前は CP-2a で決める）。AppState に `pub(crate) nir1_graph: Nir1GraphProductOwner` を1つ置く。hotspot の lib.rs と state.rs は、mod 行、field、observer の登録、入口からの呼出しの数行だけにする。
- **worker の path**: Main が AppState の構築時に絶対 path で渡す。semantic と reranker の resource root と同じ扱いにする（`electron/native/grimodex-node/src/state.rs:2698-2720`）。packaged では `<resources>/bin/nir1-c-query-worker[.exe]`、dev では repo の target を Main が解決する。renderer や env からは受け取らない。MCP の `GRIMODEX_MCP_PATH` のような env による上書きは製品 build に置かない。
- **構成要素**:
  - (a) slot：状態機械。短い mutex で守る。
  - (b) owner thread：worker 1世代につき1本。prepare と query を同じ thread で行う（F9）。
  - (c) seam observer：DT-1 の `WorkspaceLifecycleObserver`（§1.10）。
  - (d) 次 query 用 cache（§3.3）。
  - (e) 診断 counter：allowlist に限る。
- **key**: (exact `LiveBinding`, project_id)。worker は project に束縛され（cqw.rs:872、worker-bin:186-190、:279-282）、同じ project の中なら query scene と seed を問わず1回だけ答えられる。
- **slot の状態**: `Disabled`／`Empty`／`Preparing{key, epoch}`／`Ready{key, epoch, stamp, ready_at}`／`InUse{key, epoch, cancel}`／`Retiring{epoch}`／`Quarantined{reason}`。
- **有効化の条件**: 次をすべて満たすまで `Disabled` のままで、spawn もしない。
  - PUB-G の公開 gate が開いている。
  - D2a が restricted で、かつ in-flight の停止が確認済み（`pe.rs:442-467` と同じ条件）。
  - worker の path を検証済み。
  - slot が `Quarantined` でない。
  - PUB-G より前の製品 build では常に `Disabled` とする（A-1）。CP-2a の診断は試験専用の入口に隔離する（post-B §4.4）。
- **owner thread の手順**:
  1. admission：epoch が一致し、slot が自分の `Preparing` で、Core が Ready であることを確かめる。
  2. 鮮度の stamp S0 を取る。parent の main 接続で、`ReadIdentity::read_unpinned` と同じ構成の値（`SqliteSourceRevision` の connection_epoch、total_changes、data_version と、main／temp の schema_version、user_version）を autocommit で読む。`ReadIdentity` は grimodex-db の crate 内に閉じているので、比較用の公開 helper を足す（read_identity.rs）。この読取は parent の DB mutex を取るので、待ちは §1.3 の bounded wait の上限に従う。mutex を上限の内側で取れないか、接続が autocommit でなければ、S0 を取らずに `warming` のまま、作り直しの rate 上限に従って再試行する。
  3. `CQueryWorkerOwner::new(active_workspace_snapshot(ws), worker_path)` を作り、`prepare(project_id)` を呼ぶ（最大 30 s）。
  4. slot を `Ready` にする。需要があれば `related-scenes:graph-ready` を出す（§3.4）。
  5. command を待つ。`recv_timeout` の時間は idle の上限にする。受けるものは `Query{request, cancel, reply}`、`Retire`、timeout、channel の切断。
  6. `Query` を受けたら、epoch を確かめ、S1 を取って S0 と比べる（§1.4）。S1 を取れなければ `busy`、一致しなければ `stale` として query を投げない。一致したら `query_once_with_cancellation` → `lease.frame()` → 所有する DTO へ投影 → lease を drop → oneshot で返す（§1.8）。
  7. owner を drop して退役させる。cleanup を証明できなければ slot を `Quarantined` にし、thread を終える。
  8. 同じ key の需要が続いていて、epoch が変わっておらず、作り直しの rate 上限の内側なら、2 に戻る（使用後に背景で作り直す）。そうでなければ thread を終える。

### 1.4 pre-warm の方針

- **READY は最大1個**。F2 から、容量の面でも1個しか持てない。
- **需要駆動**：最初に来た seed 付きの begin で準備を始める。その query の Graph は `warming` で unavailable になる。アプリの起動時や Ready の公開時に自動で起動しない（CPU、participant、quarantine の機会を増やさないため）。
- **使用後に背景で作り直す**：query の後、idle の上限の内側に同じ key の需要があれば、同じ owner thread で次の worker を準備する（§1.2 の手順 8）。
- **別の key の需要**：その query は `busy` にする。現在の READY の最後の需要から R_min 以上たっていれば退役させ、新しい key で準備する。複数の窓が別の project を開いているときに、作り直しが交互に続かないようにするため。
- **鮮度（F10 への対処）**：prepare の前に取った S0 と、query の admission で取った S1 を比べる。どちらも同じ parent 接続の値で、connection_epoch を含む。一致したときだけ READY を使う。一致しなければ query を投げずに退役させ、作り直す（registration-drift の空振りを避ける）。異なる接続の data_version は比較しない（`docs/plans/nir1-c-scene-connection-candidate.md:74-78`）。
  - 判定の根拠：data_version は他の接続（別 process の MCP を含む）の commit で、total_changes は自分の接続の行の書込みで、schema_version は DDL で変わる。S0 は spawn の前に取る。したがって S0＝S1 なら、worker の registration より後に commit は入っていない。
  - 偽の「古い」判定（自分の接続の rollback された書込みなど）は作り直しを1回増やすだけで、結果を誤らせない。偽の「新しい」判定が仮に起きても、worker 自身の registration-drift の検査が拒否するので、誤った結果は返らない（query が1回無駄になるだけ）。
  - stamp は鮮度の判断にだけ使い、認可や結果の採否には使わない。
  - stamp の読取は parent の DB mutex を取るので、Raw の読取や autosave の書込みと mutex を取り合う。待ちは §1.3 の bounded wait の上限で縛る（S1 は wait 0、S0 は短い上限）。取れなければ query を投げない（S1 なら `busy`、S0 なら `warming` のまま再試行）。
- **idle の上限**：最後の需要から T_idle たったら退役させる。
- **作り直しの rate 上限**：最短間隔 R_min、連続失敗時の指数 backoff（上限あり）、上限回数に達したら次の Ready edge まで停止する。
- **transition の開始時に retire する**：seam の TransitionAdmitted／Unavailable／ShutdownRequested を受けたら epoch を進め、owner thread に retire を非 blocking で通知する。owner thread が owner を drop すると（最大 500 ms）participant が外れ、transition が進む（F5）。Preparing と InUse の場合は §1.3 のとおり。ReadyPublished を受けたら cache と stamp を捨て、key を更新する。pre-warm はこの時点では起動しない。
- **数値の初期案（未確定、K1b に従って実測で決める）**：T_idle 120 s、R_min 1 s、backoff 2 s から 60 s、連続5回で停止、cache の TTL 30 s、S0 の mutex 待ち 100 ms（S1 は wait 0）。
- **リスク**：編集中は autosave や maintenance の commit が続くため、READY が古くなりやすい。編集中に Graph が D の窓に届く割合を S2 で測る（§3.5）。

### 1.5 BUSY と unavailable の理由

worker の reason（graph.rs:1186-1290、cqw.rs の anyhow のコード）を、製品の閉じた理由集合へ写す。対応表は CP-1 で決め、allowlist の試験で固定する。

| 製品の理由（案） | 状況 |
|---|---|
| `not-requested` | seed がない（既存24件では既定。Graph の寄与は 0） |
| `not-activated` | PUB-G の gate が閉じている（A-1） |
| `profile-not-restricted` | D2a が成立していない |
| `warming` | 新しい READY がない（Empty か Preparing）。準備を予約した |
| `stale` | READY が commit で古くなった。作り直しを予約した（UI の表示は `warming` と同じ） |
| `busy` | slot を使用中（別の窓や別の key）。process 全体で1枠のため、待たずに返す |
| `limit` | candidate／revision／read／frame／scene の上限 |
| `timeout` | worker の deadline（100 ms）を超えた |
| `registration-unavailable` | B の seal が未完了か dirty。maintenance が必要 |
| `invalidated` | 返却時か click 時の再検証で失効した |
| `cancelled` | 取消された |
| `restart-required` | quarantine 中（§1.6） |
| `worker-unavailable` | 実行体がない、spawn の失敗、startup の拒否 |
| `failed` | その他 |

capacity と claim の BUSY（cqw.rs:43-50、:889-893）は、product owner が slot で直列化するので通常は起きない。起きた場合、quarantine 中なら `restart-required`、それ以外は `busy` とする。

### 1.6 quarantine と W1 Restore の関係

コードの事実:

- W1（quarantine になった workspace）の新しい participant はすべて拒否される（wl.rs:1541-1552）。`with_db_state` 系の DB 操作は `WorkspaceSwitching` になる（db-state.rs:384-400、:546-556）。
- W1 の Restore は admission までは通るが、physical exclusion で `ActiveOperations` を返し続ける（wl.rs:3536-3543）。Native の supervisor はこの境界で無期限に再試行する（wlv.rs:357-365）。試験はこの拒否までしか固定していない（wl.rs:5194-5241、nir1_graph/tests.rs:2047-2097）。
- 同じ file を指す Open や alias は拒否される（wl.rs:4951-5024）。別の workspace W2 は開ける（wl.rs:5194-5241）。
- close は quarantine 中に Closed を主張できない（wl.rs:4993）。
- W1 の Open／Restore の handoff の途中で quarantine になった場合は、その transition が veto される（wl.rs:1591-1630、:3529-3533）。
- exact な participant を fence に移せない場合は、participant を process 寿命で保持するか、すべての資源を `mem::forget` する（cqw.rs:2781-2813）。この場合は transition と shutdown の drain が終わらない。
- 推定：capacity permit は forget された reservation の中に残るので、process 全体で C-query が使えなくなる（cqw.rs:2816-2824、:38-57）。

製品の方針（CP-2a の受入れに入れる）:

1. 発生したら slot を `Quarantined` にし、その process では以後 spawn しない。理由は `restart-required`。
2. renderer へ再起動が必要なことを知らせる。平文は含めず、状態と理由のコードだけを送る。
3. W1 の Restore は入口で typed に拒否し、無期限の待機に入れない（例：`NIR1_GRAPH_QUARANTINE_RESTART_REQUIRED`）。現状は admission の後、Restore の blocking task が physical exclusion の境界で待ち続ける（lib.rs:10381-10384、wlv.rs:357-365）。同じ file の Open はすでに admission で `ActiveOperation` として拒否されるので（wl.rs:1366-1383、:2605-2615）、拒否の理由を `restart-required` として示すだけにする。どちらも lib.rs の入口に数行で置き、Core の規則は変えない。
4. shutdown：Native の `finish_workspace_shutdown` には期限がなく、quarantine の下では完了しない（lib.rs:3122-3140。`wait_workspace_operations` も期限なしで待つ。`electron/native/grimodex-node/src/state.rs:2827-2843`）。
   - participant を process 寿命で保持する経路（cqw.rs:2781-2813 の fallback participant と `mem::forget`）では、participant の数が 0 にならず、lib.rs:3129-3138 の loop が終わらない。
   - fence に移せた経路では C-query の participant は数から外れるが（wl.rs:1576-1638。:1631）、Core の `close` が quarantine 中は拒否するので（wl.rs:1700-1735）、Closed は出ない（shutdown の N-API はエラーを返す。lib.rs:10135-10136）。
   - どちらの経路でも終端は Main が与える。Main は Native の観測に 30 s の予算と3回の試行上限を持ち（`electron/main/narrativeMaintenanceShutdown.ts:41-112`）、終端を観測できなければ `exit(1)` で process を終える（同 :127-133、`electron/main/index.ts:643-648`）。Native は timeout でも fence を解放しない（lib.rs:3126-3127）。製品の owner もこの規則を変えない。試験は §1.9。
5. quarantine 中は、W1 で participant を経る保存も拒否される。未保存の編集をどう扱い、どう表示するかは、UX の決定として K3 または CP-3b で確認する（未決）。
6. 発生を減らすために、需要駆動と作り直しの rate 上限を守り、S2 と CR-1 で OS 別の retire 時間の分布を測る。CLEANUP の 500 ms は変えない。変えると C-resource の受入れ証跡が変わるため。

### 1.8 lease の投影と N-API の境界

- owner thread の中で、`query_once_with_cancellation` → `lease.frame()`（検証済みの view）→ 所有する DTO への投影 → lease の drop → oneshot で DTO を返す、の順に行う。
- 投影の大きさは、検証済みの frame の長さ（最大 `FRAME_BYTES`）と件数の上限（node 12、edge 144、binding 512、association は §2.2 の N_F）で、allocation の前に確かめる。
- N-API の async 関数と tokio の task は DTO だけを受け取る。lease、owner、`FrameView` を `.await` の向こうへ持ち越さない（F8）。
- 投影する内容：
  - query の identity（project、query scene、seed）
  - registration（generation、scope_revision）
  - node と edge、それぞれの binding の9 token（graph.rs:196-206）
  - Scene association（§2.2）
  - elapsed
  - 原稿本文は含めない。
- 投影した DTO は「snapshot が閉じた後の候補」として扱う。返却の前に parent の fresh read で再検証する（§2.3）。

### 1.9 受入れ試験（CP-2a）

- pre-warm：最初の query は `warming` になる → READY → 次の query で Graph が窓の内側に届く。READY が commit で古くなったら query を投げずに作り直す。idle の上限で退役する。rate 上限と backoff が効く。
- seam：TransitionAdmitted、Unavailable、ShutdownRequested のそれぞれで、Ready、Preparing、InUse の各状態から有限時間で退役し、transition の physical exclusion が成功する。
- BUSY：2つの窓で同時に query し、片方が待たずに `busy` になる。
- quarantine：cleanup を証明できないとき、slot が `Quarantined` になる。W1 の Restore が入口で typed に拒否され、待機に入らない。同じ file の Open は `restart-required` の理由で拒否される。W2 は開ける。
- quarantine 下の shutdown（§1.6 の 4）：次を assert する。
  - Native：fence に移せた経路と participant を保持する経路のそれぞれで、`shutdown_workspace_lifecycle` が Closed を返さない（前者はエラー、後者は観測の窓の間に完了しない）。どちらでも fence か participant が残ったままで、Native が timeout や shutdown の要求で解放しない。
  - Main：Native の観測が終わらない場合と、拒否を返し続ける場合のそれぞれで、finalizer が `exit(1)` に進み、`quit` を呼ばない。これは既存の試験（`electron/main/narrativeMaintenanceShutdown.test.ts:62-81`、:102-124）が汎用に固定しているので、CP-2a では Native 側の試験を足し、両者の組合せで「process は Main の timeout 経路で終わる」ことを示す。Electron 全体を起動する試験は足さない。
- env と cwd：§1.7 の試験。
- lease：DTO を返した時点で child が reap 済みで、claim が解放されている（`retirement_pending` が false）。
- A-1：PUB-G の前は、どの入口からも spawn しない。

### 1.10 DT-1 の seam と D-transport の matrix

DT-1 レーンの作業中の記録（`/home/grimodex/worktrees/Grimodex/claude-nir1-dt1/.ralph/agent/decisions.md`。本書が整合させた版は sha256 `fb404297…`、2026-10-12 22:05。未 merge なので、変更があれば本節を追随させる）は、seam の API を次のように置いている。

```rust
#[non_exhaustive]
pub enum LifecycleEdge {
    TransitionAdmitted { operation_id: OperationId, kind: AdmissionKind, revision: StateRevision },
    ReadyPublished { binding: LiveBinding, revision: StateRevision },
    Unavailable { revision: StateRevision },
    ShutdownRequested { revision: StateRevision },
}
pub trait WorkspaceLifecycleObserver: Send + Sync {
    fn on_lifecycle_edge(&self, edge: &LifecycleEdge);
}
impl WorkspaceLifecycleCore {
    pub fn register_observer(&self, observer: Arc<dyn WorkspaceLifecycleObserver>) -> Result<(), LifecycleError>;
}
pub const MAX_LIFECYCLE_OBSERVERS: usize = 4;
```

C-query の製品 owner は、この案と次の点で整合する。

- observer は Core の mutex の中で呼ばれる。そのため C-query の observer は、epoch の atomic な更新と、owner thread への非 blocking な通知（`try_send` と `unpark`）だけを行う。retire は owner thread で行う。owner thread は、通知に使う lock を保持したまま Core、DB、子 process を操作しない（lock の順序は Core → 通知）。
- edge の使い方：TransitionAdmitted／Unavailable／ShutdownRequested → retire と cache の破棄。ReadyPublished → key と stamp の更新、cache の破棄。revision だけの変化（quarantine を含む）は edge にならないが、quarantine は owner 自身が起こすので通知は要らない。
- observer の枠は、gate（DT-1）、CB-2 の reservation、CP-2a の C-query owner の3つで、上限4のうち1つが空く。
- adapter の段で通知する方式（lib.rs:2005-2034 の transition admission の hook）は採らない。DT-1 の判断（D1）と同じく、Core を直接呼ぶ経路を取りこぼすため。

D-transport の matrix:

- startup claim barrier（DT-1）の matrix は、DT-1 の decisions §4 にある。本書はこれを複製しない。
- DT-2（bounded な create／claim／finish）の matrix は、下の表で先に固定する。DT-2 の decisions はこの表を写し、実装に合わせて具体化する。表と違えた点は理由とともに decisions に記録し、本書も追随させる。この表か DT-2 の decisions の matrix がないうちは、DT-2 の mutation を始めない。integrator はこの条件を DT-2 の TASK.md に写す。
- DT-5（transport）の matrix は、K5 の確認の後に DT-5 の decisions で作る。DT-5 も matrix が置かれるまで mutation を始めない（同じく TASK.md に写す）。

DT-2 の matrix（GDX-PRECHECK-001 の全項目）:

DT-2 が扱うのは、送信（DT-5）の手前までの1件の attempt の生成、claim、終端の書込みと、その owner の解放である。製品入口は作らない（A-1）。数値は計画の DT-2 行の既定値（DB mutex の待ち 100 ms、SQLite busy 100 ms、操作ごとの期限 250 ms、drain 250 ms、sweep 5 s）で、K1b に従って実測から選ぶ。「送信していない終端」は `NotAttempted` で response digest のない終端で、5行の terminal matrix のうち送信前に当たる行だけを使う（取消は `Cancelled`。ほかの理由との対応は DT-2 で決める）。「gate の quarantine」は、DT-1 の gate を閉じ、同じ Ready entry では開け直さないことを指す（DT-1 の Consumed と同じ扱い。gate にこの閉鎖の API を足す）。

|---|---|---|---|---|

## 2. join と frame（NQG2）

### 2.1 既定案：worker の中で pin join を行う

- 到達した Entity（hop が1以上）の明示 pin を、Graph の path と同じ snapshot、同じ QueryUsage 予算（行数、bytes、SQL steps）で列挙する。`idx_scene_codex_pins_entry` と keyset を使う（`scenes.rs:143-176`、`src-tauri/crates/grimodex-db/src/migrate.rs:1654`）。
- scenes.rs の `SceneJoinBudget` は、Graph 全体で同じ instance を使う（scenes.rs:22-31 のコメントのとおり、候補ごとに作らない）。
- seed 自身の pin は寄与させない（scene-connection 候補 §1）。
- 原稿本文は worker で読まない。`read_scene_source_bounded` は worker から呼ばない。本文は parent が exact token を照合して読む（K2 の推奨、CB-4）。
- 列挙が予算の内側で完了しなければ、Graph 全体を unavailable（`limit`）にし、部分的な結果を返さない。
- `mod scenes` の `dead_code` の expect（graph.rs:20-27）を外す。

### 2.2 NQG2 の layout（案）

```text
MAGIC "NQG2"
status u8                       0 = unavailable / 1 = available
project text, query_scene text
available の場合:
  scope_revision text, generation i64, seed text
  node_count u16, edge_count u16, nodes[], edges[]      ← NQG1 と同じ符号化
  scene_total u16                                         ← 完全列挙で得た相異なる Scene の数（診断専用。資格、順位、採否には使わない）
  scene_count u16                                         ← tuple の順で先頭 N_F 件（min(scene_total, N_F)。既定は N_F=8）
  scenes[scene_count]:                                    ← tuple の昇順に並べる
    scene_id text
    scene_incarnation optional<text>   A1 binding の incarnation。binding がない Scene は None
    scene_source_token text            tree_nodes の "v{version}@{updated_at}"（本文ではない）
    scene_scope_token optional<text>   A1 binding の source_token（sha256:…）
    pin_rowid i64, pin_entry_id text, pin_created_at text    request-local な照合値
    path_hop u8 (1..=2), path_edge_count u8 (1..=2), path_edge_index u16[path_edge_count]
unavailable の場合:
  reason text（allowlist）
terminal commit "NQGC1"（変えない）
```

- NQG1 の validate は末尾に余りがないこと（trailing-free）を要求する（frame.rs:474）。association を足すと NQG1 のままでは通らないので、版を上げる。
- parent は NQG2 だけを受け付け、NQG1 との併用はしない。parent と worker は同じ release で配布されるため。NQG1 の frame を NQG2 の parent が拒否する試験を置く。
- terminal commit の意味は変わらないので `NQGC1` のままにする。
- validate は今と同じく allocation をせずに全体を検証する。`FrameView` は「先頭だけ」の公開（frame.rs:216-265）をやめ、node、edge、binding、scene の iterator を持つ typed な投影にする。
- **件数の扱い（判断 D-08）**：
  - worker は到達 Entity の pin を、予算の内側ですべて列挙する（§2.1。列挙が完了しなければ `limit` で、部分的な結果は返さない）。Scene ごとに tuple が最小の path を代表にして tuple の順に並べ、先頭 N_F 件だけを frame に載せる。
  - 既定は N_F=8（`MAX_GRAPH_SCENES`、`src-tauri/crates/grimodex-core/src/narrative_nir1.rs:32`）。候補 §6 の「資源内で完全列挙できた対象に対してのみ、同tupleの先頭8 Sceneまでを返却する」（`docs/plans/nir1-c-scene-connection-candidate.md:178-179`）と、計画 CP-1 行の「tuple 順、最大8」のとおりにする。資格判定は、parent がこの8件に tuple の順で行う（§2.3）。
  - 既定の欠点：読書順や A1 で不適格な Scene が8件を埋めると、9件目以降の適格な Scene は、追加1枠にも path の付加にも使われない。
  - 逸脱案（K1 の確認が要る）：N_F を 8 より大きい防御用の上限（K1b。初期案 16）にし、「8」は資格判定の後に製品が使う Scene の上限と読む。資格判定を8件に絞る前に置くことになり、候補 §6 と CP-1 から逸脱するので、本書だけでは採らない。K1 の `2hop／12／144／8` の 8 の意味と、CP-0 の期待値の導出に入力する（§2.5）。
  - どちらの場合も parent の作業は N_F で抑えられる（§2.3）。association 1件はおよそ 200 B なので、frame の大きさへの影響は `FRAME_BYTES`（約 1.5 MiB）に比べて小さい。
  - `scene_total` は、8件の打ち切りで落ちる Scene の数を S2 と CP-2a の診断で数え、K1 の判断の材料にするために置く。parent は資格、順位、採否に使わない。
- 順序の tuple は（hop、traversal 順の edge ID 列、到達 Entity ID、Scene ID）で、UTF-8 の byte 順に比べる（候補 §6）。同じ Scene は tuple が最小の path を代表にする。

### 2.3 parent での資格判定と再検証（返却時と click 時）

- **返却時**：Related Scenes の participant read transaction の中で、次の順に行う。
  1. (a) B の seal が frame の値と一致することを、1回だけ確かめる。
  2. 採用する association を、frame の Scene を tuple の順に見て決める。必要な件数に達したら止める。
     - path の付加：R+IR の各 Scene について、frame に同じ Scene があれば、その association を採用する。既存の R+IR の Scene には CB-4 の判定は要らない。frame の中を引くだけで、走査はしない。
     - Graph だけで追加する1枠：追加できる条件（IR が共通追加枠を使っておらず、Raw が8件未満）を満たすときだけ、R+IR にない Scene を tuple の順に CB-4 で判定する（reading-before strict、A1、v2 token、veto、POV、本文の exact token）。最初に Eligible になった Scene を採用して止める。本文を読まない判定を先に行い、不適格な Scene は飛ばす（採用しない）。本文の読取（exact token の照合と抜粋）は、ほかの判定を通って採用する1件だけに行い、token が一致しなければ (c) の不一致として扱う。
  3. 採用した association についてだけ、次を確かめる。
     - (b) その代表 path が使う material binding の9 token が current である。既存の A2／A3 の revalidate を使う。
     - (c) `recheck_scene_pin`（rowid、entry、scene、created_at の exact な再読取。scenes.rs:288-）が通り、Scene が live かつ非 archive で、source token、incarnation、scope token が一致する。
  4. (d) all-or-nothing の範囲は、採用した association に限る。採用したどれか1つでも (a)〜(c) で一致しなければ、Graph の寄与を全体で 0 にし、部分的な結果は返さない。採用しなかった association は読み直さず、失効の判定にも使わない。
- **作業量**：frame の件数 N_F で抑えられる。pin の再読取は採用した件数（最大 N_F 件）、CB-4 の本文以外の判定は最大 N_F 件、本文の読取は最大1件（既定の N_F=8 なら、どれも8件以下）。これとは別に、SQL steps と deadline の上限を置く（K1b。初期値は実測で決める）。超えたら unavailable にする。
- **click 時**：navigation handle から、新しい read で同じことを確かめる（`nir1_evidence_qualify` を拡張する。rs.rs:285-328）。対象は click した Scene の association と、その代表 path だけ。
- data_version は比較しない（接続が違う）。

### 2.4 代替案（parent 側で join する案）との比較

| 観点 | A：worker の中で join（推奨） | B：parent 側で join |
|---|---|---|
| snapshot の整合 | path と pin が同じ snapshot に入る | path（worker の snapshot）と pin（parent の snapshot）が別になる。post-B §4.2 の「別 transaction で検証したものを未検証のまま結合しない」に反しないようにするには、path の資格を parent で全部読み直す必要があり、C-query の分離が意味を失う |
| 予算 | 既存の QueryUsage（512、100,000 steps）に含まれる | 別の予算が要る（K1b の新しい上限） |
| 100 ms lease | 含まれる（admission から lease まで） | lease の外。lease を保持したまま行えば child の reap が遅れ、drop した後なら snapshot がない |
| C-resource の証跡 | worker と frame を変えるので、CP-1 の最終 head で lane を再 dispatch する | worker は変わらない |
| Raw の接続との競合 | query 本体はない（worker 専用の read-only 接続）。ただし、鮮度の stamp（§1.4）と返却時の再検証（§2.3）は parent の接続を使う。どちらも有界（stamp は §1.3 の上限、再検証は N_F 件と K1b の上限） | 左の2つに加えて、pin の列挙も parent の DB mutex を Raw と取り合う |
| process 境界を越えるデータ | pin の metadata（ID と token）。本文は含まない | なし |
| 実装量 | frame の版上げ、投影、scenes.rs の配線 | parent の reader と予算の新設 |

推奨は A（scene-connection 候補 §5 の「同じ owner、同じ snapshot、同じ予算」に合う）。B の利点は C-resource の証跡を保てることだけで、CP-1 はいずれにせよ lane を再 dispatch する（G5）。advisor の結論：未取得（integrator が adversarial review で取得し、判断 D-07 に追記する）。

### 2.5 K1、CP-0、K2 への入力

- **K1**：候補 §6 は tuple の順と先頭8件の返却を定めているが、資格判定をどこに置くかは定めていない。計画 CP-1 行は worker の段で「最大8」とする。K1 の draft は `Scene 8` を意味上の上限と seed-local query の上限に置いている（`docs/plans/nir1-l6-l9-contract-proposal-6-draft.md:95`、:109。行番号は draft を入れた commit `ba7ceb46` のもの）が、資格判定の前の件数か後の件数かは書いていない。query の上限として読むのが自然で、これは既定（worker が返す Scene の上限。§2.2）と合う。既定のままなら K1 の文を変える必要はない。逸脱案（資格判定の後に製品が使う Scene の上限と読み、frame は N_F 件で、N_F は K1b の上限）を採るなら、Session A の提示の前に K1 の文でそう明記する必要がある。逸脱案が確認されない限り、CP-1 は既定で実装する。

## 3. 遅い Graph（post-B §7.2）

### 3.1 起動と合流

- `related_scenes_begin` に seed（任意）を足す（CP-3a）。`BeginRequest` は `deny_unknown_fields` なので（rs.rs:74-82）、Native の型、`electron/shared/relatedScenesSearchWire.ts`、ipcContract の検証、renderer の wrapper を同じ PR で揃える。
- seed があり、Graph が有効なら、Native は IR の scoring と同時に、owner thread へ Graph の query を送る。begin の応答には `graph` を加え、値は `pending`（ticket 付き）、`ready`（cache が hit し、再検証済み）、`unavailable`（理由付き）のいずれかにする。
- Graph の待受けは IR とは別の command にする（例：`related_scenes_graph_continue`。名前は CP-3a で決める）。IR の continue に Graph を同梱すると、IR の到着が Graph の遅れに引きずられるため。
- renderer は、Raw-ready＋D を共通の deadline として IR と Graph を合流させ、最終結果を1回だけ公開する。段階的な表示はしない。
- 遅れて届いた Graph は、その query に混ぜない。
- Chronicle（IR）が止まったら Graph も止め、exact な R に戻す。Graph だけが止まったら R+IR に戻す（post-B §7.2）。

### 3.2 合流 helper を新しく作る（判断 D-10）

既存の `awaitNir1RelatedScenes` は、最終公開の時刻で IR の outcome を決める。公開が deadline 以降になると timeout として IR まで捨てる（`src/features/related-scenes/awaitNir1RelatedScenes.ts:49-73`、`nir1RelatedScenesDeadline.ts:88-94`）。このまま延長して「IR が揃っていても Graph を deadline まで待つ」と、窓の内側に届いた IR が timeout として数えられ、P の timeoutRate（paired.mjs:375-384、:436-437）を汚す。

新しい helper の要件:

- 成分ごとに到着時刻を記録する。IR の outcome は IR の到着時刻で決める（既存の意味のまま）。
- Graph の outcome は別に記録する：`graph-ready`、`graph-late`、`graph-unavailable:<reason>`、`not-requested`。
- 最終公開は、開始したすべての成分が揃った時点か deadline の早い方で行う。待つのは Graph が pending の場合だけで、上限は D。seed のない query は従来の経路を使い、待機を足さない。
- 公開時の再検証、取消、失効は既存の helper と同じ規則にする。
- 既存の helper と seed のない経路は変えない（24件と P の R/R+IR を保つ）。

### 3.3 次 query 用の cache は要るか

結論：要る（推奨。単一 entry とする）。ただし S2 で新しい READY の率が十分に高いと分かれば、CP-2a の判断記録に理由を残したうえで省いてよい。

- 理由1：post-B §7.2 は「次queryで使う」と定めている。
- 理由2：D の窓に届かない主因は鮮度と spawn である。遅れて届いた結果を捨てると、同じ worker の起動をやり直すことになる。
- 理由3：返却時の再検証（§2.3）は CP-2a でどのみち必須であり、cache のために新しい authority を作らない。
- 「遅い」には2つの意味がある。(i) lease の内側だが D の窓より後：current query に混ぜず、cache の対象にする。(ii) lease の期限より後：owner が拒否するので、cache にも入れない（post-B §6.2「期限後のresultは採用しない」）。
- key（exact identity）：exact な `LiveBinding`、D2a の caller epoch、project、query scene、seed、query scene の source token、scope token、incarnation、B の seal（generation、scope_revision）。値は投影済みの DTO。
- 使う時：返却時に §2.3 の再検証を通ったときだけ使う。click 時にも再検証する。
- 防御の上限：entry は1件、TTL は短くする（初期案 30 s、K1b）。seam の edge、D2a の epoch の変化、quarantine で破棄する。process-local で、永続化しない。

### 3.4 graph-ready で次の query を起こす

- Native が `related-scenes:graph-ready`（payload は projectId だけ）を出す条件は2つ。(a) 需要のある key について新しい READY ができたとき。(b) Graph を使わずに完了した query（ticket が先に release された）の結果が cache に入ったとき。
- renderer は既存の `index-ready` と同じ型で refresh する（`useNir1RelatedScenes.ts:31-57`）。直前の query の Graph が `warming`、`stale`、`busy`、`graph-late` のいずれかだった場合に限り、表示中の query の世代ごとに1回まで新しい query を起こす。
- 新しい query は自分の deadline を持つので、完了済みの query に結果を混ぜない。
- event で起こした新しい query は、IR を含む `related_scenes_begin` を最初から実行し直す（B と D をもう一度使う）。そのため P の計測には入れない。P harness は `graph-ready` を購読せず、event を契機にした再 query は、P の分母にも IR の timeoutRate にも含めない（P は sample ごとに、利用者の操作1回分の query を測る）。製品では、上のとおり表示中の query の世代ごとに1回までとする。
- この event は D2a の event allowlist（pe.ts:474-491）に加える必要がある（K3）。加えない場合、restricted 下では届かない（fail-closed で、自然に起きる次の query だけが cache を使う）。

### 3.5 D=10.84 ms の窓に届かない場合（K6 graph-eval-procedure への入力）

- S2 と CP-2a の診断で、次の値を測る。
  - (a) 定常状態での窓内到達率。query の開始時に新しい READY があることを、sample ごとに記録する。
  - (b) 実際の操作の trace（編集中、閲覧中）での窓内到達率。
  - (c) spawn から READY までの時間と、registration の時間（project の規模別）。
  - (d) write の負荷の下での prepare 失敗率。
  - (e) OS 別の retire 時間。
- K6 で観測の前に固定するもの:
  - 分母：seed があり、Graph が有効で、snapshot が usable な query。
  - warm-up の回数と、測定の起点（P と同じ）。
  - 定常状態の定義と、可用性の基準（閾値はユーザーが選ぶ）。
  - IR の timeoutRate（1%以下）は IR の outcome だけで計算し、Graph の遅れを混ぜない。
  - `graph-ready` による再 query は、P の分母にも timeoutRate にも含めない（§3.4）。可用性の (a) と (b) の分母も利用者の操作による query に限り、event による再 query は別に数える。
  - G-case の品質（G-01〜G-08）は、定常状態での R+IR+Graph で測る。そのことを receipt に明記する。
- 判断の分岐:
  1. (a) と (b) が基準を満たす → そのまま CP-4 へ進む。
  2. (a) は満たし、(b) が鮮度の理由で満たさない → K6 の手順で品質と可用性を分けて評価し、編集中の可用性の制約を Session C-1 に開示する。
  3. (a) も満たさない → HOLD（既定）。U2 の任意の高速化（C-query 内部の短縮。100 ms lease は変えない）を試すこともできる。D を広げるのは閾値の緩和にあたるので、ユーザーの確認なしには行わない。
- 次のことはしない：遅れて届いた結果を窓の内側と数えること、遅れた結果を混ぜること、事後に Gold や指標を変えること。常に unavailable の状態は PASS にしない（post-B §7.3）。

## 4. D2a の restricted 下の route 区分（K3 への入力）

### 4.1 現行の意味（コードの事実）

- `plaintext-publication`：
  - unrestricted なら検査なしで通す（pe.ts:676、:723）。
  - restricted なら invoke の時点で拒否し（pe.ts:700-711）、制限の開始後に完了した結果も拒否する（pe.ts:714-728）。
  - つまり D2a を成立させると、この区分の機能はすべて閉じる。
- `D2A_TYPED_RESULT_POLICY`（pe.ts:57-68）：
  - 値は `"plaintext-publication"` だけ。
  - `satisfies Partial<Record<keyof typeof NAPI_COMMANDS, …>>` の制約により、`NAPI_COMMANDS` にない command（未登録の `nir1_graph_query` など）は載せられない。
  - `commandRoute` はこの typed の台帳を `DENIED_COMMANDS` より先に引く（pe.ts:493-501）。
- `plaintext-publication` に分類されている NIR 関係の command：Related Scenes（pe.ts:114、:116-117）と A2 の typed reader（pe.ts:63-65）。
- internal（両 mode で通る）：`capture_current_chat_input` と Scene Scope の read／update（pe.ts:187、:294-296）。
- activation の流れ（pe.ts:808-883）：
  1. 同期的に `_restricted = true` にする。
  2. main の egress participant を quiesce する。
  3. Native で永続化する。
  4. 発行済みの identity を消す。
  - 失敗したら unavailable にする。
  - activation の途中は caller を登録しない（pe.ts:656-671）。
- Native の再認可：`begin_dispatch`／`with_authorized_dispatch`（登録済みの caller、revocation generation、workspace の一致。pe.rs:299-331、:404-437）と `with_authorized_preparation`（restricted かつ in-flight 停止済み。pe.rs:442-467）。
- event の allowlist は全窓への broadcast を前提にしている（pe.ts:474-491、:768-779）。

### 4.2 提案：区分を2つ新設する（名前は K3 で決める）

| 区分（仮称） | unrestricted | restricted |
|---|---|---|
| `nir1-publication` | 現行どおり通す（R／IR／A2 の既存の製品を変えない） | 次の (1)〜(3) をすべて満たすときだけ通す。(1) main が発行した caller identity が必須（`db_execute` と同じ扱い）。(2) Native が開始時と返却時に再認可する（permit の generation が変わっていないことと、登録済みの caller と一致すること）。(3) 結果の完了時に、Main が caller の epoch が変わっていないことを確かめる（`assertPlaintextPublication` と同じ型の検査） |
| `nir1-restricted-only` | 拒否する | `nir1-publication` と同じ条件で通す |

- `D2aTypedResultPolicy` を union に広げ、`satisfies` の制約は保つ。
- `DENIED_COMMANDS` との重複を消し、2つの台帳に同じ command がないことを試験で固定する。

## 7. Main の一回限り grant

### 7.1 要件

- 有効時間は 60 秒。
- 同時に1件だけ（process 全体で1つの slot。種類を問わない）。
- sender（WebContents）と window に束縛する。
- u64 の epoch を欠損なく扱う。
- OCC（期待する版）と digest に束縛する。
- writer の前に消費する。消費した grant は、書込みが失敗しても戻さない。

### 7.2 API

Native（grimodex-node の新しい module `main_grant.rs`）。どれも Main 専用の N-API で、`NAPI_COMMANDS` には載せない。`activateProfileEgress` と同じ扱いにするので（pe.ts:37-40）、renderer の IPC からは呼べない。

```rust
pub(crate) enum MainGrantKind { BodyDeclaration, ProfileActivation, LocalSendConsent }

// Main 専用 N-API
fn main_grant_preview(kind: &str, request_json: &str, sender_id: u32, window_id: u32)
    -> Result<String /* { previewId, display, expiresInMs } */>;
fn main_grant_issue(preview_id: &str, sender_id: u32, window_id: u32)
    -> Result<String /* { grantId } */>;
fn main_grant_revoke(id: &str) -> Result<()>;
fn main_grant_revoke_sender(sender_id: u32) -> Result<()>;

// writer 側（crate 内）
fn consume<K: GrantKindBinding>(grant_id: &str, sender_id: u32, window_id: u32)
    -> Result<ConsumedGrant<K>>;
```

- **preview**：Native が現在の DB と lifecycle を読み、種類ごとの binding を作る。binding は Native の中に保持する。Main に返すのは、dialog に出す allowlist の文字列（display）と、opaque な previewId だけ。
- **issue**：dialog が承認されたら、同じ sender と window から呼ぶ。期限の内側で、slot の状態が Previewed のときだけ Issued にする。preview の後に OCC が変わっていたら拒否する。
- **consume**：writer の入口で、write transaction を開く前に呼ぶ。次をすべて確かめてから Consumed に変える（取り消せない）。
  - 種類が一致し、sender と window が一致し、期限の内側で、状態が Issued である。
  - writer は transaction の中で、OCC と digest を現在の状態や要求と照合する。一致しなければ拒否し、暗黙の再試行はしない。
- **id**：128 bit の乱数を hex にしたもの。
- **digest**：SHA-256 にドメイン分離の接頭辞（`grimodex/main-grant/v1/<kind>\0`）を付け、binding の canonical JSON をつなげて計算する。
- **u64 の扱い**：lifecycle の revision、authority_instance、recovery_generation、caller epoch は Native の binding の中だけに置き、JS の number を通さない。どうしても JS へ出す場合（試験、診断）は、10進の文字列にする。Rust 側では先頭0、符号、空白を拒否し、checked parse する。

Main（`electron/main/mainGrant.ts`）:

- `GRANT_REQUIRED_COMMANDS`（exact な台帳。command → 種類）に載っている command だけを ipc.ts の router で横取りする（数行）。
- 処理の流れ:
  1. sender が destroyed でないことを確かめる。
  2. `BrowserWindow.fromWebContents` で window を取る。
  3. Native の preview を呼ぶ。
  4. `dialog.showMessageBox(win, …)` を出す。文字列は Native の display だけを使い、renderer が渡した文字列は使わない。既定のボタンは取消にする。
  5. 承認されたら issue を呼び、dispatch の引数に grant を enumerable でない sidecar として注入し、writer を dispatch する（callerIdentity と同じ方式。`electron/main/ipc.ts:2149-2163`）。
  6. 取消、期限切れ、エラーのときは revoke する。
- grant は renderer に返さない。
- sender の束縛は `relatedScenesSearchAuthority` と同じく、WebContents の object に結び付ける（`electron/main/relatedScenesSearchAuthority.ts:22-53`）。sender の `destroyed`、`did-start-navigation`、`render-process-gone` と、window の `closed` で revoke する。
- 同時に1件：Main の in-flight 記録と Native の slot の両方で守る。2件目は `MAIN_GRANT_BUSY` で、待たせない。
- D2a の activation は Main の内部の流れ（`activateFirstRestrictedPublication`）なので、横取りではなく、その中で preview → dialog → issue を行い、grant を Native の activation に渡す（DA-2）。

### 7.3 grant の型

| 種類 | binding | 消費する writer | 使う PR |
|---|---|---|---|
| `BodyDeclaration` | exact な `LiveBinding`、lifecycle の revision、VerifiedWorkspaceBinding（workspace ID、canonical locator）、project、scene、scene incarnation、Scene Scope の binding の版（OCC）、本文の source token と canonical digest、宣言の digest（各軸） | `narrative_scene_scope_update` の本文宣言の分岐（Native writer） | CB-2（MG-1） |
| `ProfileActivation` | profile ID、caller epoch、policy の版、開示文の digest（一方向で解除できないことを含む） | Native の `activate_first_restricted_publication`（pe.rs:193-226） | DA-2 |
| `LocalSendConsent` | route の revision の digest、endpoint の identity（IP literal と port）、provider、purpose（Writing／Review）、policy の版、開示文の digest | 永続する consent の記録。本文と credential は含めない（GDX-AI-CONSENT-001）。送信のたびに、この記録と route を照合する | DT-4／DD-1 |

history 用の宣言 grant と、生成のクリック用の確認は置かない。K4 の推奨は「生成出力は親の資格判定から導き、dialog は作らない」で、DT-2 の方針は「確認 dialog を足さない」であるため。

### 7.4 grant の lifecycle

| 区分 | 内容 |
|---|---|
| entry | grant が必要な command の invoke、または Main の内部の activation の流れ |
| start | `main_grant_preview` を呼ぶ前に、sender が destroyed でないこと、`BrowserWindow.fromWebContents` で得た window が渡された window と一致すること、sender が Main の束縛した caller であることを確かめる。どれかが違えば preview を作らない |
| retry | 期限切れや revoke の後は、新しい preview からやり直す。同じ previewId での issue のやり直しと、消費済みの grant の再利用は拒否する。暗黙の再試行はしない |
| reentrant | 同時に1件。dialog が開いている間の2件目は `MAIN_GRANT_BUSY` で、待たせない。Main の in-flight 記録と Native の slot の両方で拒否する |
| admission closure | seam の edge（TransitionAdmitted、Unavailable、ShutdownRequested）、D2a の epoch の変化、grant を使う機能の gate が閉じているとき（workspace が Ready でない、D2a の activation の途中など）は、preview を受け付けない。preview の後に起きたら、その grant を revoke する（cancel の行） |
| pending | dialog が開いている間。slot の状態は Previewed |
| active handle | Native の slot と、Main の in-flight 記録（WebContents に束縛） |
| cancel | dialog の取消、sender の destroyed／遷移、window の close、seam の edge（BodyDeclaration は古い binding に束縛されているので revoke する）、D2a の epoch の変化 |
| bounded wait | preview から 60 s。期限を過ぎてから承認しても issue は拒否する（Main は dialog を強制的に閉じられないので、承認の後に「時間切れ」を表示する） |
| 終了の証拠 | Native の slot が Consumed／Revoked／Expired になり、Main の in-flight 記録が消えること |
| error | preview の失敗は renderer に typed な error として返す。issue の失敗、consume の失敗は writer を実行しない |
| restart | 永続化しない。再起動すると grant はすべて無効になる |

### 7.5 脅威と防御

- **対象とする攻撃**：
  - renderer が確認を偽造する → renderer は grant を発行も参照もできない。
  - 別の窓で使い回す → sender と window に束縛する。
  - 再送 → 一回限り。
  - 内容のすり替えや、古い内容での書込み → OCC と digest。
  - 長く放置された承認 → 60 秒。
  - 並行する dialog の取り違え → 同時に1件。
  - u64 の切り詰め → JS を通さない。
  - TOCTOU → writer の前に消費し、OCC は transaction の中で確かめる。
- **対象外**：Main や Native そのものの侵害、OS の UI の偽装、開示を読んだうえでの利用者の判断。

### 7.6 試験

- 期限切れ、2回目の consume、別の sender、別の window、OCC の変化、digest の不一致、sender の destroyed、同時に2件、seam の edge による revoke、期限切れや revoke の後の同じ previewId での issue、閉じた gate の下での preview を、それぞれ拒否すること。
- renderer の IPC から Main 専用の N-API に届かないこと。
- grant の id が renderer への応答と event に現れないこと。
